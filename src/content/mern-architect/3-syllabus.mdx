# Browser & Rendering Internals — Architect Level

A pixels-up syllabus for engineers who must reason about *what the browser actually does* between a URL and a painted, interactive page — and who need to diagnose jank, layout thrash, and slow loads from first principles, then defend those fixes in senior/staff/architect interviews. The browser is treated here as what it really is: a **multi-process system with a rendering pipeline**, not a magic box that "shows HTML".

**Legend:** 🎯 = high-frequency interview hotspot · ⚙️ = browser/engine internals · 🧠 = mental-model / deep-theory depth

**Prerequisites:** Comfortable with HTML/CSS/JS, the DOM API, and the event loop (ideally Module 1 of this path). Some exposure to Chrome DevTools.

**Outcome:** Ability to trace a page from URL to pixels through the rendering pipeline, explain how parsing, style, layout, paint, and compositing work and what triggers each, reason about the 60fps frame budget and the event loop's rendering integration, choose compositor-friendly animations, eliminate layout thrash, optimize resource loading, and measure it all with Core Web Vitals — articulating the trade-offs at an architect's level.

## [Module 5 — Paint, Layers & the Compositor](?tab=learn#module-5) ⚙️🧠
- **Paint**: turning the render tree into paint records (draw commands), not pixels yet
- **Rasterization**: paint records → actual pixels (often on raster threads / GPU)
- **Layers** (compositing layers) and **layer promotion** (`transform`, `opacity`, `will-change`, `position: fixed`, video, canvas)
- The **compositor thread**: assembling layers into the final frame, off the main thread 🎯
- **Compositor-only properties** (`transform`, `opacity`) — animate these for free 🎯
- The cost of too many layers (memory, "layer explosion")

**Interview focus:** "What is the compositor thread and why does it matter?", "Why are `transform`/`opacity` animations cheap?", "What promotes an element to its own layer?"

## [Module 6 — The Frame & the 60fps Budget](?tab=learn#module-6) 🎯🧠
- One frame = **~16.6ms** at 60fps (and ~6.9ms at 144Hz)
- The **pixel pipeline** per frame: JS → Style → Layout → Paint → Composite
- Where a change **enters** the pipeline decides its cost (composite-only is cheapest) 🎯
- **Dropped frames** and jank; the "long frame"
- **`requestAnimationFrame`**: running JS right before the next paint

**Interview focus:** "What's the frame budget and why 16.6ms?", "Why animate with `transform` instead of `top`?", "What is `requestAnimationFrame` for?"

## [Module 7 — The Event Loop & Rendering](?tab=learn#module-7) ⚙️🎯

- Why a flood of **microtasks** can starve rendering 🎯
- **`requestIdleCallback`**: doing low-priority work in idle time
- Blocking the main thread = no rendering, no input

**Interview focus:** "Where does rendering fit in the event loop?", "rAF vs setTimeout vs microtask for visual updates?", "How can microtasks block paint?"

## High-Yield Interview Question Bank (by theme) 🎯

**Mental model / explain it**
- URL → pixels: the full navigation + rendering pipeline
- The pixel pipeline (JS → Style → Layout → Paint → Composite) and where a change enters
- Main thread vs compositor thread vs raster vs GPU
- Why CSS is render-blocking and JS can be parser-blocking
- Where rendering fits in the event loop (rAF, microtasks, idle)

**Performance / fix it**
- Reflow vs repaint vs composite — classify a list of CSS changes
- Forced synchronous layout / layout thrashing — spot it and fix it (read/write batching)
- Make an animation compositor-only (`transform`/`opacity`, `will-change`)
- Break up a long task to improve INP; yield to the main thread
- `async` vs `defer`; `preload`/`prefetch`/`preconnect`; critical CSS; font-display

**Build it / APIs**
- Infinite scroll / lazy load with `IntersectionObserver`
- Off-main-thread work with a Web Worker (and what can't cross the boundary)
- A Service-Worker caching strategy (cache-first / stale-while-revalidate)
- `requestAnimationFrame`-driven animation vs `setTimeout`

**Measure it**
- Core Web Vitals: LCP, CLS, INP — definitions, causes, fixes
- Read a DevTools Performance trace; find the long frame / long task
- Field vs lab data; the Long Tasks API and `PerformanceObserver`
