# React Internals & Concurrent Rendering

You call `setState` and the screen updates — but *what actually happens* in between? This module opens React's engine: how JSX becomes a tree of plain objects, how reconciliation and **Fiber** decide the minimal DOM change, how hooks are really stored, and how **concurrent rendering** lets React pause, prioritize, and resume work so your app stays responsive under load. By the end, React stops being a black box that "re-renders on state change" and becomes what it is — a **reconciler plus a cooperative scheduler** you can reason about.

---

<h2 id="module-0">Module 0 — The React Mental Model</h2>

Before any Fiber, scheduler, or hook makes sense, you need the one idea everything else hangs from: in React you never reach into the page and edit it yourself — you describe what the page *should* look like for the current data, and React works out the edits. Get this mental model right and "why did my component re-render?" stops being mysterious.

---

### 🪞 UI = f(state) — Describe the Result, Not the Steps

#### 🧩 What is it?
`UI = f(state)` is a one-line summary of how React thinks. Your user interface (the **UI** — what's on screen) is treated as the **output of a function** `f` whose **input is your state** (the data your app currently holds, like a count or a list of todos). Give React the same state, and you get the same UI back — every time.

#### 🤔 Why do we need it? (the problem)
The old way of building pages was **imperative**: you grabbed elements from the page and mutated them by hand — set this text, add that class, remove this node, in exactly the right order. (The **DOM** — short for Document Object Model — is the live tree of elements the browser shows on screen.) As an app grows, the number of "if this changed, also update that" rules explodes, and one missed update means the screen and the data disagree.

The **declarative** approach flips it: you stop writing the *steps* and instead describe the *result* for a given state. You never say "add a class" — you say "for this state, the button looks like *this*." React figures out the steps to make reality match.

#### ⚙️ How does it work?
You write a function that, given the current state, returns a description of the whole UI. When state changes, React calls your function again to get a fresh description, then makes the real screen match it. You are never responsible for the individual edits.

```
   IMPERATIVE (you do the steps)
   state changes ──▶ you find nodes ──▶ you mutate each one
                     (easy to forget one ──▶ screen drifts)

   DECLARATIVE (React does the steps)
   state changes ──▶ f(state) returns a full picture
                  ──▶ React makes the screen match it
```

#### 🌍 Real-life analogy
Imperative is **giving turn-by-turn driving directions**: "left, then third right, then merge" — one wrong turn and you're lost. Declarative is **typing the destination into the GPS**: you state *where you want to end up*, and the GPS computes the route. React is the GPS — you give it the destination (the UI for this state), it handles every turn.

#### 💻 Code example
```javascript
// IMPERATIVE — you mutate the DOM by hand, step by step
let count = 0;
const span = document.getElementById("count");
function increment() {
  count = count + 1;
  span.textContent = count;        // YOU must remember this line
  span.className = count > 5 ? "hot" : "";  // ...and this one
}

// DECLARATIVE (React) — you describe the result for the current state
function Counter() {
  const [count, setCount] = React.useState(0);
  // No DOM edits. You return a DESCRIPTION of the UI for this `count`.
  return (
    <span className={count > 5 ? "hot" : ""}>
      {count}
    </span>
  );
  // Change `count`, React re-runs Counter and updates the screen for you.
}
```

#### 🎤 Interview question
**Q: What does `UI = f(state)` mean?**
A: It means the UI is a pure function of state: for a given state, your components always describe the same UI, and React's job is to make the actual screen match that description. You write *what the UI should be* (declarative) instead of *how to mutate the DOM* (imperative). When state changes, React re-runs the function and reconciles the result onto the page — you never touch the DOM yourself.

### 🧱 Components Return a Description, Not DOM

#### 🧩 What is it?
A React **component** is just a JavaScript function. When React calls it, it does **not** create or touch any real page elements — it **returns a plain description** of what the UI should be: a lightweight object tree (these are called **React elements**) saying "a `span`, with this class, containing this text."

#### 🤔 Why do we need it? (the problem)
If every component immediately created real DOM nodes, React couldn't compare "what you want now" against "what's on screen already" — it would have nothing to diff, and would have to rebuild the page. By returning a cheap *description* instead, React can hold two versions in memory (the old one and the new one), compare them, and change only what differs. Plain JavaScript objects are fast to create and throw away; real DOM nodes are not.

#### ⚙️ How does it work?
The JSX you write (the HTML-looking syntax) is compiled into function calls that build plain objects. So `<span>{count}</span>` becomes roughly an object like `{ type: "span", props: { children: count } }`. That object is *inert* — it's a recipe, not a meal. React reads the recipe later and decides what cooking (DOM work) is actually needed.

> **Note (simplification):** the real element object has more fields (a `key`, a `ref`, an internal tag), and JSX compiles to `jsx()` / `React.createElement()` calls. The point that matters here: a component returns **data describing UI**, never live DOM nodes.

#### 🌍 Real-life analogy
A component is an **architect handing you a blueprint**, not a builder pouring concrete. The blueprint describes the house ("a kitchen here, two bedrooms there"). It's cheap to draw, cheap to revise, and cheap to compare against last week's blueprint. React is the construction crew that reads the blueprint and only changes the rooms that differ — it doesn't demolish and rebuild the whole house.

#### 💻 Code example
```javascript
function Greeting({ name }) {
  // This LOOKS like HTML, but nothing is rendered to the page here.
  return <h1>Hello, {name}</h1>;
}

// What that JSX really produces is a plain object (a "React element"):
const description = {
  type: "h1",
  props: { children: ["Hello, ", "Ada"] },
};
// It's just data. No <h1> exists in the page yet — React decides that later.
// console.log(typeof description) -> "object"
```

#### 🎤 Interview question
**Q: What does a React component return — DOM nodes?**
A: No. A component returns a *description* of the UI as plain JavaScript objects (React elements), built from your JSX. Those objects are inert data — a recipe, not the meal. React later reads that description, compares it to the previous one, and produces the minimal real-DOM changes. The component itself never creates or mutates DOM.

### 🔁 Render → Reconcile → Commit — The Three-Step Loop

#### 🧩 What is it?
Every time React updates the screen, it runs the same three steps. **Render**: call your components to get a fresh description of the UI. **Reconcile**: compare (diff) that new description against the previous one to find what actually changed. **Commit**: apply only those changes to the real DOM.

#### 🤔 Why do we need it? (the problem)
Naively, "state changed, so rebuild the page" would wipe and recreate everything — slow, and it would lose things like cursor position and scroll. The three-step loop exists so React can figure out the **smallest set of edits**: it renders a full new picture (cheap, just objects), diffs it to see the few things that moved, and commits only those. You get the simplicity of "describe the whole UI" with the speed of "change almost nothing."

#### ⚙️ How does it work?
```
   STATE CHANGES (e.g. setCount fires)
        │
        ▼
   ┌──────────┐   call your components,
   │  RENDER  │   get a new element-tree
   └────┬─────┘   description  (no DOM yet)
        │
        ▼
   ┌────────────┐  diff NEW description
   │ RECONCILE  │  against the OLD one;
   └────┬───────┘  list what truly changed
        │
        ▼
   ┌──────────┐   apply ONLY those changes
   │  COMMIT   │   to the real DOM (the
   └──────────┘   only step that touches it)
```
Only the **commit** step ever mutates the page. Render and reconcile happen entirely in memory with plain objects. If the diff finds nothing changed, commit does no DOM work at all.

> **Note (simplification):** real React splits commit into sub-phases and runs render as interruptible work units (Fiber) — covered later in this path. The render → reconcile → commit shape is the accurate backbone.

#### 🌍 Real-life analogy
Think of a **newspaper editor preparing tomorrow's edition**. *Render*: a fresh draft of every page is written. *Reconcile*: the editor lays the new draft next to today's printed paper and circles only the paragraphs that changed. *Commit*: the press is told to re-set *only those paragraphs* — not reprint the whole paper. Drafting and comparing are cheap; running the press (touching the real thing) is the expensive part you minimize.

#### 💻 Code example
```javascript
function Profile() {
  const [likes, setLikes] = React.useState(0);

  // Clicking calls setLikes -> React runs the 3-step loop:
  //  1. RENDER:    Profile() runs again, returns a new description
  //  2. RECONCILE: React diffs it vs the old one -> only the number changed
  //  3. COMMIT:    React updates ONLY that text node in the real DOM
  return (
    <button onClick={() => setLikes(likes + 1)}>
      Likes: {likes}
    </button>
  );
  // The <button>, its class, its handler: unchanged -> untouched in commit.
}
```

#### 🎤 Interview question
**Q: What actually happens when state changes in React?**
A: React runs a three-step loop. **Render** calls the affected components to produce a new description (an element tree) — no DOM is touched. **Reconcile** diffs that new tree against the previous one to compute the minimal set of differences. **Commit** applies just those differences to the real DOM. Only commit mutates the page; render and reconcile are pure in-memory work, which is why they're cheap and can be redone.

### 🎭 "Re-render" ≠ "DOM Update" — The Distinction That Trips Everyone

#### 🧩 What is it?
A **re-render** means React *called your component function again* to get a new description. A **DOM update** means React *changed something on the actual page*. They are different events: a re-render always produces a description, but it only causes a DOM update if the diff finds an actual difference. Often, nothing changes — so the page isn't touched.

#### 🤔 Why do we need it? (the problem)
Beginners panic at "my component re-rendered 50 times!" and assume the page is being thrashed. But a re-render is usually cheap: it's just running a function and making some objects. The expensive part — touching the DOM — only happens during commit, and only for the bits that genuinely changed. Confusing the two leads to chasing the wrong performance problems (and to misusing memoization).

#### ⚙️ How does it work?
```
   re-render  =  RENDER + RECONCILE   (call fn, diff;
                                        in memory only)
   DOM update =  the COMMIT step       (mutate the page)

   re-render with NO diff  ──▶  commit does nothing
   ────────────────────────────────────────────────
   function ran ✔   page touched ✘   ← totally normal
```
So "this component re-rendered" tells you React re-ran the function and diffed the output. Whether the screen changed is a *separate* question, answered by the diff. A re-render that produces an identical description results in **zero** DOM mutations.

#### 🌍 Real-life analogy
Re-rendering is **redrawing a sketch of your room on tracing paper**; a DOM update is **actually moving the furniture**. You can re-sketch the room ten times in a minute — if the new sketch matches the last one, you move nothing. Only when a sketch differs do you get up and shift a chair. Cheap redraws, rare furniture moves.

#### 💻 Code example
```javascript
function Clock({ now, label }) {
  // Suppose the parent re-renders every second, passing the SAME label.
  // This component RE-RENDERS each time (function runs, new description made).
  // But React diffs the result: only {now} changed, so:
  //   - the text showing `now`   -> DOM updated
  //   - the <h2> showing `label` -> identical -> NOT touched in the DOM
  return (
    <div>
      <h2>{label}</h2>   {/* re-rendered, but no DOM change */}
      <p>{now}</p>       {/* re-rendered AND DOM-updated */}
    </div>
  );
}
// Re-render count: many. DOM updates: only the parts that actually differ.
```

#### 🎤 Interview question
**Q: Does a re-render always update the DOM?**
A: No. A re-render just means React called the component again and diffed its output (render + reconcile) — all in memory. The DOM is only touched in the commit phase, and only for nodes the diff found to be different. If a re-render produces a description identical to the previous one, React commits nothing — zero DOM mutations. That's why "it re-rendered" is not the same as "the page changed," and why re-renders are usually cheap.

<h2 id="module-1">Module 1 — JSX, Elements & Components</h2>

You write `<App />` and a UI appears — but the browser has never heard of JSX, and React isn't watching your file. So what *is* that tag? In this module we follow JSX one hop down: it's secretly a function call that returns a plain JavaScript object — a tiny "to-do note" describing what you want on screen. Understand that object and three confusing words (element, component, instance) finally separate, and you'll see why React can throw away the whole description on every render without breaking a sweat.

---

### 🏷️ JSX Is Just a Function Call — the disappearing trick

#### 🧩 What is it?
**JSX** is the HTML-looking syntax you write inside React — `<button>Save</button>`. It is **not** part of JavaScript. Before your code ever runs, a build tool (Babel, or the bundler) **compiles** JSX into ordinary JavaScript function calls. The browser only ever sees the plain JavaScript.

#### 🤔 Why do we need it? (the problem)
Describing a UI tree by hand in raw JavaScript is painful and unreadable — deeply nested function calls with props passed as objects. JSX lets you write the tree in a familiar HTML-like shape, while still getting plain JavaScript underneath. It's **syntax sugar**: nicer to read, identical in meaning.

#### ⚙️ How does it work?
A compiler rewrites each tag into a function call. The tag name becomes the first argument (the **type**), the attributes become a **props** object, and the contents become **children**.

```
   YOU WRITE (JSX)            COMPILER OUTPUT (plain JS)
   ┌───────────────────┐      ┌──────────────────────────────┐
   │ <h1 id="t">Hi</h1>│ ───▶ │ _jsx("h1", {                 │
   └───────────────────┘      │   id: "t",                   │
                              │   children: "Hi"             │
                              │ })                           │
                              └──────────────────────────────┘
   Tag name → type · attributes → props · contents → children
```

The `_jsx(...)` call doesn't touch the screen. It just **returns an object**. That returned object is a **React element** (the next topic). So JSX → function call → object. The HTML look is a costume; underneath it's data.

#### 🌍 Real-life analogy
JSX is like writing a recipe in plain English — "two eggs, one cup flour". The kitchen's ordering system can't read English, so a clerk rewrites it onto a **standard order ticket** with fixed fields. The English is for *you*; the ticket is what the kitchen actually processes. JSX is the English; the function call is the ticket.

#### 💻 Code example
```jsx
// What you write (JSX):
const x = <h1 id="t">Hi</h1>;

// What the compiler turns it into (modern automatic runtime):
import { jsx as _jsx } from "react/jsx-runtime";
const x = _jsx("h1", { id: "t", children: "Hi" });

// They are EXACTLY equivalent. The browser only ever runs the second.
```

#### 🎤 Interview question
**Q: What does JSX compile to?**
A: Plain JavaScript function calls that return objects. A build step (Babel / the bundler) rewrites each tag into a call — `React.createElement(type, props, ...children)` under the **classic** transform, or `_jsx(type, props)` under the **modern automatic** transform. The browser never sees JSX itself; it sees the resulting function calls, which produce React **element** objects.

---

### 🔀 Classic vs. Automatic Transform — why `import React` vanished

#### 🧩 What is it?
There are **two** ways the compiler can rewrite JSX. The older **classic** transform turns every tag into `React.createElement(...)`. The newer **automatic** transform (default since React 17) turns every tag into `_jsx(...)`, a helper it **imports for you** from `react/jsx-runtime`.

#### 🤔 Why do we need it? (the problem)
Under the classic transform, because every tag became `React.createElement(...)`, the name `React` had to be in scope in **every** file — so you wrote `import React from "react"` at the top even when you never typed the word "React" yourself. Forget it, and the file broke with a confusing error. The automatic transform was created to remove that boilerplate (and to let React build elements a bit more efficiently).

#### ⚙️ How does it work?
The two transforms differ in what call they emit and who imports the helper:

```
   CLASSIC TRANSFORM                AUTOMATIC TRANSFORM (React 17+)
   ─────────────────                ───────────────────────────────
   needs: import React              build tool auto-adds:
   from "react"  (by hand)            import {jsx as _jsx}
                                       from "react/jsx-runtime"
   <Foo a={1}/>  ──▶                <Foo a={1}/>  ──▶
   React.createElement(Foo,{a:1})   _jsx(Foo, {a:1})
```

Key differences with the automatic transform:
- **No `import React` needed** just to use JSX — the bundler injects the import for the helper itself.
- The helper is `_jsx` (and `_jsxs` for multiple children), pulled from `react/jsx-runtime`.
- You only `import React` now if you actually use the `React` object directly (e.g. `React.useState` instead of a named import).

Both transforms produce the **same kind of result**: a React element object. Only the call shape and the import differ.

> **Note (simplification):** `_jsx` and `React.createElement` are very close but not byte-identical — `_jsx` takes `children` and `key` slightly differently, and is tuned for the build pipeline. For learning, treat them as "two spellings of the same idea: make an element object."

#### 🌍 Real-life analogy
It's the difference between **bringing your own pen** to fill out a form versus the office **leaving a pen chained to the desk**. Classic: you must remember to bring the pen (`import React`) every time, or you can't sign. Automatic: the pen is already there — you just fill in the form and the tools handle the rest.

#### 💻 Code example
```jsx
// SAME component, two transforms.

// 1) Classic — you must import React even though you never type "React":
import React from "react";
function Hi() {
  return <span>hi</span>;
}
// compiles to: React.createElement("span", null, "hi")

// 2) Automatic (default today) — no React import required:
function Hi() {
  return <span>hi</span>;
}
// compiles to: _jsx("span", { children: "hi" })
//   ...with import {jsx as _jsx} from "react/jsx-runtime" added FOR you.
```

#### 🎤 Interview question
**Q: Why don't modern React files need `import React from "react"` at the top?**
A: Because of the **automatic JSX transform** (default since React 17). Classic JSX compiled every tag to `React.createElement(...)`, so `React` had to be in scope in every file. The automatic transform compiles tags to `_jsx(...)` and has the build tool auto-import that helper from `react/jsx-runtime`, so `React` no longer needs to be imported just to write JSX — only if you use the `React` object directly.

### 📦 The React Element — a plain object, nothing magic

#### 🧩 What is it?
A **React element** is the **plain JavaScript object** that `_jsx(...)` / `React.createElement(...)` returns. It's a lightweight **description** of what you want on screen: its `type` (what kind of thing), its `props` (its data, including children), and a few internal fields like `key`. It is **immutable** — once made, you don't change it; you make a new one.

#### 🤔 Why do we need it? (the problem)
React needs a representation of your UI that it can **inspect, compare, and reason about** *before* touching the slow, real DOM (the page's actual elements). A description object is cheap to build and easy to diff. So instead of you commanding the DOM directly, you hand React a description, and React figures out the DOM changes. The element object is that description.

#### ⚙️ How does it work?
`createElement` / `_jsx` just packages your arguments into an object roughly shaped like this:

```
   _jsx("h1", { id: "t", children: "Hi" })  returns:
   ┌──────────────────────────────────────┐
   │ {                                     │
   │   type: "h1",        // what to make  │
   │   key: null,         // list identity │
   │   props: {                            │
   │     id: "t",                          │
   │     children: "Hi"   // contents      │
   │   }                                   │
   │ }                                     │
   └──────────────────────────────────────┘
   A STRING type ("h1") = a DOM tag.
   A FUNCTION type (Foo) = your component.
```

- `type` is either a **string** (`"h1"`, `"div"` → a real DOM tag) or a **function/class** (`Foo` → one of your components).
- `props` holds everything you passed, with `children` as one of the props.
- The object is just data — it does **nothing** on its own. React reads it later during rendering.
- It's **immutable**: React (and you) never mutate an existing element. A new render produces brand-new element objects.

> **Note (simplification):** Real elements carry a few extra internal fields (such as `$$typeof`, a Symbol React uses to tell real elements from random objects, plus `ref`). The `{ type, key, props }` shape is the part that matters for understanding.

#### 🌍 Real-life analogy
An element is an **Amazon order in your cart** — a slip that says *"1 blue mug, quantity 2"*. The slip isn't the mug; it's a **description** of what you want. It's cheap to create, easy to change your mind about (make a new slip), and only later does the warehouse (React) act on it to ship a real object (the DOM node).

#### 💻 Code example
```jsx
// An element is literally just an object — you can log it:
const el = <h1 id="t">Hi</h1>;
console.log(el);
// roughly:
// { type: "h1", key: null, props: { id: "t", children: "Hi" } }
//   (plus internal fields like $$typeof)

// It's immutable — this is a no-op / mistake, NOT how you update UI:
// el.props.id = "x";  ❌  never mutate an element
// Instead: render again and produce a NEW element.
```

#### 🎤 Interview question
**Q: What is a React element, really?**
A: A plain, immutable JavaScript object that **describes** a piece of UI — it has a `type` (a DOM tag string or a component function), a `props` object (including `children`), and internal fields like `key`. It's produced by `_jsx` / `React.createElement` and does nothing by itself; React reads it during rendering to decide what DOM to create or update.

### 🧬 Element vs. Component vs. Instance — the three people conflate

#### 🧩 What is it?
Three different things that share vocabulary:
- **Component** — the **function (or class)** you write that *returns* elements. The blueprint.
- **Element** — the **description object** produced when that component (or a DOM tag) is used. The order slip.
- **Instance** — the **live, running thing** React keeps internally (on a **Fiber** — its internal record) that holds the component's state and tracks it across renders.

#### 🤔 Why do we need it? (the problem)
Interviews and bug reports get muddled because people say "component" for all three. Separating them answers real questions: *"Why does `<Foo />` not run my function immediately?"* (it makes an **element**, React calls the component later) and *"Where does my `useState` value live between renders?"* (in the **instance** React keeps, not in the element).

#### ⚙️ How does it work?

```
   COMPONENT (you write it — a blueprint)
   ┌────────────────────────────────┐
   │ function Greeting({name}) {     │
   │   return <h1>Hi {name}</h1>;    │
   │ }                               │
   └────────────────────────────────┘
            │  use it as <Greeting name="Ada"/>
            ▼
   ELEMENT (a description object — NOT called yet)
   ┌────────────────────────────────┐
   │ { type: Greeting,               │
   │   props: { name: "Ada" } }      │
   └────────────────────────────────┘
            │  React renders it → calls Greeting(props)
            ▼
   INSTANCE (live thing React keeps on a Fiber)
   ┌────────────────────────────────┐
   │ holds state, effects, identity  │
   │ across re-renders               │
   └────────────────────────────────┘
```

- Writing `<Greeting name="Ada" />` does **not** call `Greeting`. It creates an **element** whose `type` is the `Greeting` function. React calls the function **later**, during rendering.
- When React renders that element, it creates/updates an **instance** (internally, a Fiber node) that remembers this `Greeting`'s state and effects between renders.
- In **function components** you almost never touch the instance directly — it's React's internal bookkeeping. (With old class components, `this` *was* the instance. Hooks hide it.)

#### 🌍 Real-life analogy
A **component** is a **cookie cutter** (the blueprint). An **element** is your written note *"cut one star cookie, sprinkles on top"* (a description, no cookie yet). The **instance** is the **actual baked cookie on the tray**, which the baker (React) tracks — refrosting it (state changes) without throwing it away. You design the cutter and write notes; you rarely handle the cookie on the tray yourself.

#### 💻 Code example
```jsx
// COMPONENT: the function (blueprint)
function Greeting({ name }) {
  return <h1>Hi {name}</h1>;
}

// ELEMENT: using it just builds a description object — Greeting is NOT called yet
const el = <Greeting name="Ada" />;
// el ≈ { type: Greeting, props: { name: "Ada" } }

// INSTANCE: created by React when it renders <el>. It lives on a Fiber and
// holds state across renders. In function components you don't touch it directly:
function Counter() {
  const [n, setN] = React.useState(0); // `n` is stored on THIS instance, not in any element
  return <button onClick={() => setN(n + 1)}>{n}</button>;
}
```

#### 🎤 Interview question
**Q: What's the difference between a React element, a component, and an instance?**
A: A **component** is the function/class you write that returns elements — the blueprint. An **element** is the immutable description object (`{ type, props, ... }`) created when you use that component or a DOM tag — `<Foo />` makes an element, it doesn't call `Foo`. An **instance** is the live thing React keeps internally on a **Fiber**, holding the component's state and identity across renders; in function components you rarely interact with it directly.

### 🪆 `props.children` & Cheap Elements — composition for free

#### 🧩 What is it?
**`children` is just another prop.** Whatever you nest between a component's opening and closing tags is passed to it as `props.children`. There's nothing special about it — it's a regular field in the same `props` object as everything else. This is what makes React **composition** (putting components inside components) work.

#### 🤔 Why do we need it? (the problem)
You want reusable "wrapper" components — a `Card`, a `Modal`, a `Layout` — that don't know in advance what goes inside them. `children` lets a component accept arbitrary content as data and decide *where* to place it, without hard-coding what that content is. Second problem it answers: *"Doesn't rebuilding the whole UI description on every render waste memory?"* No — and `children` being plain data is why.

#### ⚙️ How does it work?
Nesting in JSX simply fills the `children` prop:

```
   <Card>Hello</Card>
        │  compiles to
        ▼
   _jsx(Card, { children: "Hello" })
        │  inside Card, props.children === "Hello"
        ▼
   Card renders props.children wherever it wants.
```

And here's why making a fresh element tree **every render is cheap**:
- Elements are **tiny plain objects** — a `type`, a `props`, a couple of fields. Creating one is just allocating a small object, which JavaScript does extremely fast.
- They are **NOT DOM nodes.** No layout, no paint, no browser work happens when you create an element — that's the expensive part, and it doesn't occur here.
- So React happily lets you return a brand-new tree of these lightweight objects on every render, then **diffs** the new description against the old one and only touches the **real DOM** where something actually changed (that's Module 2's reconciliation).

> **Note:** "Cheap" means *cheap relative to the DOM*. Building millions of elements still costs something — but for normal UIs it's negligible next to the DOM work React saves you.

#### 🌍 Real-life analogy
`children` is a **gift box**: the box (the `Card` component) is designed without knowing what it'll hold; you drop *anything* inside and it wraps it. And creating elements every render is like **rewriting a shopping list** versus **re-buying the groceries** — scribbling a fresh list (elements) is instant and free; only actually going to the store (the DOM) costs time, so React compares lists and re-buys only what changed.

#### 💻 Code example
```jsx
// `children` is just a prop — a reusable wrapper that doesn't know its contents:
function Card({ children }) {
  return <div className="card">{children}</div>;
}

// Anything nested becomes props.children:
<Card>
  <h2>Title</h2>
  <p>Body text</p>
</Card>;
// compiles to roughly:
//   _jsxs(Card, { children: [ _jsx("h2", {children:"Title"}),
//                            _jsx("p",  {children:"Body text"}) ] })

// Re-rendering builds a WHOLE new tree of these little objects — and that's fine.
// They're plain objects, not DOM nodes, so it's cheap. React diffs old vs new
// and only updates the real DOM where it differs.
```

#### 🎤 Interview question
**Q: Why is creating a new element tree on every render cheap?**
A: Because React elements are **lightweight plain JavaScript objects** — just `type`, `props`, and a few fields — not real DOM nodes. Allocating small objects is very fast, and crucially, building elements does **no** DOM work (no layout, paint, or reflow). React creates the fresh description, diffs it against the previous one, and only the genuinely changed parts get applied to the actual (expensive) DOM. The cheap part runs every render; the expensive part is minimized.

<h2 id="module-2">Module 2 — Reconciliation & the Virtual DOM</h2>

When state changes, React doesn't blindly rebuild the page. It re-runs your components to get a fresh *description* of the UI, compares that description to the previous one, and then touches only the parts of the real page that actually changed. This compare-and-update step is called **reconciliation**, and the description it works on is the **virtual DOM**. Understand this one chapter and "why doesn't my list keep its input values?" stops being a mystery.

---

### 🌳 The Virtual DOM — React's Lightweight Sketch of the UI

#### 🧩 What is it?
The **virtual DOM** (often shortened to **VDOM**) is a tree of plain JavaScript objects that *describes* what the UI should look like — nothing more. Each object (a **React element**) records a type (like `div` or your `Button`), its props, and its children. It is a sketch, not the real page. The real page lives in the **DOM** — the browser's live tree of actual on-screen elements.

#### 🤔 Why do we need it? (the problem)
Touching the real DOM is the slow, awkward part of UI work. If every state change made you hand-write "find this node, change that text, remove that row," your code would be a tangle of manual edits and easy to get wrong. React flips it around: you just describe *what the UI should be* for the current state, and React figures out the edits. To figure out the edits, it needs a cheap before-and-after picture it can compare. That picture is the virtual DOM.

#### ⚙️ How does it work?
On every render React builds a **new** virtual-DOM tree from your components, then **diffs** it against the **previous** tree it kept from the last render. The differences become a small list of real-DOM changes, which React applies.

```
   render N            render N+1          DIFF result
   (previous VDOM)     (new VDOM)
   ┌──────────┐        ┌──────────┐
   │  <ul>    │        │  <ul>    │   ul: same type, keep
   │   <li>A  │   vs   │   <li>A  │   li A: text same, no-op
   │   <li>B  │        │   <li>X  │   li B: text B -> X, patch
   └──────────┘        └──────────┘
        │                   │
        └──────► compare ───┴──► one real-DOM edit: set li.text = "X"
```

> **Note (simplification):** the virtual DOM is **not** magically faster than well-written direct DOM code. Building and diffing trees has its own cost. Its real value is the **programming model** (you describe state, not steps) plus **batched, minimal** updates so the app stays correct and maintainable. "VDOM is fast" is marketing shorthand, not a law.

#### 🌍 Real-life analogy
Think of an architect's **paper blueprint** versus the **actual building**. Redrawing a blueprint is cheap; rebuilding a wall is expensive. When the design changes, the architect compares the new blueprint to the old one, spots that only one window moved, and tells the crew to change *just that window* — not to demolish and rebuild the house. The blueprint is the virtual DOM; the building is the real DOM.

#### 💻 Code example
```javascript
// A React element is just a plain object describing UI — not real DOM.
const element = {
  type: "li",
  props: { className: "row", children: "Buy milk" },
};
// JSX <li className="row">Buy milk</li> compiles to roughly the object above.
// React keeps a TREE of these. On the next render it builds a fresh tree
// and compares it to this one to decide what (if anything) to touch.
```

#### 🎤 Interview question
**Q: Is the virtual DOM faster than directly manipulating the real DOM?**
A: Not inherently — diffing two trees has a real cost, and hand-tuned DOM code can beat it. The virtual DOM's value is the **declarative programming model** (you describe the UI for a given state instead of scripting each mutation) plus **batched, minimal** DOM updates that keep the app correct as it grows. It trades a little CPU for a lot of maintainability.

---

### 🔀 Reconciliation Heuristics — How React Decides What Changed

#### 🧩 What is it?
**Reconciliation** is the process of diffing the new virtual-DOM tree against the previous one to produce the minimal set of real-DOM changes. It runs on a few simple **heuristics** — practical shortcuts that are right almost all the time — rather than a perfect, exhaustive comparison.

#### 🤔 Why do we need it? (the problem)
A truly *optimal* algorithm that finds the smallest possible set of edits between two arbitrary trees is famously expensive — on the order of **O(n³)** (cube of the number of nodes). For a tree of 1,000 nodes that is roughly a billion operations every update. No interactive app can afford that. React makes the problem tractable by **assuming** a couple of things about real UIs, which lets it diff in **O(n)** (linear) time instead.

#### ⚙️ How does it work?
React walks both trees together, comparing node to node, using three rules:

```
   compare old node  ──▶  new node at the SAME position

   1) DIFFERENT TYPE  (e.g. <div> became <span>)
        tear DOWN the whole old subtree,
        BUILD a fresh one  ── component STATE is LOST

   2) SAME TYPE       (e.g. <div> stayed a <div>)
        KEEP the existing DOM node,
        update only the props/attrs that changed,
        then recurse into the children

   3) LIST OF CHILDREN
        match children across renders by their KEY
        (no key -> match by position/index)
```

The two assumptions that make this work:
- Elements of a **different type** produce different trees, so it's safe to throw the old subtree away rather than try to reuse it.
- Children that the developer marks with a **stable key** keep their identity across renders, so React can match "same item, new position" instead of re-diffing blindly.

When rule 1 fires, the old DOM nodes are removed and new ones are created from scratch — which means any state inside that subtree (a text input's value, a hook's state, scroll position) is **gone**. When rule 2 fires, the same DOM node stays in place and only the changed bits are patched, so state is preserved.

> **Note (simplification):** "different type → remount" is about the element's *type identity* at the same position. Changing only props on the **same** type does not remount; it updates in place.

#### 🌍 Real-life analogy
Imagine a hotel housekeeper comparing yesterday's room layout to today's plan. If the plan still says "double bed" (same type), they leave the bed and just change the sheets (update props). If the plan now says "swap the bed for a desk" (different type), they haul the bed out and bring a desk in — and whatever was *in* the bed's drawers (its state) is gone. For a row of identical chairs, they read the little name tags (keys) to know which chair is which after a reshuffle.

#### 💻 Code example
```jsx
// SAME TYPE across renders -> DOM node kept, only changed props patched.
function Greeting({ name }) {
  // <h1> stays an <h1>; React just updates the text node inside it.
  return <h1 className="title">Hello, {name}</h1>;
}

// DIFFERENT TYPE at the same position -> old subtree torn down, new one built.
function Panel({ loading }) {
  // Switching <Spinner/> <-> <Content/> REMOUNTS: any state inside is reset,
  // because they are different component types at this position.
  return loading ? <Spinner /> : <Content />;
}
```

#### 🎤 Interview question
**Q: How does React's diffing algorithm work, and what happens when an element's type changes?**
A: React compares the new element tree to the previous one position by position. **Same type** at a position → it keeps the existing DOM node and updates only the changed props, then recurses into children. **Different type** → it unmounts the entire old subtree and mounts a fresh one, so all state inside that subtree is lost. For lists it matches children by **key**. These heuristics let it diff in O(n) instead of the optimal-but-impractical O(n³).

---

### 🔑 Keys — Stable Identity for List Items

#### 🧩 What is it?
A **key** is a special prop you put on each element in a list (`key={...}`). It gives React a **stable, unique identity** for each item so that, across re-renders, React can tell "this is the same item that moved" apart from "this is a brand-new item."

#### 🤔 Why do we need it? (the problem)
Lists reorder, get items inserted in the middle, and have items deleted. Without a stable identity, React falls back to matching list children **by their position** (index 0 to index 0, index 1 to index 1, and so on). That's fine if the list never changes shape — but the moment you insert at the front or reorder, position-matching pairs up the **wrong** old and new items. React then "updates" item 0's DOM node to show item 1's data while leaving item 0's internal state (like a typed-in input value) attached to it. The result: wrong text, wrong checkboxes, and inputs that show the wrong row's value.

#### ⚙️ How does it work?
With keys, React matches new children to old children by key, not by slot:

```
   INSERT "X" at the front, NO keys (match by index):
     old: [ A ,  B ,  C ]      new: [ X ,  A ,  B ,  C ]
     idx:   0    1    2               0    1    2    3
            │    │    │               │    │    │    │
   React pairs index-to-index:  A->X, B->A, C->B, (new) C
   => it patches THREE existing nodes + adds one. State stays
      glued to the wrong rows.

   INSERT "X" at the front, WITH stable keys:
     old: A(k=a) B(k=b) C(k=c)
     new: X(k=x) A(k=a) B(k=b) C(k=c)
   React matches by key:  a->a, b->b, c->c unchanged;
   x is new => it INSERTS one node, A/B/C keep their state.
```

The key must be **stable** (same item → same key on every render) and **unique among siblings**. Good keys are an item's database id or any value derived from the data itself. The array **index** is *not* a stable identity: when the list reorders or you insert/delete in the middle, an item's index changes, so the "same key" now points at a *different* item.

> **Note:** using the index as a key is only safe when the list is **static** — it never reorders, and items are never inserted or removed anywhere but the end. The instant any of those happen, index keys cause the bugs above.

#### 🌍 Real-life analogy
Keys are **assigned seat numbers** versus "wherever you're standing in line." If you track people by line position and someone cuts to the front, everyone's position shifts — and your notes about each person now describe the person who used to stand there. Give everyone a **named ticket** (a stable key) and a cut-in-line doesn't scramble who's who; you just slot the newcomer in and everyone else keeps their identity.

#### 💻 Code example
```jsx
// ❌ INDEX-AS-KEY BUG: each row has its own input state. Insert at the top
//    and React reuses node 0 for the new item — the old input values stay
//    bound to the wrong rows.
function BadList({ items }) {
  return (
    <ul>
      {items.map((item, index) => (
        <li key={index}>            {/* index changes when list reorders */}
          <input defaultValue={item.label} />
        </li>
      ))}
    </ul>
  );
}

// ✅ STABLE-ID KEY: identity travels WITH the item. Inserting at the top
//    only adds one node; every other row keeps its own input value.
function GoodList({ items }) {
  return (
    <ul>
      {items.map((item) => (
        <li key={item.id}>          {/* stable, unique per item */}
          <input defaultValue={item.label} />
        </li>
      ))}
    </ul>
  );
}
```

#### 🎤 Interview question
**Q: Why do lists need keys, and why is the array index a bad key?**
A: Keys give React a stable identity for each list item so it can match items across renders and move/keep them instead of rebuilding. The array index is *positional*, not identity — when the list reorders or you insert/delete anywhere but the end, an item's index changes, so React pairs up the wrong old and new items. It then patches the wrong DOM nodes and leaves component state (like input values) attached to the wrong row. Index keys are only safe for a list that never changes order or shape.

---

### 📐 The O(n) Trade-off — Why React Diffs the Way It Does

#### 🧩 What is it?
React's diffing is a deliberate **trade-off**: it gives up finding the theoretically *smallest* set of changes in exchange for being **fast enough to run on every keystroke**. It compares two trees in **O(n)** time (work grows linearly with the number of nodes) by leaning on its heuristics, instead of the **O(n³)** an optimal general tree-diff would cost.

#### 🤔 Why do we need it? (the problem)
The general "minimum edit distance between two trees" problem is genuinely cube-time hard. At interactive speeds — diffing potentially thousands of nodes many times per second — that's a non-starter. React's bet is that real UIs don't need the perfect answer; they need a *very good* answer computed *instantly*. So it constrains the problem with assumptions until it becomes linear.

#### ⚙️ How does it work?
React buys its O(n) speed with two assumptions, and you "pay it back" by honoring them:

```
   General optimal tree diff ........ O(n^3)   (too slow)

   React's heuristic diff ........... O(n)     (fast)
     assumes:
       (1) different element TYPE
           => different tree  (don't try to reuse it)
       (2) developer-supplied KEYS
           => stable item identity across renders

   If those assumptions hold, the diff is correct AND linear.
   If you break them (e.g. index keys on a reordering list),
   the diff is still O(n) FAST but produces WRONG matches.
```

The important nuance: breaking the assumptions doesn't make React *slow* — it makes it **wrong** (reused state on the wrong nodes). The heuristics are about correctness-of-matching, not just speed. Honoring them (stable types per position, stable keys for lists) is what keeps the fast path also the *correct* path.

#### 🌍 Real-life analogy
A librarian *could* reshelve perfectly by re-sorting every book against every other book — but that's a closing-the-library-for-a-week job. Instead they trust two shortcuts: books are grouped by section (type), and each book has a call number on its spine (key). With those, returning a cart of books takes minutes. The shortcuts only work because the labels are accurate — slap wrong call numbers on the spines (index keys on a shuffled shelf) and books land in the wrong place, fast.

#### 💻 Code example
```jsx
// The whole bargain in one component:
function TodoList({ todos }) {
  return (
    <ul>
      {todos.map((todo) => (
        // STABLE key  -> O(n) diff that also matches items CORRECTLY,
        // even when `todos` is reordered or has items inserted/removed.
        <li key={todo.id}>{todo.text}</li>
      ))}
    </ul>
  );
}
// Swap key={todo.id} for key={index} and the diff stays just as FAST,
// but item identity breaks the moment the list changes shape.
```

#### 🎤 Interview question
**Q: Why does React use an O(n) heuristic diff instead of an optimal algorithm?**
A: The optimal minimum-edit tree-diff is about O(n³), far too slow to run on every update. React assumes two things — different element types produce different trees, and developer-provided keys give list items stable identity — which collapse the problem to O(n). Those assumptions are why the Rules (don't change types at a position arbitrarily, give lists stable keys) exist: honor them and you get a diff that's both fast *and* correctly matched; break them and it's still fast but matches the wrong nodes.

<h2 id="module-3">Module 3 — Fiber Architecture</h2>

You already know React diffs a new tree against the old one (Module 2). But *how* does React walk those trees without freezing the page on a huge update? The answer is **Fiber** — React's internal rewrite that turned rendering from one giant, unstoppable function call into a list of tiny, pausable steps. Meet the data structure that makes interruptible rendering possible.

---

### 🧱 The Fiber Node — One Unit of Work, One Component's Memory

#### 🧩 What is it?
A **Fiber** is a plain JavaScript object React creates for **each** thing it renders — every component, every DOM element. It plays two roles at once: it's a **unit of work** (a to-do item React processes), and it's the **memory** for one component instance — it remembers the component's type, its props, its state, its hooks, and links to its neighbours.

Glossary: an **instance** = one live copy of a component on screen (the `Counter` at the top is a different instance from the `Counter` below it).

#### 🤔 Why do we need it? (the problem)
A React element (Module 1) is **throwaway** — a fresh description object built on every render, then discarded. But React needs something that **survives** across renders to remember "this component's `useState` count is 5" and "this is the work I still owe." The element can't hold that — it's recreated every time. The Fiber is the **long-lived** counterpart that persists between renders and stores the durable facts.

#### ⚙️ How does it work?
For every element React encounters, it keeps a matching fiber holding fields like these (heavily simplified):

```
   FIBER  (one node — a component's persistent record)
   ┌──────────────────────────────────────────┐
   │ type      : Counter   (function/tag/'div')│
   │ pendingProps : { label: 'A' }  (new props)│
   │ memoizedState: hooks list (useState, ...) │
   │ stateNode : the real DOM node or instance │
   │ child     : ● first child fiber           │
   │ sibling   : ● next fiber at same level     │
   │ return    : ● parent fiber                 │
   │ alternate : ● twin fiber in the other tree │
   │ flags     : what changed (Placement, ...)  │
   └──────────────────────────────────────────┘
```

> **Note (simplification):** a real fiber has *many* more fields (`lanes`, `effectTag`, `updateQueue`, `key`, `index`, and more). These are the ones that matter for the mental model — don't treat this as the literal struct.

#### 🌍 Real-life analogy
A React **element** is a sticky-note order slip — "make one latte" — written fresh and thrown away each time. A **fiber** is the barista's **job ticket clipped to the machine**: it names the drink (type), the new order details (props), notes already pulled from the last order (state/hooks), and points to the next ticket in line. The slip is disposable; the ticket sticks around and tracks progress.

#### 💻 Concrete illustration
There's no public API for fibers, but conceptually one looks like this:

```javascript
// A fiber is just an object React builds and reuses (simplified).
const counterFiber = {
  type: Counter,                  // the component (or 'div', 'span'...)
  pendingProps: { label: 'A' },   // props for the NEXT render
  memoizedState: /* hooks list */ null, // useState/useEffect chain
  stateNode: null,                // the real DOM node, for host fibers
  child: null,    // pointer to first child fiber
  sibling: null,  // pointer to next fiber at the same level
  return: null,   // pointer to parent fiber
  alternate: null // the twin fiber in the other tree (see below)
};
// React processes this object as ONE unit of work, then moves on.
```

#### 🎤 Interview question
**Q: What is a Fiber?**
A: A Fiber is a JavaScript object React keeps for each element it renders. It serves two purposes: it's a **unit of work** React processes one at a time, and it's the **persistent record of a component instance** — storing its `type`, `props`, `state`, its hooks list, and pointers to its parent, child, and sibling. Unlike a React element (which is recreated every render), a fiber survives across renders, which is what lets it remember state and track pending work.

---

### 🌲 The Fiber Tree — A Tree You Can Walk One Node at a Time

#### 🧩 What is it?
The fibers aren't loose — they're linked into a **tree** that mirrors your component tree. But instead of a parent holding an *array* of children, each fiber holds just **three pointers**: `child` (first child), `sibling` (next node beside it), and `return` (its parent). This makes the tree shaped like a **linked list** that React can traverse one step at a time.

#### 🤔 Why do we need it? (the problem)
To process work *one node at a time*, React must always be able to answer "where do I go next?" with a single pointer hop — and "after this whole subtree, where do I resume?" If children were stored as an array, React would need to recurse into them, which means relying on the call stack — and **you can't pause a call stack mid-recursion**. Three explicit pointers let React track its exact position as plain data it can stop and resume at will.

#### ⚙️ How does it work?
`child` goes down, `sibling` goes across, `return` goes back up. Here `App` has two children, `Header` and `List`; `List` has two `Item`s:

```
              App
               │ child
               ▼
            Header ──sibling──▶ List
               ▲                 │ child
               │ return          ▼
               └────── Item1 ──sibling──▶ Item2
                         │ return ▲
                         └────────┘  (return points to List)

   child  = go to first child (down)
   sibling= go to next node beside me (across)
   return = go back to parent (up, when done)
```

React walks it like reading: go down to the first child, across the siblings, and when a node has no child or sibling left, follow `return` up to the parent and continue from there.

#### 🌍 Real-life analogy
Think of a **scavenger hunt with chained clues** instead of a map. Each clue tells you only three things: the first place to go next (`child`), the place to check right after this one (`sibling`), and where to head back to when you hit a dead end (`return`). You never need the whole map in your head — just the clue in your hand. So you can stop anytime, pocket the clue, and pick up exactly where you left off.

#### 💻 Concrete illustration
A loop can walk the whole tree using only those pointers — no recursion:

```javascript
// Depth-first walk using only child / sibling / return (simplified).
function walk(root) {
  let fiber = root;
  while (fiber) {
    visit(fiber);                 // "do the work" for this one node
    if (fiber.child) {            // 1) go DOWN if there's a child
      fiber = fiber.child;
      continue;
    }
    while (fiber && !fiber.sibling) {
      fiber = fiber.return;       // 2) no sibling → go UP to parent
    }
    fiber = fiber?.sibling ?? null; // 3) then ACROSS to the next sibling
  }
}
// Because position is just `fiber`, we could `return` from this loop
// at ANY point and resume later by passing the saved fiber back in.
```

#### 🎤 Interview question
**Q: How is the fiber tree linked, and why not just use arrays of children?**
A: Each fiber has three pointers: `child` (first child), `sibling` (next node at the same level), and `return` (parent). This turns the tree into a linked-list-shaped structure React can traverse iteratively. Arrays would push React back into recursion to descend into children, and a recursive call stack can't be paused. With explicit pointers, React's current position is just a variable, so it can stop after any node and resume later.

---

### 🔁 Double Buffering — Two Trees, Swapped on Commit

#### 🧩 What is it?
React keeps **two** fiber trees at once. The **`current`** tree is what's on screen right now. The **`workInProgress`** tree is the new one React is building during a render. When the new tree is finished and applied to the DOM (the **commit**), React **swaps** them — `workInProgress` becomes the new `current`. This two-tree trick is called **double buffering**.

#### 🤔 Why do we need it? (the problem)
React's render phase is **interruptible** — it can be paused or even thrown away halfway (we'll see why next). If React edited the on-screen tree directly while building, a pause would leave the UI in a **half-updated, broken state**. By building changes on a *separate* `workInProgress` tree and only swapping when it's completely done, the screen always reflects one **consistent, finished** tree. An abandoned render simply throws away `workInProgress` — the visible `current` tree was never touched.

#### ⚙️ How does it work?
The two trees aren't built from scratch each time. Each fiber has an `alternate` pointer to its twin in the other tree, and React **reuses** those twin objects to avoid garbage. Before commit, both exist side by side:

```
   current tree (ON SCREEN)        workInProgress (BEING BUILT)
   ┌──────────┐                    ┌──────────┐
   │  App     │◀───alternate──────▶│  App'    │
   └────┬─────┘                    └────┬─────┘
        ▼                               ▼
   ┌──────────┐                    ┌──────────┐
   │  Count=5 │◀───alternate──────▶│  Count=6 │
   └──────────┘                    └──────────┘
        on screen                   new version

   ── COMMIT ──▶  the trees SWAP:
   workInProgress becomes the new `current`; the old
   `current` is kept as the alternate for next time.
```

> **Note (simplification):** "two trees" sounds like double the memory, but React **recycles** the alternate fibers and only rebuilds parts that change — it doesn't clone the whole tree every render.

#### 🌍 Real-life analogy
It's like a stage with **two backdrops on a rotating set**. The audience sees the front backdrop (`current`) while stagehands paint the *next* scene on the back one (`workInProgress`) — out of sight. Only when it's fully painted does the stage **rotate** to reveal it, in one clean motion. The audience never sees a half-painted backdrop, and if the new scene is scrapped, they were never shown the mess.

#### 💻 Concrete illustration
```javascript
// React holds a handle to the current tree and builds a workInProgress.
let current = appFiberOnScreen;        // what the user sees
let workInProgress = current.alternate; // its twin, reused as scratch space

// ...render phase fills in workInProgress with the new state...

function commit(finishedWork) {
  // apply DOM changes from finishedWork, THEN swap:
  current = finishedWork;              // the swap = one pointer assignment
  // finishedWork.alternate is now the OLD tree, kept for next render
}
```

#### 🎤 Interview question
**Q: What are the current and work-in-progress trees, and when do they swap?**
A: They're React's two fiber trees. `current` is the tree reflecting what's on screen; `workInProgress` is the tree React builds during a render with the new state. Because rendering can be interrupted, React builds changes on `workInProgress` so the visible tree is never left half-done. When the render finishes and React commits to the DOM, it **swaps** — `workInProgress` becomes the new `current`. This is "double buffering," and the two trees are linked node-for-node by `alternate` pointers.

---

### ⏸️ Why Fiber Replaced the Stack Reconciler — Making Render Pausable

#### 🧩 What is it?
Before Fiber (React 15 and earlier; Fiber shipped *in* React 16), React used the **stack reconciler**. It rendered by **recursing** through your component tree with normal function calls — and once that recursion started, it ran straight to the end. Fiber replaced it with a **work loop**: instead of one deep recursive call, React processes the fiber list one node per loop iteration, so it can **pause, resume, or abandon** the work between nodes.

#### 🤔 Why do we need it? (the problem)
The stack reconciler was **synchronous and un-pausable**. Its progress lived on the JavaScript **call stack** — and you can't freeze a call stack, hand control back to the browser, and unfreeze it later. So a large render would **hog the main thread**: the browser couldn't paint, scroll, or respond to typing until the *entire* tree finished. On a big update, the page **froze**. There was no way to say "this render is taking too long — let me handle this keystroke first, then continue."

#### ⚙️ How does it work?
Fiber moves the "where am I" state **off the call stack and into the fiber objects** (those `child`/`sibling`/`return` pointers). Now rendering is a `while` loop, and React checks between nodes whether it should yield control back to the browser:

```
   OLD: stack reconciler (recursion)
   render(App)
     └─ render(Header)        ← all one synchronous
          └─ render(List)        call stack: cannot
               └─ render(Item)   pause until DONE → UI FREEZES

   NEW: Fiber work loop (iteration)
   while (workInProgress && !shouldYield()) {
        workInProgress = performUnit(workInProgress);
   }                            ← can STOP between nodes,
                                  let the browser breathe,
                                  then RESUME or THROW AWAY
```

Because position is stored in data (the current fiber), React can stop after any node, let the browser paint or handle input, and resume from the saved fiber later — or drop a stale render entirely.

#### 🌍 Real-life analogy
The stack reconciler is **reading a 500-page book aloud in one breath** — you can't be interrupted until the last page, so the room waits. Fiber is reading it **one paragraph at a time with a bookmark**: after each paragraph you can pause to answer a question (a keystroke, an animation frame), slip in the bookmark, and later resume exactly where you stopped — or, if plans change, close the book and start a different one.

#### 💻 Concrete illustration
```javascript
// The heart of Fiber: an interruptible work loop (simplified).
function workLoop(deadline) {
  while (workInProgress && !shouldYield()) {
    // process ONE fiber, return the next one to work on
    workInProgress = performUnitOfWork(workInProgress);
  }
  if (workInProgress) {
    // not finished — yield to the browser, continue next frame
    requestIdleCallback(workLoop); // (React ships its own scheduler, Module 9)
  } else {
    commitRoot(); // tree complete → commit + swap (double buffering)
  }
}
// shouldYield() asks: "has the browser waited long enough? give it a turn."
```

> **Note (simplification):** React does **not** actually use `requestIdleCallback` — it ships its own cooperative scheduler (Module 9). It's shown here only to convey "do some work, then yield."

#### 🎤 Interview question
**Q: Why did React rewrite the reconciler as Fiber?**
A: To make rendering **interruptible**. The old stack reconciler rendered by synchronous recursion, so its progress lived on the call stack and couldn't be paused — a large render blocked the main thread and froze the page until it finished. Fiber moves the traversal state into fiber objects (`child`/`sibling`/`return`) and renders in a loop over units of work. That lets React pause between nodes to yield to the browser, resume later, reprioritize, or throw away a stale render — the foundation for concurrent rendering.

<h2 id="module-4">Module 4 — Render & Commit Phases</h2>

When you call `setState`, React does its work in **two clearly separated stages**: first it quietly figures out *what* should change (the **render phase**), then it actually touches the screen (the **commit phase**). Keeping these two apart is the single idea that makes everything else — interruptible rendering, why your components must be pure, why effects fire when they do — finally click. Let's pull them apart.

---

### 🎨 The Render Phase — React Asks "What Changed?"

#### 🧩 What is it?
The **render phase** is where React **calls your component functions** to build a fresh tree — the **`workInProgress` tree** (a work-in-progress copy of the UI, glossed in Module 3). Calling your component just returns a *description* of what the UI should look like. React compares that description to the previous one and notes the differences. Crucially, **nothing on the actual page changes yet** — this phase only computes a to-do list.

#### 🤔 Why do we need it? (the problem)
React wants to stay fast even when there's a lot of work to do. If a big update could **freeze the page** — blocking typing, clicks, and animations until it finished — the app would feel broken. So React needs a stage where it can do the heavy "figure out what changed" thinking in a way it can **pause, resume, or even throw away** if something more urgent (like a keystroke) comes in. The render phase is exactly that: a safe, abortable scratchpad.

#### ⚙️ How does it work?
React walks the component tree one node at a time, calls each component to get its output, and builds up the `workInProgress` tree. Because it processes one unit at a time, it can **stop between units** and hand control back to the browser.

```
  setState
     │
     ▼
  RENDER PHASE  (interruptible scratchpad)
  ┌──────────────────────────────────────┐
  │ call <App/>   -> describe UI          │
  │ call <List/>  -> describe UI   [pause]│ <- can yield here
  │ call <Row/>   -> describe UI          │
  │ ...build workInProgress tree...       │
  │ diff vs current tree -> list of edits │
  └──────────────────────────────────────┘
     │  (NO DOM touched yet)
     ▼
  hand the edit list to the COMMIT phase
```

The render phase is **interruptible**: React may pause it, resume it later, restart it from the top, or **discard it entirely** if the input that triggered it is now stale. Nothing it does is visible to the user, so throwing the work away is harmless.

> **Note (simplification):** Rendering is only interruptible when an update is scheduled through a **concurrent feature** (covered in Module 8). The point that matters here: the render phase is *designed* to be safely abortable, which is why the purity rules below exist.

#### 🌍 Real-life analogy
Think of an architect drafting a new floor plan **on paper** before any builders touch the building. They can erase lines, restart the sketch, or bin the whole draft — and the real house is completely unaffected, because it's still just paper. The render phase is that paper draft. The commit phase (next topic) is when the builders finally show up.

#### 💻 Code example
Because the draft can be redrawn many times or thrown away, your component **must not do anything with lasting consequences while React is calling it**.

```jsx
// ❌ ANTI-PATTERN: side effect during render
function Profile({ userId }) {
  // This FIRES every time React calls the component while drafting.
  // If React restarts or discards this render, you've still sent the
  // request -> duplicate/wasted network calls, out of your control.
  fetch(`/api/track?view=${userId}`);   // side effect in render!

  return <h1>User {userId}</h1>;
}

// ✅ CORRECT: keep render pure, do the side effect in an effect
import { useEffect } from "react";

function Profile({ userId }) {
  // Render is now pure: it only describes UI, nothing else.
  useEffect(() => {
    // Runs AFTER the screen is committed, exactly once per real update.
    fetch(`/api/track?view=${userId}`);
  }, [userId]);

  return <h1>User {userId}</h1>;
}
```

#### 🎤 Interview question
**Q: What happens during the render phase, and is it interruptible?**
A: React **calls your components** to build the `workInProgress` tree and diff it against the previous tree, producing a list of changes — but it does **not** touch the real DOM. It is **interruptible**: React can pause it, resume it, restart it, or throw it away, which is exactly why render-phase work must be pure and free of side effects.

---

### 🧼 Why Render Must Be Pure — The Golden Rule

#### 🧩 What is it?
A **pure** function returns the same output for the same inputs and has **no side effects** — it doesn't change anything outside itself. React requires your component body (the render phase) to be pure: given the same props and state, it should produce the same UI description, and it must **not** mutate the DOM, start subscriptions, write to shared variables, or fire network requests *while rendering*.

#### 🤔 Why do we need it? (the problem)
Remember the render phase can run your component **multiple times** for one update, or **discard a run** halfway through. If your component had side effects during render, those effects would fire on every speculative attempt and on every thrown-away draft — so you'd get **duplicate requests, double subscriptions, or DOM changes that don't match the final result**. Purity is the contract that makes "run it as many times as I like, or never finish it" *safe*.

#### ⚙️ How does it work?
Keeping render pure means: read props/state, compute, return JSX — and push everything with consequences into the **right place** (effects, event handlers).

```
  ALLOWED during render          NOT allowed during render
  ┌──────────────────────┐       ┌────────────────────────────┐
  │ read props / state   │       │ fetch / network calls      │
  │ compute values       │       │ mutate the DOM directly    │
  │ build/return JSX      │       │ setState of another comp   │
  │ call other pure fns   │       │ subscribe to a store       │
  └──────────────────────┘       │ write a shared/global var  │
                                 │ start a timer / log w/ side │
                                 └────────────────────────────┘
  Side effects belong in: useEffect / useLayoutEffect / handlers
```

Because React may call render **2+ times** and keep only one result, side effects placed here are unpredictable — they fire a number of times you don't control.

> **Note:** React's **StrictMode** in development *deliberately* double-invokes your render to surface impure code — if something breaks when run twice, it wasn't pure. (Effect timing under StrictMode is its own topic, in Module 7.)

#### 🌍 Real-life analogy
A pure render is like a **chef rehearsing a recipe out loud** before cooking: they can repeat the steps ten times and nothing happens to the kitchen. The moment the chef *actually cracks eggs* while merely rehearsing, repeating the rehearsal wastes ten cartons. Side effects are the cracked eggs — save them for the real cook (the commit/effects), not the rehearsal (render).

#### 💻 Code example
```jsx
// ❌ IMPURE: mutates a value outside the function during render
let renderCount = 0;

function Counter({ value }) {
  renderCount++;             // side effect: mutating outer state in render
  document.title = value;    // side effect: touching the DOM in render
  return <p>{value}</p>;
}
// If React renders this twice (e.g. StrictMode or a restart),
// renderCount jumps by 2 and document.title may be set from a
// draft that gets discarded -> behavior you didn't intend.

// ✅ PURE: render only describes UI; the DOM write moves to an effect
import { useEffect } from "react";

function Counter({ value }) {
  useEffect(() => {
    document.title = value;  // runs after commit, for the FINAL value only
  }, [value]);
  return <p>{value}</p>;     // same input -> same output, no side effects
}
```

#### 🎤 Interview question
**Q: Why must a React component's render be a pure function?**
A: Because the render phase can be **run multiple times, paused, restarted, or thrown away** before anything reaches the screen. If render had side effects, they'd fire on speculative or discarded attempts — causing duplicate requests, double subscriptions, or DOM changes inconsistent with the final UI. Purity guarantees render can be re-run or abandoned safely; side effects belong in effects or event handlers.

---

### 🛠️ The Commit Phase — React Touches the Real DOM

#### 🧩 What is it?
The **commit phase** is where React takes the list of changes computed during render and **applies them to the actual DOM** — inserting, updating, and removing real elements on the page. This is the moment the user's screen finally changes.

#### 🤔 Why do we need it? (the problem)
The render phase was abortable on purpose, but **the real DOM can't be left half-finished**. If React paused partway through DOM updates, the user could glimpse a **broken, half-updated screen** — half-old and half-new. So once React has decided exactly what to change, applying it must happen **all at once, without interruption**, so every visible change lands together.

#### ⚙️ How does it work?
The commit phase is **synchronous and NOT interruptible** — React runs it to completion in one go. It can't be paused, restarted, or thrown away, because it's mutating real, visible state.

```
  RENDER (done) -> edit list ready
        │
        ▼
  COMMIT PHASE  (synchronous, runs to the end)
  ┌──────────────────────────────────────┐
  │ apply ALL DOM edits in one burst      │
  │ no yielding, no pausing, no restart   │
  └──────────────────────────────────────┘
        │
        ▼
  DOM is now fully consistent -> browser can paint
```

Because it never yields, the user never sees an in-between state. The trade-off: committing must be **fast**, since it blocks the browser until it finishes — which is one reason React works so hard to keep the *render* phase (the expensive part) out of this synchronous window.

#### 🌍 Real-life analogy
Think of a **theatre stage change between acts**: the curtain drops, the crew swaps the entire set in one coordinated rush, then the curtain rises. The audience never watches a half-moved couch slide across the stage — they only see the finished scene. The commit phase is that curtain-down swap: all at once, no peeking.

#### 💻 Code example
```jsx
// You never call the commit phase yourself — React runs it.
// But you observe the split clearly here:
function Box() {
  console.log("render");          // RENDER phase: may run 0+ times, pure

  useLayoutEffect(() => {
    console.log("layout effect"); // COMMIT phase (layout sub-step), sync
  });

  useEffect(() => {
    console.log("passive effect"); // AFTER paint, async
  });

  return <div>hi</div>;
}
// Typical order for one update:
//   "render"  ->  "layout effect"  ->  (browser paints)  ->  "passive effect"
```

#### 🎤 Interview question
**Q: Why is the commit phase synchronous and not interruptible?**
A: Because it **mutates the real DOM**. If React paused mid-commit, the user could see a half-updated screen — some elements new, some old. By committing **synchronously and atomically**, React guarantees every change lands together, so the UI is always internally consistent. The cost is that commit blocks the browser, so it must be kept short — which is why the heavy work lives in the interruptible render phase instead.

---

### 🔬 Inside Commit — The Three Sub-Phases & Where Effects Fire

#### 🧩 What is it?
The commit phase isn't one undivided step — it runs in **three ordered sub-phases**: **before-mutation**, **mutation**, and **layout**. Each does a specific job, and they decide exactly when `useLayoutEffect` runs and when refs get attached. Separately, `useEffect` (the "passive" effect) is flushed **asynchronously after the browser paints**.

#### 🤔 Why do we need it? (the problem)
Some work must happen at very precise moments. A `ref` to a DOM node is useless until that node actually exists; measuring an element's size must happen **after** it's in the DOM but **before** the user sees it, or you'll get a visible flicker. Splitting commit into sub-phases gives React (and you, via `useLayoutEffect`) those exact, well-defined slots.

#### ⚙️ How does it work?
Here's the full timeline from render through paint and beyond:

```
  RENDER PHASE                 (interruptible, pure, no DOM)
     │  build workInProgress tree, compute edits
     ▼
  ========== COMMIT PHASE ==========  (synchronous)
     │
     │ 1) BEFORE-MUTATION
     │      read DOM before it changes
     │      (e.g. getSnapshotBeforeUpdate)
     │
     │ 2) MUTATION
     │      write changes to the DOM
     │      (detach old refs)
     │
     │ 3) LAYOUT
     │      run previous useLayoutEffect CLEANUP,
     │      attach refs, run useLayoutEffect (sync)
     │
  =================================
     ▼
  BROWSER PAINT  (user finally sees the new screen)
     ▼
  PASSIVE EFFECTS  (async, after paint)
        run useEffect cleanup, then useEffect
```

Key facts to lock in:
- **Mutation sub-phase** = the actual DOM writes (and old refs are detached).
- **Layout sub-phase** = the previous render's `useLayoutEffect` **cleanup** runs, then **refs are attached**, then your **`useLayoutEffect` callbacks run synchronously** — all *before* the browser paints. So a `useLayoutEffect` can measure/adjust the DOM with no visible flicker.
- **`useEffect`** is flushed **asynchronously, after the paint**. The user already sees the screen by the time it runs — perfect for non-visual work like fetching or logging.

> **Note (simplification):** "before-mutation" mostly serves the legacy `getSnapshotBeforeUpdate` lifecycle and internal bookkeeping; as a hooks-only developer you'll rarely touch it. The distinction you must know is **layout (sync, before paint)** vs **passive (async, after paint)**.

#### 🌍 Real-life analogy
Picture a shop window display being changed overnight. **Before-mutation**: the dresser notes how the old display looked. **Mutation**: they swap mannequins and clothes (and clear away the old props — the cleanup). **Layout**: they step back *behind the closed blinds* to straighten every collar and pin the labels (refs + `useLayoutEffect`) — all before opening. **Paint**: the blinds go up and shoppers see it. **Passive effects (`useEffect`)**: only *after* the shop is open does someone phone head office to report the change — non-urgent, done last.

#### 💻 Code example
```jsx
import { useEffect, useLayoutEffect, useRef, useState } from "react";

function Tooltip({ text }) {
  const ref = useRef(null);
  const [height, setHeight] = useState(0);

  // ✅ useLayoutEffect: LAYOUT sub-phase — DOM exists, ref is attached,
  // runs BEFORE paint, so measuring + adjusting causes no flicker.
  useLayoutEffect(() => {
    setHeight(ref.current.offsetHeight); // measure synchronously pre-paint
  }, [text]);

  // useEffect: AFTER paint — fine for non-visual work; if you measured
  // and repositioned here instead, the user could see a 1-frame jump.
  useEffect(() => {
    console.log("reported tooltip shown"); // async, post-paint
  }, [text]);

  return <div ref={ref} style={{ marginTop: -height }}>{text}</div>;
}
```

#### 🎤 Interview question
**Q: What are the commit sub-phases, and when do `useLayoutEffect` and `useEffect` each run?**
A: Commit runs in three sub-phases — **before-mutation** (read the DOM pre-change), **mutation** (write DOM changes and run the previous `useLayoutEffect` cleanup), and **layout** (attach refs, run `useLayoutEffect` callbacks **synchronously, before paint**). `useEffect` is different: it's a **passive** effect flushed **asynchronously after the browser paints**. So `useLayoutEffect` is for reading/adjusting layout without flicker; `useEffect` is for non-visual work like data fetching or logging.

<h2 id="module-5">Module 5 — Hooks Internals</h2>

You call `useState` and React magically remembers your value across renders — but a component is just a plain function that runs top to bottom every time, with no memory of last run. So *where* does that state live, and how does React know that *this* `useState` call is the same one as last render? The answer is delightfully low-tech: React keeps a list of hook "slots" on the fiber and matches them up purely by **the order you call them**. Once you see that, every Rule of Hooks stops being a rule you memorize and becomes the only thing that could possibly work.

---

### 🔗 The Hook List — How React Remembers Your State

#### 🧩 What is it?
Every component has a **fiber** — React's internal record of that component instance (its type, props, state, and pointers; see Module 3). Hanging off that fiber is a **linked list of hooks**: one node per hook you call, stored in the exact order you called them. The first `useState` is node 1, the second hook (say a `useRef`) is node 2, and so on.

#### 🤔 Why do we need it? (the problem)
A component function has no memory. Run this twice and `count` is `0` both times — the function restarts from scratch every render:

```javascript
function Counter() {
  let count = 0;     // resets to 0 on EVERY call — useless for state
  return count;
}
```

React needs somewhere *outside* the function to stash state, and it needs a way to say "this `useState` call is the same one I saw last render, give it back its saved value." It can't use the variable name (`count`) — React never sees your variable names, it only sees that *a hook was called*. So it uses the one thing it can observe: **the order of the calls**.

#### ⚙️ How does it work?
On the fiber there's a pointer called `memoizedState` that points at the **first** hook node. Each node has a `next` pointer to the following hook. As your component runs, React walks this list one node per hook call:

```
  FIBER (the component's record)
  ┌────────────────────────────┐
  │ memoizedState  ●           │
  └────────────────┼───────────┘
                   ▼
   ┌─────────┐   ┌─────────┐   ┌─────────┐
   │ hook 1  │──▶│ hook 2  │──▶│ hook 3  │──▶ null
   │ useState│   │ useRef  │   │ useState│
   │ value=0 │   │ {cur:…} │   │ value=''│
   └─────────┘   └─────────┘   └─────────┘
        ▲             ▲             ▲
    1st call      2nd call      3rd call
```

The mechanism is just a cursor:

1. On the **first** render (mount), each hook call **creates** a new node and appends it to the list.
2. On **every later** render (update), React resets the cursor to the head and, for each hook call, returns **the next existing node** in the list — node 1 for the first call, node 2 for the second, etc.

So "which `useState` is which" is answered entirely by **position**. Hook number 3 always reads slot 3. React doesn't know it's named `count` — it knows it's the third hook called.

> **Note (simplification):** the real list is a singly-linked list of hook objects with `memoizedState`, `queue`, and `next` fields. The tiny engine below uses a plain array + an index cursor, which behaves identically for our purposes (position-based lookup) and is easier to read.

#### 🌍 Real-life analogy
Think of a **coat check** at a theatre. You don't hand over a coat with your *name* on it — you hand it over and get **ticket number 1, 2, 3** in the order you arrive. When you come back, you don't say "I'm Sarah"; you show ticket 3 and get coat 3. The hooks list is the coat rack, your call order is the ticket number, and React is the attendant who *only* trusts the numbers. If you ever skipped getting a ticket one day, every later number would point at the wrong coat — which is exactly the bug the Rules of Hooks prevent.

#### 💻 Code example
```javascript
// A peek at what React stores on the fiber for:
//   const [count, setCount] = useState(0);
//   const inputRef = useRef(null);
//   const [name, setName] = useState('');

fiber.memoizedState = {          // hook 1
  memoizedState: 0,              //   the state value
  queue: { /* pending updates */ },
  next: {                        // hook 2
    memoizedState: { current: null }, // the ref box
    next: {                      // hook 3
      memoizedState: '',
      queue: { /* … */ },
      next: null
    }
  }
};
// React walks .next once per hook call, in order. Position is identity.
```

#### 🎤 Interview question
**Q: How does React know which `useState` corresponds to which piece of state?**
A: By **call order**, not by name. Hooks are stored as a linked list on the component's fiber, one node per hook, appended in the order called on the first render. On every later render React walks that list from the head, handing back node 1 to the first hook call, node 2 to the second, and so on. React never sees your variable names — it only sees that the Nth hook was called, so the Nth slot is its identity.

---

### 🚧 The Rules of Hooks — Why Order Is Sacred

#### 🧩 What is it?
The **Rules of Hooks** are two constraints: (1) only call hooks at the **top level** of your component — never inside conditions, loops, or after an early `return`; and (2) only call hooks from React functions (components or custom hooks). Rule 1 is the one that falls straight out of the linked-list mechanism.

#### 🤔 Why do we need it? (the problem)
Because identity is *position*, the list of calls must be **identical on every render**. If render 1 calls 3 hooks and render 2 calls 2 hooks, the cursor gets out of sync and React reads the wrong slot — silently handing your `name` state to your `count` variable. Memorizing "don't put hooks in `if`s" is fine, but seeing *why* makes it impossible to forget.

#### ⚙️ How does it work?
Watch what a conditional hook does to the cursor. Say on render 1 the condition is true, then on render 2 it's false:

```
  RENDER 1 (cond = true)        RENDER 2 (cond = false)
  call useState  → slot 0  ✓    call useState  → slot 0  ✓
  call useState  → slot 1  ✓    (skipped!)     → slot 1  ✗
  (inside if)                   call useEffect → slot 1  ⚠
  call useEffect → slot 2  ✓       ^ reads the WRONG slot
```

On render 2 the skipped hook means `useEffect` now lands on slot 1 — the slot that belonged to the *second* `useState` last time. The cursor shifted by one and every subsequent hook reads stale, mismatched data. That's why a hook in an `if`, a loop with a varying count, or a hook placed after an early `return` is forbidden: any of them can change how many hooks run, desyncing the order.

```javascript
// ❌ BREAKS THE ORDER — do not do this
function Bad({ show }) {
  const [a, setA] = useState(0);
  if (show) {
    const [b, setB] = useState(0); // only sometimes called → shifts the cursor
  }
  useEffect(() => {});             // lands on a different slot per render
}

// ✅ CORRECT — hooks always run, branch INSIDE them
function Good({ show }) {
  const [a, setA] = useState(0);
  const [b, setB] = useState(0);   // always called
  useEffect(() => {
    if (show) { /* conditional logic goes here, not the hook call */ }
  });
}
```

#### 🌍 Real-life analogy
Back to the coat check, but now imagine a **fixed conveyor belt** of numbered hooks behind the counter. The attendant advances the belt exactly one notch per coat handed over. If one day you sometimes hand over a coat and sometimes don't, the belt advances a different number of notches than yesterday — and now everyone's tickets point at the wrong coats. The fix isn't "be careful"; it's "always hand over the same coats in the same order." Hooks at the top level guarantee the belt always advances the same way.

#### 💻 Code example
```javascript
// The linter `eslint-plugin-react-hooks` enforces this statically,
// but here's the runtime symptom in our tiny engine (see next topic):

// render 1: cond true  → useState, useState, useEffect  (3 hooks)
// render 2: cond false → useState,          useEffect  (2 hooks)
//   slot 1 was "b" last render; this render slot 1 is the effect's deps.
//   React 18+ also throws:
//   "Rendered fewer hooks than expected." — it counts hooks per render.
```

#### 🎤 Interview question
**Q: Why can't you call a hook inside an `if` statement?**
A: Because hooks are matched to their stored state by **call order**, not by name. React walks a fixed list of hook slots, one per call, in sequence. A conditional hook changes *how many* hooks run between renders, which shifts every later hook onto the wrong slot — so a `useState` could start reading another hook's state. React even detects the count mismatch and throws "Rendered fewer hooks than expected." Keeping hooks at the top level guarantees the same calls in the same order every render.

---

### 🔀 The Dispatcher — Mount vs. Update Modes

#### 🧩 What is it?
The **dispatcher** is the object React points to that holds the *current implementation* of every hook (`useState`, `useEffect`, etc.). React doesn't have one fixed `useState` — it has at least two: a **mount** version (used on the first render) and an **update** version (used on re-renders). Before rendering a component, React swaps in the right one.

#### 🤔 Why do we need it? (the problem)
The first render and later renders do genuinely different work. On mount, `useState` must **create** a brand-new hook node and append it to the list. On an update, `useState` must **find** the existing node and return its (possibly updated) value. Rather than put an `if (mounting)` check inside every hook, React swaps the entire set of hook implementations once per render. It's the same trick as the mode itself being the switch.

#### ⚙️ How does it work?
There's a shared pointer (internally `ReactCurrentDispatcher.current`). React sets it right before calling your component, and your `useState` import just forwards to whatever it currently points at:

```
  Before rendering a component, React picks a dispatcher:

  first render?  ── yes ──▶  HooksDispatcherOnMount
       │                     useState = mountState  (creates a slot)
       │
       └──── no ─────────▶  HooksDispatcherOnUpdate
                             useState = updateState (reads next slot)

  your code:  const [n] = useState(0)
                           │
                           ▼
              ReactCurrentDispatcher.current.useState(0)
              (forwards to mount OR update version)
```

A nice side effect: if you call a hook *outside* a render (e.g. at the top of a module), the dispatcher points at a stub that throws the classic "Invalid hook call" error — because there's no fiber to attach a slot to. The dispatcher is the gate that knows whether you're "inside a render" at all.

#### 🌍 Real-life analogy
Imagine a **reception desk** with two different staff handbooks. On a guest's **first** visit, the receptionist opens the "new guest" handbook: create a file, assign a locker. On **return** visits, they open the "returning guest" handbook: look up the existing file. Same desk, same word "check in," but the procedure swapped based on first-visit-or-not. React swaps the whole handbook (dispatcher) before each render so each hook word means the right procedure.

#### 💻 Code example
```javascript
// Conceptual shape of the swap (heavily simplified):
const Dispatcher = { current: null };

const MountDispatcher  = { useState: mountState,  useRef: mountRef  };
const UpdateDispatcher = { useState: updateState, useRef: updateRef };

function renderComponent(fiber, Component) {
  Dispatcher.current =
    fiber.alreadyMounted ? UpdateDispatcher : MountDispatcher;
  const output = Component(fiber.props); // hooks now use the right impl
  fiber.alreadyMounted = true;
  return output;
}

// The public useState you import is just a forwarder:
function useState(initial) {
  return Dispatcher.current.useState(initial); // mount or update
}
```

#### 🎤 Interview question
**Q: How does React run different logic for `useState` on the first render vs. later renders without branching inside the hook?**
A: It uses a **dispatcher** — a pointer to an object of hook implementations that React swaps before each render: a mount dispatcher (whose `useState` *creates* a hook slot) on the first render, and an update dispatcher (whose `useState` *reads* the next existing slot) on re-renders. The `useState` you import just forwards to whatever the dispatcher currently points at. It's also why calling a hook outside a render throws — the dispatcher then points at a stub that errors.

### 🎛️ useState & useReducer — The Update Queue

#### 🧩 What is it?
Under the hood `useState` behaves like `useReducer` with a built-in reducer. Each state hook node stores two things: the current **state value** and an **update queue** — a list of pending changes. The function you get back (`setCount`, the *dispatch*) doesn't change state on the spot; it **enqueues** an update and **schedules** a re-render.

#### 🤔 Why do we need it? (the problem)
Calling `setCount(5)` can't mutate `count` immediately — `count` is a `const` captured by this render's closure, and React wants to batch several updates into one re-render (Module 6). So `setCount` records "please apply this update" in a queue tied to that hook's slot, then asks React to render again. On the next render, React drains the queue to compute the new value.

#### ⚙️ How does it work?
Each state hook node carries a `queue`. The dispatch function is bound to *that specific node's* queue, so it always finds the right slot:

```
  setCount(c => c + 1)         ┌─ hook node (slot for count) ─┐
        │  enqueue update      │ memoizedState: 0   (current) │
        └────────────────────▶ │ queue: [ +1 ] ──── pending   │
                               └──────────────────────────────┘
                                        │ schedule re-render
                                        ▼
  next render: drain queue → newState = reduce(0, [+1]) = 1
               store 1 in memoizedState, hand it back
```

Steps:
1. `setX(update)` pushes `update` onto the node's `queue` and calls React's scheduler to re-render.
2. On the next render, `updateState` walks the queue, applying each update to the previous value (for a value `setX(5)` the "reducer" just returns `5`; for a function `setX(c => c+1)` it calls your function). This is exactly why three `setCount(c => c+1)` in a row add three — each is a separate queued update.
3. The final value is saved in `memoizedState` and returned. `useReducer` is the same machinery but *you* supply the reducer.

#### 🌍 Real-life analogy
The dispatch function is a **suggestion box**, not a control panel. When you drop a note in ("increase by 1"), nothing changes that instant. At the next scheduled meeting (the re-render), the manager opens the box and applies every note **in order** to arrive at the new number. Drop three "increase by 1" notes and you get +3 — because each was a separate note in the queue, not an overwrite.

#### 💻 Code example
```javascript
// useState built on useReducer, conceptually:
function basicStateReducer(state, action) {
  // action is either a value (setX(5)) or a function (setX(c => c + 1))
  return typeof action === 'function' ? action(state) : action;
}

// useState(initial) ≈ useReducer(basicStateReducer, initial)
// so: setCount(5)        → queue.push(5)        → reducer returns 5
//     setCount(c=>c+1)   → queue.push(c=>c+1)   → reducer returns prev+1

// Three updater calls in one event:
setCount(c => c + 1); // queue: [f]
setCount(c => c + 1); // queue: [f, f]
setCount(c => c + 1); // queue: [f, f, f]
// next render drains: 0 → 1 → 2 → 3   (adds 3, not 1)
```

#### 🎤 Interview question
**Q: What does `setState` actually do when you call it?**
A: It doesn't change state synchronously. The dispatch function is bound to its hook's **update queue**: it pushes the update (a value or an updater function) onto that queue and schedules a re-render. On the next render React drains the queue, applying each update in order via the state reducer (for `useState`, a built-in reducer that returns the value, or calls your updater), saves the result in the hook's `memoizedState`, and returns it. `useState` *behaves like* `useReducer` with that built-in reducer (internally they're separate but closely related).

### 📦 useRef — The Stable Mutable Box

#### 🧩 What is it?
`useRef(initial)` returns a stable object shaped `{ current: initial }`. It's a **box** that survives every render (React stores it in the hook slot and hands back the *same* object each time), and writing to `.current` does **not** trigger a re-render.

#### 🤔 Why do we need it? (the problem)
Sometimes you need to remember a value across renders that *isn't* UI state — a DOM node, a timer id, the previous value of a prop, a "has this run yet?" flag. A plain variable resets every render. State (`useState`) would work but re-renders on every change, which is wasteful and sometimes wrong (you'd loop). `useRef` fills the gap: persistent like state, but silent — change it freely without scheduling a render.

#### ⚙️ How does it work?
On mount, `useRef` creates `{ current: initial }`, stores it in the hook node's `memoizedState`, and returns it. On every later render it ignores the argument and returns the **same** stored object. Because it's the same object, mutating `.current` is just a normal property write — React isn't watching it, so nothing schedules a render:

```
  render 1 (mount): create box ───▶ ┌──────────────┐
                                     │ { current: 0 }│  stored in slot
                                     └──────────────┘
  render 2,3,…    : return SAME box ─────────▲
                                             │
  ref.current = 99   ← plain write, React doesn't notice → NO re-render
```

Contrast with `useState`, whose setter routes through the update queue and the scheduler. `useRef`'s box has no queue and no dispatch — it's deliberately invisible to the render system.

#### 🌍 Real-life analogy
A ref is a **whiteboard bolted to the wall** of the component. You can wipe it and rewrite it as many times as you like, and it keeps whatever you last wrote even after you leave and come back (across renders). But scribbling on the whiteboard doesn't ring a bell to summon anyone — nobody re-renders just because the board changed. State, by contrast, is a board wired to an alarm: change it and the alarm calls everyone back in.

#### 💻 Code example
```javascript
function Timer() {
  const intervalId = useRef(null);   // same box every render
  const [seconds, setSeconds] = useState(0);

  function start() {
    // mutating .current persists, but causes NO re-render:
    intervalId.current = setInterval(() => {
      setSeconds(s => s + 1);        // THIS re-renders (it's state)
    }, 1000);
  }
  function stop() {
    clearInterval(intervalId.current); // reads the persisted id
  }
  // intervalId.current survives every re-render triggered by setSeconds,
  // yet writing it never triggered one itself.
  return null;
}
```

#### 🎤 Interview question
**Q: Why doesn't mutating a ref cause a re-render, and when would you use one over state?**
A: `useRef` returns the **same** `{ current }` object every render and stores it in its hook slot — but unlike `useState`, it has no update queue and no dispatch wired to the scheduler. Writing `ref.current = x` is a plain property assignment React isn't observing, so nothing schedules a render. Use a ref when you need a value that *persists* across renders but shouldn't drive the UI: DOM nodes, timer/interval ids, the previous value of something, or a one-time-init flag. Use state when the value *should* be reflected on screen.

### 🛠️ Implement From Scratch — A Tiny useState Engine

#### 🧩 What is it?
A self-contained, runnable model of the hooks engine: an **array of slots** plus a **cursor** that resets to `0` before each render. It reproduces the real behavior that matters — position-based identity, persistence across renders, and the "conditional hooks break it" failure — in about 30 lines you can run in any JS file.

#### 🤔 Why do we need it? (the problem)
The single best way to *prove* you understand hooks is to rebuild the core. Once you've written the array-and-cursor version, the linked list, the dispatcher swap, and the Rules of Hooks all click — they're the production-grade version of this same idea. This is the classic "implement a minimal `useState`" interview exercise.

#### ⚙️ How does it work?
We keep one module-level array `hooks` (the slots) and an index `cursor`. `render` resets `cursor` to `0`, then calls the component; each `useState` call grabs slot `cursor`, then advances the cursor. Because the cursor resets each render and the calls happen in the same order, slot N always belongs to the Nth hook — exactly like React.

```
  hooks = [ 0 , 'hi' ]      ← persistent slots (survive renders)
  cursor →  ^               ← resets to 0 each render, ++ per hook
  call 1 (useState) reads slot 0, then cursor → 1
  call 2 (useState) reads slot 1, then cursor → 2
```

#### 💻 Code example
```javascript
// ---- a tiny hooks engine: array of slots + a cursor ----
let hooks = [];     // persistent state slots (like the fiber's hook list)
let cursor = 0;     // which slot we're on THIS render
let scheduleRender; // set below; re-runs the component

function useState(initial) {
  const i = cursor;                       // capture THIS hook's slot index
  if (hooks[i] === undefined) hooks[i] = initial; // first render: seed it

  const setState = (next) => {
    // support updater functions, just like real useState:
    hooks[i] = typeof next === 'function' ? next(hooks[i]) : next;
    scheduleRender();                      // enqueue + re-render
  };

  cursor++;                               // advance for the next hook
  return [hooks[i], setState];
}

// ---- a component that uses it ----
function Component() {
  const [count, setCount] = useState(0);
  const [name, setName]   = useState('Ada');
  console.log(`count=${count}, name=${name}`);
  return { setCount, setName };
}

// ---- the "React" that renders it ----
let api;
scheduleRender = function render() {
  cursor = 0;                 // CRITICAL: reset cursor before each render
  api = Component();          // call order maps 1:1 to slots 0,1,…
};

render();                     // count=0, name=Ada      (mount: seeds slots)
api.setCount(5);              // count=5, name=Ada       (slot 0 updated)
api.setCount(c => c + 1);     // count=6, name=Ada       (updater form)
api.setName('Grace');         // count=6, name=Grace     (slot 1 updated)
```

> **Note (simplifications, flagged):** (1) real React stores hooks as a *linked list* on the per-component fiber, not one shared module array — so many components can each have their own list; ours has a single global list, fine for one component. (2) Real dispatch *batches* updates into a queue and re-renders asynchronously via the scheduler; ours applies the update and re-renders immediately. (3) We didn't model the mount/update dispatcher swap — our single `useState` handles both via the `=== undefined` check. The **position-based identity** (the whole point) is faithfully reproduced.

You can also *see the Rules of Hooks break*: wrap the second `useState` in an `if` that's true on render 1 and false on render 2, and `cursor` desyncs — the effect/state after it reads the wrong slot, exactly as described earlier.

#### 🎤 Interview question
**Q: Implement a minimal `useState`.**
A: Keep a persistent array of slots and a cursor that resets to `0` at the start of each render. `useState` captures the current cursor index `i`, seeds `hooks[i]` on first call, and returns `[hooks[i], setState]` where `setState` writes `hooks[i]` (supporting updater functions) and triggers a re-render; then it increments the cursor so the next hook gets the next slot. Identity comes purely from **call order via the cursor** — which is also why hooks must be called in the same order every render. (Real React swaps an array for a linked list on the fiber and batches updates through a queue, but the array-and-cursor model captures the essence.)

<h2 id="module-6">Module 6 — State, Updates & Batching</h2>

Here's a bug that has confused every React developer at least once: you click a button that calls `setCount(count + 1)` three times in a row — and the number goes up by **one**, not three. Or you read `count` inside a `setTimeout` and it shows the *old* value. None of this is a glitch. It all falls out of one rule: **within a single render, your state is a frozen snapshot**. This module unpacks that rule, then explains how React groups updates (**batching**), what React 18 changed, and the **updater function** trick that fixes the "+1" surprise.

---

### 📸 State Is a Snapshot — Why `count` Shows the Old Value

#### 🧩 What is it?
When your component function runs (one **render**), every state variable is a plain `const` for that run — a fixed value, frozen for the whole render. The next render is a brand-new function call with a brand-new value. Each render's code closes over (remembers) **its own** snapshot.

#### 🤔 Why do we need it? (the problem)
Beginners imagine `count` as a live box that always holds the "current" number. So this looks like a bug:

```javascript
function Counter() {
  const [count, setCount] = useState(0);
  function handleClick() {
    setCount(count + 1);
    setTimeout(() => {
      alert(count); // shows 0, NOT 1 — surprising!
    }, 3000);
  }
}
```

You called `setCount(count + 1)`, so surely `count` is now `1`? No. The `count` inside this `handleClick` is the `const count = 0` captured by **this** render. `setCount` schedules a *future* render with a new value — it does not reach back and edit the `count` in the function that's already running.

#### ⚙️ How does it work?
Think of each render as a numbered photo of your UI. The code in render number 0 only ever sees the values from render 0:

```
 render 0:  const count = 0   ← every closure here sees 0
     │  click → setCount(count+1) schedules a new render
     ▼
 render 1:  const count = 1   ← a NEW function call, NEW const
     │
     ▼
 render 2:  const count = 2   ← and so on...
```

A `setTimeout` callback created during render 0 keeps pointing at render 0's `count` forever, even if it fires seconds later — because that's the variable it closed over (this is the JavaScript closure rule from Module 3, not a React rule).

> **Note (simplification):** "state is a `const`" is the mental model. React stores the value on the fiber's hook list (Module 5); each render reads it out into a local that behaves exactly like a constant for that render. The takeaway — a render never sees a value updated after it started — is literally true.

#### 🌍 Real-life analogy
A render is like a **printed restaurant receipt**. Once it prints, the total on that paper never changes. If the kitchen adds an item later, they print a **new** receipt — they don't sneak back and rewrite the old one in your hand. Reading `count` in a `setTimeout` is reading the old receipt you're still holding.

#### 💻 Code example
```javascript
function handleClick() {
  // Suppose count is 0 in this render.
  console.log(count);        // 0
  setCount(count + 1);       // schedules render with count = 1
  console.log(count);        // STILL 0 — count is frozen for this render
  setCount(count + 1);       // schedules render with count = 1 (again!)
  // After all handlers run, React re-renders ONCE with count = 1.
}
```

#### 🎤 Interview question
**Q: Why does reading state right after `setState` give the old value?**
A: Because a state variable is a snapshot — it's constant for the entire render it belongs to. `setState` schedules a future render with a new value; it doesn't mutate the current render's variable. The new value is only visible in the **next** render's function call. This is also why a stale value appears inside `setTimeout`/async callbacks: they closed over the old render's snapshot.

---

### 📦 Batching — Many `setState` Calls, One Re-render

#### 🧩 What is it?
**Batching** is React grouping several state updates that happen in the same event handler into **one** single re-render, instead of re-rendering once per `setState` call.

#### 🤔 Why do we need it? (the problem)
Without batching, this handler would re-render the component three separate times:

```javascript
function handleClick() {
  setCount(c => c + 1);
  setFlag(true);
  setName("Ada");
}
```

Three renders means three trips through reconcile + commit for what is really *one* logical change. That's wasted work and can cause flickering — the screen could paint a half-updated state in between. Batching makes the whole handler feel atomic: React waits until your handler finishes, then renders once with all the changes applied together.

#### ⚙️ How does it work?
Each `setState` doesn't render immediately — it pushes an update onto a **queue** on that hook. When the event handler returns, React drains the queue and renders one time:

```
 handleClick runs:
   setCount(...) ─┐
   setFlag(...)  ─┤──▶ [ update queue ]   (nothing rendered yet)
   setName(...)  ─┘
 handler returns
        │
        ▼
   React processes the queue  →  ONE re-render  →  ONE commit
```

#### 🌍 Real-life analogy
A waiter taking your table's order. They don't sprint to the kitchen after each person speaks — they collect everyone's choices, then walk to the kitchen **once**. Batching is React waiting for the whole "order" (the event handler) before making a single trip.

#### 💻 Code example
```javascript
function handleClick() {
  setCount(c => c + 1); // queued
  setFlag(true);        // queued
  setName("Ada");       // queued
  // component re-renders exactly ONCE after this function returns,
  // with all three updates applied — not three times.
}
```

#### 🎤 Interview question
**Q: If you call `setState` three times in one click handler, how many re-renders happen?**
A: One. React batches all the updates queued during a single event handler and flushes them in a single re-render. The updates are still all applied — batching changes the number of *renders*, not whether each update takes effect.

---

### 🌊 Automatic Batching in React 18 — Now Timeouts and Promises Too

#### 🧩 What is it?
**Automatic batching** is the React 18 change that extends batching to **every** update, including ones inside `setTimeout`, promises (`.then`/`await`), and native event handlers — not just React's own synthetic events.

#### 🤔 Why do we need it? (the problem)
In React 17, batching only happened inside React event handlers (`onClick`, `onChange`, etc.). The moment you stepped outside — into a `setTimeout`, a `fetch().then(...)`, or an `await` — batching stopped, and each `setState` triggered its own render:

```
 React 17:
   inside onClick        → batched      → 1 render
   inside setTimeout      → NOT batched  → 1 render per setState
   inside .then / await   → NOT batched  → 1 render per setState

 React 18 (automatic batching):
   inside onClick        → batched → 1 render
   inside setTimeout      → batched → 1 render
   inside .then / await   → batched → 1 render
```

This inconsistency was a footgun: the same two `setState` calls re-rendered once in a click but twice in a `setTimeout`. React 18 made it uniform — updates batch **everywhere** by default.

#### ⚙️ How does it work?
React 18 (when you mount via `createRoot`) batches based on a shared "is React currently flushing?" boundary rather than on which kind of callback you're in. If you genuinely need an update applied and the DOM re-rendered **before** the next line runs, opt out with **`flushSync`**, which forces a synchronous render right then.

#### 🌍 Real-life analogy
React 17's batching was a coupon that **only worked at the front register** (synthetic events). Walk to the self-checkout (a `setTimeout`) and the coupon stopped applying. React 18 made the coupon valid at **every** register in the store. `flushSync` is you saying "ring this one item up by itself, right now" — opting out of the grouping on purpose.

#### 💻 Code example
```javascript
import { flushSync } from "react-dom";

// React 18: both batched into ONE render, even inside a timeout.
setTimeout(() => {
  setCount(c => c + 1);
  setFlag(f => !f);   // ← one re-render total (in React 17: two)
}, 1000);

// Opt OUT of batching when you must read the updated DOM immediately:
function handleClick() {
  flushSync(() => {
    setCount(c => c + 1);   // forces a synchronous render here
  });
  // DOM is now updated; safe to measure it, scroll, etc.
  flushSync(() => {
    setFlag(f => !f);       // a second, separate synchronous render
  });
}
```

#### 🎤 Interview question
**Q: What changed about batching in React 18?**
A: **Automatic batching.** In React 17, multiple `setState` calls were only batched inside React's synthetic event handlers; inside `setTimeout`, promises, or native events each call caused its own re-render. React 18 (with `createRoot`) batches updates in *all* of those contexts by default, so behavior is consistent everywhere. You can opt out for a specific update with `flushSync` when you need the DOM updated synchronously.

### 🔁 Updater Functions — Why x3 Adds 1, but `c => c + 1` Adds 3

#### 🧩 What is it?
`setState` accepts two forms: a **value** — `setCount(count + 1)` — or an **updater function** — `setCount(c => c + 1)`. The updater receives the **latest queued** state and returns the next one. That difference is exactly why calling one form three times behaves differently from the other.

#### 🤔 Why do we need it? (the problem)
The classic puzzle. Both buttons look like "+3", but only one is:

```javascript
// Snapshot form — count is frozen at, say, 0 for this whole render:
setCount(count + 1);   // queues "set to 0 + 1 = 1"
setCount(count + 1);   // queues "set to 0 + 1 = 1"  (count is STILL 0)
setCount(count + 1);   // queues "set to 0 + 1 = 1"
// Final value: 1   (all three read the SAME snapshot)
```

Because `count` is a snapshot (topic 1), every line reads `0`. Three identical "set to 1" updates land in the queue, so the result is `1`. The updater form fixes this:

```javascript
setCount(c => c + 1);  // queues "take latest, add 1"
setCount(c => c + 1);  // queues "take latest, add 1"
setCount(c => c + 1);  // queues "take latest, add 1"
// Final value: 3   (each runs on the result of the previous)
```

#### ⚙️ How does it work?
React keeps a queue of updates per hook. At render time it walks the queue, starting from the current state, applying each entry in order. A **value** update ignores what's already in the queue and just overwrites with that fixed number. An **updater function** receives the running result so far:

```
 start state = 0

 VALUE form: setCount(count+1) x3   (count snapshot = 0)
   queue: [ set→1 ] [ set→1 ] [ set→1 ]
   apply: 0 → 1 → 1 → 1                         result = 1

 UPDATER form: setCount(c => c+1) x3
   queue: [ c=>c+1 ] [ c=>c+1 ] [ c=>c+1 ]
   apply: 0 →(+1)→ 1 →(+1)→ 2 →(+1)→ 3          result = 3
```

Rule of thumb: when the **next** state depends on the **previous** state, use the updater form. It's the only form guaranteed to see every queued update.

#### 🌍 Real-life analogy
The value form is three people writing checks against your bank balance from a **statement they each photocopied this morning** — all three see "balance: 0" and each writes "deposit to make it 1", so you end at 1. The updater form is three people who each **ask the teller for the live balance** before depositing — so they stack: 0 → 1 → 2 → 3.

#### 💻 Code example
```javascript
function Counter() {
  const [count, setCount] = useState(0);

  function tripleValue() {
    setCount(count + 1);
    setCount(count + 1);
    setCount(count + 1);
    // count was a snapshot (e.g. 0); result is 1, not 3.
  }

  function tripleUpdater() {
    setCount(c => c + 1);
    setCount(c => c + 1);
    setCount(c => c + 1);
    // each updater gets the latest queued value; result is 3.
  }

  return null; // (buttons omitted for brevity)
}
```

#### 🎤 Interview question
**Q: Why does `setCount(count + 1)` called three times only add 1, while `setCount(c => c + 1)` adds 3?**
A: `count` is a snapshot — constant for that render — so all three value-form calls read the same number and queue the *same* result. All three are applied in order, but each just sets the state to the fixed value `1` (`0 → 1 → 1 → 1`), so it ends at +1. The updater form `c => c + 1` instead receives the latest **queued** value each time, so the three updates stack on each other: +3. Use the updater form whenever the next state depends on the previous.

---

### 🪞 Bailouts — When React Skips the Re-render

#### 🧩 What is it?
A **bailout** is React deciding *not* to re-render after a `setState` because the new value is the **same** as the current one. The comparison uses **`Object.is`** (essentially `===`, with two edge cases: `NaN` equals `NaN`, and `+0` is *not* equal to `-0`).

#### 🤔 Why do we need it? (the problem)
Updating state to the value it already holds is pure waste — the UI can't change. Without a bailout, code like `setStatus("idle")` while status is already `"idle"` would schedule a needless render. React short-circuits these so identical updates cost (almost) nothing:

```
 setStatus("idle"):
   Object.is(prev "idle", next "idle") === true
        │
        ▼
   React bails out → no re-render (the component is skipped)
```

#### ⚙️ How does it work?
After a `setState`, React compares the new value to the current one with `Object.is`. If they're equal, it bails out and skips rendering that component's subtree. The catch for objects: `Object.is` checks **reference identity**, not contents. A *new* object with identical fields is a *different* reference, so it does **not** bail out:

```javascript
const [user, setUser] = useState({ name: "Ada" });
setUser({ name: "Ada" });        // NEW object → different ref → RE-RENDERS
setUser(user);                   // same reference → bailout, no re-render
```

> **Note (simplification):** React may still call your component function once before fully bailing out (especially the first time), then discard the result if children are unchanged — it doesn't always skip 100% of the work. The reliable takeaway: setting state to an `Object.is`-equal value will not cause a *visible* re-render of your subtree.

#### 🌍 Real-life analogy
It's like asking a painter to repaint a wall the **exact same color** it already is. A sensible painter checks, sees it matches, and walks away — no work done. React's `Object.is` check is that glance at the wall before lifting the brush.

#### 💻 Code example
```javascript
const [n, setN] = useState(5);

setN(5);   // Object.is(5, 5) → true → bailout, NO re-render
setN(6);   // Object.is(5, 6) → false → re-renders

const [obj, setObj] = useState({ a: 1 });
setObj({ a: 1 });  // a brand-new object → different reference
                   // Object.is(old, new) → false → RE-RENDERS anyway
```

#### 🎤 Interview question
**Q: If you `setState` to the same value, does the component re-render?**
A: Usually not — React compares the new value to the current one with `Object.is` and bails out (skips the re-render) if they're equal. The gotcha is objects/arrays: a new object with the same contents is a different reference, so `Object.is` returns false and React *does* re-render. Bailout works on identity, not deep equality.

<h2 id="module-7">Module 7 — Effects & Their Timing</h2>

Your component returns some UI — but sometimes you need to do something *outside* that UI: fetch data, start a timer, listen to the window, log a page view. These are **side effects**, and React gives you two hooks to run them. The catch isn't *how* to write them — it's *when* they run. Get the timing wrong and you flicker, leak memory, or read a stale value. This module is about that timing.

---

### ⏳ `useEffect` — Run It After the Paint

#### 🧩 What is it?
`useEffect` is a React Hook (a special function you call inside a component) that runs a piece of code **after** React has updated the screen. You hand it a function; React remembers it and runs it once the browser has finished painting the new UI.

A **side effect** is any work that reaches *outside* rendering: fetching from a server, subscribing to something, setting a timer, or logging. Rendering itself should be pure (just compute UI) — effects are where the "impure" stuff lives.

#### 🤔 Why do we need it? (the problem)
A component's job is to turn data into UI and nothing else. But real apps must also talk to the outside world. If you did that work *during* render, you'd block the screen from showing and could fire the same request many times (React may render more than once before painting). `useEffect` gives you a safe, dedicated slot that runs **after** the UI is on screen — so the user sees the page first, and the side effect happens after.

#### ⚙️ How does it work?
React splits an update into a **render phase** (compute the new UI) and a **commit phase** (put it on the DOM — the page's live elements). `useEffect` callbacks are queued during commit and then run **asynchronously after the browser paints**:

```
  render → commit (DOM mutated) → browser PAINTS → useEffect runs
                                       ▲                 ▲
                                  user sees it      AFTER paint
                                                    (async)
```

Because it runs after paint, a slow effect does **not** delay what the user sees. That is exactly why `useEffect` is the right home for non-visual work: data fetching, subscriptions, logging, timers.

> **Note (simplification):** "after paint" is the model to hold. Precisely, React flushes passive effects asynchronously after the commit; in most cases that lands after the browser has painted the frame.

#### 🌍 Real-life analogy
Think of opening a restaurant for the day. First you **unlock the doors and let customers in and seated** (the paint — they can see and use the place). *Then* you go in back and **turn on the music and start the dishwasher** (the effect). You don't make hungry customers wait outside while you fiddle with the stereo — the room is usable first, the background chores happen after.

#### 💻 Code example
```javascript
import { useEffect, useState } from "react";

function Clock() {
  const [now, setNow] = useState(Date.now());

  useEffect(() => {
    // runs AFTER the first paint
    console.log("subscribing to the tick");
    const id = setInterval(() => setNow(Date.now()), 1000);

    // cleanup — runs before re-run AND on unmount (see below)
    return () => {
      console.log("unsubscribing");
      clearInterval(id);
    };
  }, []); // [] = run once on mount, never re-run

  return <span>{new Date(now).toLocaleTimeString()}</span>;
}
// Console on mount: "subscribing to the tick"
// Console on unmount: "unsubscribing"
```

#### 🎤 Interview question
**Q: When exactly does a `useEffect` callback run relative to the screen update?**
A: **Asynchronously, after** React commits the changes to the DOM and the **browser has painted** the new UI. The user sees the update first; the effect runs after. That is why it's safe for slow, non-visual work — it never blocks the paint.

---

### 📐 `useLayoutEffect` — Run It Before the Paint

#### 🧩 What is it?
`useLayoutEffect` is the sibling hook that runs your code **synchronously, after React mutates the DOM but before the browser paints**. Same shape as `useEffect` — a function, optional cleanup, a dependency array — but the timing is earlier and blocking.

#### 🤔 Why do we need it? (the problem)
Sometimes you must **measure** something the browser just laid out (an element's width, a scroll position) and then **adjust the DOM** based on that measurement — for example, position a tooltip so it doesn't run off-screen. If you did that in a normal `useEffect`, the user would briefly see the *wrong* position, then a flicker as it jumps to the right one (because `useEffect` runs after paint). `useLayoutEffect` runs *before* paint, so you can measure and fix things while the screen is still blank — the user only ever sees the corrected result.

#### ⚙️ How does it work?
Both hooks run in the commit phase, but at different moments around the paint:

```
  render → DOM mutated → useLayoutEffect → browser PAINTS → useEffect
                              ▲                  ▲              ▲
                         sync, BLOCKS        user sees      async,
                         the paint           final result   after paint
```

Because `useLayoutEffect` is **synchronous and blocks the paint**, overusing it is a performance trap: a slow layout effect delays everything the user sees. Rule of thumb: reach for `useEffect` first; only switch to `useLayoutEffect` when you actually see a visual flicker from measuring/mutating after paint.

#### 🌍 Real-life analogy
A theater stage. `useLayoutEffect` is the crew adjusting the set **while the curtain is still down** — the audience never sees the scramble, only the finished scene. `useEffect` is a stagehand walking on **after** the curtain is up — fine for handing an actor a prop, but the audience *will* notice if you rearrange the furniture now. Measuring-and-fixing belongs behind the curtain (before paint).

#### 💻 Code example
```javascript
import { useLayoutEffect, useRef, useState } from "react";

function Tooltip({ text }) {
  const ref = useRef(null);
  const [tooHigh, setTooHigh] = useState(false);

  useLayoutEffect(() => {
    // measure BEFORE paint, so the user never sees a wrong position
    const rect = ref.current.getBoundingClientRect();
    setTooHigh(rect.top < 0); // flip it before the browser paints
  }, [text]);

  return (
    <div ref={ref} style={{ top: tooHigh ? 0 : -40 }}>
      {text}
    </div>
  );
}
// No flicker: the corrected position is painted on the first frame.
```

#### 🎤 Interview question
**Q: `useEffect` vs `useLayoutEffect` — when do you use each?**
A: Default to `useEffect` — it runs **async after paint**, so it doesn't block what the user sees; perfect for fetching, subscriptions, logging. Use `useLayoutEffect` when you must **measure the DOM and mutate it before the user sees the result** (e.g. positioning) to avoid a visible flicker. It runs **sync before paint** and *blocks* the paint, so don't overuse it.

---

### 🎯 The Dependency Array & the Stale-Closure Trap

#### 🧩 What is it?
The **dependency array** is the second argument to `useEffect`/`useLayoutEffect` — the `[...]` listing the values the effect depends on. React uses it to decide whether to re-run the effect after a render. The **stale-closure trap** is the classic bug where an effect captures an *old* value because you left a dependency out.

#### 🤔 Why do we need it? (the problem)
Without a deps array, an effect would run after *every* render — wasteful, and often wrong (re-subscribing constantly). With deps, React only re-runs the effect when something the effect actually uses has changed. But this puts the burden on *you* to list everything the effect reads. Omit one, and the effect keeps running its *first* version, which still "remembers" the old value — a **stale closure**.

#### ⚙️ How does it work?
After each render, React compares each item in the new deps array to the previous one using **`Object.is`** (the same equality used for `===`, with tweaks for `NaN` and `-0`). If **any** dep changed, React runs cleanup for the old effect and then runs the new effect:

```
  render N+1
     │  compare deps with Object.is, item by item
     ▼
  ┌─────────────────────────────┐
  │ any dep changed?            │
  │   no  → skip effect         │
  │   yes → cleanup old, run new│
  └─────────────────────────────┘
  []          → run once (deps never change)
  no array    → run every render
  [a, b]      → run when a OR b changes
```

`Object.is` compares by **identity** for objects — a new array/object literal each render counts as "changed" even if it looks the same. That is a common reason effects re-run more than expected.

#### 🌍 Real-life analogy
The deps array is a **photograph you took when the effect was created**. The effect always reads from *that photo*, not from the live scene. If you forgot to list `count`, the effect keeps looking at an old snapshot where `count` was `0` — it has no idea the real value moved on. Listing `count` as a dependency tells React: "retake the photo whenever `count` changes."

#### 💻 Code example
```javascript
import { useEffect, useState } from "react";

// 🐞 STALE-CLOSURE BUG
function BuggyCounter() {
  const [count, setCount] = useState(0);

  useEffect(() => {
    const id = setInterval(() => {
      // `count` is frozen at 0 — this effect ran once and
      // closed over the FIRST count. It logs 0 forever.
      console.log("count is", count); // always "count is 0" ❌
    }, 1000);
    return () => clearInterval(id);
  }, []); // ❌ missing `count` in deps

  return <button onClick={() => setCount(count + 1)}>{count}</button>;
}

// ✅ FIX A — list the dependency (effect re-subscribes on change)
useEffect(() => {
  const id = setInterval(() => console.log("count is", count), 1000);
  return () => clearInterval(id);
}, [count]); // re-runs when count changes → always fresh

// ✅ FIX B — updater form needs no dependency on the value
setCount((c) => c + 1); // reads the latest count from React, not the closure
```

#### 🎤 Interview question
**Q: Explain the stale-closure bug and how to fix it.**
A: An effect (or callback) **captures the values from the render it was created in**. If a value it reads isn't in the deps array, the effect never re-runs, so it keeps using that *old* captured value — a stale closure. Fix it by **adding the value to the deps array** (so the effect re-creates with the fresh value), or by **not depending on it at all** — e.g. use the updater form `setCount(c => c + 1)`, which reads the latest state from React instead of the closure.

---

### 🧹 Cleanup, StrictMode & Idempotency

#### 🧩 What is it?
**Cleanup** is the function you `return` from an effect. React runs it to undo what the effect set up — unsubscribe, clear a timer, abort a fetch. **StrictMode** is a development-only wrapper that deliberately runs your effects an extra time to expose effects that forgot to clean up.

#### 🤔 Why do we need it? (the problem)
An effect that *adds* a subscription, timer, or listener but never *removes* it leaks: the old one keeps running after the component is gone (or after the effect re-runs), piling up duplicates and holding memory. Cleanup is how an effect tidies after itself. StrictMode's double-run is React's way of *forcing* the bug into the open during development, before it reaches users.

#### ⚙️ How does it work?
The cleanup runs at **two** moments: **before the effect re-runs** (to tear down the previous setup) and **on unmount** (when the component leaves the screen):

```
  mount        → run effect (setup #1)
  deps change  → run CLEANUP of #1 → run effect (setup #2)
  unmount      → run CLEANUP of the last effect
```

In development, **StrictMode double-invokes** each effect — it mounts, immediately runs cleanup, then mounts again:

```
  StrictMode (DEV ONLY):
    mount → effect → cleanup → effect
                     ▲ surfaces a missing/broken cleanup
```

If your effect is **idempotent** (running it twice leaves the same state as running it once — because cleanup undoes setup), this is invisible. If it isn't (e.g. you push to an array with no cleanup), you'll see doubled work — which is the bug StrictMode wants you to find. This double-invoke happens **only in development, never in production**.

> **Note:** StrictMode's extra run is a development check, not real behavior. Don't "fix" it by removing StrictMode — fix the missing cleanup.

#### 🌍 Real-life analogy
Cleanup is **checking out of a hotel room**: before the next guest (next effect) arrives, housekeeping resets the room; when the hotel closes (unmount), they clear it for good. StrictMode is the **manager doing a surprise check-in/check-out drill** during training (dev) — if housekeeping forgot to reset the room, the drill reveals it immediately. The manager never runs the drill once real guests are staying (production).

#### 💻 Code example
```javascript
import { useEffect, useState } from "react";

function ChatRoom({ roomId }) {
  const [status, setStatus] = useState("connecting");

  useEffect(() => {
    const conn = createConnection(roomId);
    conn.on("open", () => setStatus("online"));
    conn.connect();                  // SETUP: subscribe

    return () => conn.disconnect();  // CLEANUP: unsubscribe
  }, [roomId]); // re-runs when roomId changes

  // Timeline if roomId goes "general" -> "random":
  //   connect("general")
  //   disconnect("general")   <- cleanup before re-run
  //   connect("random")
  // On unmount: disconnect("random")
  //
  // In StrictMode (dev): connect -> disconnect -> connect
  //   With the cleanup above, this is harmless (idempotent).
  //   Without it, you'd leak a "general" connection. ❌

  return <span>{status}</span>;
}
```

#### 🎤 Interview question
**Q: Why does my effect run twice in dev, and what's the cleanup contract?**
A: In development, **StrictMode intentionally double-invokes** effects (mount → unmount → mount) to surface effects that don't clean up or aren't idempotent. It happens **only in dev, not in production**. The cleanup function — the one you `return` — runs **before each re-run** of the effect and **on unmount**. Write effects so setup + cleanup pair up cleanly, and the double-invoke is harmless.

<h2 id="module-8">Module 8 — Concurrent Rendering</h2>

For years, when React started turning your components into UI, it ran *all the way to the end* without stopping — even if that took long enough to freeze a button click or stutter an animation. Concurrent rendering changes the deepest rule of all: React can now **pause** mid-render, let the browser breathe, and **resume** later. This module is about what that buys you, what it costs, and why it's something you turn on rather than something that just happens.

---

### 🛑 The Big Shift — Render Becomes Interruptible

#### 🧩 What is it?
"Rendering" is the work React does to figure out what your UI should look like — it calls your components, builds a tree of elements, and compares it to the last one. In the old days this work was **synchronous and uninterruptible**: once React started, it ran to completion before the browser could do anything else. Concurrent rendering makes that render phase **interruptible** — React can do a bit of work, pause to let the browser handle a click or paint a frame, then pick up where it left off.

#### 🤔 Why do we need it? (the problem)
The browser's main thread does one thing at a time. If React spends 200 milliseconds rendering a big list, then for those 200ms the page is **frozen** — clicks don't register, typing lags, animations jank. The user feels the app is "stuck". With an uninterruptible renderer there's no escape: React grabbed the thread and won't give it back until it's done.

#### ⚙️ How does it work?
React splits its work into two phases. The **render phase** (calling components, diffing) is the part that became interruptible. The **commit phase** (actually mutating the real page) stays synchronous and is never paused — so the screen never shows a half-applied update.

```
  LEGACY (blocking, synchronous):
  start ───────────────────────▶ done
  [████████ render runs to end ████████]
  browser is FROZEN this whole time

  CONCURRENT (interruptible, sliced):
  [██ render ██] pause [██ render ██] pause [██ commit]
        │              │
        ▼              ▼
   browser handles  browser paints
   a click here     a frame here
```
Because the work can pause, React can also **throw it away**: if a more urgent update arrives mid-render, React abandons the in-progress work and restarts with the newer, higher-priority state. Nothing half-finished ever reaches the screen.

#### 🌍 Real-life analogy
Old React is a chef who, once he starts a 20-minute dish, **ignores the doorbell, the phone, and everything else** until the plate is done. Concurrent React is a chef who stirs for a few seconds, glances up to answer the door if someone rings, then goes back to stirring. The dish still gets made — but the kitchen stays responsive to anything urgent.

#### 💻 Concrete illustration
```jsx
// You opt into the concurrent renderer with createRoot.
import { createRoot } from 'react-dom/client';

const root = createRoot(document.getElementById('root'));
root.render(<App />);

// Legacy mode used ReactDOM.render(<App/>, container) instead,
// which had NO interruptible rendering at all.
// (createRoot turns ON the concurrent renderer — but see the
//  "opt-in" topic: it does not make every update concurrent.)
```

#### 🎤 Interview question
**Q: What is concurrent rendering and what problem does it solve?**
A: It makes React's **render phase interruptible**: React can render part of the tree, pause to let the browser respond to input or paint, then resume — or discard the work if a higher-priority update arrives. It solves the "frozen UI" problem where a long synchronous render blocked the main thread and made clicks, typing, and animations feel stuck. The commit phase stays synchronous, so users never see a half-rendered screen.

---

### ⏱️ Time-Slicing — Rendering Across Frames

#### 🧩 What is it?
**Time-slicing** is the technique that makes interruptibility useful: instead of doing all the render work in one long block, React does it in small **slices**, handing control back to the browser between slices. A "slice" is just a chunk of rendering small enough to fit comfortably inside one frame.

#### 🤔 Why do we need it? (the problem)
Screens repaint about **60 times a second**, which gives the browser roughly **16 milliseconds per frame** to do everything — run JavaScript, handle input, and paint. If React hogs the thread for 100ms straight, it blows through about six frame deadlines in a row, and the user sees a visible freeze. Slicing the work into sub-16ms chunks lets the browser slip a frame (or an input handler) in between.

#### ⚙️ How does it work?
React renders a slice, then checks: *"have I used up my time budget for this frame?"* If yes, it **yields** — pauses and lets the browser run. The browser paints / handles events, then calls React back to do the next slice. React keeps a pointer to where it stopped, so it resumes instead of restarting.

```
  16ms frame   16ms frame   16ms frame
  ┌─────────┐  ┌─────────┐  ┌─────────┐
  │ slice 1 │  │ slice 2 │  │ slice 3 │  React render
  │ yield ▶ │  │ yield ▶ │  │ commit  │
  └────┬────┘  └────┬────┘  └─────────┘
       ▼            ▼
    paint +      paint +       main thread
    input        input         never blocks
```
This cooperation with the browser is run by React's **scheduler** (covered in Module 9). The key idea here: render work is spread across frames so the main thread stays free.

#### 🌍 Real-life analogy
Imagine mowing a huge lawn, but you've promised to wave at every car that drives past. Instead of mowing nonstop (and missing every car), you mow one strip, look up to wave if a car's coming, then mow the next strip. The lawn still gets fully mowed — you just **interleave** it with staying responsive to the road.

#### 💻 Concrete illustration
```jsx
// Conceptual: React does NOT expose slicing as an API you call.
// You enable behavior that lets React slice; the scheduler does the rest.
//
//  one giant render:   [████████████████]  16ms+  -> frame drop
//  time-sliced render: [██] [██] [██] [██]        -> frames stay smooth
//
// You never write the slicing. You opt into a concurrent feature
// (next topic) and React decides where it's safe to yield.
```

#### 🎤 Interview question
**Q: What is time-slicing and how does it keep the UI responsive?**
A: Time-slicing breaks rendering into small chunks and yields control back to the browser between them, instead of rendering everything in one blocking pass. Because each chunk fits inside a frame's ~16ms budget, the browser can paint and handle input in the gaps, so animations and typing stay smooth even during a heavy render. You don't slice manually — React's scheduler decides when to pause and resume.

---

### 🔌 Concurrency Is Opt-In — Not "Everything Is Async"

#### 🧩 What is it?
A common myth: "React 18 made rendering concurrent, so everything is now async and interruptible." Not true. `createRoot` switches on the concurrent **renderer**, but an individual update only renders **concurrently** when you mark it with a **concurrent feature**: a transition (`startTransition` / `useTransition`), `useDeferredValue`, or Suspense. Plain state updates still render in a synchronous, urgent pass.

#### 🤔 Why do we need it? (the problem)
If React quietly made *every* update interruptible, it could pause and delay things that should feel instant — like a checkbox toggling or text appearing as you type. Some updates are **urgent** (must happen now) and some are **non-urgent** (can wait a beat). React can't read your mind about which is which, so it makes you **tell it**: wrap the update you're willing to interrupt, and leave the urgent ones alone.

#### ⚙️ How does it work?
You label an update as non-urgent; React renders it at a lower priority where it's allowed to pause, yield, and be thrown away if something urgent shows up.

```
  createRoot enables the concurrent renderer
              │
              ▼
  ┌───────────────────────────────────────┐
  │ plain setState      -> URGENT          │
  │                        (sync-ish, not  │
  │                         interrupted)   │
  │                                        │
  │ startTransition     -> NON-URGENT      │
  │ useDeferredValue       (can pause /    │
  │ Suspense               yield / restart)│
  └───────────────────────────────────────┘
  Concurrency switches ON only inside that
  bottom group. It is opt-in, per update.
```
> **Note (simplification):** I'm calling urgent updates "synchronous" for intuition. Under the concurrent renderer even urgent updates flow through React's scheduler, but they run at a high priority that isn't deliberately sliced or deferred — so they *behave* like the old blocking model.

#### 🌍 Real-life analogy
Think of a hospital with one doctor. Turning on the concurrent renderer is like hiring a **triage nurse**. The nurse doesn't slow anyone down by default — but when you mark a patient "non-urgent" (a transition), they can be asked to wait so a heart-attack case (an urgent click) jumps the queue. Without you marking priorities, everyone is just treated in order, like before.

#### 💻 Concrete illustration
```jsx
import { useState, useTransition } from 'react';

function Search({ allItems }) {
  const [query, setQuery] = useState('');
  const [results, setResults] = useState(allItems);
  const [isPending, startTransition] = useTransition();

  function onChange(e) {
    setQuery(e.target.value);          // URGENT: input stays snappy

    startTransition(() => {            // NON-URGENT: heavy filter render
      setResults(filterHeavy(allItems, e.target.value));
    });                                // React may pause / restart THIS
  }

  return (
    <>
      <input value={query} onChange={onChange} />
      {isPending ? <span>Updating…</span> : <List items={results} />}
    </>
  );
  // Without startTransition, the heavy filter render is urgent too —
  // every keystroke would block, and typing would lag.
}
```

#### 🎤 Interview question
**Q: Does React 18 make everything concurrent automatically?**
A: No. `createRoot` enables the concurrent renderer, but updates only render concurrently when you use a concurrent **feature** — transitions, `useDeferredValue`, or Suspense. Ordinary state updates stay urgent and render in a blocking-style pass. Concurrency is opt-in **per update**, because React needs you to tell it which work is interruptible and which must feel instant.

---

### ⚠️ Tearing — The New Consistency Hazard

#### 🧩 What is it?
**Tearing** is a visual inconsistency unique to concurrent rendering: because a render can be **paused**, an external data source can change *in the middle* of that render — so two parts of the same screen, rendered before and after the change, show **different values** for the same data. The UI is literally "torn" between two states.

#### 🤔 Why do we need to know it? (the problem)
In the old synchronous world this couldn't happen: React read your data and finished rendering in one uninterrupted shot, so every component saw the same value. Concurrent rendering breaks that guarantee for **external stores** — data that lives *outside* React (a global variable, a Redux-style store, a `window` value, a subscription). If React renders the top half, pauses, the store mutates, then React renders the bottom half, the two halves disagree.

#### ⚙️ How does it work?
```
  External store value = 5

  React renders top half  ── reads 5 ──▶  shows "5"
        │
        ▼  React PAUSES (concurrent)
  store changes: value = 9   ← happened mid-render
        │
        ▼  React resumes
  React renders bottom half ── reads 9 ──▶ shows "9"

  Result on screen:  top = 5,  bottom = 9   ❌ TORN
```
The fix is the hook **`useSyncExternalStore`**. It's the official, tearing-safe way to read an external store: React uses it to detect that the store changed mid-render and **re-renders consistently** so the whole tree agrees on one value. Note this hazard applies to **external** stores — React's own `useState` / `useReducer` are already managed by React and don't tear.

#### 🌍 Real-life analogy
Imagine photocopying a long report, but you take a coffee break halfway. While you're away, someone edits page 50 of the original. You come back and finish copying. Now your copy has the **old** first half and the **new** second half — a single document that contradicts itself. `useSyncExternalStore` is the rule "don't take a break mid-copy; if the original changed, start the copy over."

#### 💻 Concrete illustration
```jsx
import { useSyncExternalStore } from 'react';

// An external store living OUTSIDE React:
function useCount(store) {
  return useSyncExternalStore(
    store.subscribe,        // how React subscribes to changes
    store.getSnapshot,      // read the CURRENT value (consistently)
    store.getServerSnapshot // value to use during server render
  );
  // React guarantees every component reading this store in one
  // render sees the SAME value — no tearing, even if it pauses.
}
//
// Most app developers never call this directly — state libraries
// (Redux, Zustand, etc.) use it INTERNALLY so their stores are
// concurrent-safe for you.
```

#### 🎤 Interview question
**Q: What is tearing, and how does `useSyncExternalStore` prevent it?**
A: Tearing is when different parts of the UI display different values for the same data, because a concurrent render paused and an **external** store changed mid-render — so components rendered before and after the change disagree. `useSyncExternalStore` is React's tearing-safe way to subscribe to and read external stores: it lets React detect the mid-render change and re-render so the whole tree reads one consistent value. React's own `useState`/`useReducer` don't tear, so the hook is specifically for external stores (and is what libraries like Redux and Zustand use under the hood).

<h2 id="module-9">Module 9 — The Scheduler & Lanes</h2>

Module 8 said React can *pause* a render and let the browser breathe. But who decides *when* to pause, and *what* to work on next when three updates are waiting? That job belongs to two pieces of machinery beginners rarely see: a tiny **scheduler** that runs work in chunks and yields to the browser, and a **lanes** system that tags every pending update with a priority. Together they let typing stay instant while a heavy screen update waits its turn.

---

### ⏱️ The Cooperative Scheduler — render in chunks, then step aside

#### 🧩 What is it?
The **scheduler** is a small, separate package React ships (literally named `scheduler`) whose only job is to run work *a little at a time*. Instead of rendering your whole component tree in one long, blocking burst, React asks the scheduler to run render work in **chunks**, and between chunks it **yields** — hands control back to the browser so the page can respond to clicks, typing, and painting.

#### 🤔 Why do we need it? (the problem)
The browser's main thread does everything on one line: running your JavaScript, handling input, and painting pixels. If React renders a big tree in one go, that long task **hogs** the thread. While it runs, a click does nothing and the cursor freezes — the page feels janky. The scheduler fixes this by chopping the work up and **checking, frequently, "should I yield now?"** If the chunk has run long enough (a few milliseconds), React stops, lets the browser handle input and paint, then resumes the render right where it left off.

#### ⚙️ How does it work?
React does a bit of render work, then asks the scheduler `shouldYield()`. If yes, it pauses and re-schedules the rest for the next turn. Originally the scheduler drove this "come back soon" loop using a **`MessageChannel`** (a browser API that posts a message to yourself, scheduling a callback after the browser has had a chance to paint).

```
  main thread timeline (one chunk ≈ a few ms)
  ┌───────┐        ┌───────┐        ┌───────┐
  │render │ yield  │render │ yield  │render │  done
  │ part1 │ ─────▶ │ part2 │ ─────▶ │ part3 │ ─────▶ commit
  └───────┘   │    └───────┘   │    └───────┘
              ▼                ▼
         browser handles  browser handles
         input + paint    input + paint
```

> **Note (simplification):** "ask `shouldYield()`, pause, resume" is the mental model. The real scheduler manages a task queue, deadlines, and a host callback whose transport has evolved across React versions — the internals are intricate and change over time.

#### 🌍 Real-life analogy
Think of a **kitchen with one chef** (the main thread). Plating a giant banquet order all at once means walk-in customers wait at the counter, ignored. A good chef plates a few dishes, then **glances at the counter** to take any new orders or hand out ready food, then plates a few more. The render is the banquet; the glance at the counter is the yield.

#### 💻 Concrete illustration
```javascript
// A *mental sketch* of React's work loop — NOT the real source.
function workLoop() {
  while (workInProgress !== null && !shouldYield()) {
    workInProgress = performUnitOfWork(workInProgress); // render one fiber
  }
  if (workInProgress !== null) {
    scheduleCallback(workLoop); // not done — come back next chunk
  } else {
    commitRoot(); // tree finished — now touch the DOM (synchronously)
  }
}
// shouldYield() roughly: "have I been running longer than my time slice?"
```

#### 🎤 Interview question
**Q: What does it mean that React's scheduler is "cooperative"?**
A: React isn't forcibly interrupted by the OS — it **chooses** to stop. It runs a chunk of render work, voluntarily checks `shouldYield()`, and if it has used up its time slice it pauses and gives the browser a turn to handle input and paint, then resumes later. "Cooperative" means React cooperates with the browser by yielding on its own, rather than being preempted.

---

### 🚫 Why not `requestIdleCallback`? — React ships its own scheduler

#### 🧩 What is it?
`requestIdleCallback` (rIC) is a browser API that runs a callback when the main thread is **idle** — meaning the browser thinks it has spare time before the next frame. On paper that sounds exactly like what React wants. React deliberately **does not** rely on it and ships its own scheduler instead.

#### 🤔 Why do we need it? (the problem)
rIC has two problems for React. First, it fires **too infrequently and unpredictably** — if the browser is even mildly busy, idle callbacks can be delayed for a long time (sometimes hundreds of milliseconds), which would make React's rendering feel stalled. Second, rIC has **no concept of priority**: it can't say "this urgent update should jump ahead of that background one." React needs **fine-grained priorities** *and* **reliable, frequent yielding** that it controls precisely. So it built a scheduler that gives it both.

#### ⚙️ How does it work?
React's scheduler schedules its own callbacks (historically via `MessageChannel`, which fires more reliably and sooner than rIC), measures its own time budget, and layers a **priority system** on top. Each unit of work carries a priority level, and the scheduler runs the highest-priority work first while still yielding between chunks.

```
  requestIdleCallback              React's own scheduler
  ─────────────────────            ─────────────────────
  fires "when idle"        vs.     fires reliably + soon
  can be delayed a lot             tight, controlled budget
  NO priorities                    SEVERAL priority levels
  one-size-fits-all                urgent ▸ normal ▸ idle
```

> **Note (simplification):** browsers and the scheduler both evolve; the takeaway is *reliability + priorities*, not the exact transport API of any one version.

#### 🌍 Real-life analogy
`requestIdleCallback` is like telling a busy friend **"help me whenever you happen to be free"** — they might not get to it for hours, and they can't tell your urgent favor from a trivial one. React's scheduler is like hiring a **dedicated assistant** who works in steady short bursts *and* knows which tasks are urgent versus which can wait until quiet time.

#### 💻 Concrete illustration
```javascript
// rIC: no priority — you just get "spare time" whenever it shows up.
requestIdleCallback((deadline) => {
  while (deadline.timeRemaining() > 0 && work.length) doSomeWork();
});

// React's scheduler (conceptual): you ALSO pass a PRIORITY.
scheduleCallback(ImmediatePriority,  handleUrgentInput);
scheduleCallback(NormalPriority,     renderNormalUpdate);
scheduleCallback(IdlePriority,       prefetchOffscreenStuff);
// the scheduler runs urgent work first, yielding between chunks.
```

#### 🎤 Interview question
**Q: Why does React have its own scheduler instead of using `requestIdleCallback`?**
A: Because `requestIdleCallback` fires too infrequently and unpredictably, and it has **no priorities**. React needs to yield **reliably and often** (so renders don't stall) and to **prioritize** updates (urgent input over background work). Its own scheduler gives it precise control over the time budget plus several priority levels — neither of which rIC provides.

---

### 🛣️ The Lanes Model — priority as bits in a bitmask

#### 🧩 What is it?
A **lane** is React's label for the *priority* of a pending update. Internally each priority is a single **bit** in a 31-bit number (a **bitmask**). When you trigger an update, React tags it with a lane — for example a *sync/urgent input* lane, a *transition* lane (from `startTransition`), or an *idle* lane for the lowest-priority background work. Many pending updates' lanes can be combined into one bitmask, and React picks the **highest-priority** set of lanes to render next.

#### 🤔 Why do we need it? (the problem)
Multiple updates can be waiting at the same time: the user is typing (must feel instant) *and* a big filtered list is re-rendering (can lag a little). React needs a fast way to say "which of these waiting updates matters most right now?" Representing priorities as bits lets React answer that with cheap bitwise operations — checking, combining, and clearing many priorities at once is just a couple of CPU instructions, which keeps the scheduler itself fast.

#### ⚙️ How does it work?
Each lane is one bit. A set of pending lanes is a bitmask (bits turned on). React finds the highest-priority lanes still pending, renders *only* those, then commits — and updates in lower lanes wait for a later render pass.

```
  one update's lane = one bit set:

   bit:  31 .........  3   2   1   0
   ┌───┬───┬───┬───┬───┬───┬───┬───┐
   │idl│...│   │   │trn│   │snc│urg│   lanes (high→low priority)
   └───┴───┴───┴───┴───┴───┴───┴───┘
            urg = urgent input  (sync)
            trn = transition    (non-urgent)
            idl = idle          (lowest)

  pending bitmask = urgent | transition
   ┌─────────────────────────────────┐
   │ ...0 0 1 ... 0 0 1 ...           │  two bits on
   └─────────────────────────────────┘
   React renders the URGENT lane first, transition next.
```

> **Note (simplification):** real React has *many* lanes with specific names and subtle grouping rules, and the bit layout is an internal detail that changes between versions. The idea to keep is **priority = a bit; a set of priorities = a bitmask; highest wins**.

#### 🌍 Real-life analogy
A hospital **triage** board. Every arriving patient gets a colored tag: red (treat now), yellow (soon), green (can wait). The board lets staff scan everyone at a glance and always take the most urgent next. Lanes are React's triage tags; the bitmask is the whole triage board read in one look.

#### 💻 Code example
```javascript
// CONCEPTUAL lane bitmask — illustrative bits, not React's real values.
const NoLanes        = 0b0000;
const UrgentLane     = 0b0001; // e.g. typing / click  (sync)
const TransitionLane = 0b0010; // from startTransition  (non-urgent)
const IdleLane       = 0b1000; // background, lowest

// two updates pending at once → OR their lanes together:
let pending = UrgentLane | TransitionLane;       // 0b0011

// "is an urgent update waiting?"  → bitwise AND:
const urgentPending = (pending & UrgentLane) !== 0; // true

// pick highest priority = lowest set bit here (urgent),
// render it, then clear it from the pending mask:
pending = pending & ~UrgentLane;                 // 0b0010 (transition left)
```

#### 🎤 Interview question
**Q: What are lanes in React?**
A: Lanes are React's priority system for pending updates. Each priority is a single **bit** in a bitmask, so an update gets tagged with a lane (urgent input, transition, idle, etc.). Because priorities are bits, React can combine many pending updates into one bitmask and use fast bitwise checks to select the **highest-priority** lanes to render next, deferring lower ones.

---

### ⏳ Starvation Avoidance — old work eventually gets promoted

#### 🧩 What is it?
**Starvation** is when low-priority work *never* gets to run because higher-priority work keeps cutting in line. React avoids it: if a low-priority lane (like a transition) has waited **too long**, React **bumps it up** in priority so it finally renders. A background update can be delayed, but it won't be ignored forever.

#### 🤔 Why do we need it? (the problem)
Priorities create a danger. Imagine the user keeps typing — every keystroke is an *urgent* update. A transition (say, rendering a heavy search-results list) is lower priority, so it keeps getting preempted by the next keystroke. Without a safeguard, that list might **never** render as long as typing continues — it's *starved*. Users would see results that never update. React must guarantee that waiting work eventually completes.

#### ⚙️ How does it work?
When React first defers a lane, it records an **expiration time** for it. On each render pass React checks the pending lanes: any lane that has sat past its expiration is marked **expired** and treated as urgent (synchronous), so it can no longer be skipped. The longer low-priority work waits, the closer it gets to being forced through.

```
  transition lane waiting while urgent keeps preempting:

  t0  start ─ expiration set ──────────────▶ t_exp
      │                                        │
      ▼ (keystroke) ▼ (keystroke) ▼ (keystroke)│
      urgent wins   urgent wins   urgent wins  │
                                               ▼
                              EXPIRED → promoted to urgent,
                              forced to render now (no more skips)
```

> **Note (simplification):** the exact timeouts and promotion rules are internal and version-specific; the principle — *waited too long ⇒ priority is raised* — is the durable idea.

#### 🌍 Real-life analogy
Back to hospital **triage**: a green-tagged patient (minor injury) keeps getting bumped as ambulances bring in red-tag emergencies. A good triage system tracks how long the green patient has waited — and once that's too long, it **upgrades their priority** so they're finally seen. Nobody is left in the waiting room forever.

#### 💻 Concrete illustration
```javascript
// CONCEPTUAL starvation check — not React's real code.
function pickLanesToRender(pending, now) {
  // urgent always renders immediately:
  if (pending & UrgentLane) return UrgentLane;

  // has a deferred lane sat past its deadline?
  for (const lane of deferredLanes(pending)) {
    if (now >= expirationOf(lane)) {
      return lane; // EXPIRED → promote it; render now, don't skip again
    }
  }
  return lowestPriority(pending); // otherwise normal priority order
}
// Effect: a transition that waits too long stops being skippable.
```

#### 🎤 Interview question
**Q: With priorities, what stops a low-priority update from never rendering — and how does React prevent it?**
A: That hazard is **starvation** — urgent updates keep preempting a low-priority lane so it never completes. React prevents it by giving deferred lanes an **expiration time**. Once a lane has waited past its deadline, React marks it expired and promotes it to a synchronous, can't-be-skipped priority, so even a continuously-preempted transition is eventually forced to render.

<h2 id="module-10">Module 10 — Concurrent Features: Transitions & Deferred Values</h2>

You have a search box over a list of 10,000 items. You type "react" and the input freezes between keystrokes — your letters appear in bursts because React is busy re-filtering the giant list on every keypress. The work isn't optional, but its *priority* is: showing your letters matters **right now**; the filtered list can lag a few milliseconds behind. This module is about telling React exactly that — "this update is not urgent" — using **transitions** and **deferred values**.

---

### 🚦 `useTransition` / `startTransition` — Mark an Update as "Not Urgent"

#### 🧩 What is it?
`startTransition` lets you wrap a state update and label it a **transition** — React-speak for **"this update is non-urgent, render it at low priority."** `useTransition` is the hook version: it gives you that wrapper plus an `isPending` flag (a `true`/`false` telling you the transition is still rendering).

```javascript
const [isPending, startTransition] = useTransition();
```

The key idea: state updates inside `startTransition(...)` can be **interrupted** and **thrown away** if something more urgent (like another keystroke) comes in.

#### 🤔 Why do we need it? (the problem)
By default, **every** state update is urgent. When you type into an input that also filters a big list, React tries to do both in one go — update the text *and* re-render the whole list — before it lets the browser paint. The list render is slow, so your keystrokes stall behind it. The input feels laggy even though the typing itself is trivially fast.

We need a way to say: *"the text update is urgent; the list update can wait and yield to the browser."* That's a transition.

#### ⚙️ How does it work?
React keeps two state updates with different **priorities** (in Module 9's terms, different **lanes** — urgent updates go on a high-priority lane, transitions on a low-priority "transition lane"):

```
  You type "r"
      │
      ├─ setText("r")                URGENT  ──┐ renders first,
      │                              (high lane) │ paints immediately
      │                                          ▼
      └─ startTransition(() =>        NON-URGENT  ──┐ low-priority render,
           setQuery("r"))            (transition    │ can be PAUSED and
                                      lane)          ▼ resumed / abandoned

  You type "e" before the list finishes:
      → urgent setText("re") renders NOW
      → the in-progress list render is THROWN AWAY,
        React restarts it for "re" (interruptible!)
```

Step by step:
1. The urgent update (`setText`) renders and paints right away — typing stays snappy.
2. The transition update (`setQuery`) renders **in the background** at low priority, yielding to the browser between chunks (time-slicing, Module 8).
3. If a new urgent update arrives mid-render, React **interrupts and discards** the half-done transition render and starts over with the newest value. No wasted frame is shown.

> **Flag (simplification):** a transition does **not** make the filtering *faster*. The same work runs. React just **reprioritizes** it — runs it at low priority, off the critical path, and lets it be interrupted — so the urgent stuff isn't blocked.

#### 🌍 Real-life analogy
Think of a **barista** taking orders. A customer ordering a black coffee (fast, urgent) shouldn't wait behind someone ordering twelve custom lattes (slow). A good barista takes the quick order, hands it over, *then* keeps working the big one — and if a new quick order comes in, pauses the big one again. `startTransition` is you telling the barista: *"this big order is low-priority; serve the quick ones first, and feel free to set mine down if someone urgent shows up."*

#### 💻 Code example
```jsx
import { useState, useTransition } from "react";

function Search({ items }) {
  const [text, setText] = useState("");       // urgent: the input value
  const [query, setQuery] = useState("");      // non-urgent: drives filtering
  const [isPending, startTransition] = useTransition();

  function handleChange(e) {
    const next = e.target.value;
    setText(next);                  // URGENT — input updates instantly

    startTransition(() => {
      setQuery(next);               // NON-URGENT — filtering runs at low priority
    });                             // (interruptible if you keep typing)
  }

  // Expensive: filtering a very large list on every render
  const results = items.filter((it) => it.includes(query));

  return (
    <div>
      <input value={text} onChange={handleChange} />
      {/* subtle pending hint while the transition renders */}
      <ul style={{ opacity: isPending ? 0.6 : 1 }}>
        {results.map((it) => (
          <li key={it}>{it}</li>
        ))}
      </ul>
    </div>
  );
}
// Typing stays responsive: `text` (and the input) updates every keystroke,
// while the heavy `results` list re-renders at low priority and can be
// abandoned if you type again before it finishes.
```

> **Note:** only put **state updates** inside `startTransition`. The async value itself (like an `await`ed result) is read normally — you wrap the `setState` calls, not the data.

#### 🎤 Interview question
**Q: What does `startTransition` do, and how does it keep typing responsive?**
A: It marks the state updates inside it as **non-urgent transitions**, scheduling them on a low-priority lane. Urgent updates (the input's own value) render and paint first, so keystrokes feel instant; the expensive update (filtering) renders in the background, yields to the browser, and — crucially — can be **interrupted and discarded** if you type again before it finishes. It does not speed up the work; it reprioritizes it so urgent work isn't blocked.

---

### ⏳ `isPending` — A Subtle "Still Working" Indicator

#### 🧩 What is it?
`isPending` is the first value returned by `useTransition`. It's `true` while a transition you started is still rendering, and `false` once React has committed the new low-priority result. You use it to show a gentle "updating…" hint.

#### 🤔 Why do we need it? (the problem)
Because a transition lets the **old** UI stay on screen while the new one renders in the background, there's a moment where the list still shows *stale* results. Without a hint, the user can't tell whether anything is happening. `isPending` lets you say *"results are catching up"* — without blocking the screen or yanking the old content away.

#### ⚙️ How does it work?
```
  startTransition(setQuery)  ──▶  isPending = true
        (low-priority render running, old UI still shown)
                            │
        transition commits  ▼
                                 isPending = false
        (new UI on screen)
```
`isPending` flips `true` the instant the transition starts and `false` when it commits. Note it covers transitions started by **this** `useTransition` instance — it's local to the hook.

#### 🌍 Real-life analogy
It's the **"typing…" bubble** in a chat app. The message hasn't arrived yet, but the bubble reassures you the other person is on it. `isPending` is that bubble for your UI: *"the new results are coming — sit tight."*

#### 💻 Code example
```jsx
{isPending && <span className="text-neutral-500">Updating results…</span>}

// Or dim the stale list instead of replacing it (no jarring blank state):
<ul style={{ opacity: isPending ? 0.6 : 1 }}>
  {results.map((it) => <li key={it}>{it}</li>)}
</ul>
// While `isPending` is true the OLD list stays visible, just faded,
// so nothing flashes or disappears mid-type.
```

#### 🎤 Interview question
**Q: What is `isPending` and why is it useful with transitions?**
A: It's a boolean from `useTransition` that's `true` while the transition is still rendering at low priority. Since transitions keep the previous UI on screen during the background render, `isPending` lets you show a subtle pending hint (a spinner, or dimming the stale content) so the user knows results are catching up — without blocking or clearing the screen.

---

### 🪞 `useDeferredValue` — A Copy That Lags Behind on Purpose

#### 🧩 What is it?
`useDeferredValue` takes a value and returns a **deferred copy** of it. During urgent updates the copy **lags behind** — it keeps the *previous* value while the urgent render happens, then catches up to the latest value in a low-priority render afterward.

```javascript
const deferredQuery = useDeferredValue(query);
```

#### 🤔 Why do we need it? (the problem)
`useTransition` works when *you* own the `setState` call — you wrap it. But sometimes the value comes from **above** as a prop, or from a controlled input, and you can't wrap the update that produced it. You still want the expensive child to render at low priority. `useDeferredValue` solves this from the **reading** side: feed the value in, render the expensive part from the *deferred* copy, and the input stays urgent.

#### ⚙️ How does it work?
```
  query:          "r" ── "re" ── "rea"   (urgent, every keystroke)
                    │       │       │
  useDeferredValue: │       │       │
  deferredQuery:   "r" ───── "r" ── "re"  (lags, catches up at low priority)
                    ▲                 ▲
              input updates      heavy child re-renders from the
              immediately        DEFERRED value, in the background
```
1. On each keystroke, `query` updates urgently → the input repaints instantly.
2. `useDeferredValue` returns the **old** value for that urgent render (so the heavy child does *not* re-run on the critical path).
3. React then schedules a **low-priority** render where `deferredQuery` catches up to the latest `query`. That render is interruptible — if you keep typing, the catch-up is restarted with the newest value.

> **Flag (simplification):** "lags behind" means React intentionally renders the heavy subtree from a slightly stale value during fast input, then reconciles it once things settle. It's the same interruptible low-priority mechanism as transitions, just driven by a value instead of a wrapped `setState`. Like transitions, it does **not** make the child faster — it reprioritizes when the child re-renders.

#### 🌍 Real-life analogy
It's a **live TV broadcast on a few-seconds delay**. The studio (your input) happens in real time, but what airs (the heavy view) is intentionally a beat behind, so the control room has breathing room to keep the picture clean. Viewers barely notice the lag, and the feed never glitches mid-frame.

#### 💻 Code example
```jsx
import { useState, useDeferredValue, useMemo } from "react";

function Search({ items }) {
  const [query, setQuery] = useState("");
  const deferredQuery = useDeferredValue(query); // lagging copy

  // Heavy work reads the DEFERRED value, not `query` directly:
  const results = useMemo(
    () => items.filter((it) => it.includes(deferredQuery)),
    [items, deferredQuery]
  );

  // Optional pending hint: the value hasn't caught up yet
  const isStale = query !== deferredQuery;

  return (
    <div>
      {/* input is driven by `query` → updates every keystroke, stays snappy */}
      <input value={query} onChange={(e) => setQuery(e.target.value)} />
      <ul style={{ opacity: isStale ? 0.6 : 1 }}>
        {results.map((it) => (
          <li key={it}>{it}</li>
        ))}
      </ul>
    </div>
  );
}
// The input reads `query` (urgent, instant). The list filters on
// `deferredQuery` (low priority), so typing never waits on the list.
```

> **Tip:** pair `useDeferredValue` with `useMemo` (and often `React.memo` on the child) so the expensive render only re-runs when the *deferred* value changes — not on every urgent keystroke.

#### 🎤 Interview question
**Q: `useDeferredValue` vs `useTransition` — when do you reach for each?**
A: Use `useTransition` when **you control the state update** and can wrap the `setState` in `startTransition` — you mark *the update* as non-urgent and get `isPending`. Use `useDeferredValue` when you only have **a value** (a prop, or a controlled input you can't wrap) and want the expensive consumer to render from a **lagging copy** at low priority. Both use the same interruptible low-priority mechanism; one works from the *writing* side, the other from the *reading* side.

---

### ⚖️ Transition vs Debounce — Reprioritize, Don't Just Delay

#### 🧩 What is it?
**Debounce** is a timer trick: after the user stops typing for, say, 300 ms, *then* run the expensive work. A **transition** doesn't delay anything — it runs the work at **low priority**, interruptibly, right away. They look similar (both keep typing responsive) but work completely differently.

#### 🤔 Why do we need to compare them? (the problem)
Debounce is the classic fix for laggy filtering, and it has real downsides that transitions remove. Knowing the difference is a high-frequency interview question and a real architecture decision.

#### ⚙️ How does it work?
```
  DEBOUNCE (timer-based, NOT interruptible):
    type type type ──(wait 300ms idle)──▶ run filter (BLOCKS while it runs)
    • Nothing updates until you pause.
    • When it finally runs, it still blocks the main thread.
    • Fixed delay — same on a fast laptop and a slow phone.

  TRANSITION (priority-based, interruptible):
    type ─▶ low-priority filter starts immediately, yields to browser
    type ─▶ in-progress filter ABANDONED, restarts with new value
    • UI updates every keystroke; list catches up in the background.
    • If new input arrives, the half-done render is thrown away.
    • Adapts to the device — yields more on a slow phone.
```

The crucial differences:
- **Debounce delays** the work on a timer; nothing happens until the timer fires, and **while the work runs it still blocks** the thread (it's a normal, synchronous render once triggered).
- **A transition reprioritizes** the work: it runs at low priority, **yields to the browser**, and is **interruptible/abandonable** — a stale in-progress render is discarded when newer input arrives.
- **Debounce is a fixed timer** you tune by guessing; **a transition adapts** to device speed, yielding more on a slow device and less on a fast one — no magic number to pick.

These two are **complementary**, not enemies: debounce is great for limiting *expensive side effects* (like network requests — don't fire one per keystroke), while transitions/deferred values are for keeping *rendering* responsive. You'll often debounce the fetch **and** wrap the resulting state update in a transition.

#### 🌍 Real-life analogy
**Debounce** is a printer set to "wait until the user stops sending pages, then print the whole batch." If you keep adding pages, nothing prints — and once it starts, it hogs the printer until done. **A transition** is a smart print queue that starts immediately but at low priority: if an urgent one-page memo comes in, it pauses your big job, prints the memo, then resumes — and it speeds up or slows down based on how busy the office is.

#### 💻 Code example
```jsx
// DEBOUNCE — delays on a timer; the run itself still blocks:
function handleChange(e) {
  const next = e.target.value;
  setText(next);
  clearTimeout(timer.current);
  timer.current = setTimeout(() => {
    setQuery(next);   // runs only after 300ms idle — and blocks when it does
  }, 300);
}

// TRANSITION — runs now, at low priority, interruptible:
function handleChange(e) {
  const next = e.target.value;
  setText(next);
  startTransition(() => {
    setQuery(next);   // low priority, yields, abandoned if you type again
  });
}

// REAL-WORLD COMBO — debounce the network call, transition the render:
function handleChange(e) {
  const next = e.target.value;
  setText(next);                          // urgent input
  clearTimeout(timer.current);
  timer.current = setTimeout(() => {      // debounce the EXPENSIVE fetch
    fetchResults(next).then((data) => {
      startTransition(() => setResults(data));  // low-priority render
    });
  }, 300);
}
```

#### 🎤 Interview question
**Q: `useDeferredValue`/`useTransition` vs debounce — what's the real difference?**
A: Debounce **delays** work on a timer and doesn't run anything until the user pauses; once it runs, it still **blocks** the main thread, and the delay is a fixed number that's the same on every device. A transition (or `useDeferredValue`) **reprioritizes** the work instead of delaying it: it runs immediately at low priority, yields to the browser, is **interruptible** (a stale in-progress render is abandoned when newer input arrives), and **adapts to device speed**. They're complementary — debounce to throttle expensive side effects like network calls, transitions/deferred values to keep rendering responsive.

<h2 id="module-11">Module 11 — Suspense & Data Fetching</h2>

Every app eventually hits the same awkward moment: a component is ready to render, but the *data* (or the *code*) it needs hasn't arrived yet. The old answer was a tangle of `isLoading` flags and early `return <Spinner />` lines scattered through your tree. **Suspense** flips this around — a component can simply say "I'm not ready," and React handles the waiting, the loading UI, and the retry *for* it. This module unpacks the surprisingly simple mechanism behind that: a thrown promise, caught by a boundary.

---

### ⏸️ Suspense — "I'm Not Ready, Show the Fallback"

#### 🧩 What is it?
**Suspense** is a built-in React component — written `<Suspense fallback={...}>` — that wraps part of your tree. If any child inside it "**suspends**" (signals it isn't ready to render yet), React shows the `fallback` UI you provided instead of that child, and automatically swaps in the real content once the child becomes ready.

So a "boundary" is just a `<Suspense>` you've placed in the tree. It's the nearest ancestor that catches a suspension from below.

#### 🤔 Why do we need it? (the problem)
Without Suspense, every component that loads something has to manage its own loading state by hand:

```javascript
function Profile() {
  const [user, setUser] = useState(null);
  useEffect(() => { fetchUser().then(setUser); }, []);
  if (!user) return <Spinner />;   // ❌ boilerplate in EVERY component
  return <h1>{user.name}</h1>;
}
```

This spreads `if (!data) return <Spinner />` across your whole app, makes coordinated loading states ("show one spinner until *all three* widgets are ready") painful, and tightly couples each component to its loading UI. Suspense lets a component focus on the *happy path* (data is here) and lets a **parent** decide what the loading UI looks like and where it appears.

#### ⚙️ How does it work?
A component "suspends" by **throwing a promise** during render. That sounds strange, but it reuses a mechanism React already had: just as an **error boundary** catches a thrown *error*, a **Suspense boundary** catches a thrown *promise*.

The cycle is: suspend (throw a promise) → React catches it at the nearest boundary → show the fallback → wait for the promise → re-render (retry) when it resolves.

```
   <Suspense fallback={<Spinner/>}>
            │
            ▼
      render <Child/>
            │
   data not ready?
            │ throw promise  ───────┐
            ▼                        │ caught by nearest
   ┌──────────────────┐             │   <Suspense>
   │  show <Spinner/>  │ ◀───────────┘
   │  (the fallback)   │
   └──────────────────┘
            │  promise resolves
            ▼
      RE-RENDER <Child/>  ──▶ data ready ──▶ real UI
```

Key point: React **retries** the render of the boundary's children when the promise resolves — it doesn't keep the half-finished render around. The component re-runs from the top, and this time its data is ready, so it doesn't throw.

> **Note (flag a simplification):** the promise must be *cached* across renders (e.g. by your data layer), so the *retry* sees a resolved result instead of throwing a brand-new promise forever. A naive `fetch()` started inside render would re-fetch every retry and loop. This is exactly why the practical rule (last topic) is: let a framework or a Suspense-enabled data layer do the suspending — don't hand-throw promises in app code.

#### 🌍 Real-life analogy
Think of a **restaurant kitchen with a pass-through window**. A waiter (the component) goes to grab a dish, but it isn't plated yet — so instead of standing there blocking everyone, they hang a **"preparing" ticket** (throw a promise) and walk away. The **expediter at the window** (the Suspense boundary) sees the ticket, tells the table "your food is on its way" (shows the fallback), and the moment the kitchen rings the bell (promise resolves), sends the waiter back to pick up the finished plate (re-render). Nobody blocks; the boundary coordinates.

#### 💻 Code example
```jsx
import { Suspense } from "react";

// The fallback is shown while ANY child below suspends.
function Page() {
  return (
    <Suspense fallback={<p>Loading profile…</p>}>
      <Profile />     {/* if this suspends, the <p> shows */}
      <Posts />       {/* a sibling: same boundary covers it too */}
    </Suspense>
  );
}

// You can nest boundaries for finer-grained loading UI:
function App() {
  return (
    <Suspense fallback={<FullPageSkeleton />}>
      <Header />
      <Suspense fallback={<SidebarSkeleton />}>
        <Sidebar />   {/* its own, smaller fallback */}
      </Suspense>
    </Suspense>
  );
}
```

#### 🎤 Interview question
**Q: What does it mean for a component to "suspend," and how does the Suspense boundary handle it?**
A: To suspend means the component **throws a promise** during render to signal "my data/code isn't ready." React catches that thrown promise at the **nearest `<Suspense>` boundary** above it, renders that boundary's `fallback` instead, and subscribes to the promise. When the promise **resolves**, React **re-renders** (retries) the boundary's children — this time the data is ready, so the component returns real UI. It's the same catch mechanism as error boundaries, but for promises instead of errors.

### 🦥 React.lazy — Suspense for *Code* (Not Just Data)

#### 🧩 What is it?
**`React.lazy`** lets you load a component's *code* on demand — its JavaScript bundle is fetched only when the component first renders, not upfront. And it works through the **exact same Suspense mechanism**: while the code is downloading, the component suspends, and the nearest boundary shows its fallback.

#### 🤔 Why do we need it? (the problem)
Shipping your entire app as one giant JavaScript file means users download code for screens they may never visit. **Code-splitting** breaks the bundle into chunks loaded on demand, shrinking the initial download. `React.lazy` makes a lazily-loaded component behave like any other component — Suspense handles the "still downloading" gap.

#### ⚙️ How does it work?
`lazy()` wraps a dynamic `import()`, which returns a **promise** for the module. The first time the lazy component renders, its code isn't there yet → it **suspends** (throws that import promise) → the nearest `<Suspense>` shows the fallback → when the chunk finishes downloading, React **retries** and renders the real component. Same suspend → fallback → resolve → retry cycle as data Suspense.

```
   first render of <Settings/> (lazy)
            │
     code chunk not downloaded yet
            │ throw import() promise
            ▼  caught by nearest <Suspense>
   ┌────────────────────┐
   │  show fallback      │
   └────────────────────┘
            │ chunk downloads / resolves
            ▼
     RE-RENDER ──▶ real <Settings/> appears
```

#### 🌍 Real-life analogy
It's like a **furniture store showroom**. They don't keep every sofa on the floor — when you pick one, they radio the warehouse to bring it out (the dynamic import). Meanwhile you're handed a **"fetching your item" card** (the fallback). When the sofa arrives, it replaces the card. You only ever wait for the things you actually chose.

#### 💻 Code example
```jsx
import { Suspense, lazy } from "react";

// Code for Settings is NOT in the main bundle.
// import() returns a promise → lazy() makes it Suspense-aware.
const Settings = lazy(() => import("./Settings"));

function App() {
  return (
    <Suspense fallback={<p>Loading settings…</p>}>
      <Settings />   {/* suspends while its chunk downloads */}
    </Suspense>
  );
}
```

#### 🎤 Interview question
**Q: How is `React.lazy` related to Suspense?**
A: `React.lazy` is **code-splitting built on Suspense**. It wraps a dynamic `import()`; the first render of the lazy component throws the import's promise, which **suspends** it. The nearest `<Suspense>` boundary shows its fallback until the code chunk downloads, then React retries and renders the component. Data Suspense and `lazy` are the same mechanism — one waits on data, the other on code.

### 🌊 Streaming SSR — Send the Shell First, Stream the Rest

#### 🧩 What is it?
**Streaming server-side rendering** lets the server send a page's HTML **in pieces over time** instead of waiting until everything is ready. With Suspense, the server immediately sends the parts that are ready plus a **fallback** for each not-yet-ready boundary, then streams in the real HTML for each boundary as its data resolves. On the server, this is driven by **`renderToPipeableStream`** (Node) / `renderToReadableStream` (web streams).

#### 🤔 Why do we need it? (the problem)
Classic, non-streaming SSR is **all-or-nothing**: the server renders the *entire* page to an HTML string, and the user stares at a blank screen until the *slowest* piece of data finishes. One slow database query holds the whole page hostage. Streaming fixes this — the fast parts (header, layout, nav) reach the user instantly, and slow sections fill in progressively.

#### ⚙️ How does it work?
On the server, a component inside a `<Suspense>` that needs data **suspends**. Instead of blocking, the server streams the boundary's **fallback** HTML now, keeps rendering everything else, and when the suspended data resolves, streams the **real HTML** for that boundary plus a tiny inline script that swaps the fallback out — all on one open connection.

```
   TIME ──────────────────────────────────▶

   t0  send: <Header/> + nav  + [fallback: spinner]
       │                         (boundary not ready)
   t1  ...user already sees & reads the shell...
   t2  data resolves on server
       │
   t3  stream: real <Posts/> HTML  ──▶ script
       swaps the spinner for the content
```

**Selective hydration** is the client-side partner. *Hydration* = attaching React's event handlers to the server-sent HTML to make it interactive. Instead of waiting for the whole page's JS before *anything* becomes interactive, React hydrates **each Suspense boundary independently**, as its HTML and code arrive — and it **prioritizes the boundary the user interacts with first**. Click a region that isn't hydrated yet, and React hydrates *that* part ahead of the others.

> **Note (flag a simplification):** the swap-in scripts and the streaming protocol are implementation details React manages for you; modern frameworks (e.g. Next.js App Router) wire `renderToPipeableStream` up so you mostly just place `<Suspense>` boundaries.

#### 🌍 Real-life analogy
Old SSR is a **restaurant that won't bring out a single dish until the entire table's order is cooked** — your appetizer goes cold waiting on someone's slow steak. Streaming SSR brings out **each dish the moment it's ready**, with a little "your steak is coming" note (the fallback) on the empty plate. Selective hydration is the waiter noticing **you reached for the bread first**, so they uncork *your* side of the table before the rest.

#### 💻 Code example
```jsx
// SERVER — Node entry point
import { renderToPipeableStream } from "react-dom/server";

function handler(req, res) {
  const { pipe } = renderToPipeableStream(<App />, {
    bootstrapScripts: ["/main.js"],
    onShellReady() {
      // The shell (everything NOT suspended) is ready.
      // Start streaming immediately; suspended boundaries
      // send their fallback now, real HTML later.
      res.setHeader("content-type", "text/html");
      pipe(res);
    },
  });
}

// <Posts/> inside a <Suspense> can suspend on the server.
// Its fallback streams first; its real HTML streams when ready.
function App() {
  return (
    <html><body>
      <Header />
      <Suspense fallback={<p>Loading posts…</p>}>
        <Posts />
      </Suspense>
    </body></html>
  );
}
```

#### 🎤 Interview question
**Q: How does Suspense enable streaming SSR, and what is selective hydration?**
A: A component inside a `<Suspense>` boundary that isn't ready on the server **suspends** instead of blocking. The server streams the boundary's **fallback** HTML right away, continues rendering the rest, and **streams the real HTML** for that boundary (plus a swap-in script) once its data resolves — so users see the page shell immediately rather than waiting for the slowest query. **Selective hydration** then lets React hydrate (attach interactivity to) each boundary **independently** as its HTML/JS arrives, and **prioritizes whichever boundary the user interacts with first**, instead of needing the whole page's JS before anything is interactive.

### 🪝 The `use` Hook — Read a Promise During Render (React 19)

#### 🧩 What is it?
**`use`** is a React 19 API that **reads the value of a promise (or a context) during render**. Given a promise, `use(promise)` **suspends** the component until that promise resolves, then returns its resolved value — so your component reads async data as if it were synchronous. It's the official, supported way to suspend on data, replacing the hand-rolled "throw a promise" trick.

#### 🤔 Why do we need it? (the problem)
Before `use`, the *concept* of "throw a promise to suspend" existed, but there was no clean, public API to do it in app code — you needed a data library to wire it up. `use` makes suspending a first-class operation: pass it a promise and React handles the suspend/fallback/retry cycle. It's also unusually flexible — unlike other hooks, `use` **can be called inside conditionals and loops**.

#### ⚙️ How does it work?
`use(promise)` integrates directly with the Suspense machinery:

```
   const data = use(somePromise)   // inside render
            │
    promise pending?
            │  yes → component SUSPENDS
            ▼        (nearest <Suspense> shows fallback)
   ┌────────────────────┐
   │   fallback shown    │
   └────────────────────┘
            │  promise resolves
            ▼
   RE-RENDER ──▶ use() returns the value ──▶ real UI
```

So under the hood it's the same suspend → fallback → resolve → retry loop from the first topic — `use` is just the clean front door to it. Same caveat applies: the promise should be **created outside render / cached** (typically by a framework or RSC, see next topic) so the retry resolves instead of re-suspending forever.

#### 🌍 Real-life analogy
`use` is like a **coffee-shop buzzer**. You order, and instead of standing frozen at the counter, you're handed a buzzer (`use(promise)`) and told to sit down (the component suspends, the room shows its normal state — the fallback). When your drink is ready the buzzer goes off (promise resolves), you walk up, and **collect the actual coffee** (`use` returns the value). You never block the queue; you just get pulled back when it's ready.

#### 💻 Code example
```jsx
import { Suspense, use } from "react";

// fetchUser() is started OUTSIDE render and the promise is
// passed down as a prop (so retries reuse the same promise).
function Profile({ userPromise }) {
  const user = use(userPromise);   // suspends until resolved
  return <h1>Hello, {user.name}</h1>;
}

function Page({ userPromise }) {
  return (
    // When Profile suspends, THIS boundary shows the fallback.
    <Suspense fallback={<p>Loading user…</p>}>
      <Profile userPromise={userPromise} />
    </Suspense>
  );
}

// use() also reads context — and may be called conditionally:
function Banner({ show }) {
  if (!show) return null;
  const theme = use(ThemeContext);   // ✅ allowed inside an `if`
  return <div className={theme}>Welcome</div>;
}
```

#### 🎤 Interview question
**Q: What does the `use` hook do, and how is it different from other hooks?**
A: `use` (React 19) reads a **promise** or a **context** during render. Given a promise, it **suspends** the component until the promise resolves and then returns the resolved value, plugging directly into the nearest `<Suspense>` boundary's fallback/retry cycle. Unlike every other hook, `use` is **not bound by the Rules of Hooks the same way** — it can be called **inside conditionals and loops**, because it doesn't rely on stable call-order positioning the way `useState`/`useEffect` do. (It still must be called during render, not in event handlers/effects, and not inside a `try/catch`.)

### 🧱 Suspense for Data in Practice — Let the Framework Suspend

#### 🧩 What is it?
The practical rule: in real apps you **don't hand-throw promises** to trigger Suspense. You let a **Suspense-enabled data layer or framework** do it — a library like React Query, or a **React Server Components (RSC)** setup (e.g. Next.js App Router) where an `async` Server Component naturally suspends while it awaits data.

#### 🤔 Why do we need it? (the problem)
Hand-throwing promises is genuinely hard to get right. The promise **must be cached/stable** across the render retries, or the component re-throws a fresh promise every attempt and **loops forever**. You also have to handle errors, deduplicate in-flight requests, and integrate with SSR streaming. A framework or data layer solves all of this for you — your component just *reads* data and the plumbing handles caching, retries, and streaming.

#### ⚙️ How does it work?
With **RSC**, an `async` Server Component can `await` data directly; while it awaits, React treats it as suspended and the nearest `<Suspense>` boundary streams its fallback. With a **data library**, a hook (or `use(query.promise)`) suspends on a *cached* promise the library manages.

```
   YOUR CODE                FRAMEWORK / DATA LAYER
   ─────────                ──────────────────────
   read data       ──▶      • starts + CACHES the promise
   (use / async)            • throws it to suspend
                            • dedupes + handles errors
                            • streams fallback (SSR)
        ▲                   • RE-RENDERS on resolve
        └───── returns resolved value ─────┘
```

#### 🌍 Real-life analogy
Hand-throwing promises is like **wiring your own house's electricity** — possible, but one mistake and everything shorts (the infinite re-throw loop). Using a framework or data layer is hiring a **licensed electrician with the panel already up to code**: you just flip the switch (`await` / `use`) and the wiring, breakers, and safety are handled for you.

#### 💻 Code example
```jsx
// ✅ RSC: an async Server Component suspends naturally on await.
// (Next.js App Router-style — the framework wires Suspense + streaming.)
async function Posts() {
  const posts = await db.posts.findMany(); // suspends while awaiting
  return <ul>{posts.map(p => <li key={p.id}>{p.title}</li>)}</ul>;
}

function Page() {
  return (
    <Suspense fallback={<p>Loading posts…</p>}>
      <Posts />   {/* framework streams the fallback, then the real HTML */}
    </Suspense>
  );
}

// ❌ DON'T do this in app code — a new promise every render → infinite loop:
// function Bad() {
//   const data = use(fetch("/api").then(r => r.json())); // re-throws forever
//   return <pre>{JSON.stringify(data)}</pre>;
// }
```

#### 🎤 Interview question
**Q: Should you trigger Suspense by throwing promises yourself? Why or why not?**
A: No — in app code you should suspend through a **framework or a Suspense-enabled data layer** (RSC's `async` components, or a library like React Query). The reason is that the suspending promise must be **cached and stable across render retries**; if you throw a fresh promise on every render, the component re-suspends forever in an infinite loop. Frameworks also handle deduplication, error handling, and SSR streaming integration. Throwing promises by hand is the *underlying mechanism*, not the *intended public API* — `use` plus a data layer is.

<h2 id="module-12">Module 12 — Memoization & Re-render Control</h2>

A surprising number of "React is slow" complaints come down to one fact beginners are never taught clearly: a child component re-renders when its **parent** re-renders — even if you passed it the exact same props. This module is about *when* React re-renders, and the three tools (`React.memo`, `useMemo`, `useCallback`) you use to stop the re-renders you don't want. We finish with the React Compiler, which may soon do all of this for you automatically.

---

### 🔁 When a Component Re-renders — It's Not (Only) About Props

#### 🧩 What is it?
A "re-render" means React **calls your component function again** to get a fresh description of the UI. (It does not necessarily touch the real page — see Module 0: render is not the same as a DOM update.) A component re-renders for exactly three reasons:

1. Its **parent** re-rendered (so React re-renders the children too).
2. Its **own state** changed (a `useState` / `useReducer` setter ran with a new value).
3. A **context** it consumes changed value (covered in its own topic below).

#### 🤔 Why do we need to know this? (the problem)
Beginners almost always believe "a child re-renders **because its props changed**." That is the single most common React misconception. The truth: a child re-renders when its parent does **regardless of props** — even if every prop is byte-for-byte identical to last time — *unless* you opt the child out with `React.memo`. Props changing is not the trigger; the parent re-rendering is.

#### ⚙️ How does it work?
When state changes in a component, React re-renders that component and then walks **down** the tree, re-rendering its descendants by default:

```
   <Parent>  state changed --> re-renders
       |
       v  React re-renders children by default,
          even if their props are identical
   +---------+   +---------+   +---------+
   | ChildA  |   | ChildB  |   | ChildC  |
   | re-runs |   | re-runs |   | re-runs |
   +---------+   +---------+   +---------+
```

This is usually fine — re-rendering is just calling functions and diffing cheap description objects (Module 2), not rebuilding the DOM. React only updates the parts of the real page that actually changed. You only need to *control* re-renders when a component is genuinely expensive to render or sits in a hot path (like every keystroke).

> **Simplification flag:** there is a built-in *bailout* — if a component's state setter is called with a value `Object.is`-equal to the current state, React may still render that component once but then bails out of re-rendering its subtree (Module 6). That's about *state*, not props. The "parent re-rendered" rule above still holds for everything else.

#### 🌍 Real-life analogy
Think of a manager (parent) sending an updated memo to their whole team (children). When the manager revises *anything*, they re-send the memo to **everyone** — even the people whose section of the memo did not change. Each person still has to read it again. `React.memo` is like an employee with a rule: "if my section is identical to the last copy, I won't bother re-reading it."

#### 💻 Code example
```jsx
function Parent() {
  const [count, setCount] = useState(0);

  // Clicking re-renders Parent. <Child /> re-renders too,
  // even though we pass it NO props at all.
  return (
    <div>
      <button onClick={() => setCount(c => c + 1)}>{count}</button>
      <Child />
    </div>
  );
}

function Child() {
  console.log("Child rendered"); // logs on EVERY button click
  return <p>I have no props, yet I re-render with my parent.</p>;
}
```

#### 🎤 Interview question
**Q: When does a React component re-render?**
A: When its parent re-renders, when its own state changes, or when a context it consumes changes value. Crucially, a child re-renders when its parent does **even if its props are identical** — props changing is not what triggers the re-render; the parent re-rendering is. To skip that, you wrap the child in `React.memo`. (There's also a state-level bailout: an `Object.is`-equal `setState` can be skipped.)

---

### 🛡️ React.memo — Skip a Re-render When Props Didn't Change

#### 🧩 What is it?
`React.memo` is a wrapper for a component. It tells React: "before re-rendering this component because its parent re-rendered, **compare its new props to the old props**. If they are shallow-equal, reuse the previous result and skip the re-render."

#### 🤔 Why do we need it? (the problem)
From the last topic: children re-render with their parent for free. Most of the time that's cheap and you ignore it. But when a child is **expensive** (renders a big list, does heavy work) and its parent re-renders often (every keystroke, every tick), those wasted re-renders add up. `React.memo` lets that child opt out when nothing it cares about actually changed.

#### ⚙️ How does it work?
`React.memo` does a **shallow** comparison of props: it checks each prop with `Object.is(prevProp, nextProp)`. Shallow means it compares **one level deep** — it does *not* look inside objects or arrays.

```
   Parent re-renders
        |
        v
   React.memo(Child): shallow-compare props
        |
   prev === next for every prop?
        |                 |
       YES               NO
        |                 |
   SKIP re-render    re-render Child
   (reuse output)
```

The catch — and why `React.memo` so often "does nothing": if a prop is a **new object, array, or function created during the parent's render**, it is a brand-new reference every time, so the shallow check always says "different," and the memo never skips. Example of a prop that defeats `memo`: `style={{ color: "red" }}` or `onClick={() => doThing()}` written inline — a fresh object/function on every render.

> **Accuracy note:** `React.memo` only guards against re-renders caused by the **parent**. If the memoized component has its **own** state or consumes a **changed context**, it still re-renders — `memo` cannot stop that.

#### 🌍 Real-life analogy
`React.memo` is a bouncer checking IDs at a club door. Each time you approach (the parent re-renders), the bouncer compares your ID to the one on file. Same ID? You stay seated, no re-entry needed. The trick: if you hand over a **freshly printed ID every single time** (a new inline object/function), the bouncer sees a "different" ID on each pass and waves you through to re-render anyway — that's how `memo` silently backfires.

#### 💻 Code example
```jsx
// Wrapped in memo: re-renders only when its props are shallow-different.
const ExpensiveList = React.memo(function ExpensiveList({ items }) {
  console.log("ExpensiveList rendered");
  return <ul>{items.map(i => <li key={i.id}>{i.text}</li>)}</ul>;
});

function Page() {
  const [text, setText] = useState("");
  const items = [{ id: 1, text: "a" }, { id: 2, text: "b" }];

  // BUG: `items` is a NEW array on every keystroke, so its reference
  // differs every render -> React.memo's shallow check fails ->
  // ExpensiveList re-renders on every keystroke anyway.
  return (
    <>
      <input value={text} onChange={e => setText(e.target.value)} />
      <ExpensiveList items={items} />
    </>
  );
}
```
The fix for that new-array-every-render problem is the next topic: `useMemo`.

#### 🎤 Interview question
**Q: What does `React.memo` compare, and when does it backfire?**
A: It does a **shallow** comparison of props (`Object.is` on each prop, one level deep) and skips the re-render if all props are equal. It backfires when you pass **new object/array/function references on every render** (e.g. inline `{...}`, `[...]`, or `() => ...`) — the shallow check always sees them as different, so `memo` never skips. You fix that by stabilizing those references with `useMemo`/`useCallback`.

---

### 🧮 useMemo & useCallback — Keep References Stable

#### 🧩 What is it?
Both cache something across renders so its **reference stays the same** when its inputs haven't changed:

- **`useMemo(fn, deps)`** caches a computed **value** (the result of running `fn`). It re-runs `fn` only when a dependency in `deps` changes.
- **`useCallback(fn, deps)`** caches a **function identity** (the function itself). It returns the same function reference until a dependency changes. (`useCallback(fn, deps)` is just `useMemo(() => fn, deps)` — a function-shaped special case.)

#### 🤔 Why do we need them? (the problem)
Two distinct jobs:

1. **Skip expensive recalculation.** If a render computes something costly (sorting 10,000 rows), `useMemo` avoids redoing it when the inputs are unchanged.
2. **Preserve referential equality** so `React.memo` actually works. As we saw, a new array or function created each render gives a memoized child "new" props every time. Wrapping that value in `useMemo` (for objects/arrays) or `useCallback` (for functions) keeps the **same reference** across renders, so the child's shallow prop check passes and it can skip.

#### ⚙️ How does it work?
React stores the cached value and the dependency array on the fiber (Module 5). On each render it compares the new `deps` to the previous ones (shallow `Object.is` per item). Same deps -> return the cached value (or function). Changed deps -> recompute and cache the new one.

```
   render N:   useMemo(fn, [a, b])
                 deps changed?
                /            \
             NO               YES
              |                |
   return cached value   run fn(), cache result, return it
```

> **Accuracy note:** these are a **performance hint**, not a guarantee — React may legitimately throw away a cache (e.g. to free memory) and recompute. Never use `useMemo`/`useCallback` for *correctness* (don't rely on a function "definitely" being the same instance for logic that must not run twice). Use them for speed and stable references only.

#### 🌍 Real-life analogy
`useMemo` is a **chef prepping a sauce that takes an hour**. As long as the recipe (the deps) hasn't changed, they ladle from the batch already made instead of cooking it again from scratch. `useCallback` is like keeping the **same phone number** instead of printing new business cards every morning — your contacts (memoized children) don't have to update their address book each day, because the number they have still works.

#### 💻 Code example — child re-rendering needlessly, fixed with `React.memo` + `useCallback`
```jsx
// The expensive child, memoized so it skips re-renders when props are equal.
const Button = React.memo(function Button({ onClick, label }) {
  console.log("Button rendered:", label);
  return <button onClick={onClick}>{label}</button>;
});

function Toolbar() {
  const [count, setCount] = useState(0);
  const [text, setText] = useState("");

  // WITHOUT useCallback, `handleSave` would be a NEW function every
  // render. Typing in the input re-renders Toolbar, which would hand
  // <Button> a new onClick each time -> React.memo's shallow check
  // fails -> Button re-renders on every keystroke (wasteful).
  //
  // WITH useCallback + empty deps, the SAME function reference is
  // reused across renders, so Button's props are shallow-equal and
  // React.memo lets it SKIP re-rendering while you type.
  const handleSave = useCallback(() => {
    console.log("saved");
  }, []); // no deps -> stable forever

  return (
    <>
      <input value={text} onChange={e => setText(e.target.value)} />
      <button onClick={() => setCount(c => c + 1)}>count: {count}</button>
      {/* Button now logs only once, not on every keystroke */}
      <Button onClick={handleSave} label="Save" />
    </>
  );
}
```

#### 🎤 Interview question
**Q: `useMemo` vs `useCallback` — when does each help?**
A: `useMemo` caches a **value** (the result of a computation) and is used both to skip expensive recalculation and to keep an object/array prop's reference stable. `useCallback` caches a **function's identity** so a function prop stays the same reference across renders. Both exist to preserve **referential equality** so memoized children (`React.memo`) or effect/`useMemo` dependency arrays don't see a "new" value every render. They're performance optimizations, not correctness guarantees — and both only pay off when paired with something that actually compares references (like `React.memo` or a dependency array).

### 🌐 The Context Re-render Problem — Every Consumer Re-renders Together

#### 🧩 What is it?
React Context lets components read shared data without passing props down by hand. The catch: when a context's **value changes**, **every** component that consumes that context re-renders — *all* of them — even consumers that only use a part of the value that didn't change.

#### 🤔 Why do we need to know this? (the problem)
People reach for one big context ("AppContext") holding the user, the theme, the cart, and a dozen setters. Then changing *any* field — even a high-frequency one — re-renders every single consumer in the app, including ones that only read an unrelated field. That turns a convenient pattern into a performance footgun.

#### ⚙️ How does it work?
Context consumers don't shallow-compare individual fields. They re-render whenever the **provider's `value` is a different reference** than before (`Object.is`):

```
   <ThemeContext.Provider value={...}>  value changed
        |
        +--> ConsumerA (uses theme)      re-renders
        +--> ConsumerB (uses user)       re-renders  <- even if user
        +--> ConsumerC (uses setTheme)   re-renders     didn't change!
```

Two classic mistakes make this worse:

1. **A fresh `value` object every render.** Writing `value={{ user, theme }}` inline creates a new object each render, so even when `user` and `theme` are unchanged, the reference differs and all consumers re-render. Fix: wrap the value in `useMemo`.
2. **One giant context.** Unrelated data shares a single value, so any change wakes every consumer. Fix: **split** into focused contexts (e.g. a `ThemeContext` and a separate `UserContext`) so a change only re-renders the consumers that actually use that slice.

#### 🌍 Real-life analogy
A context is an **office-wide PA announcement**. When the value changes, the speaker blares to the *entire* building — accounting looks up even when the message was only for the kitchen. Splitting contexts is like installing **separate speakers per department**: the kitchen announcement only interrupts the kitchen. Memoizing the value is like not re-broadcasting the same message on a loop just because someone walked past the microphone.

#### 💻 Code example
```jsx
// ❌ Problem: a new value object every render -> all consumers re-render,
// and theme + user are bundled, so a theme change also wakes user consumers.
function AppBad({ children }) {
  const [user, setUser] = useState(null);
  const [theme, setTheme] = useState("light");
  return (
    <AppContext.Provider value={{ user, setUser, theme, setTheme }}>
      {children}
    </AppContext.Provider>
  );
}

// ✅ Fix 1: memoize the value so its reference is stable when inputs are equal.
// ✅ Fix 2: split into separate contexts so changing theme doesn't
//           re-render components that only read user.
function AppGood({ children }) {
  const [user, setUser] = useState(null);
  const [theme, setTheme] = useState("light");

  const userValue = useMemo(() => ({ user, setUser }), [user]);
  const themeValue = useMemo(() => ({ theme, setTheme }), [theme]);

  return (
    <UserContext.Provider value={userValue}>
      <ThemeContext.Provider value={themeValue}>
        {children}
      </ThemeContext.Provider>
    </UserContext.Provider>
  );
}
```

#### 🎤 Interview question
**Q: Why does context cause extra re-renders, and how do you fix it?**
A: When a provider's `value` changes reference, **every** consumer of that context re-renders — even ones reading a field that didn't change — because consumers subscribe to the whole value, not individual fields. Two fixes: (1) **memoize the value** with `useMemo` so it isn't a brand-new object on every render, and (2) **split contexts** so unrelated data lives in separate providers and a change only re-renders the consumers that use that slice. (For finer control, libraries like `use-context-selector` or external stores let consumers subscribe to just a slice.)

### 🤖 The React Compiler — Auto-Memoization (and the End of Manual Memo?)

#### 🧩 What is it?
The **React Compiler** (a separate build-time package — `babel-plugin-react-compiler` — that landed in the React 19 era and works with React 17+; originally codenamed "React Forget") is a build-time tool that **automatically memoizes** your components and values. It analyzes your code and inserts the equivalent of `React.memo`, `useMemo`, and `useCallback` for you, so you get stable references and skipped re-renders **without writing them by hand**.

#### 🤔 Why do we need it? (the problem)
Everything in this module — wrapping children in `memo`, hand-stabilizing every object/function with `useMemo`/`useCallback` — is tedious, easy to get wrong, and clutters code. People over-apply it (memoizing things that were never expensive) or under-apply it (forgetting the one dependency that matters). The compiler's goal: let you write plain, straightforward React and have the optimization applied **correctly and automatically** at build time.

#### ⚙️ How does it work?
It runs as a build step (a Babel plugin) and rewrites your components so values and functions are cached based on what they actually depend on:

```
   Your plain code  -->  React Compiler (build time)  -->  Optimized code
   (no manual memo)        analyzes deps, inserts            (auto-memoized
                           caching automatically)             re-renders skipped)
```

It relies on your code following the **Rules of React** (components and hooks must be pure — Module 4); if they aren't, the compiler safely **skips** optimizing that component rather than breaking it. The practical upshot: in a project using the compiler, manually written `useMemo`, `useCallback`, and `React.memo` become **largely unnecessary** — the compiler does that work.

> **Accuracy / status flag:** the React Compiler is real and shipping, but as of React 19 it's still maturing and is **opt-in** per project. Until it's universally adopted, the manual tools in this module are still the everyday answer — and you must still understand them to reason about re-renders and to read existing codebases.

#### 🌍 Real-life analogy
Manual memoization is like **hand-tuning every gear shift** in a car — possible, but exhausting and easy to miss. The React Compiler is the **automatic transmission**: you just drive (write plain components) and it shifts (memoizes) at the right moments for you. You still need to understand *how gears work* to diagnose problems — but you no longer change them by hand on every trip.

#### 💻 Code example
```jsx
// Without the compiler, you'd hand-write memo + useCallback to stop
// <Row> re-rendering on every parent render:
const Row = React.memo(function Row({ onSelect, item }) {
  return <li onClick={onSelect}>{item.name}</li>;
});

function ListManual({ items }) {
  const handleSelect = useCallback(() => {/* ... */}, []);
  return <ul>{items.map(it =>
    <Row key={it.id} item={it} onSelect={handleSelect} />
  )}</ul>;
}

// WITH the React Compiler enabled, you write the plain version and the
// compiler inserts the equivalent caching for you at build time:
function ListAuto({ items }) {
  function handleSelect() {/* ... */}        // compiler stabilizes this
  return <ul>{items.map(it =>
    <Row key={it.id} item={it} onSelect={handleSelect} />
  )}</ul>;
}
// Same runtime behavior, no manual memo/useCallback written by hand.
```

#### 🎤 Interview question
**Q: What is the React Compiler, and does it make `useMemo`/`useCallback` obsolete?**
A: It's a build-time tool (React 19, formerly "React Forget") that **auto-memoizes** components, values, and functions by analyzing dependencies, inserting the equivalent of `React.memo`/`useMemo`/`useCallback` so you don't have to. Where it's enabled, manual memoization becomes **largely unnecessary**. But it's still maturing and opt-in, it only optimizes code that follows the Rules of React (pure components/hooks), and you still need to understand re-render behavior — both to use the compiler well and to maintain the huge amount of existing code written with manual memoization.

<h2 id="module-13">Module 13 — Server Components & React 19</h2>

For years React lived entirely in the browser: the server sent a near-empty HTML shell, then a big JavaScript bundle rebuilt the whole UI on the user's machine. React 19 changes the *shape* of the question. Now a component can decide to render **only on the server** and ship **zero** JavaScript for itself to the browser — fetching data, reading a database, and using heavy libraries that the user never has to download. This module is about that new server/client split, the directives that draw the line, and the React 19 features that go with it.

---

### 🖥️ React Server Components (RSC) — code that runs on the server and ships no JS

#### 🧩 What is it?
A **React Server Component (RSC)** is a component that runs **only on the server**. It renders to a *description* of UI, and that description is sent to the browser — but the **component's own JavaScript code is never sent to the client**. The browser cannot re-run it, click it back to life, or even know its source. It is, by design, non-interactive on the client.

Glossary for this module: the **client** = the browser running your JavaScript. The **server** = the machine (Node.js, an edge worker) that runs ahead of the browser. **Bundle** = the JavaScript file the browser downloads.

#### 🤔 Why do we need it? (the problem)
In a classic single-page app (**SPA** — the whole UI is built in the browser), *every* component you write becomes JavaScript the user must download, parse, and run. That includes:
- Components that just display static text or a fetched article — purely read-only.
- The big libraries they depend on (a Markdown parser, a date formatter, a syntax highlighter) — shipped to every visitor even though the output never changes after render.
- Data fetching that bounces: browser loads JS, *then* JS asks the server for data, *then* re-renders. Two round trips before the user sees content.

RSC removes all of that for the parts of your UI that don't need interactivity. The work happens once, on the server, close to the data — and only the result travels to the browser.

#### ⚙️ How does it work?
The server runs the RSC, including any `await fetch(...)` or direct database call inside it. It produces a serialized **RSC payload** (covered in its own topic below) describing the output. The browser receives that description and paints it. Crucially, the RSC's *code* never enters the bundle.

```
   CLASSIC SPA              vs       WITH RSC
   ┌──────────┐                      ┌──────────┐
   │ server   │ sends shell+         │ server   │ runs the
   │          │ big JS bundle        │          │ component,
   └────┬─────┘                      │          │ fetches data
        │                            └────┬─────┘
        ▼ browser downloads JS,           │ sends a tiny
   ┌──────────┐ runs it, THEN             ▼ description
   │ browser  │ fetches data,        ┌──────────┐
   │          │ then renders         │ browser  │ paints it.
   └──────────┘                      │          │ No JS for
   2 round trips, big bundle         └──────────┘ this part.
```

Because an RSC runs on the server, it can do server-only things directly: read environment secrets, query a database, hit an internal API — no public endpoint needed.

> **Note (simplification):** RSCs are a feature of frameworks (like Next.js) that wire up the RSC pipeline. You don't get them by importing plain `react` into a script; the framework provides the server runtime, the bundler split, and the streaming transport. The mental model "server-only component" is exact; the plumbing is framework-supplied.

#### 🌍 Real-life analogy
Think of ordering a printed photo. A **client component** is a colouring book mailed to you — you receive the *tools* (page, crayons) and do the colouring yourself at home. An **RSC** is a finished, framed photo: all the printing equipment, ink, and the original negative stayed at the lab. You receive only the final picture. You can't re-print it at home, and you didn't have to own a printer.

#### 💻 Code example
```jsx
// app/article/page.jsx
// No 'use client' at the top → this is a Server Component by default.
// It runs ONLY on the server. Its code is never sent to the browser.

import { db } from '../lib/db';        // a server-only DB client — fine here

export default async function ArticlePage() {
  // Server Components can be async and await directly during render:
  const article = await db.articles.find('react-19');  // direct DB access

  return (
    <article>
      <h1>{article.title}</h1>
      <p>{article.body}</p>
      {/* The db client, the article body, none of this JS ships. */}
    </article>
  );
}
// Output in the browser: the rendered <article> HTML appears,
// but ArticlePage's code and the `db` import are NOT in the bundle.
```

#### 🎤 Interview question
**Q: What problem do Server Components solve?**
A: They let parts of the UI render **only on the server**, shipping **zero JavaScript** for those parts to the client. That shrinks the bundle, keeps heavy dependencies (parsers, formatters, DB clients) off the user's machine, and lets components fetch data directly on the server — close to the data, without a public API or a browser round trip. They are ideal for static, read-only, or data-heavy UI that doesn't need client interactivity.

---

### 🚧 The server/client boundary — `'use client'` draws the line

#### 🧩 What is it?
By default, in an RSC-enabled app, **every component is a Server Component**. To make a component (and the components it imports) run on the **client** — so it can be interactive — you put the directive `'use client'` as the first line of the file. That line marks the **boundary**: that file and the import subtree below it become client code.

#### 🤔 Why do we need it? (the problem)
The server and the browser are two different worlds. The server can read a database; the browser can respond to a click. React needs an explicit way to know **which world each component belongs to** — because anything using `useState`, `useEffect`, `onClick`, or browser APIs *must* run in the browser, while data-fetching, secret-reading components must stay on the server. The `'use client'` directive is that explicit signal.

#### ⚙️ How does it work?
- No directive → **Server Component** (the default).
- `'use client'` at the top of a file → that file is a **Client Component**, and everything it `import`s into that subtree is bundled for the browser too.
- A Server Component **can render** a Client Component (it's allowed to go server → client).
- A Client Component **cannot import** a Server Component directly — but a Server Component can pass one in as `children` or a prop (server → client, again).

```
   SERVER SIDE                  CLIENT BOUNDARY
   ┌─────────────────────┐
   │ <Page>      (server)│
   │  fetches data       │
   │   │                 │
   │   ├─ <Article> srv  │   'use client' marks the line ↓
   │   │                 │   ┌───────────────────────────┐
   │   └─ renders ──────────▶│ <LikeButton> (client)     │
   │                     │   │  useState, onClick — ships │
   └─────────────────────┘   │  JS to the browser         │
                             └───────────────────────────┘
```

The boundary is a *one-way door for code* (server can include client), but data can only flow **into** a client component as serializable props (next topic).

#### 🌍 Real-life analogy
A restaurant has a **kitchen** (server) and a **dining room** (client). The pass-through window is the boundary. Plated food can go from kitchen to table; a diner can't wander into the kitchen and start cooking. `'use client'` is the sign hung on the window that says "everything past here is the dining room — guests interact here."

#### 💻 Code example
```jsx
// components/LikeButton.jsx
'use client';                      // ← the boundary marker, first line

import { useState } from 'react';  // hooks require the client

export default function LikeButton({ initialLikes }) {
  const [likes, setLikes] = useState(initialLikes);
  return (
    <button onClick={() => setLikes((n) => n + 1)}>
      {likes} likes
    </button>
  );
}
// Because of 'use client', this component's JS IS shipped to the
// browser so the onClick can actually run. The server component
// that renders it stays on the server.
```

#### 🎤 Interview question
**Q: In an RSC app, are components server or client by default, and how do you change it?**
A: They're **Server Components by default**. To make a component client-side and interactive, add the `'use client'` directive as the first line of its file. That marks the file and its imported subtree as client code, which gets bundled and shipped to the browser. Hooks like `useState`/`useEffect`, event handlers, and browser APIs all require a `'use client'` component.

### 📦 Serializable props & the RSC payload — what crosses the boundary

#### 🧩 What is it?
When a Server Component renders a Client Component, it can pass **props** down. Those props must be **serializable** — convertible to a flat, transmittable format. Strings, numbers, booleans, `null`, plain objects, arrays, and (with the RSC transport) even JSX and promises can cross. **Functions, class instances, and other non-serializable values cannot.** React turns the whole server render into a serialized **RSC payload** — a streamed description of the output — and sends that to the browser.

#### 🤔 Why do we need it? (the problem)
The server and browser are *separate processes*, often on separate machines. You can't hand a live JavaScript function from one to the other across the network — there's no shared memory. So whatever crosses the boundary has to be packaged into data that survives the trip. A function's *behaviour* can't be packaged; only data can. That's why the rule exists.

#### ⚙️ How does it work?
React renders the server tree and emits the **RSC payload**: a serialized stream that describes the rendered output — the server-produced UI, slots where Client Components go (referenced by which bundle chunk to load), and the props for those client components. The browser reads this stream and stitches it together with the actual client component code. Because it's a **stream**, the browser can start showing finished parts while slower parts (e.g. a pending data fetch behind Suspense) are still arriving.

```
   SERVER renders tree → emits RSC PAYLOAD (a stream)
   ┌──────────────────────────────────────────────┐
   │ "div > h1 'Hello'"            (server output) │
   │ "here: ClientComp #chunk-7"  (which JS chunk) │
   │ "props: { likes: 42 }"       (serializable!)  │
   └───────────────────┬──────────────────────────┘
                       ▼  streamed over the network
   BROWSER reads it, loads chunk-7, fills in props,
   composes server output + client components + Suspense.
```

What can cross (serializable): `string`, `number`, `boolean`, `null`, `undefined`, plain objects/arrays of these, JSX elements, and promises.
What cannot cross: **functions** (e.g. an `onClick` callback), **class instances**, and anything carrying live behaviour. (Plain data — objects, arrays, strings, numbers, and even `Date`/`Map`/`Set`/`BigInt`/typed arrays — *does* serialize across the boundary.) (One special exception: **Server Actions**, covered next, look like functions but are passed as references the client can call back — they're not ordinary functions.)

#### 🌍 Real-life analogy
Sending props across the boundary is like **shipping furniture flat-packed**. A bookshelf (data) flattens into boards and screws and travels fine. But you can't flat-pack a *plumber* (a function — a live skill that does something): you can only ship the *parts*, not the *person who acts*. So data ships; behaviour doesn't.

#### 💻 Code example
```jsx
// app/post/page.jsx  (Server Component — no directive)
import LikeButton from '../../components/LikeButton';  // a 'use client' comp

export default async function PostPage() {
  const res = await fetch('https://api.example.com/post/1');
  const post = await res.json();

  return (
    <section>
      <h2>{post.title}</h2>
      {/* OK: initialLikes is a number → serializable, crosses fine. */}
      <LikeButton initialLikes={post.likes} />

      {/* ❌ Would ERROR: onClick is a function → not serializable.
          <LikeButton onClick={() => save()} /> can't cross the boundary. */}
    </section>
  );
}
```

#### 🎤 Interview question
**Q: What can cross the server/client boundary, and what can't?**
A: Only **serializable** values can cross as props: strings, numbers, booleans, `null`/`undefined`, plain objects and arrays of those, JSX, and promises. **Functions and class instances cannot** — the server and client are separate processes with no shared memory, so React serializes the render into an **RSC payload** (a streamed description), and live behaviour like a callback can't be serialized. The one exception is Server Actions, which are passed as callable references, not as ordinary functions.

---

### ⚡ Server Actions & React 19 — `'use server'`, `use`, and `ref` as a prop

#### 🧩 What is it?
A **Server Action** is a function marked with the `'use server'` directive. It **runs on the server** but can be **called from the client** — for example, passed directly as a form's `action`. When the user submits, React invokes the function on the server. React 19 pairs this with hooks for UI feedback (`useActionState`, `useOptimistic`) and adds other shifts: the **`use`** hook, **`ref` as a regular prop** (no more `forwardRef`), and native **document metadata** support.

#### 🤔 Why do we need it? (the problem)
Before, to run server logic from a click you hand-wrote an API route, a `fetch` call, request/response plumbing, loading state, and error handling — a lot of glue for "save this form." Server Actions collapse that: you write a server function and use it directly. And while it's running, the UI needs to show *pending* and ideally *optimistic* feedback — which the new hooks handle declaratively.

#### ⚙️ How does it work?
- **`'use server'`** marks a function (or a whole file of functions) as a Server Action. React generates a secure reference so the client can call it; the body only ever runs on the server.
- **`useActionState`** wraps an action and gives you back `[state, formAction, isPending]` — current result, the action to attach to a `form`, and a pending flag.
- **`useOptimistic`** lets you show an *expected* result immediately (e.g. the comment appears instantly), then reconciles with the real server result when it returns.
- **`use`** (a hook) unwraps a **promise** or **context** during render; unlike other hooks it may be called conditionally.
- **`ref` as a prop**: in React 19 you can accept `ref` like any normal prop in a function component — `forwardRef` is no longer required.
- **Document metadata**: rendering `<title>`, `<meta>`, or `<link>` anywhere now hoists them into the document `<head>` automatically.

```
   CLIENT (a form)                    SERVER
   ┌────────────────────┐
   │ <form action={save}│  submit
   │   ...fields...      │ ───────────▶  save() runs here
   │ <SubmitButton/>     │             ('use server')
   │  isPending → spinner│ ◀───────────  returns new state
   └────────────────────┘   result      (useActionState updates UI)
```

#### 🌍 Real-life analogy
A Server Action is a **"call" button on a hotel room phone**. You press it in your room (client), but the *action* — someone bringing towels — happens at the front desk (server). You didn't install a switchboard in your room; you just pressed one button. `useActionState`'s pending flag is the little "calling…" light that glows while the desk responds, and `useOptimistic` is you already laying out where the towels will go before they arrive.

#### 💻 Code example
```jsx
// app/comments/actions.js
'use server';                          // every export here is a Server Action

import { db } from '../lib/db';
export async function addComment(prevState, formData) {
  const text = formData.get('text');
  await db.comments.insert({ text }); // runs ONLY on the server
  return { ok: true, text };          // returned state goes back to the client
}
```
```jsx
// app/comments/CommentForm.jsx
'use client';
import { useActionState } from 'react';
import { addComment } from './actions';

export default function CommentForm() {
  // useActionState → [currentState, theFormAction, isPending]
  const [state, formAction, isPending] = useActionState(addComment, null);

  return (
    <form action={formAction}>      {/* the action runs on the server */}
      <input name="text" />
      <button disabled={isPending}>
        {isPending ? 'Saving…' : 'Add comment'}
      </button>
      {state?.ok && <p>Saved: {state.text}</p>}
    </form>
  );
}
```

#### 🎤 Interview question
**Q: What is a Server Action, and how does React 19 help show pending UI for it?**
A: A Server Action is a function marked `'use server'` that runs on the server but is **callable from the client** — often passed straight to a form's `action`. React 19 adds `useActionState`, which wraps the action and returns `[state, formAction, isPending]` so you can show a spinner or disable the button while it runs, plus `useOptimistic` to show the expected result immediately and reconcile when the server responds. (Bonus React 19 shifts: the `use` hook to unwrap promises/context, `ref` as a plain prop instead of `forwardRef`, and automatic document-metadata hoisting.)

### 🔀 RSC vs SSR — they sound the same; they are not

#### 🧩 What is it?
Both **SSR** (Server-Side Rendering) and **RSC** (React Server Components) involve "running React on the server," which is why they get confused. But they do different jobs. **SSR** renders your *client* components to HTML on the server for a fast first paint, then **hydrates** them in the browser so they become interactive. **RSC** components render on the server and **never ship or hydrate at all** — they're not client components pre-rendered; they're server-only by nature.

#### 🤔 Why do we need it? (the problem)
Knowing the difference is the difference between "I made my page server-rendered" and "I removed JavaScript from my page." SSR makes the *first paint* faster but **still ships and hydrates** all that component JS. RSC actually *removes* JS for the server-only parts. They solve different problems and, in modern frameworks, work **together**.

#### ⚙️ How does it work?
- **SSR (the classic flow):** server runs your client components → produces HTML → browser shows it → browser downloads the same components' JS → **hydration**: React attaches event listeners and "wakes up" the static HTML into a live app. The JS *is* shipped; SSR just front-loaded the HTML.
- **RSC:** server runs Server Components → produces the **RSC payload** (a description, not just HTML) → browser composes it with client components. The Server Components' JS is **never shipped**, so there is **nothing to hydrate** for them.

```
   SSR: render client comps → HTML → ship SAME JS → HYDRATE
        ┌──────┐   ┌──────┐   ┌──────────┐   ┌─────────┐
        │server│──▶│ HTML │──▶│ ship JS  │──▶│ hydrate │ interactive
        └──────┘   └──────┘   └──────────┘   └─────────┘
        JS is shipped and re-run in the browser.

   RSC: render server comps → payload → compose. NO hydrate.
        ┌──────┐   ┌─────────┐   ┌──────────────┐
        │server│──▶│ payload │──▶│ compose w/    │ (no JS for
        └──────┘   └─────────┘   │ client comps  │  server comps)
        Server-comp JS NEVER ships → nothing to hydrate.
```

> **Note (they combine):** A real app uses both — RSC for the server-only shell and data, SSR to pre-render the *client* components inside it for a fast first paint, then hydration only for those client parts. "RSC vs SSR" is about *what each does*, not "pick one."

#### 🌍 Real-life analogy
**SSR** is **IKEA shipping a pre-assembled bookshelf**: it arrives looking done (fast first impression), but you still receive the toolkit and have to tighten every screw yourself before you can use it — that screw-tightening is **hydration**. **RSC** is a **printed poster**: it arrives finished, there's nothing to assemble, and no toolkit was shipped with it. One needs assembly in your home; the other never does.

#### 💻 Code example
```jsx
// CONCEPTUAL — the same UI, two boundaries.

// SERVER COMPONENT (RSC): never ships, never hydrates.
async function ProductPage() {
  const product = await fetch('/api/p/1').then((r) => r.json());
  return (
    <main>
      <h1>{product.name}</h1>        {/* server-only, zero JS */}
      <AddToCart id={product.id} />  {/* a client island ↓ */}
    </main>
  );
}

// CLIENT COMPONENT: this one IS sent to the browser & hydrated
// (and, with SSR, its HTML was pre-rendered on the server first).
('use client'); // (directive belongs at top of its own file)
function AddToCart({ id }) {
  // useState/onClick → must run in the browser → ships + hydrates
  return <button onClick={() => addToCart(id)}>Add to cart</button>;
}
// Result: <h1> ships as description only; <AddToCart> ships JS and
// hydrates. RSC removed JS for the heading; SSR/hydration powers
// only the interactive button.
```

#### 🎤 Interview question
**Q: RSC vs SSR — how are they different?**
A: **SSR** renders your *client* components to HTML on the server for a fast first paint, then ships those same components' JavaScript to the browser and **hydrates** them so they become interactive — the JS is still sent. **RSC** components render on the server, produce a serialized payload, and **never ship JavaScript or hydrate at all**; they're server-only by design. SSR is about *when/where the first HTML is produced*; RSC is about *removing client JS entirely* for non-interactive parts. Modern frameworks use both together.

## Conclusion

React is no longer magic. You can trace an update from `setState` through scheduling, the render phase (interruptible, pure), reconciliation over the Fiber tree, and the synchronous commit — and you know *why* hooks must be called in order, *why* render must be pure, and *how* concurrent rendering keeps the main thread responsive by slicing and prioritizing work with lanes.

The architect's edge isn't memorising hook signatures — it's holding the **render → reconcile → commit** loop and the **scheduler + lanes** model in your head, so that re-render bugs, tearing, Suspense behavior, and "why is this slow" all have an obvious place to look.
