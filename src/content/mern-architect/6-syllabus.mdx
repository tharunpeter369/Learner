# State Management & Data Fetching — Architect Level

A first-principles syllabus for the question that derails most front-end architectures: *where does state live, and who owns it?* The central insight is that **"state" is two very different things** — short-lived **client state** you own, and **server state** that's really a cache of data owned elsewhere — and that conflating them is the root of most state-management pain. This module covers the client side (local state, Context, Redux/RTK, atomic stores, state machines) and the server side (the data-fetching problem, TanStack Query, caching/invalidation, normalization, real-time sync), so you can pick the right tool and defend it in a senior/staff/architect interview.

**Legend:** 🎯 = high-frequency interview hotspot · ⚙️ = library/runtime internals · 🧠 = mental-model / architecture depth

**Prerequisites:** Comfortable with React (components, hooks, Context — ideally Module 5 of this path) and async JavaScript (promises, the event loop — Module 1). Some exposure to Redux or a data-fetching library helps.

**Outcome:** Ability to separate client state from server state, choose between local state / Context / Redux / atomic stores / state machines with clear reasoning, explain how these libraries avoid unnecessary re-renders, articulate why server data needs caching/invalidation/sync rather than a store, use TanStack Query (queries, mutations, optimistic updates, invalidation) and normalized caches correctly, and design a coherent state architecture — at an architect's level.

## [Module 0 — Client State vs Server State](?tab=learn#module-0) 🧠🎯
- The single most important distinction: **client state** (UI, owned by you, synchronous) vs **server state** (a *cache* of remote data, owned elsewhere, async, shared, can go stale) 🎯
- Why putting server data in Redux feels wrong: you're hand-rolling a cache
- A third category: **URL state** and **form state**
- The decision lens every later module hangs off of 🧠

**Interview focus:** "What's the difference between client state and server state?", "Why is fetching data into Redux often an anti-pattern?", "Where should a given piece of state live?"

- `useState` vs `useReducer` — when a reducer's explicit transitions win 🎯
- **Colocation**: keep state as close to where it's used as possible
- **Lifting state up** to the nearest common ancestor; the cost
- **Prop drilling**: the problem that motivates Context and stores 🎯
- Derived state vs stored state — don't store what you can compute

## [Module 2 — Context as State (and Its Limits)](?tab=learn#module-2) 🎯⚙️
- Context is **dependency injection**, not a state manager 🧠
- The **re-render problem**: every consumer re-renders when the value changes (identity) 🎯
- Mitigations: memoize the value, **split contexts**, selector libraries (`use-context-selector`)
- When Context is the right tool (low-frequency, app-wide config: theme, auth, locale)
- Why Context doesn't scale to high-frequency state

**Interview focus:** "Why does Context cause extra re-renders, and how do you fix it?", "When is Context the wrong choice?", "Context vs a state library?"

## [Module 3 — Flux & Redux Fundamentals](?tab=learn#module-3) 🎯🧠
- **Unidirectional data flow** (Flux): action → reducer → store → view → action 🎯
- The three principles: single source of truth, state is read-only, changes via pure reducers
- **Actions, reducers, the store**; `dispatch` and subscription
- Why Redux exists: predictable state, time-travel, middleware, devtools
- When you **don't** need Redux (and why it's less default now) 🎯

**Interview focus:** "Explain unidirectional data flow.", "What are actions, reducers, and the store?", "When would you reach for Redux today?"

## [Module 4 — Redux Toolkit in Depth](?tab=learn#module-4) ⚙️🎯
- **Redux Toolkit (RTK)** as the standard: `configureStore`, `createSlice` (reducers + actions together) 🎯
- **Immer** under the hood: "mutating" draft state safely
- **Middleware** and async: `createAsyncThunk`, the thunk middleware
- **Selectors** and memoization with `reselect` (`createSelector`) — avoiding recompute/re-render 🎯
- The store subscription model and how `useSelector` re-renders

**Interview focus:** "How does `createSlice` reduce boilerplate?", "How does RTK let you 'mutate' state?", "What does `createSelector` solve?"

## [Module 5 — Lightweight & Atomic State (Zustand, Jotai, Valtio)](?tab=learn#module-5) ⚙️🎯
- The modern lightweight stores and why they took off (less boilerplate, no provider hell)
- **Zustand**: a tiny store hook built on `useSyncExternalStore`; selecting slices to avoid re-renders 🎯
- **Jotai**: bottom-up **atoms** (composable units of state) — and why atoms avoid the context re-render trap
- **Valtio**: proxy-based mutable state; subscribe to what you read
- How all three integrate with concurrent React via `useSyncExternalStore` ⚙️

**Interview focus:** "Why do Zustand/Jotai avoid Context's re-render problem?", "Store-based vs atomic state — what's the difference?", "What does `useSyncExternalStore` do for these libraries?"

## [Module 6 — State Machines (XState)](?tab=learn#module-6) 🧠
- Modeling state as an explicit **finite state machine**: states, events, transitions 🧠
- Why ad-hoc booleans (`isLoading`, `isError`, `isOpen`) create impossible states
- **Statecharts**: hierarchical/parallel states, guards, actions, context
- When a machine pays for itself (complex flows: wizards, checkout, media players)

## [Module 7 — The Server State Problem](?tab=learn#module-7) 🎯🧠
- Why server data is **fundamentally different**: asynchronous, shared across components, can be stale, must be cached and kept in sync 🎯
- The pains of doing it by hand in `useState` + `useEffect`: loading/error flags everywhere, no caching, no dedup, no background refresh
- Server state is a **cache**, not a source of truth — the reframing that fixes everything 🧠
- Why a dedicated server-state library beats Redux for this

**Interview focus:** "Why is server state different from client state?", "What problems does a data-fetching library solve that `useEffect` doesn't?", "Is your fetched data a source of truth?"

## [Module 10 — TanStack Query: Mutations & Cache Updates](?tab=learn#module-10) 🎯

## [Module 11 — Normalized Caching & RTK Query](?tab=learn#module-11) ⚙️🧠

- The normalization debate: when it's worth the complexity (vs document caching)
- Apollo/GraphQL normalized caches (concept) and cache identity

**Interview focus:** "Document cache vs normalized cache?", "How does RTK Query's tag invalidation work?", "When is normalization worth it?"
