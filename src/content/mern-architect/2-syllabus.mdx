# TypeScript Mastery — Architect Level

A deep, type-system-up syllabus for engineers who must reason about *why* TypeScript infers what it does, model complex domains in types, push back on `any`, and defend their type architecture in senior/staff/architect interviews. TypeScript is treated here not as "JavaScript with annotations" but as a **structural type system and a compiler** with its own semantics.

**Legend:** 🎯 = high-frequency interview hotspot · ⚙️ = compiler / tooling internals · 🧠 = type-level / mental-model depth

**Prerequisites:** Comfortable writing production JavaScript (closures, `this`, prototypes, async, modules — ideally Module 1 of this path), able to read ES2015+ syntax, and some prior exposure to typed code (TS, Flow, or a statically-typed language).

**Outcome:** Ability to explain how the type system models values as sets, drive and debug inference, build reusable type-level utilities (conditional, mapped, template-literal types), design type-safe public APIs and runtime boundaries, configure `tsconfig` strictness deliberately, reason about the compiler/emit pipeline and type-check performance, and lead a JavaScript-to-TypeScript migration — articulating the trade-offs at the level expected of an architect.

## [Module 0 — How to Think in Types](?tab=learn#module-0) 🧠
- TypeScript is a **structural** type system: compatibility is by shape, not by name (vs nominal typing in Java/C#)
- **Types are sets of values**: `string` is "all strings", a union is set union, `never` is the empty set, `unknown` is the universal set
- The two worlds: **type space vs value space** — what exists at compile time vs runtime, and why a name can mean different things in each
- **Type erasure**: types vanish during compilation — TypeScript guarantees *nothing* at runtime
- The compiler's job: **type-check** *and* **emit/downlevel** are separate concerns; type errors don't (by default) stop emit
- Soundness vs convenience: TS is deliberately **unsound** in places (it trades a few holes for productivity) 🧠

**Interview focus:** "What is structural typing and how does it differ from nominal?", "Why can't TypeScript catch a wrong API response shape at runtime?", "Is TypeScript sound? Give an example where it isn't."

- Type assertions (`as`), `as const`, non-null assertion (`!`), and when each is a code smell
- Array, tuple, readonly tuple, and named tuple members

**Interview focus:** "`any` vs `unknown` — when do you use each?", "`type` vs `interface` — which and why?", "What does `as const` actually do?"

## [Module 11 — Runtime Validation & The Type Boundary](?tab=learn#module-11) 🎯

## High-Yield Interview Question Bank (by theme) 🎯

**Mental model / explain it**
- Structural vs nominal typing; where TS is deliberately unsound
- `any` vs `unknown` vs `never`; types as sets of values
- Type space vs value space; why types are erased at runtime
- Covariance / contravariance / bivariance with concrete examples
- `as` vs `satisfies`; literal widening and `as const`

**Implement from scratch (type-level)**
- `Pick`, `Omit`, `Partial`, `Required`, `Readonly`, `Record`
- `ReturnType`, `Parameters`, `Awaited`, `NonNullable`
- `DeepPartial` / `DeepReadonly` (recursive mapped types)
- A `infer`-based conditional (e.g. `UnwrapPromise`, `First<T>`, `Last<T>`)
- Template-literal types (e.g. `CamelCase`, `PathOf<T>`)

**Model it**
- A discriminated union for an async result / state machine
- Branded types for IDs / validated input
- A typed event emitter with per-event payloads
- "Make illegal states unrepresentable" for a real domain (form, order, connection)

**Tooling / architecture**
- Add types to an untyped npm package (`declare module` / `@types`)
- Choose and justify a `tsconfig` strictness baseline
- Validate untrusted input at the boundary (Zod + `z.infer`)
- Speed up a slow `tsc` build; explain `tsc` vs esbuild/swc
- Plan a gradual JS → TS migration with ratcheting strictness
