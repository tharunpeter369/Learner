# State Management & Data Fetching

"Where should this state live?" is the question that quietly decides whether a front-end stays maintainable or collapses into a tangle of providers and `useEffect` fetches. The breakthrough is realizing that **"state" is two different things**: short-lived **client state** you own, and **server state** that's really a *cache* of data owned elsewhere — and that most state-management pain comes from treating them the same. This module gives you the mental model and the toolbox: local state, Context, Redux, atomic stores, and state machines on the client; the data-fetching problem, TanStack Query, caching, and real-time sync on the server.

---

<h2 id="module-0">Module 0 — Client State vs Server State</h2>

Every painful state-management decision starts with one question almost nobody asks out loud: *is this state actually mine, or is it a copy of something that lives on a server?* Get this one distinction right and most of the "which library do I use?" arguments quietly answer themselves.

---

### 🧠 Client State — The State You Actually Own

#### 🧩 What is it?
**Client state** is data that is *born* in your app and *lives* in your app — in memory, in the browser. You created it, you own it, and nobody else has a copy. Think: is a dropdown open or closed, which tab is selected, the half-typed text in a form, the chosen theme (light/dark). It's **synchronous** — glossary: it exists *right now*, you never have to "wait" for it.

#### 🤔 Why do we need it? (the problem)
Without a name for this category, beginners treat *all* state the same way and reach for heavy tools (a global store) to remember something as trivial as "this menu is open." Naming client state lets you say: this is mine, it's tiny, it's local, it doesn't need fetching, caching, or syncing — keep it simple.

#### ⚙️ How does it work?
Client state lives in a plain variable the UI library watches — in React that's usually `useState` or `useReducer`. When you change it, the component re-renders. There's no network, no waiting, no "is it fresh?" question. It is the single source of truth for itself: what's in memory *is* the answer.

```
   CLIENT STATE  (you own the original)
   ┌───────────────────────────────────┐
   │  isMenuOpen = true                │
   │  selectedTab = "billing"          │
   │  formDraft  = "hello wor..."      │
   │  theme      = "dark"              │
   └───────────────────────────────────┘
     • synchronous  • in memory  • yours
     • no server has a copy of this
```

#### 🌍 Real-life analogy
Client state is the **sticky note on your own desk**. You wrote it, it's in front of you, and reading it is instant — you just look. Nobody else has that note, so it can never be "out of date" with someone else's version. When you toss it, it's gone.

#### 💻 Code example
```javascript
// Pure client state: owned, synchronous, lives in memory.
const [isOpen, setIsOpen] = useState(false);   // is the menu open?
const [tab, setTab]       = useState("profile"); // which tab is selected?

// Changing it is instant — no awaiting, no network.
setIsOpen(true);   // menu opens on the next render. Done.
```

#### 🎤 Interview question
**Q: What makes a piece of state "client state"?**
A: You **own** it and it's **synchronous** — it originates in the app, lives in memory, and no server holds the authoritative copy. UI concerns like open/closed, selected tab, or a form draft are classic examples. Because nobody else has it, it can't go "stale," so it needs no caching or syncing — plain `useState`/`useReducer` is enough.

### 🌐 Server State — A Cache of Data You Don't Own

#### 🧩 What is it?
**Server state** is data that *actually lives on a server* (in a database), and your app only holds a **copy** of it — a snapshot you fetched a moment ago. The user list, a product, a list of todos: the real version is on the server, and what you have is a cache. Glossary: a **cache** is a local copy of remote data kept around so you don't have to re-fetch it every time.

#### 🤔 Why do we need it? (the problem)
Because a copy can be **wrong**. The instant you fetch the todo list, someone else could add a todo — now your copy is **stale** (glossary: *stale* = out of date compared to the real server version). Server state is **asynchronous** (you must *wait* for the network), **shared** across many components (the same user list shows in three places), and **stale-able**. Pretending it's just like client state is the root cause of most data bugs.

#### ⚙️ How does it work?
You don't *own* server state; you **borrow and refresh** it. The lifecycle is: request it (and wait), receive a copy, *use* the copy, and accept it may drift from the truth — so you re-fetch ("revalidate") on triggers like re-opening the page. The server stays the single source of truth; your cache just tries to stay close to it.

```
   SERVER (the real source of truth)
   ┌─────────────────────────────┐
   │  todos: [A, B, C, D]  ← real│
   └──────────────┬──────────────┘
        fetch ()  │  (async — you WAIT)
                  ▼
   YOUR APP holds only a COPY (a cache)
   ┌─────────────────────────────┐
   │  todos: [A, B, C]   ← stale!│
   └─────────────────────────────┘
     someone added D on the server;
     your copy hasn't caught up yet.
```

#### 🌍 Real-life analogy
Server state is a **printed bank statement**. The bank holds your real balance; the paper is a snapshot from the moment it printed. Spend money after printing and the paper is now wrong — *stale*. You don't "edit the paper" to change your balance; you go back to the bank (re-fetch) for a fresh statement. The paper is a cache; the bank is the source of truth.

#### 💻 Code example
```javascript
// Server state lives elsewhere; you only ever hold a COPY.
// fetch() is async — note the await. The result can be stale.
const res   = await fetch("/api/todos");
const todos = await res.json();   // a snapshot of the SERVER's list

// The moment this line runs, the server could already differ.
// To stay correct you must RE-FETCH later (revalidate) —
// you can't just trust the copy forever.
```

#### 🎤 Interview question
**Q: How is server state different from client state?**
A: Server state is a **cache** of data owned elsewhere, so it is **asynchronous** (you fetch and wait), **shared** across components, and can go **stale** the instant after you fetch it. Client state is **owned and synchronous** — it lives in memory and can't be out of date with anyone. The reframing that matters: your fetched data is a *cache*, not the source of truth; the server is.

### 🚫 Why Dumping Server Data in Redux/`useState` Is an Anti-Pattern

#### 🧩 What is it?
The anti-pattern: fetching server data and shoving the result into a plain store (`useState`, or a global store like Redux) as if it were client state — then managing everything by hand.

#### 🤔 Why do we need it? (the problem)
Because the moment you do that, you've signed up to **hand-roll a cache** — and a cache is hard. A store like `useState`/Redux is a great box for state you *own*, but it has zero built-in idea of "fresh vs stale," "is a request in flight," or "re-fetch in the background." So you end up re-inventing all of it, badly:

```
   What a cache must do      Doing it by hand in Redux/useState
   ──────────────────────    ──────────────────────────────────
   loading / error flags  →  isLoading, isError in every slice
   re-fetch when stale    →  manual refetch() calls everywhere
   dedupe same request    →  (usually skipped → double fetches)
   background refresh      →  hand-written, often forgotten
   keep N views in sync   →  copy-paste the fetch in each place
```

#### ⚙️ How does it work?
A purpose-built **server-state library** (TanStack Query v5, or RTK Query — mentioned conceptually) treats the data as what it is: a cache keyed by a query key. It gives you loading/error states, automatic de-duplication of identical in-flight requests, background re-fetching, and one shared cache so every component sees the same fresh copy — for free. You describe *what* to fetch; it owns the caching.

> **Note (simplification):** Redux/`useState` aren't "bad" — they're excellent for *client* state. The anti-pattern is specifically using them as a **cache for server data**, where their lack of caching features forces you to rebuild a worse version by hand.

#### 🌍 Real-life analogy
It's like running a **library with no librarian**. Every patron who wants a book walks to the publisher to print a fresh copy (no caching), two people asking for the same book trigger two print jobs (no dedup), and nobody notices when a new edition comes out (no background refresh). A server-state library *is* the librarian: one shelved copy, shared by all, quietly restocked when it gets old.

#### 💻 Code example
```javascript
// ❌ Server data hand-rolled as client state (you build the cache yourself)
const [todos, setTodos]       = useState([]);
const [isLoading, setLoading] = useState(false);
const [error, setError]       = useState(null);
useEffect(() => {
  setLoading(true);
  fetch("/api/todos")
    .then(r => r.json())
    .then(setTodos)
    .catch(setError)
    .finally(() => setLoading(false));
  // no dedup, no background refresh, stale forever unless YOU refetch
}, []);

// ✅ The IDEA of a query: declare what to fetch; the library owns the cache.
// (TanStack Query v5 — conceptual; covered in depth in later modules)
const { data: todos, isLoading, error } = useQuery({
  queryKey: ["todos"],          // the cache key (shared across the app)
  queryFn: () => fetch("/api/todos").then(r => r.json()),
});
// caching, dedup, loading/error, and background refetch: handled for you.
```

#### 🎤 Interview question
**Q: Why is fetching data into Redux often an anti-pattern?**
A: Because server data is a **cache**, and Redux/`useState` give you no caching features — so you end up hand-rolling loading/error flags, manual re-fetching, request de-duplication, and background refresh in every slice, usually incompletely. A dedicated server-state library (TanStack Query, RTK Query) provides all of that out of the box. Redux is still great — for the **client** state it was designed for.

### 🗺️ Two More Categories — URL State & Form State

#### 🧩 What is it?
Not everything is "client vs server." Two important sub-categories deserve their own home:
- **URL state** — data that belongs *in the address bar*: filters, search terms, the current page number, the selected tab. The URL itself is the store.
- **Form state** — the values, validation errors, "touched/dirty" flags, and submission status of a form. It's its own discipline (often handled by tools like React Hook Form — conceptual).

#### 🤔 Why do we need it? (the problem)
If a filter or page number lives only in `useState`, then refreshing the page or sharing the link **loses it** — the other person sees a different view. Things people expect to bookmark, share, or reach with the back button belong in the **URL**, not in memory. And forms have so many moving parts (per-field errors, dirty tracking, submit state) that treating them as ordinary client state gets messy fast — hence their own category.

#### ⚙️ How does it work?
URL state is read from and written to the address bar (query string), so a link *is* the state:

```
   /products?category=shoes&page=2&sort=price
              └───┬────┘    └─┬─┘  └──┬───┘
              URL state — shareable, bookmarkable,
              survives refresh, works with Back button
```
Form state is held while the user edits, validated as they go, and resolved on submit — distinct from both "UI I own forever" and "a cache of the server."

#### 🌍 Real-life analogy
**URL state** is the **page number you write in a shared book** — anyone who picks up the book (opens the link) lands exactly where you were; the location travels *with* the book. **Form state** is a **half-filled paper form on a clipboard**: scribbled answers, little "required!" notes in the margins, not yet handed in — a self-contained thing with its own rules.

#### 💻 Code example
```javascript
// URL state — the filter lives in the address bar, not just memory.
// Share /products?category=shoes&page=2 and the view is reproduced exactly.
const params   = new URLSearchParams(window.location.search);
const category = params.get("category");  // "shoes"
const page     = Number(params.get("page") ?? 1); // survives refresh & sharing

// Form state — its own category: values + errors + status, not server data.
const [values, setValues] = useState({ email: "", password: "" });
const [errors, setErrors] = useState({});      // per-field validation
const [status, setStatus] = useState("idle");  // idle | submitting | done
```

#### 🎤 Interview question
**Q: Where should a piece of state live?**
A: Run it through a lens. Is it shareable/bookmarkable (filters, pagination, current tab)? → **URL state**. Is it the live contents of a form (values, errors, submit status)? → **Form state**. Is it a copy of data from a server (lists, records)? → **server state**, in a cache (TanStack Query / RTK Query). Is it UI you own that nobody else has (open/closed, theme)? → **client state**, in `useState`/`useReducer`. Picking the wrong home is the source of most state pain — and this lens is the decision framework the rest of the module builds on.

<h2 id="module-1">Module 1 — Local State & Lifting</h2>

Before you reach for Context, Redux, or any fancy store, almost every UI begins with the humblest tool in React: a single component holding its own state with `useState`. The hard part isn't the syntax — it's the *placement*. Where should a piece of state live? Who owns it? Should you even store it at all, or can you compute it on the fly? Get these answers right and most "I need a state library" problems quietly disappear.

---

### 🎚️ `useState` vs `useReducer` — two ways to hold state, one big decision

#### 🧩 What is it?
Both `useState` and `useReducer` are React hooks that give a component **state** — a value that survives between renders and, when changed, tells React to re-render. `useState` gives you a value plus a setter. `useReducer` gives you a value plus a `dispatch` function that sends **named actions** to a single **reducer** — a pure function that takes the current state and an action and returns the next state.

#### 🤔 Why do we need it? (the problem)
`useState` is perfect for small, independent values: a toggle, an input string, a counter. But it gets messy when:
- the **next state depends on the previous** one in non-trivial ways,
- **several sub-values change together** (and must stay consistent), or
- you have **many different ways** to update the same state and you keep scattering `setX(...)` calls all over your component.

When that happens, your update logic is smeared across click handlers, effects, and callbacks — hard to read, hard to test, hard to trace. `useReducer` fixes this by **centralizing every transition** in one place with explicit, named action types.

#### ⚙️ How does it work?
With `useReducer`, all state changes flow through one funnel. A component **dispatches an action** (just an object describing *what happened*, like `{ type: 'increment' }`), and the **reducer** decides *how the state changes*:

```
  component                 reducer                 React
  ─────────                 ───────                 ─────
  dispatch({type:'inc'}) ─▶ (state, action) ─▶ next ─▶ re-render
                            switch on type:
                              'inc' → count+1
                              'reset' → 0
```

- The reducer is a **pure function**: same inputs → same output, no side effects. That makes it trivial to unit-test in isolation.
- Every way the state can change is a labelled `case` in one `switch` — so you can read the whole "state machine" of the component top to bottom.
- `dispatch` has a **stable identity** (React guarantees it doesn't change between renders), which is handy when passing it down to children.

A useful rule of thumb: reach for `useReducer` when you find yourself calling several related `setState`s together, or when the next value is computed from the previous in a way you'd want to name (`'increment'`, `'addItem'`, `'submitFailed'`).

#### 🌍 Real-life analogy
`useState` is a **light switch** — flip it directly, on or off. `useReducer` is a **front desk at a hotel**: you don't walk into the back office and rearrange the room assignments yourself. You hand the receptionist a **request slip** ("check in guest", "cancel booking"), and the receptionist — following one fixed rulebook (the reducer) — updates the records consistently. Every change goes through the same desk, so the books never disagree with themselves.

#### 💻 Code example
The **same counter logic**, written both ways. Notice how `useReducer` names each transition and gathers them in one place.

```javascript
import { useState, useReducer } from 'react';

// ── With useState: fine for simple, independent updates ──
function CounterState() {
  const [count, setCount] = useState(0);
  // Use the updater form so the next value is based on the previous one:
  return (
    // (JSX shown as a comment to keep this snippet framework-agnostic)
    // <button onClick={() => setCount(c => c + 1)}>{count}</button>
    count
  );
}

// ── With useReducer: explicit, named, testable transitions ──
// The reducer is a PURE function — easy to test without rendering anything.
function counterReducer(state, action) {
  switch (action.type) {
    case 'increment': return { count: state.count + 1 };
    case 'decrement': return { count: state.count - 1 };
    case 'incrementBy': return { count: state.count + action.amount };
    case 'reset': return { count: 0 };
    default: return state; // unknown action → no change
  }
}

function CounterReducer() {
  const [state, dispatch] = useReducer(counterReducer, { count: 0 });
  // dispatch({ type: 'increment' })       → state.count + 1
  // dispatch({ type: 'incrementBy', amount: 5 }) → state.count + 5
  // dispatch({ type: 'reset' })           → 0
  return state.count;
}

// You can test the reducer with zero React involved:
counterReducer({ count: 2 }, { type: 'increment' }); // → { count: 3 }
counterReducer({ count: 9 }, { type: 'reset' });     // → { count: 0 }
```

#### 🎤 Interview question
**Q: When would you choose `useReducer` over `useState`?**
A: When state transitions get complex: the next state depends on the previous, multiple related sub-values change together, or there are many distinct update paths. `useReducer` **centralizes all transition logic** in one pure reducer function with named actions, which makes the logic easier to read, trace, and unit-test in isolation. `useState` is better for simple, independent values where a reducer would just be ceremony.

### 📍 Colocation — keep state where it's used

#### 🧩 What is it?
**Colocation** means putting state as **close as possible** to the component that actually uses it — ideally *inside* that component — instead of hoisting it up to some far-away parent "just in case."

#### 🤔 Why do we need it? (the problem)
Beginners often park all their state at the top of the app, like a junk drawer, and pass it down everywhere. The result: a tiny change to one input re-renders huge swaths of the tree, the top component balloons into an unreadable mess, and it becomes impossible to tell which state belongs to which feature. Colocation keeps each piece of state owned by the smallest component that needs it, so code stays readable and re-renders stay local.

#### ⚙️ How does it work?
The mechanism is simply *where you call the hook*. State lives in the component that declares it; when it changes, **only that component and its children re-render** (not its parents or siblings). So pushing state **down** shrinks the re-render blast radius.

```
  ❌ hoisted needlessly        ✅ colocated
  ─────────────────────        ──────────────
  App  (holds searchText)      App
   ├─ Header                    ├─ Header
   └─ Sidebar                   └─ Sidebar (holds searchText)
       └─ Search                    └─ Search
  typing re-renders App         typing re-renders only Sidebar
  → Header re-renders too        → Header untouched
```

The guideline: **only lift state as high as it genuinely needs to go — and no higher.**

#### 🌍 Real-life analogy
Keep the **TV remote in the living room**, where you watch TV — not locked in a safe in the basement that everyone has to trek to. Tools live where they're used. Moving the remote to the basement "so it's central" just makes every channel change a hassle for the whole house.

#### 💻 Code example
```javascript
// ❌ Needlessly hoisted: App owns state only <Search> cares about.
function App() {
  const [query, setQuery] = useState(''); // typing re-renders ALL of App
  // ...passes query + setQuery down through Sidebar to Search...
}

// ✅ Colocated: the state lives inside the component that uses it.
function Search() {
  const [query, setQuery] = useState(''); // typing re-renders only Search
  // setQuery(e.target.value) on input change
  return query;
}
```

#### 🎤 Interview question
**Q: What does "colocate state" mean and why is it good?**
A: It means declaring state in the smallest component that uses it rather than hoisting it up the tree. Benefits: re-renders stay local (only that subtree updates), the code is easier to read and reason about, and you avoid bloating parent components. You lift state up *only* when something above genuinely needs to share it.

### ⬆️ Lifting State Up — sharing between siblings

#### 🧩 What is it?
**Lifting state up** means moving a piece of state out of a child and into the **nearest common ancestor** of every component that needs it — then passing the value down as props and passing changes back up via callback props.

#### 🤔 Why do we need it? (the problem)
Two sibling components can't see each other's state — a sibling is neither a parent nor a child, so there's no prop path between them. If a `FahrenheitInput` and a `CelsiusInput` must stay in sync, neither can own the temperature alone. The fix: move the shared state **up** to the parent that contains both, making the parent the single source of truth. The children become "controlled" — they receive the value and report changes upward.

#### ⚙️ How does it work?
Find the lowest component that is an ancestor of **all** the components that need the state. Put the state there. Pass the value **down** as a prop and pass a setter/callback **down** so children can request changes.

```
            ┌──────────────┐
            │   Parent     │  ← owns `temp` (the shared state)
            │ value=temp   │
            └──────┬───────┘
        value+onChange     value+onChange
          ┌────────┴───┐   ┌───┴─────────┐
          │  Celsius   │   │ Fahrenheit  │  siblings stay in sync
          └────────────┘   └─────────────┘
```

**The cost (say this in an interview):** the state now lives in the parent, so **every change re-renders the parent** — and therefore *all* of its children, not just the ones that care. Lifting trades locality for sharing. Lift only as high as needed; lifting *too* high is exactly the over-hoisting that colocation warns against, and it's what eventually pushes teams toward Context or a store.

#### 🌍 Real-life analogy
Two kids arguing over **one TV remote** can't resolve it between themselves. The parent takes the remote (the shared state), and now both kids ask the parent to change the channel. There's one source of truth — but every request goes through the parent, who's now busier (re-renders more).

#### 💻 Code example
```javascript
// Parent owns the shared value; siblings are "controlled" by it.
function Converter() {
  const [celsius, setCelsius] = useState(0); // lifted to the common ancestor

  // Both children read `celsius` and report changes up via onChange.
  // <CelsiusInput   value={celsius} onChange={setCelsius} />
  // <FahrenheitView value={celsius} />   // stays in sync automatically
  // NOTE: any setCelsius() re-renders Converter AND both children.
  return celsius;
}

// A child receives the value down and sends changes up — it owns nothing.
function CelsiusInput({ value, onChange }) {
  // onChange(Number(e.target.value))  // asks the parent to update
  return value;
}
```

#### 🎤 Interview question
**Q: What does "lifting state up" mean, and what's the downside?**
A: It's moving shared state into the nearest common ancestor of the components that need it, then passing the value down as props and changes back up via callbacks — giving you one source of truth. The downside is that the common ancestor now re-renders on every change, which re-renders its whole subtree, not just the interested children. So you lift only as high as necessary; lifting needlessly hurts performance and readability.

### 🪛 Prop Drilling — the pain that motivates Context

#### 🧩 What is it?
**Prop drilling** is passing a prop down through **many intermediate components that don't actually use it** — they just forward it along — purely to get it from where it lives to a deeply nested component that needs it.

#### 🤔 Why do we need to know it? (the problem)
Lifting state up is great for siblings a level or two apart. But when the consumer is buried *many* levels deep, lifting forces the value through every component in between. Those middle components gain props they don't care about, their signatures get noisy, and refactoring one prop means editing a whole chain of files. It's tedious and brittle — and it's the exact pain that **Context** and **stores** exist to solve (covered in the next modules).

#### ⚙️ How does it work?
The value has to travel the prop "pipe" because props only flow **parent → child**. There's no shortcut: every link in the chain must accept and re-pass it.

```
  App (has `user`)
   └─ Layout      ← gets user, doesn't use it, passes down
       └─ Page    ← gets user, doesn't use it, passes down
           └─ Sidebar  ← gets user, doesn't use it, passes down
               └─ Avatar  ← FINALLY uses user.name
  4 components touch `user`; only 1 needs it.
```

Context (next module) lets the deep `Avatar` read `user` **directly** from a shared provider, so the middle components never see it. That's the motivation — not that prop drilling is *wrong*, but that it doesn't scale to deep trees.

#### 🌍 Real-life analogy
It's a **bucket brigade** to put out a fire: ten people stand in a line passing one bucket hand to hand, even though only the last person actually throws the water. Everyone in the middle is just a relay. A hose (Context) would let the water reach the fire directly without ten people holding buckets.

#### 💻 Code example
```javascript
// ❌ Prop drilling: `user` is threaded through components that ignore it.
function App() {
  const [user] = useState({ name: 'Ada' });
  // <Layout user={user} />
  return user;
}
function Layout({ user }) {  /* doesn't use user */  return user; } // just forwards
function Page({ user })   {  /* doesn't use user */  return user; } // just forwards
function Sidebar({ user }) { /* doesn't use user */  return user; } // just forwards
function Avatar({ user })  { return user.name; }  // ✅ the ONLY real consumer

// The fix (preview of Module 2): a Context lets <Avatar> read `user`
// directly, so Layout/Page/Sidebar never need to know about it.
```

#### 🎤 Interview question
**Q: What is prop drilling and how do you avoid it?**
A: Prop drilling is passing a prop through many intermediate components that don't use it, just to reach a deeply nested consumer. It clutters component signatures and makes refactors painful. You avoid it by **lifting state only as far as needed** plus, for app-wide or deeply shared values, using **Context** (dependency injection) or a state store so the consumer reads the value directly instead of receiving it through a long prop chain. Component **composition** (passing JSX as `children`) can also sidestep it.

### 🧮 Derived vs Stored State — compute, don't duplicate

#### 🧩 What is it?
**Stored state** is a value you keep in `useState`/`useReducer` and update by hand. **Derived state** is a value you **compute from existing state or props during render** — you don't store it at all, you calculate it fresh each time the component runs. The rule: *store the minimum; derive the rest.*

#### 🤔 Why do we need it? (the problem)
A classic beginner bug: you have a `todos` array in state, and you *also* store `completedCount` in state. Now every place that changes `todos` must **remember** to update `completedCount` too. Miss one spot and the two disagree — the count says 3 but the list shows 4 done. Stored derived state can silently go **out of sync** with its source. If a value can be computed from what you already have, computing it during render means it's **always correct by construction** — there's nothing to keep in sync.

#### ⚙️ How does it work?
React re-runs your component function on every render. So any plain calculation inside the function is automatically up to date with the latest state and props — no extra state, no effect, no manual syncing needed.

```
  STORE the source of truth        DERIVE everything else
  ──────────────────────────       ─────────────────────────
  todos  (in state)  ───────────▶  completedCount = todos.filter(done).length
                                   remaining      = todos.length - completedCount
                                   allDone        = remaining === 0
  one update to `todos`            ...recomputed automatically, never stale
```

Only reach for stored state (or memoization like `useMemo`) when the computation is genuinely expensive — and even then, you memoize the derived value; you don't store a separate copy you must update.

#### 🌍 Real-life analogy
Your bank shows a **balance**, but it doesn't store the balance as a number someone edits by hand every transaction — it **derives** it by summing your deposits and withdrawals. If a clerk kept a separate sticky note of "current balance" and updated it manually, sooner or later the note and the ledger would disagree. The ledger is the source of truth; the balance is derived from it.

#### 💻 Code example
```javascript
// ❌ WRONG — storing derived state. Two sources of truth that drift apart.
function TodoListWrong() {
  const [todos, setTodos] = useState([
    { text: 'A', done: true }, { text: 'B', done: false },
  ]);
  const [completedCount, setCompletedCount] = useState(1); // ❌ duplicated!

  function toggle(i) {
    const next = todos.map((t, idx) =>
      idx === i ? { ...t, done: !t.done } : t);
    setTodos(next);
    // ❌ Easy to forget this line — then the count is wrong forever:
    setCompletedCount(next.filter(t => t.done).length);
  }
  return completedCount;
}

// ✅ RIGHT — derive during render. Impossible to be out of sync.
function TodoListRight() {
  const [todos, setTodos] = useState([
    { text: 'A', done: true }, { text: 'B', done: false },
  ]);
  // Computed fresh every render from the single source of truth:
  const completedCount = todos.filter(t => t.done).length; // ✅ always correct
  const remaining = todos.length - completedCount;

  function toggle(i) {
    setTodos(todos.map((t, idx) =>
      idx === i ? { ...t, done: !t.done } : t)); // only the source changes
  }
  return { completedCount, remaining };
}
```

#### 🎤 Interview question
**Q: Should you store derived values in state?**
A: No — by default, compute them from existing state/props **during render** instead. Storing a derived value creates a second source of truth that can drift out of sync with its source, and forces you to remember to update it everywhere the source changes. Computing it on render keeps it correct by construction. The only exception is a genuinely expensive computation, which you wrap in `useMemo` — but you still derive it, you don't keep a separate, manually-updated copy.

<h2 id="module-2">Module 2 — Context as State (and Its Limits)</h2>

React's **Context** is the feature everyone reaches for the moment they're tired of passing props down five levels. But here's the trap that derails interviews and apps alike: Context is *not* a state manager. It's a delivery pipe. Treat it like a store and a single click can re-render your entire screen. Let's see exactly why — and how the pros tame it.

---

### 📦 Context Is Dependency Injection — A Pipe, Not a Store

#### 🧩 What is it?
**Context** is React's built-in way to make a value available to a deep part of your component tree *without* threading it through every component in between as a prop. You wrap a section of the tree in a **Provider**, hand it a `value`, and any component inside — no matter how deep — can read that value with `useContext`.

The key idea: Context is **dependency injection** — a fancy term for "hand a deeply-nested thing the value it needs, instead of making everyone above it pass it down." Context **injects** the dependency for you.

#### 🤔 Why do we need it? (the problem)
Without Context you get **prop drilling**: a value the top of your app owns (say, the logged-in user) has to be passed as a prop through `Layout` → `Sidebar` → `Menu` → `Avatar`, even though only `Avatar` actually uses it. Every component in the chain becomes a middleman that knows about a prop it doesn't care about. Add a second such value and the noise doubles.

Context cuts out the middlemen: the value travels *invisibly* from Provider straight to the consumer that wants it.

#### ⚙️ How does it work?
A Provider sits at some level of the tree and publishes a `value`. Any descendant that calls `useContext` subscribes to it and gets the value directly — the components in between are skipped entirely.

```
   PROP DRILLING (the pain)      CONTEXT (injection)
   ┌──────────┐                  ┌── Provider (value) ──┐
   │  App     │ user prop        │  App                 │
   │   │      │                  │   │                  │
   │ Layout   │ user prop        │ Layout               │
   │   │      │                  │   │   (knows nothing)│
   │ Sidebar  │ user prop        │ Sidebar              │
   │   │      │                  │   │                  │
   │ Avatar ◀─┘ finally uses it  │ Avatar ◀── useContext│
   └──────────┘                  └──────────────────────┘
```

The crucial thing a beginner must internalize: **Context does not store state and does not optimize anything by itself.** It holds whatever `value` you give it for *this render* and passes it along. The actual state still lives in a `useState` or `useReducer` somewhere — usually right beside the Provider. Context is just the *pipe* the value flows through.

> **Flag (common misconception):** People say "I'll put it in Context" as if Context were a database. It isn't. It has no internal store, no caching, no change-detection on individual fields. It's a wire. The state lives in a hook; Context only carries it.

#### 🌍 Real-life analogy
Context is the **building's plumbing**, not the water tank. The tank (your `useState`) holds the water (the state). The pipes (Context) carry it to whichever apartment opens a tap (`useContext`), so you don't have to walk a bucket up every staircase (prop drilling). The pipes themselves store nothing — yank the tank out and the pipes are just empty tubes.

#### 💻 Code example
```jsx
import { createContext, useContext, useState } from "react";

// 1. Create the pipe.
const UserContext = createContext(null);

function App() {
  // 2. The REAL state lives here, in a normal hook.
  const [user] = useState({ name: "Ada" });

  // 3. Provider pushes the value into the pipe.
  return (
    <UserContext.Provider value={user}>
      <Layout />
    </UserContext.Provider>
  );
}

// Layout and Sidebar pass NOTHING down — no prop drilling.
function Layout()  { return <Sidebar />; }
function Sidebar() { return <Avatar />; }

// 4. The deep consumer pulls the value straight out of the pipe.
function Avatar() {
  const user = useContext(UserContext); // { name: "Ada" }
  return <span>Hi, {user.name}</span>;  // renders: Hi, Ada
}
```

#### 🎤 Interview question
**Q: Is React Context a state management solution?**
A: No — Context is **dependency injection**, a transport mechanism for passing a value deep into the tree without prop drilling. It doesn't store state, cache it, or prevent re-renders on its own. The state itself lives in a `useState`/`useReducer` (or an external store); Context only delivers whatever value you currently hand the Provider. Calling it a "state manager" is a common but inaccurate shorthand.

---

### 🔁 The Re-Render Problem — One Change, Everybody Re-Renders

#### 🧩 What is it?
When the Provider's `value` **changes identity**, **every** component that consumes that context re-renders — *even consumers that only read a field which didn't change.* This is the single most important fact about Context's performance, and the most common reason a Context-heavy app feels slow.

"Changes identity" means: React compares the new `value` to the old one with **`Object.is`** (the same equality `===` uses for objects). If they're not the *same* value — the same primitive, or literally the same object in memory — every consumer is told to re-render.

#### 🤔 Why do we need it? (the problem)
Beginners assume Context is smart: "I only read `value.theme`, so I'll only re-render when `theme` changes." Not true. Context has **no per-field tracking**. It sees one `value`. If that one value's identity changed, *all* consumers re-render, regardless of which field each one actually used. Put fast-changing state (a counter, a text input, mouse position) in a context and every consumer re-renders on every change — even the ones that don't care.

#### ⚙️ How does it work?
On each render of the Provider, React checks: is the new `value` the same (by `Object.is`) as last render's `value`? If **yes**, consumers are skipped. If **no**, *all* consumers re-render.

```
   Provider value identity CHANGED (Object.is = false)
                    │
        ┌───────────┼───────────┐
        ▼           ▼           ▼
   ┌─────────┐ ┌─────────┐ ┌─────────┐
   │Consumer1│ │Consumer2│ │Consumer3│
   │re-render│ │re-render│ │re-render│
   └─────────┘ └─────────┘ └─────────┘
   ALL re-render — even ones reading an unchanged field
```

The killer detail: writing `value={{ user, theme }}` **inline** creates a **brand-new object on every single render** of the Provider. A new object is never `Object.is`-equal to the previous one — so this guarantees *all* consumers re-render every time the Provider renders, even when `user` and `theme` are byte-for-byte identical. This is the **new-object-value re-render trap**.

> **Flag (precision):** The re-render is triggered by the *`value` prop's identity*, not by "the state changing." An inline object literal changes identity every render even if its contents are unchanged — that's the whole trap.

#### 🌍 Real-life analogy
Imagine an **office-wide intercom**. The Provider is the announcer; consumers are everyone wearing a speaker. When the announcer presses the button, **everyone's speaker blares** — you can't address just the accounting team. So if the announcer re-reads the *same* memo every few seconds (a new-object value each render), the whole office keeps stopping to listen to news that didn't change. That constant interruption is the re-render problem.

#### 💻 Code example
```jsx
import { createContext, useContext, useState } from "react";

const AppContext = createContext(null);

function App() {
  const [count, setCount] = useState(0);
  const [theme] = useState("dark");

  // ❌ THE TRAP: a NEW object literal every render.
  // Object.is(prev, next) is false EVERY time, so on each
  // setCount BOTH consumers below re-render — even ThemeLabel,
  // which never reads `count`.
  return (
    <AppContext.Provider value={{ count, theme }}>
      <button onClick={() => setCount((c) => c + 1)}>+1</button>
      <CountLabel />
      <ThemeLabel />
    </AppContext.Provider>
  );
}

function CountLabel() {
  const { count } = useContext(AppContext);
  return <p>Count: {count}</p>;
}

function ThemeLabel() {
  const { theme } = useContext(AppContext);
  // Re-renders on EVERY +1 click, even though `theme` never changed. ❌
  return <p>Theme: {theme}</p>;
}
```

#### 🎤 Interview question
**Q: Why does Context cause extra re-renders, and what exactly triggers them?**
A: When the Provider's `value` prop changes identity (compared with `Object.is`), React re-renders **every** consumer of that context — even consumers that only read a field that didn't change, because Context tracks the whole value, not individual fields. The classic cause is an **inline object** `value={{ ... }}`, which creates a new object every render and so is never `Object.is`-equal to the previous one, forcing all consumers to re-render constantly.

---

### ✂️ The Fixes — Memoize the Value and Split the Context

#### 🧩 What is it?
Three standard techniques tame the re-render problem: (1) **memoize** the `value` so its identity is stable across renders, (2) **split one context into several** so a change to one concern doesn't re-render consumers of another, and (3) reach for a **selector library** like `use-context-selector` when you need to subscribe to a single field.

#### 🤔 Why do we need it? (the problem)
The trap from the last topic — unnecessary re-renders — has to be fixed for Context to be usable beyond trivial cases. We need two outcomes: the `value` shouldn't change identity unless its contents actually changed, and consumers that only care about a rarely-changing concern (theme) shouldn't be dragged into re-renders caused by a frequently-changing one (a counter).

#### ⚙️ How does it work?
**Fix 1 — `useMemo` the value.** Wrap the object in `useMemo` with a dependency array of its real parts. Now React reuses the *same* object across renders until a dependency genuinely changes, so `Object.is` stays `true` and consumers are skipped.

**Fix 2 — split the context.** Instead of one mega-context carrying everything, give each independent concern its own Provider. A common split is **state vs. dispatch** (the dispatch function is stable and never changes, so its consumers *never* re-render from state updates), or simply **theme vs. user**. Now a change to one context can't re-render consumers of the other.

```
   ONE MEGA-CONTEXT            SPLIT CONTEXTS
   ┌── {user, theme,           ┌─ UserCtx ─┐  ┌─ ThemeCtx ─┐
   │     count} ──┐            │  changes  │  │  stable    │
   any change →   │            │  rarely   │  │            │
   ALL consumers  │            └─────┬─────┘  └─────┬──────┘
   re-render      │              only user      only theme
                  ▼              consumers        consumers
        everybody pays           re-render         untouched
```

**Fix 3 — selector libraries.** Plain `useContext` can't subscribe to "just one field." Libraries like `use-context-selector` add a `useContextSelector(ctx, v => v.theme)` API that only re-renders a consumer when *its selected slice* changes — the per-field tracking React's built-in Context lacks. (This is also exactly why external stores like Zustand and Jotai avoid the problem natively, covered in Module 5.)

#### 🌍 Real-life analogy
Splitting contexts is like replacing one **building-wide fire alarm** with **per-floor alarms**. Before, burning toast on floor 1 evacuates the whole tower (every consumer re-renders). After the split, the toast alarm only clears floor 1; the other floors keep working. Memoizing the value is like agreeing **"don't sound the alarm unless something actually changed"** — no more drills over an unchanged memo.

#### 💻 Code example
```jsx
import { createContext, useContext, useMemo, useState } from "react";

// FIX 2: split into two independent contexts.
const ThemeContext = createContext(null);
const CountContext = createContext(null);

function App() {
  const [count, setCount] = useState(0);
  const [theme] = useState("dark");

  // FIX 1: memoize each value so its identity is stable
  // until its real dependency changes.
  const themeValue = useMemo(() => ({ theme }), [theme]);
  const countValue = useMemo(
    () => ({ count, inc: () => setCount((c) => c + 1) }),
    [count]
  );

  return (
    <ThemeContext.Provider value={themeValue}>
      <CountContext.Provider value={countValue}>
        <Buttons />
        <CountLabel />
        <ThemeLabel />
      </CountContext.Provider>
    </ThemeContext.Provider>
  );
}

function Buttons() {
  const { inc } = useContext(CountContext);
  return <button onClick={inc}>+1</button>;
}

function CountLabel() {
  const { count } = useContext(CountContext);
  return <p>Count: {count}</p>; // re-renders on +1 — correct, it shows count
}

function ThemeLabel() {
  const { theme } = useContext(ThemeContext);
  // ✅ Does NOT re-render on +1: themeValue's identity is unchanged,
  // and it lives in a SEPARATE context from count.
  return <p>Theme: {theme}</p>;
}
```

#### 🎤 Interview question
**Q: How do you fix Context's re-render problem?**
A: Three standard moves. First, **memoize the `value`** with `useMemo` so it keeps a stable identity and `Object.is` skips consumers when nothing changed — this kills the inline-object trap. Second, **split one context into several** (e.g. state vs. dispatch, or theme vs. user) so a change to a frequently-updating concern doesn't re-render consumers of an unrelated, stable one. Third, when you need to subscribe to a single field, use a **selector library** like `use-context-selector`, which re-renders a consumer only when its selected slice changes — the per-field tracking built-in Context lacks.

---

### 🎯 When Context Is Right — and When It Isn't

#### 🧩 What is it?
Context is the **right** tool for **low-frequency, app-wide** values: theme, the current user / auth status, locale (language), feature flags, and stable functions like a `dispatch`. It's the **wrong** tool for **high-frequency** state that changes many times a second — anything tied to typing, dragging, or scrolling.

#### 🤔 Why do we need it? (the problem)
Knowing the *fixes* isn't enough; an architect must know when *not* to use Context at all. Even with memoization and splitting, Context fundamentally re-renders all consumers whenever its value legitimately changes. If that value changes on every keystroke, no amount of memoizing saves you — the value genuinely changed, so every consumer genuinely re-renders. The right move is to pick a different tool, not to fight Context.

#### ⚙️ How does it work?
Match the tool to the **change frequency** of the value:

```
   CHANGE FREQUENCY ──────────────────────────▶
   rare (load/login)        often (per keystroke)
   ┌───────────────────┐    ┌────────────────────┐
   │ theme, user/auth, │    │ form input text,    │
   │ locale, flags,    │    │ drag position,      │
   │ stable dispatch   │    │ scroll, live cursor │
   ├───────────────────┤    ├────────────────────┤
   │ ✅ CONTEXT fits   │    │ ❌ store / local    │
   │  (changes seldom, │    │   state instead     │
   │   tree-wide)      │    │  (changes flood the │
   │                   │    │   whole tree)       │
   └───────────────────┘    └────────────────────┘
```

Why it doesn't scale to high-frequency state: every change broadcasts to the whole subtree. A value updating 60 times a second means 60 re-render cascades a second across every consumer — the browser can't keep up and the UI janks. Tools built on `useSyncExternalStore` (Zustand, Jotai — Module 5) let a component subscribe to *just the slice it reads*, so a high-frequency change re-renders only the few components that depend on it, not the entire tree.

#### 🌍 Real-life analogy
Context is a **company-wide email blast**. Perfect for "the office is closed Monday" (rare, everyone needs it). Catastrophic for "Bob just typed another letter in his document" — sending that to all 500 employees every keystroke would bury everyone in noise. Rare, broadly-relevant news → blast it (Context). Constant, narrowly-relevant chatter → a direct message to the few who care (a store with per-component subscriptions).

#### 💻 Code example
```jsx
// ✅ GOOD FIT: theme — changes maybe once per session (user toggles it).
const ThemeContext = createContext("light");
// Whole app re-rendering on a theme switch is fine: it's rare and the
// whole UI genuinely needs the new theme anyway.

// ❌ BAD FIT: live search text in Context.
const SearchContext = createContext("");
function SearchBox() {
  const [text, setText] = useState("");
  // If `text` were pushed into Context on every keystroke, EVERY
  // consumer of SearchContext re-renders on every character typed —
  // the whole tree janks. Keep fast-changing input in LOCAL state
  // (here) or a store with per-slice subscriptions, not Context.
  return <input value={text} onChange={(e) => setText(e.target.value)} />;
}
```

#### 🎤 Interview question
**Q: When is Context the right choice, and when is it the wrong one? How does it compare to a state library?**
A: Context fits **low-frequency, app-wide** values — theme, current user/auth, locale, feature flags, a stable `dispatch` — where changes are rare and most of the tree genuinely needs them. It's wrong for **high-frequency** state (form inputs, drag/scroll positions) because any value change re-renders *all* consumers, so frequent updates flood the whole tree. A state library (Redux, Zustand, Jotai) differs by supporting **selective subscriptions**: a component re-renders only when the specific slice it reads changes, which is exactly what Context can't do on its own. Rule of thumb: Context for stable shared config, a store for state that changes often or needs fine-grained subscriptions.

<h2 id="module-3">Module 3 — Flux & Redux Fundamentals</h2>

Picture a component reaching deep into another component's state, flipping a value, and a third place quietly breaking because of it. When state can change from anywhere, bugs become un-traceable: you can't answer *"who changed this, and why?"* Flux and Redux answer that with one rule — state changes flow in **one direction only**, through a single, predictable pipeline. This module is the *mental model*; the next one (Redux Toolkit) is how you actually write it today.

---

### 🔁 Unidirectional Data Flow — State Moves in One Direction Only

#### 🧩 What is it?
**Unidirectional data flow** means data travels around your app in a **single loop**, never sideways or backwards. An event happens, it becomes an **action** (a plain object that *describes* what happened), a **reducer** uses that action to compute the next state, the **store** holds that state, and the **view** (your UI) re-renders from it. The view never edits state directly — it can only kick off the next action. This pattern is called **Flux**, the architecture Facebook introduced; Redux is the most popular library built on it.

#### 🤔 Why do we need it? (the problem)
In a "two-way" or free-for-all setup, any component can mutate any state, and state can flow back into the thing that produced it. That creates loops and surprises: you change one value and three unrelated views shift, and you can't tell which line of code did it. Debugging becomes detective work. A one-way loop fixes this by making **every** change pass through the *same single door* — so there's exactly one place to look, and one trail to follow.

#### ⚙️ How does it work?
The loop has four stations, and data only ever moves clockwise:

```
        ┌──────────────────────────────────┐
        │                                  ▼
   ┌─────────┐   describes    ┌─────────────────┐
   │  VIEW   │   "what         │     ACTION      │
   │  (UI)   │   happened"     │ { type: '...' } │
   └─────────┘ ───dispatch───▶ └─────────────────┘
        ▲                              │
        │ re-render                    │ given to
        │ from state                   ▼
   ┌─────────┐   holds new   ┌───────────────────┐
   │  STORE  │ ◀──state────  │     REDUCER       │
   │ (state) │               │ (state, action)   │
   └─────────┘               │   => newState     │
                             └───────────────────┘
```

1. The **view** dispatches an action when something happens (a click).
2. The **action** describes the event as data — never *how* to change state, only *what occurred*.
3. The **reducer** receives the current state plus the action and returns the **next** state.
4. The **store** saves that new state and notifies the view, which re-renders. Loop closed.

#### 🌍 Real-life analogy
Think of a **fast-food kitchen**. You (the view) don't walk behind the counter and cook — you hand a **written order ticket** (the action) to the counter. The **cook** (the reducer) reads the ticket plus the current state of the kitchen and produces the meal. The **pass / shelf** (the store) holds finished meals, and the screen shows what's ready. Orders only flow one way: customer to ticket to cook to shelf to screen. Nobody reaches into the fryer themselves, so the kitchen never descends into chaos.

#### 💻 Code example
```javascript
// 1. ACTION — a plain object describing WHAT happened
const addTodo = { type: 'todos/added', payload: 'Buy milk' };

// 2. REDUCER — given (state, action), returns the NEXT state (pure!)
function todosReducer(state = [], action) {
  switch (action.type) {
    case 'todos/added':
      return [...state, action.payload]; // new array, no mutation
    default:
      return state;                      // unknown action -> unchanged
  }
}

// 3. The loop in miniature:
let state = [];                          // store's state
state = todosReducer(state, addTodo);    // dispatch -> reducer -> new state
console.log(state);                      // -> ['Buy milk']
```

#### 🎤 Interview question
**Q: Explain unidirectional data flow.**
A: Data moves in one loop: the view **dispatches** an action (a plain object describing what happened), a reducer takes the current state plus that action and returns the next state, the store holds the new state, and the view re-renders from it. The view never mutates state directly — it can only dispatch the next action. Because every change passes through that single pipeline, state is predictable and traceable.

---

### 📜 The Three Principles — Redux's Constitution

#### 🧩 What is it?
Redux rests on **three rules** that, together, make state behave predictably:
1. **Single source of truth** — your whole app's state lives in **one** store, one object tree.
2. **State is read-only** — you never assign to it directly; the *only* way to change it is to **dispatch an action**.
3. **Changes are made by pure reducers** — a reducer is a pure function `(state, action) => newState` that computes the next state without mutating the old one or causing side effects.

#### 🤔 Why do we need it? (the problem)
Without these rules, "state management" is just scattered variables anyone can poke. You lose the ability to reason about your app: *Where is the truth? Who's allowed to change it? Will the same action always do the same thing?* The three principles answer all three — one place for truth, one channel for change, and changes that are deterministic. That's what unlocks the famous features: replaying actions, **time-travel debugging**, and easy testing.

#### ⚙️ How does it work?
```
   ONE store (single source of truth)
   ┌──────────────────────────────┐
   │  state = { user, todos, ui } │  read-only
   └──────────────────────────────┘
        ▲                  ▲
        │ getState()       │ ONLY way in:
        │ (read)           │ dispatch(action)
        │                  │
   ┌─────────┐        ┌───────────────────┐
   │  views  │        │ pure reducer       │
   │ read &  │        │ (state, action)    │
   │ dispatch│        │   => NEW state     │
   └─────────┘        └───────────────────┘
```
- **Read** by calling `getState()` — you look, you don't touch.
- **Write** only by `dispatch(action)`, which runs the reducer.
- The reducer must be **pure**: same inputs always give the same output, it returns a **new** object instead of editing the old one, and it does no I/O (no network calls, no random, no `Date.now()`).

#### 🌍 Real-life analogy
A bank **ledger**. There's one official ledger (single source of truth). You can't walk up and erase a balance (read-only). The only way to change it is to file a **transaction slip** (dispatch an action), which a teller applies by the rules (the pure reducer), writing a **new** line rather than scribbling over the old one. Because every change is a recorded slip, you can audit exactly how any balance came to be — and even replay the slips from the start to reach the same total. That replay is *time-travel debugging*.

#### 💻 Code example
```javascript
// A PURE reducer obeys principle #3.
function counter(state = { count: 0 }, action) {
  switch (action.type) {
    case 'counter/incremented':
      // ✅ returns a NEW object — old state untouched
      return { count: state.count + 1 };
    default:
      return state;
  }
}

// ❌ What a reducer must NEVER do:
function badCounter(state, action) {
  state.count += 1;          // mutation! edits the old state in place
  fetch('/api/log');         // side effect! reducers must be pure
  return state;              // returns the SAME object -> UI may not update
}
```

#### 🎤 Interview question
**Q: What are Redux's three principles?**
A: (1) **Single source of truth** — all state in one store. (2) **State is read-only** — the only way to change it is to dispatch an action. (3) **Changes are made by pure reducers** — `(state, action) => newState`, with no mutation and no side effects. These guarantees are what make Redux predictable and enable devtools, action replay, and time-travel debugging.

---

### 🧱 The Building Blocks — Actions, Reducers, and the Store

#### 🧩 What is it?
Redux is just **three pieces** working together:
- **Actions** — plain objects with a `type` string (and usually a `payload`) that describe an event.
- **Reducers** — pure functions that take `(state, action)` and return the next state.
- **The store** — the object that holds state and exposes three methods: `getState()` (read it), `dispatch(action)` (send an action through the reducer), and `subscribe(listener)` (run a callback whenever state changes).

#### 🤔 Why do we need it? (the problem)
You need a clear division of labour so the one-way loop actually works. Actions are *what happened* (data, not logic). Reducers are *how state responds* (logic, but pure). The store is the *glue* that wires dispatch to the reducer and tells the view to update. Separating these means you can test a reducer in total isolation — feed it a state and an action, check the output — with no React, no network, nothing.

#### ⚙️ How does it work?
```
  dispatch(action)
        │
        ▼
   ┌─────────┐   calls reducer(state, action)
   │  STORE  │ ─────────────────────────────┐
   │         │                              ▼
   │ getState│                       new state computed
   │ dispatch│ ◀──── saves it ───────────────┘
   │subscribe│
   └─────────┘
        │ notifies every subscriber
        ▼
   listeners run -> view re-renders from getState()
```
- `dispatch(action)` hands the action to the reducer, stores the returned state, then calls every subscriber.
- `subscribe(fn)` registers `fn` to fire on each change; it returns an unsubscribe function.
- In React you rarely call these yourself — `react-redux` (`useSelector`, `useDispatch`) wires `subscribe` and `dispatch` to your components for you.

#### 🌍 Real-life analogy
A **suggestion box** at a company. Employees drop in slips (**actions**) describing what should change. The **policy handbook** (**reducer**) says, for each type of slip, exactly how the official rules update. The **front-desk binder** (**store**) holds the current rules, lets anyone read them (`getState`), accepts new slips (`dispatch`), and pings a mailing list (`subscribe`) whenever the rules change so everyone re-reads.

#### 💻 Code example
```javascript
import { createStore } from 'redux'; // raw Redux, for illustration (createStore is deprecated — ship configureStore)

// ACTION creators — functions that build action objects
const increment = () => ({ type: 'counter/incremented' });

// REDUCER — pure (state, action) => newState
function counter(state = { count: 0 }, action) {
  switch (action.type) {
    case 'counter/incremented':
      return { count: state.count + 1 };
    default:
      return state;
  }
}

// STORE — holds state, wires dispatch to the reducer
const store = createStore(counter);

store.subscribe(() => console.log(store.getState())); // listen
store.dispatch(increment()); // -> logs { count: 1 }
store.dispatch(increment()); // -> logs { count: 2 }
```

#### 🎤 Interview question
**Q: What are actions, reducers, and the store?**
A: An **action** is a plain object with a `type` describing what happened. A **reducer** is a pure function `(state, action) => newState`. The **store** holds the state and exposes `getState()` to read, `dispatch(action)` to trigger a change (which runs the reducer), and `subscribe(listener)` to react to changes. Together they form the one-way loop: dispatch goes through the reducer, the store saves the result and notifies subscribers.

### 🧭 Why Redux Exists — and When You Don't Need It

#### 🧩 What is it?
Redux is a **predictable state container**. Its payoff isn't just "global variables" — it's the *discipline* of the one-way loop, which unlocks tooling: **time-travel debugging** (step backward and forward through actions), **action logs** (an exact history of what happened), **middleware** (intercept actions to add logging, async, etc.), and the **Redux DevTools** browser extension. But that discipline has a cost — boilerplate and indirection — so it isn't always worth it.

#### 🤔 Why do we need it? (the problem)
Some apps have **complex client state** that many distant parts of the UI read and write — and you need to trust it and debug it. That's Redux's sweet spot: when *"what changed this, and in what order?"* is a question you'll actually have to answer, the traceable action log earns its keep. The flip side: for a small app, or for state that's really a copy of **server data**, Redux adds ceremony without enough benefit.

#### ⚙️ How does it work?
Decide with this rough lens:

```
  Is the state really SERVER data (fetched, cached)?
        │ yes -> use a QUERY LIBRARY (TanStack Query / RTK Query)
        ▼ no
  Is it complex client state shared across the app,
  where you need traceability / debugging?
        │ yes -> Redux (use Redux Toolkit, next module)
        ▼ no
  Small / local / app-config?
        -> useState, useReducer, or Context
```

- **Don't use Redux for server state.** Fetched data is asynchronous, shared, and can go stale — it's a **cache**, not a source of truth. A query library handles caching, refetching, and invalidation that you'd otherwise hand-roll in Redux (covered in later modules).
- **Don't reach for it by default in small apps.** Local component state or Context is often enough.

> **Note (modern practice):** Almost nobody writes raw Redux (`createStore`, hand-written switch reducers) by hand today — it's verbose and error-prone. Modern Redux **is** **Redux Toolkit (RTK)**, which generates actions and reducers for you and lets you write "mutating" code safely. This module teaches the raw building blocks so the next module's RTK makes sense; treat the hand-written `createStore`/switch code above as *educational*, not the style you'd ship.

#### 🌍 Real-life analogy
Redux is a **flight data recorder ("black box")** for your app's state — every change is logged so you can replay exactly what happened and why. A black box is invaluable on an airliner with thousands of interacting systems. Bolting one onto a **bicycle**, though, is pure overhead: a bike's "state" is simple enough that you'd just look at it. Match the tool to the complexity.

#### 💻 Code example
```javascript
// Middleware demonstrates WHY the action pipeline is powerful:
// because every change is an action, you can intercept them all.
const logger = (store) => (next) => (action) => {
  console.log('dispatching:', action.type); // log every action centrally
  const result = next(action);              // let it through to the reducer
  console.log('next state:', store.getState());
  return result;
};
// This single, tiny function logs EVERY state change in the whole app —
// that's only possible because all changes funnel through dispatch.
```

#### 🎤 Interview question
**Q: When would you reach for Redux today, and when would you not?**
A: Reach for it when you have **complex client state** shared widely across the app and you need predictability, a traceable action history, and tooling (DevTools, time-travel, middleware) — and use **Redux Toolkit**, not raw Redux. Skip it when the app is small (use `useState`/`useReducer`/Context) or when the data is really **server state** (fetched/cached) — there, a query library like TanStack Query or RTK Query is the right tool, because that data is a cache that needs invalidation and refetching, not a hand-rolled store.

<h2 id="module-4">Module 4 — Redux Toolkit in Depth</h2>

Classic Redux works, but writing it by hand is *tedious* — a file of action-type constants, a file of action creators, a switch-statement reducer, and a careful dance to never mutate state. Redux Toolkit (RTK) is the official answer: the same predictable Redux underneath, but with the boilerplate, the immutability traps, and the async plumbing handled for you. This module is how modern Redux is actually written.

---

### 🏭 `configureStore` & `createSlice` — Redux With the Boilerplate Removed

#### 🧩 What is it?
**Redux Toolkit (RTK)** is the official, recommended toolset for writing Redux. Its two stars are `configureStore` — which builds the **store** (the single object that holds all your app state) with sensible defaults already wired in — and **`createSlice`** — which lets you describe one "slice" of state and its update logic in one place, then *auto-generates* the action creators and action types for you.

#### 🤔 Why do we need it? (the problem)
Hand-written Redux makes you write the same things over and over: a string constant for every action type, a small function (an **action creator**) to build each action, a big reducer `switch`, plus manual setup of **middleware** (code that sits between dispatch and the reducer) and the **DevTools** browser extension. It's a lot of ceremony for "change this number." Mistakes (a typo'd action string, forgetting DevTools setup) are easy and silent. RTK removes nearly all of it.

#### ⚙️ How does it work?
- `createSlice` takes a `name`, an `initialState`, and a `reducers` object. Each key in `reducers` is a small function describing one state change. From those keys, RTK **generates a matching action creator and action type automatically** — you never write the strings yourself.
- `configureStore` takes your slice reducers, and *for free* sets up the **thunk** middleware (for async, covered later), turns on the Redux **DevTools**, and adds dev-only checks that warn you if you accidentally mutate state outside a slice.

```
   createSlice({ name:'counter', reducers:{ increment }})
        │  auto-generates
        ▼
   actions.increment()  ──▶ { type:'counter/increment' }
        │  dispatched into
        ▼
   configureStore({ reducer:{ counter }})  =  the store
   (+ thunk middleware + DevTools + dev checks, all default)
```

#### 🌍 Real-life analogy
Plain Redux is **building furniture from raw lumber** — cut every board, label every screw yourself. RTK is the **flat-pack kit**: the boards come pre-cut and labelled (action creators and types generated for you), the right tools are in the box (thunk, DevTools), and there's a warning sticker if you assemble it wrong (the mutation checks).

#### 💻 Code example
```javascript
import { createSlice, configureStore } from '@reduxjs/toolkit';

const counterSlice = createSlice({
  name: 'counter',
  initialState: { value: 0 },
  reducers: {
    // looks like mutation — it's SAFE here (Immer; next topic)
    increment: (state) => { state.value += 1; },
    decrement: (state) => { state.value -= 1; },
    addBy: (state, action) => { state.value += action.payload; },
  },
});

// RTK generated these action creators + types for us:
export const { increment, decrement, addBy } = counterSlice.actions;
// increment()      -> { type: 'counter/increment' }
// addBy(5)         -> { type: 'counter/addBy', payload: 5 }

export const store = configureStore({
  reducer: { counter: counterSlice.reducer },
  // thunk middleware + DevTools + dev mutation checks are ON by default
});

store.dispatch(addBy(5));
console.log(store.getState().counter.value); // 5
```

#### 🎤 Interview question
**Q: How does `createSlice` reduce boilerplate?**
A: You write only the reducer functions in one object. From their keys, `createSlice` **auto-generates the action creators and action type strings** (namespaced as `sliceName/reducerName`), so you never hand-write action constants or creators. Paired with `configureStore`, which pre-wires thunk middleware, DevTools, and dev-only mutation checks, the typical "constants + creators + switch + store setup" boilerplate collapses to a single slice file.

### 🪄 Immer — How "Mutating" Code Stays Immutable

#### 🧩 What is it?
Inside a `createSlice` reducer you write what *looks* like mutation — `state.value += 1`, `state.list.push(item)`. RTK is using a library called **Immer** under the hood. Immer gives your reducer a special **draft** of the state; you "mutate" the draft, and Immer produces a brand-new, correctly **immutable** copy with your changes applied.

#### 🤔 Why do we need it? (the problem)
Redux's rules say reducers must be **pure** and must **never mutate** the old state — they have to return a *new* object. Done by hand for nested data, that means spread-operator pyramids like `{ ...state, a: { ...state.a, b: [...state.a.b, x] } }`. It's verbose, easy to get wrong, and one missed spread silently mutates state and breaks Redux's change detection. Immer lets you write the obvious mutating line and get the correct immutable update for free.

#### ⚙️ How does it work?
Immer wraps your state in a **Proxy** draft — an object that *records* what you change instead of changing the real thing. Your reducer scribbles on the draft; Immer watches, then **structurally shares** the untouched parts and builds new objects only along the path you edited.

```
   real state ──▶ Immer wraps it ──▶ DRAFT (a Proxy)
                                       │ you "mutate" the draft
                                       │ state.value += 1
                                       ▼
                 Immer records the change, then PRODUCES
                 a new immutable state (untouched parts reused)
```
> **Note (important):** "mutation" is safe **only inside** `createSlice` / `createReducer` reducers, because *those* run through Immer. Writing `state.value += 1` in a normal function or React component is a real, unsafe mutation — Immer is not involved there.

#### 🌍 Real-life analogy
Immer is **tracing paper laid over an original drawing**. You sketch your edits on the tracing sheet (the draft), and the studio then prints a fresh drawing combining the untouched original with your traced changes. The original is never marked, and parts you didn't touch are reused exactly.

#### 💻 Code example
```javascript
const todosSlice = createSlice({
  name: 'todos',
  initialState: { items: [] },
  reducers: {
    // "mutating" the draft — Immer makes this immutable for real:
    addTodo: (state, action) => {
      state.items.push({ id: action.payload.id, done: false });
    },
    toggle: (state, action) => {
      const t = state.items.find((i) => i.id === action.payload);
      if (t) t.done = !t.done; // safe: it's a draft, not the live state
    },
  },
});
// Equivalent hand-written immutable reducer would need spreads +
// items.map(...) to avoid mutating — Immer removes all of that.
```

#### 🎤 Interview question
**Q: How does Redux Toolkit let you "mutate" state?**
A: It doesn't actually mutate your state. `createSlice` runs each reducer through **Immer**, which hands the reducer a **Proxy draft**. Your mutating-looking code records changes on that draft, and Immer then produces a new immutable state (reusing untouched parts via structural sharing). It's safe **only inside** RTK reducers — the same syntax in a component or plain function is a genuine, unsafe mutation.

### 🌐 `createAsyncThunk` — Async Logic Through Middleware

#### 🧩 What is it?
Reducers must be pure and synchronous, so they can't do `fetch`. **Middleware** is code that sits between `dispatch` and the reducer and *can* do async work. RTK's `createAsyncThunk` is a helper that wraps an async function and automatically generates three actions describing its lifecycle: **pending**, **fulfilled**, and **rejected**. You respond to those in a slice's `extraReducers`.

#### 🤔 Why do we need it? (the problem)
Data fetching has three moments your UI cares about: *it started* (show a spinner), *it succeeded* (show data), *it failed* (show an error). Wiring that by hand means manually dispatching three separate actions and never forgetting one. `createAsyncThunk` standardises this: write the request once, and the pending/fulfilled/rejected actions are dispatched for you at the right times.

#### ⚙️ How does it work?
- You give `createAsyncThunk` a type prefix (e.g. `'users/fetch'`) and an async **payload creator** that returns a promise.
- When dispatched, the thunk middleware runs it and dispatches: `pending` immediately, then `fulfilled` with the resolved value, or `rejected` if it throws.
- You handle these in **`extraReducers`** — a section for reacting to actions defined *outside* this slice (here, the thunk's auto-generated ones).

```
   dispatch(fetchUsers())
        │  thunk middleware runs the async fn
        ▼
   'users/fetch/pending'    → set status = 'loading'
        │ promise resolves          │ promise rejects
        ▼                           ▼
   '.../fulfilled'            '.../rejected'
   set data + 'idle'         set 'error'
```

#### 🌍 Real-life analogy
It's a **package-tracking notification**. You place one order (dispatch the thunk) and the courier sends three updates on its own: *Order placed* (pending), then either *Delivered* (fulfilled) or *Delivery failed* (rejected). You don't ping the courier yourself — the updates arrive automatically, and you just decide what each one shows.

#### 💻 Code example
```javascript
import { createAsyncThunk, createSlice } from '@reduxjs/toolkit';

export const fetchUsers = createAsyncThunk('users/fetch', async () => {
  const res = await fetch('/api/users');
  return res.json(); // becomes action.payload on "fulfilled"
});

const usersSlice = createSlice({
  name: 'users',
  initialState: { data: [], status: 'idle', error: null },
  reducers: {},
  extraReducers: (builder) => {
    builder
      .addCase(fetchUsers.pending,   (s) => { s.status = 'loading'; })
      .addCase(fetchUsers.fulfilled, (s, a) => {
        s.status = 'idle';
        s.data = a.payload;
      })
      .addCase(fetchUsers.rejected,  (s, a) => {
        s.status = 'error';
        s.error = a.error.message;
      });
  },
});
```

#### 🎤 Interview question
**Q: How do you handle async logic in Redux Toolkit?**
A: With `createAsyncThunk`. You wrap an async function; dispatching it runs through the **thunk middleware** (on by default in `configureStore`) and auto-dispatches **pending / fulfilled / rejected** actions. You handle those in the slice's `extraReducers` to set loading, data, and error state. Reducers themselves stay pure and synchronous — all the async happens in the middleware layer.

### 🎯 Selectors & `createSelector` — Reading State Without Wasted Re-renders

#### 🧩 What is it?
A **selector** is just a function that reads a value out of the store, e.g. `state => state.cart.items`. In React you read with the **`useSelector`** hook. **`createSelector`** (from the **reselect** library, re-exported by RTK) builds a *memoized* selector for **derived data** — values you compute from state (a total, a filtered list) — so the computation runs only when its inputs actually change.

#### 🤔 Why do we need it? (the problem)
`useSelector` re-runs after every dispatch and re-renders your component whenever its **selected output changes** — and by default it compares outputs with **strict equality (`===`)**. That's a trap for derived data: a selector like `state => state.items.filter(...)` returns a **brand-new array every call**, which is never `===` the previous one, so the component re-renders on *every* dispatch even when nothing relevant changed. `createSelector` fixes this by caching: same inputs → same output reference.

#### ⚙️ How does it work?
`createSelector` takes one or more **input selectors** plus a **result function**. It remembers the last inputs and last result. On each call it grabs the inputs; if they're all **reference-equal (`===`)** to last time, it skips the result function and returns the **cached** result (same reference) — so `useSelector`'s `===` check passes and no re-render fires.

```
   inputs same as last time?  (=== check)
        │ yes                     │ no
        ▼                         ▼
   return CACHED result      run result fn,
   (same reference →         cache new result
    no re-render)            (recompute)
```
> **Note:** memoization here is **reference-based**. If an input selector itself returns a new object each call, the cache never hits. Keep input selectors returning stable slices of raw state (like `s => s.items`).

#### 🌍 Real-life analogy
`createSelector` is a **barista who remembers your last order**. If you ask for the exact same thing as before (same inputs), they hand you the cup they already made — no re-brewing. Only when your order changes do they make a fresh one. Without it, they'd brew a new (and *different-looking*) cup every single time you walked past, even to ask the time.

#### 💻 Code example
```javascript
import { createSelector } from '@reduxjs/toolkit';
import { useSelector } from 'react-redux';

// input selectors return stable slices of raw state:
const selectItems = (state) => state.cart.items;
const selectTaxRate = (state) => state.cart.taxRate;

// memoized derived selector:
export const selectCartTotal = createSelector(
  [selectItems, selectTaxRate],
  (items, taxRate) => {
    // runs ONLY when items or taxRate change by reference:
    const subtotal = items.reduce((sum, i) => sum + i.price, 0);
    return subtotal * (1 + taxRate);
  }
);

function CartTotal() {
  // same inputs -> same cached number -> no needless re-render
  const total = useSelector(selectCartTotal);
  return <span>Total: {total}</span>;
}
```

#### 🎤 Interview question
**Q: What problem does `createSelector` solve?**
A: Needless recomputation and re-renders for **derived state**. `useSelector` re-renders whenever its output changes by **strict equality**, so a selector that builds a new array/object each call (e.g. a filter or a computed total) re-renders on every dispatch. `createSelector` **memoizes by reference-equal inputs**: if its input selectors return the same references as last time, it returns the **cached result** (same reference), the `===` check passes, the expensive computation is skipped, and no re-render happens.

<h2 id="module-5">Module 5 — Lightweight & Atomic State (Zustand, Jotai, Valtio)</h2>

Redux is powerful, but for many apps it feels like a lot of ceremony — actions, reducers, a provider wrapping your whole tree. A newer family of libraries — **Zustand**, **Jotai**, and **Valtio** — asked a simpler question: what if global state were just a few lines, with no provider and no boilerplate, and a component re-rendered **only** when the exact piece it cares about changes? This module is about how they pull that off — and the one hook (`useSyncExternalStore`) they all quietly rely on.

---

### 🪶 Why Lightweight Stores Took Off — Less Ceremony, Fewer Re-Renders

#### 🧩 What is it?
A wave of tiny state libraries — Zustand, Jotai, Valtio (all from the same author, *Poimandres*) — that hold global state with **minimal boilerplate**, **no Provider wrapping**, and **opt-in re-renders** (a component subscribes only to the slice of state it reads).

#### 🤔 Why do we need it? (the problem)
Two pains pushed people to look past the older tools.

- **Boilerplate.** Classic Redux makes you write an action type, an action creator, a reducer case, and wire it all up — a lot of typing to change one number. (Redux Toolkit fixed much of this; see Module 4.)
- **The Context re-render trap.** React's built-in **Context** — the API for sharing a value down the tree without prop-drilling — has a sharp edge: when the context value changes, **every** component consuming that context re-renders, even ones that only read an unrelated field. Put your whole app's state in one Context and a single change re-renders everything.

These libraries attack both: almost no boilerplate, and re-renders that are **opt-in per slice**.

#### ⚙️ How does it work?
The shared trick is that the store lives **outside React**, in a plain JavaScript object. Components *subscribe* to it and ask to be notified only when their chosen slice changes.

```
   Context (built-in)        Lightweight store
   ──────────────────        ─────────────────
   value changes             one field changes
        │                          │
        ▼                          ▼
   ALL consumers             only components that
   re-render                 READ that field re-render
```

No `<Provider>` is required because the store is just an importable module — any component can grab it directly.

#### 🌍 Real-life analogy
Context is a building-wide **fire alarm**: change anything and *everyone* evacuates. A lightweight store is a set of **personal pagers**: you only buzz when the specific thing *you* signed up for happens.

#### 💻 Code example
```javascript
// No Provider, no boilerplate — just import and use.
// (Full Zustand/Jotai examples are in the topics below.)

// The whole "setup" for a Zustand store can be ~5 lines:
import { create } from 'zustand';
const useStore = create((set) => ({
  count: 0,
  inc: () => set((s) => ({ count: s.count + 1 })),
}));
// That's it — no <Provider>, no action types, no reducer files.
```

#### 🎤 Interview question
**Q: Why do Zustand and Jotai avoid Context's re-render problem?**
A: They don't store state *in* Context. State lives in an external store/atom, and components **subscribe to just the slice they read**. When a field changes, only the subscribers of that field re-render — unlike Context, where any change to the context value re-renders every consumer.

---

### 🐻 Zustand — One `create` Call, Read With a Selector

#### 🧩 What is it?
**Zustand** ("state" in German) is a small store library. You call **`create`** once and it returns a **hook**. Components call that hook with a **selector** function to read just the slice they need.

#### 🤔 Why do we need it? (the problem)
A single global store is convenient, but naive global state makes *every* consumer re-render on *any* change. Zustand's selector model fixes that: a component that reads only `count` is not re-rendered when an unrelated `user` field changes.

#### ⚙️ How does it work?
1. `create(initializer)` builds a store object **outside React** and returns a hook (commonly `useStore`).
2. You read with a **selector**: `useStore(s => s.count)`. Zustand remembers what you selected.
3. On every update it runs your selector again and compares the result to the previous one (a `===` check by default). If the selected value is unchanged, your component does **not** re-render.

```
   useStore(s => s.count)   ← you pick a slice
        │
        ▼
   store updates  →  re-run selector  →  changed?
                                          │
                          no ───► skip re-render
                          yes ──► re-render this component
```

So selecting `s => s.count` means *"re-render me only when count changes."* Selecting the **whole** store (`s => s`) re-renders on every change — so prefer narrow selectors. (Simplification: the comparison is a shallow/`Object.is` equality; you can pass a custom equality function for object slices.)

#### 🌍 Real-life analogy
The store is a **stock ticker board**. Each trader (component) tapes a card over the board saying *"only ping me about TSLA"* (the selector). The board updates constantly, but a trader only looks up when *their* stock moves.

#### 💻 Code example
```javascript
import { create } from 'zustand';

// 1. create() returns a HOOK. The store lives outside React.
const useCounter = create((set) => ({
  count: 0,
  user: { name: 'Ada' },
  inc: () => set((s) => ({ count: s.count + 1 })),
}));

// 2. Read with a SELECTOR — this component re-renders
//    ONLY when `count` changes, not when `user` changes.
function CountLabel() {
  const count = useCounter((s) => s.count); // fine-grained subscription
  return <span>{count}</span>;
}

// 3. Actions are just functions on the store.
function IncButton() {
  const inc = useCounter((s) => s.inc); // selecting the fn never changes ref
  return <button onClick={inc}>+1</button>;
}
// Changing `user` elsewhere will NOT re-render CountLabel — it didn't read user.
```

#### 🎤 Interview question
**Q: How does Zustand avoid unnecessary re-renders?**
A: You read state through a **selector** (`useStore(s => s.count)`). After each update Zustand re-runs the selector and compares the result to the previous one; it re-renders the component only when *that selected value* changed. Reading the whole store removes this benefit, so you select the narrowest slice you need.

---

### ⚛️ Jotai — Bottom-Up Atoms You Compose

#### 🧩 What is it?
**Jotai** ("state" in Japanese) models state as many tiny independent units called **atoms**. You create one with `atom(initialValue)`, and a component reads/writes it with `useAtom`. State is built **bottom-up** from small atoms rather than top-down from one big store.

#### 🤔 Why do we need it? (the problem)
Same Context trap, attacked from the other side. Instead of one big object that everyone subscribes to, Jotai splits state into **separate atoms**. A component re-renders **only for the atoms it actually uses** — so an atom changing never disturbs components that didn't read it. This is precisely why atoms sidestep Context's *"all consumers re-render"* problem: there is no single shared value to invalidate.

#### ⚙️ How does it work?
- An **atom** is a small piece of state: `const countAtom = atom(0)`. The atom itself is just a *definition* (a key) — it holds no value until used.
- `const [count, setCount] = useAtom(countAtom)` reads and writes it, much like `useState` but **shared** across components.
- **Derived atoms** compute from other atoms: `atom(get => get(countAtom) * 2)`. Jotai tracks the dependency, so the derived atom recomputes only when its inputs change, and only its readers re-render.

```
   countAtom (0)      nameAtom ("Ada")
       │                  │
       ▼                  ▼
   doubleAtom = count*2   (derived, auto-tracks countAtom)

   A component using doubleAtom re-renders when count changes,
   but NEVER when nameAtom changes.
```

#### 🌍 Real-life analogy
A big store is one giant **whiteboard** everyone watches. Atoms are individual **sticky notes** on a wall — you only glance at the notes you personally pinned up, and someone editing a different note doesn't pull your attention.

#### 💻 Code example
```javascript
import { atom, useAtom } from 'jotai';

// 1. Atoms are tiny, independent units of state. No Provider needed.
const countAtom = atom(0);

// 2. A DERIVED atom composes from another atom and auto-tracks it.
const doubleAtom = atom((get) => get(countAtom) * 2);

function Counter() {
  // useAtom works like useState, but the state is shared.
  const [count, setCount] = useAtom(countAtom);
  return <button onClick={() => setCount((c) => c + 1)}>{count}</button>;
}

function Double() {
  const [double] = useAtom(doubleAtom); // recomputes only when count changes
  return <span>{double}</span>;          // = count * 2
}
// Add a separate `nameAtom`; changing it will NOT re-render these two,
// because neither component read nameAtom.
```

#### 🎤 Interview question
**Q: How do Jotai atoms avoid the Context re-render trap?**
A: Context shares **one** value, so any change re-renders every consumer. Jotai splits state into **many independent atoms**; a component subscribes only to the atoms it reads, so changing one atom re-renders only that atom's readers. Derived atoms track their dependencies and recompute (and re-render) only when those inputs change.

---

### 🧬 Valtio — Mutate a Proxy, Re-Render What You Read

#### 🧩 What is it?
**Valtio** lets you keep state as a plain mutable object created with **`proxy({...})`**. You change it by **mutating it directly** (`state.count++`), and components read it with **`useSnapshot`**, which re-renders a component only for the fields it actually **read**.

#### 🤔 Why do we need it? (the problem)
Immutable updates (`setState(s => ({ ...s, count: s.count + 1 }))`) feel verbose and easy to get wrong. Valtio lets you write the *intuitive* mutation — `state.count++` — while still getting precise, minimal re-renders. It bridges "mutable feels natural" with "React needs to know what changed."

#### ⚙️ How does it work?
- `proxy` wraps your object in a **JavaScript Proxy** — an object that can intercept reads and writes. Valtio uses it to notice when you **mutate** a field and to notice which fields a component **reads**.
- In a component, `const snap = useSnapshot(state)` gives a read-only snapshot. As you read `snap.count`, the proxy **records** that this component depends on `count`.
- When you later mutate `state.count`, Valtio re-renders only the components that read `count` — not those that only read `state.user`.

```
   proxy({ count: 0, user })   ← mutate directly: state.count++
        │
   useSnapshot(state)
        │  reads snap.count  →  tracks "depends on count"
        ▼
   state.count++  →  re-render only count-readers
   state.user = …  →  count-readers are untouched
```

(Simplification: you **mutate** the original `proxy` object, but you **read** through the `snap` from `useSnapshot` — reading the raw proxy in render won't track dependencies correctly.)

#### 🌍 Real-life analogy
A proxy is a **smart highlighter on a shared document**. As each reader runs their highlighter over the sentences they care about, the system remembers it. Edit a sentence, and only the people who highlighted *that* sentence get a notification.

#### 💻 Code example
```javascript
import { proxy, useSnapshot } from 'valtio';

// 1. proxy() wraps a normal mutable object.
const state = proxy({ count: 0, user: { name: 'Ada' } });

// 2. Mutate it DIRECTLY — no setState, no spreads.
function inc() {
  state.count++; // intuitive mutation, Valtio sees it
}

function CountView() {
  // 3. Read via a snapshot; reading snap.count tracks the dependency.
  const snap = useSnapshot(state);
  return <button onClick={inc}>{snap.count}</button>;
}
// A component that reads only snap.user.name will NOT re-render
// when count changes — it never read count.
```

#### 🎤 Interview question
**Q: How does Valtio know which components to re-render when you mutate state directly?**
A: It wraps state in a JavaScript **Proxy**. `useSnapshot` reads through that proxy, which **records which fields each component reads**. A direct mutation like `state.count++` is intercepted, and Valtio re-renders only the components that read `count`. So you write natural mutations and still get fine-grained, opt-in re-renders.

---

### 🛡️ The Common Thread — `useSyncExternalStore` & No Tearing

#### 🧩 What is it?
All three libraries plug into React through one official hook: **`useSyncExternalStore`**. It is React 18's standard way for an **external** store (state living outside React) to subscribe a component safely, including under **concurrent rendering**.

#### 🤔 Why do we need it? (the problem)
React 18 can pause, resume, and even restart a render. If your data lives outside React and changes *mid-render*, two parts of the same screen can read **different** values of the same state — the UI shows inconsistent data. That bug is called **tearing** (see Module 5 of the React module). A naive `useState` + manual subscription can tear under concurrent features.

#### ⚙️ How does it work?
`useSyncExternalStore(subscribe, getSnapshot)` takes two things: a way to **subscribe** to changes, and a `getSnapshot` that returns the store's current value. React calls `getSnapshot` at the right moments and guarantees that a single render sees **one consistent value** everywhere — no tearing. Zustand, Jotai, and Valtio each implement these two functions internally, so you get concurrency safety for free.

```
   External store (Zustand / Jotai / Valtio)
        │ subscribe(cb)        │ getSnapshot()
        ▼                      ▼
   ┌───────────────────────────────────┐
   │      useSyncExternalStore         │
   │  one consistent value per render  │  → no tearing
   └───────────────────────────────────┘
```

#### 🌍 Real-life analogy
Imagine a TV studio with many monitors (components) showing a live score. `useSyncExternalStore` is the **broadcast switcher** that guarantees every monitor shows the *same frame* at any instant — even while the score updates rapidly. Without it, one monitor could show the old score and another the new one (tearing) in the same shot.

#### 💻 Code example
```javascript
import { useSyncExternalStore } from 'react';

// A hand-rolled "store" to show the shape these libraries implement.
let value = 0;
const listeners = new Set();
const store = {
  subscribe(cb) { listeners.add(cb); return () => listeners.delete(cb); },
  getSnapshot() { return value; },              // current value (consistent)
  inc() { value++; listeners.forEach((cb) => cb()); },
};

function Counter() {
  // React guarantees one consistent value per render — no tearing.
  const count = useSyncExternalStore(store.subscribe, store.getSnapshot);
  return <button onClick={store.inc}>{count}</button>;
}
// Zustand/Jotai/Valtio build exactly this subscribe + getSnapshot pair
// for you, plus the selector/atom/proxy tracking on top.
```

#### 🎤 Interview question
**Q: What does `useSyncExternalStore` do for these libraries?**
A: It's React's official bridge to **external** stores. It subscribes a component to the store and guarantees every component sees **one consistent snapshot** within a render — preventing **tearing** under React 18's concurrent rendering. Zustand, Jotai, and Valtio all use it internally, which is why they're concurrent-safe out of the box.

<h2 id="module-6">Module 6 — State Machines (XState)</h2>

Most UI bugs aren't logic errors — they're the app being in a state it was never supposed to reach: a spinner *and* an error showing at once, a "Submit" button that's both disabled and clickable. What if your code physically *could not* enter those broken states? That's the promise of a **finite state machine**: name every state your feature can be in, name the events that move between them, and the impossible combinations simply stop existing.

---

### 🚦 Finite State Machines — One State at a Time

#### 🧩 What is it?
A **finite state machine (FSM)** is a way of describing a feature as a *fixed, named set of states* plus the *events* that move you between them. "Finite" just means the list of states is known and limited. At any moment the machine is in **exactly one** of those states — never zero, never two. An **event** (a user click, a network response) triggers a **transition** from the current state to another allowed state.

#### 🤔 Why do we need it? (the problem)
Without it, we track state with a scatter of separate variables and *hope* they stay consistent. But nothing stops them from disagreeing. An FSM replaces "a pile of variables that might contradict each other" with "one variable that names exactly where we are", and a fixed map of which moves are even legal. If a transition isn't on the map, it can't happen.

#### ⚙️ How does it work?
You list the states, then for each state you list which events are handled and where each one leads. Everything else is ignored. A data fetch has four states:

```
        ┌──────────────────────────────────┐
        ▼                                   │
     ┌──────┐  FETCH   ┌─────────┐ RESOLVE ┌─────────┐
     │ idle │ ───────▶ │ loading │ ──────▶ │ success │
     └──────┘          └─────────┘         └─────────┘
                          │   ▲   REJECT
                   REJECT │   │ RETRY    ┌───────┐
                          └───┴────────▶ │ error │
                                         └───────┘
   one state at a time · only drawn arrows are allowed
```

From `loading`, a `RESOLVE` event leads to `success` and a `REJECT` event leads to `error`. Crucially, there is *no* arrow that lands you in both — the machine is always sitting on exactly one box.

#### 🌍 Real-life analogy
A **traffic light**. It is `red`, `green`, or `amber` — never two colours at once, and never a colour in between. The events are "timer fires", which moves it `green → amber → red → green` in a fixed loop. You will never see a working light glowing red and green together, because the machine that drives it has no transition that produces that. An FSM gives your UI the same guarantee.

#### 💻 Code example
```javascript
// The machine as a plain object: state -> (event -> next state).
// This is the whole "diagram" expressed as a lookup table.
const machine = {
  idle:    { FETCH:   'loading' },
  loading: { RESOLVE: 'success', REJECT: 'error' },
  success: { FETCH:   'loading' },              // refetch
  error:   { RETRY:   'loading' },
};

function transition(state, event) {
  // Only follow an arrow that actually exists; otherwise stay put.
  return machine[state]?.[event] ?? state;
}

transition('idle', 'FETCH');      // 'loading'
transition('loading', 'RESOLVE'); // 'success'
transition('success', 'RETRY');   // 'success'  (no RETRY arrow from success → ignored)
transition('idle', 'RESOLVE');    // 'idle'     (illegal here → ignored, not a crash)
```

#### 🎤 Interview question
**Q: What is a finite state machine, and what guarantee does it give you?**
A: It's a model with a fixed set of named **states** and **events** that cause **transitions** between them. The core guarantee is that the system is in **exactly one** state at any time, and only the transitions you explicitly defined can happen. That makes a whole class of "how did we even get here?" bugs structurally impossible, because illegal moves aren't on the map.

---

### 💥 Boolean Soup — How Flags Create Impossible States

#### 🧩 What is it?
"Boolean soup" is the common pattern of describing one feature with several independent on/off flags — `isLoading`, `isError`, `isSuccess`, `isOpen`. Each looks harmless. The problem is *combinations*: with four booleans there are sixteen possible combinations, but only a handful are ever valid. The rest are **impossible states** — combinations your code can technically represent but that should never occur, like `isLoading` and `isError` both `true`.

#### 🤔 Why do we need to fix it? (the problem)
Every place that sets one flag must remember to correctly set all the others, in the right order. Miss one — forget to clear `isError` before a retry, say — and the UI renders a contradiction: a spinner overlapping an error message. These bugs are nasty because each flag, read alone, looks fine. The fix is to make the bad combinations **unrepresentable**: replace the independent booleans with a single `status` value that can hold only one label at a time. Four booleans give 16 combinations; one enum of four states gives exactly 4 — and they're all valid.

#### ⚙️ How does it work?
Collapse the flags into one variable whose type is a fixed list of strings (an **enum** — a value restricted to a known set). Because the variable holds one string, it cannot be `loading` and `error` simultaneously. The illegal region of the grid is gone:

```
  FOUR BOOLEANS                 ONE status ENUM
  16 combos, ~4 valid           exactly 4 states, all valid
  ┌───────────┬───────────┐     ┌──────────────────────────┐
  │ isLoading │ isError   │     │ status =                 │
  │ isSuccess │ isOpen ...│     │  'idle' | 'loading'      │
  │ many can be true at   │     │  | 'success' | 'error'   │
  │ once → contradictions │     │ one label, no overlap    │
  └───────────┴───────────┘     └──────────────────────────┘
```

#### 🌍 Real-life analogy
A traffic light wired as three separate switches — one for red, one for amber, one for green — *can* be flipped to all-on or all-off; it relies on whoever flips them never making a mistake. A real light instead has a single dial that points at one colour. The dial *can't* point at two colours. Swapping booleans for a `status` enum is swapping the three error-prone switches for that one safe dial.

#### 💻 Code example
```javascript
// ❌ BOOLEAN SOUP — nothing stops a contradictory mix
let isLoading = false, isError = false, isSuccess = false;

function onFetchStart() {
  isLoading = true;
  // forgot to reset isError! If a previous attempt failed,
  // we now render isLoading=true AND isError=true — a spinner
  // sitting on top of an error message. Impossible-but-rendered.
}

// ✅ SINGLE status ENUM — the bad combos can't be expressed
let status = 'idle';   // 'idle' | 'loading' | 'success' | 'error'

function fetchStart() { status = 'loading'; } // any old state is wiped out
function fetchOk()    { status = 'success'; }
function fetchFail()  { status = 'error';   }

// The view reads ONE value — exhaustive and unambiguous:
function render(status) {
  switch (status) {
    case 'idle':    return 'Click to load';
    case 'loading': return 'Spinner…';
    case 'success': return 'Here is your data';
    case 'error':   return 'Something went wrong';
  }
}
// There is no branch for "loading + error" because there is no such value.
```

#### 🎤 Interview question
**Q: Why are several boolean flags worse than one status enum?**
A: Independent booleans multiply into many combinations, most of which are invalid — `isLoading && isError` both true is an **impossible state** the type system still lets you build, so it shows up as real bugs. A single `status` enum can hold only one of its allowed values at a time, so the contradictory combinations are **unrepresentable** rather than merely "discouraged". You also get exhaustive handling: a `switch` over the enum forces you to consider every real case.

---

### 🪆 Statecharts — FSMs With Hierarchy, Guards, Actions & Context

#### 🧩 What is it?
A plain FSM gets unwieldy once a feature has dozens of states, or needs to remember *data*, or must do something on the way between states. **Statecharts** (the model XState implements) are FSMs with four extensions: **hierarchical/nested states** (a state can contain its own sub-machine), **parallel states** (two independent regions active at once), **guards** (a condition that must be true for a transition to fire), **actions** (side effects that run during a transition), and **context** (extended data carried alongside the state, like a retry count).

#### 🤔 Why do we need it? (the problem)
Pure FSMs suffer "state explosion": modelling a media player that can independently be playing/paused *and* muted/unmuted as flat states needs four states, and it grows multiplicatively. Hierarchy and parallel regions tame that. **Guards** let you express "only allow checkout if the cart isn't empty" without inventing extra states. **Actions** give you a clean place to fire side effects (log, focus an input) exactly on a transition. **Context** holds the numbers and strings the finite states can't — the *value* in the input, the *count* of retries — keeping the named states finite while the data stays flexible.

#### ⚙️ How does it work?
The finite states form the skeleton; context rides alongside; guards gate the arrows; actions hang off them. A nested example — a `form` state that contains its own sub-states:

```
  STATECHART (states + context + guards + actions)
  context: { attempts: 0 }

  ┌─ form ─────────────────────────────────┐
  │   ┌────────┐  SUBMIT [guard: valid?]    │
  │   │ typing │ ─────────────────────────▶ │  submitting
  │   └────────┘  action: attempts += 1     │
  └─────────────────────────────────────────┘
  guard = transition only fires if condition true
  action = side effect run during the transition
```

The `SUBMIT` event only transitions if the `valid?` **guard** passes; as it transitions it runs the **action** that bumps `attempts` in **context**. The `typing` state lives *inside* `form` — that's the **hierarchy**.

#### 🌍 Real-life analogy
Back to the traffic light, now upgraded. **Hierarchy:** the whole junction is in a `daytime` mode that *contains* the normal red/amber/green cycle, and at night it switches to a `flashing` mode with its own little cycle. **Parallel:** the pedestrian "walk / don't-walk" sign runs alongside the car light as a separate region. **Guard:** the light only turns green *if* a car is detected on the sensor. **Action:** turning green also rings the crossing's beeper. **Context:** a counter remembering how many cars passed. Same one-state-at-a-time core, with structure bolted on.

#### 💻 Code example
```javascript
// A tiny statechart-style reducer: states + context + a guard + an action.
const initial = { state: 'typing', context: { value: '', attempts: 0 } };

function reducer(machine, event) {
  const { state, context } = machine;

  if (state === 'typing' && event.type === 'CHANGE') {
    return { state, context: { ...context, value: event.value } };
  }

  if (state === 'typing' && event.type === 'SUBMIT') {
    const isValid = context.value.length > 0;   // GUARD
    if (!isValid) return machine;               // guard failed → no transition
    return {
      state: 'submitting',
      context: { ...context, attempts: context.attempts + 1 }, // ACTION (data update)
    };
  }

  return machine; // unknown event in this state → ignored, stay put
}

reducer(initial, { type: 'SUBMIT' });
// → stays in 'typing' (value is empty, guard blocks it)

let m = reducer(initial, { type: 'CHANGE', value: 'hi' });
reducer(m, { type: 'SUBMIT' });
// → { state: 'submitting', context: { value: 'hi', attempts: 1 } }
```
> **Note (simplification):** real XState separates pure context updates ("assign" actions) from side-effecting actions and lets transitions be declared as data. This reducer just shows the *shapes* — states, context, a guard, a data-changing action — without the library's full API.

#### 🎤 Interview question
**Q: What do statecharts add over a plain finite state machine?**
A: Five things: **hierarchical (nested) states** and **parallel states** to avoid state explosion in complex features; **guards** for conditional transitions ("only fire if X"); **actions** for side effects that run during a transition; and **context** for the extended data the finite states can't hold (counts, input values). The finite-state core — one state at a time, explicit transitions — is unchanged; statecharts just make it scale to real-world flows.

---

### ⚖️ When a Machine Pays Off — and When It's Overkill

#### 🧩 What is it?
The judgement call of *whether to reach for a state machine at all*. A machine adds vocabulary — states, events, transitions, guards, context — and that vocabulary is worth learning only when the flow is genuinely stateful and tangled. For simple state it's ceremony you don't need.

#### 🤔 Why do we need it? (the problem)
Reaching for XState on a single toggle is over-engineering: you've imported a library and written a machine to express what `useState(false)` already nailed. But *avoiding* a machine on a multi-step checkout means re-deriving "can I be here?" logic by hand in scattered `if`s — exactly where impossible-state bugs breed. The skill is matching the tool to the complexity.

#### ⚙️ How does it work?
Gauge it by the number of distinct states and the complexity of the transitions between them:

```
  COMPLEXITY ──────────────────────────────▶
  simple toggle    a few states     many states,
  (open/closed)    (idle→load→ok)   guards, steps
       │                 │                │
       ▼                 ▼                ▼
   useState         useReducer /     state machine
   boolean          status enum      (XState)
   overkill ◀── machine ──▶ pays for itself
```

Rule of thumb: **toggles and one-off flags** → a boolean or `status` enum. **Complex multi-step flows** — checkout, multi-page wizards, media players, authentication (logged-out → authenticating → 2FA → logged-in) → a real machine earns its keep.

#### 🌍 Real-life analogy
You don't file a flight plan to walk to the corner shop — that's a single, trivial trip. But you absolutely file one for a cross-country flight with multiple legs, weather rules, and fuel stops. A `useState` boolean is the walk; an XState machine is the flight plan. Using the flight plan for the corner shop is the overkill; skipping it for the cross-country flight is the bug waiting to happen.

#### 💻 Code example
```javascript
// ✅ OVERKILL TERRITORY — a machine here is pure ceremony.
// A sidebar toggle is genuinely just one boolean.
let isOpen = false;
function toggle() { isOpen = !isOpen; }   // done. No machine needed.

// ✅ PAYS-OFF TERRITORY — a checkout has many states, and several
// transitions are illegal (you can't 'PAY' before an address exists).
const checkout = {
  cart:      { CHECKOUT: 'address' },
  address:   { NEXT: 'payment', BACK: 'cart' },
  payment:   { PAY:  'processing', BACK: 'address' },
  processing:{ OK:   'confirmed', FAIL: 'payment' },
  confirmed: {},                            // terminal: no way out
};
// Note there is NO 'PAY' arrow out of 'cart' or 'address' — so paying
// before entering payment details is impossible, not just discouraged.
```

#### 🎤 Interview question
**Q: When would you reach for a state machine, and when is it overkill?**
A: Reach for one when a feature has several distinct states with non-trivial, conditional transitions — checkout flows, multi-step wizards, media players, auth — where impossible states would otherwise creep in. It's overkill for simple toggles and single flags, where a boolean or a small `status` enum already makes the state clear and the bad combinations rare or absent. The trade is real: a machine costs you extra concepts to learn, and buys you a feature whose logic is a diagram you can reason about and whose impossible states are unrepresentable.

<h2 id="module-7">Module 7 — The Server State Problem</h2>

You have spent the last six modules taming **client state** — the data your app owns, that lives in memory, that you can change instantly. Now meet the troublemaker: data that lives on a **server** far away. It arrives late, many parts of your app want it at once, and it can change behind your back without warning. The moment you treat this data the same way you treat a counter or a toggle, things start to break. This module is about *why* server data is a different animal — and the one mental flip that makes it manageable.

---

### 🌐 Why Server State Is a Different Animal — it isn't really "yours"

#### 🧩 What is it?
**Server state** is data that lives somewhere else — in a database behind an API — and that your app *borrows* over the network. A list of products, the logged-in user's profile, the comments on a post: none of it is owned by your browser. You ask the server for a copy, and it hands you one.

**Client state**, by contrast, is data your app fully owns: a modal's open/closed flag, the text in an input, the current tab. You created it, you change it, nobody else can touch it.

#### 🤔 Why do we need to know this? (the problem)
Most state-management pain comes from treating these two as the same thing. They have four differences that change *everything* about how you should handle them:

- **Asynchronous** — client state is there the instant you read it. Server data is not: you ask, then you **wait** for the network, and only later does it arrive (or fail).
- **Shared** — many components often want the *same* data. The header wants the user's name, the sidebar wants their avatar, the settings page wants their email. All the same user.
- **Stale-able** — the server's copy is the real one, and it can change without telling you. Someone edits the product price on another device; your copy is now **out of date** and you have no idea.
- **Needs caching and syncing** — because it is slow to fetch and shared by many, you want to keep a copy around (a **cache**) and keep that copy roughly in sync with the server's truth.

Client state has none of these problems. A boolean toggle is never "stale", never "loading", and is never shared with a database in another country.

#### ⚙️ How does it work?
Picture the two kinds of state side by side:

```
  CLIENT STATE                 SERVER STATE
  (you own it)                 (you borrow it)

  ┌──────────────┐             ┌──────────────┐
  │  isModalOpen │             │   YOUR APP    │
  │  inputText   │             │  (a copy of   │
  │  activeTab   │             │   the data)   │
  └──────────────┘             └──────┬───────┘
   instant, yours                     │ network
   never stale                        │ (slow, can fail)
                                       ▼
                              ┌──────────────┐
                              │   SERVER /DB  │  ← the REAL data
                              │  (the truth)  │     can change
                              └──────────────┘     anytime
```

Your app never holds the *real* data — it holds a **copy** that the server handed over at one moment in time. The instant the server's copy changes, your copy is lying to you until you re-fetch.

#### 🌍 Real-life analogy
Client state is your **shopping list in your pocket** — you wrote it, only you can change it, it's correct because it's yours.

Server state is the **prices on a store's website** that you screenshotted this morning. The screenshot is *your* copy, but the store owns the real prices and can change them at noon. Your screenshot doesn't update itself — it quietly goes out of date, and you won't know until you reload the page.

#### 💻 Code example
```javascript
// CLIENT STATE — instant, yours, never "stale"
const [isOpen, setIsOpen] = useState(false);
setIsOpen(true);   // done. true, immediately. no waiting, no failure.

// SERVER STATE — you ask, then WAIT, then maybe it fails,
// and even when it works your copy can go out of date later.
const res = await fetch('/api/user');   // wait for the network...
const user = await res.json();          // a COPY of the server's user
// Meanwhile, the user edits their name on their phone.
// `user.name` here is now STALE — but nothing told your app.
```

#### 🎤 Interview question
**Q: Why is server state different from client state?**
A: Client state is synchronous and owned by the app — it's there instantly and nobody else can change it. Server state is **asynchronous** (you wait on the network and it can fail), **shared** (many components want the same data), and **stale-able** (the server owns the real copy and can change it without telling you). Because it's slow and shared, it also wants **caching and syncing**. Those four properties — async, shared, stale, cached — are why server data needs different tooling than a `useState` toggle.

---

### 🩹 Doing It By Hand — the useState plus useEffect trap

#### 🧩 What is it?
The "obvious" way to load server data in React: store it in `useState`, kick off the fetch in `useEffect`, and track whether you're still loading or have hit an error with a couple of boolean flags. It works for one component. Then you copy-paste it into the next component, and the next, and the cracks appear.

#### 🤔 Why do we need to know this? (the problem)
Because this pattern silently fails to give you the things server data actually needs. Every component that fetches by hand re-implements the same chores — badly:

- **Loading and error flags duplicated everywhere** — every component declares its own `isLoading` and `error`, copy-pasted, easy to get subtly wrong.
- **No caching** — when a component unmounts and remounts, the data is gone, so it re-fetches from scratch every single time. Nothing is remembered.
- **No deduplication** — if two components mount at once and both want `/api/user`, you fire **two identical network requests** for the exact same data.
- **No background refresh** — once loaded, the data just sits there going stale. Nothing re-checks the server when the user comes back to the tab.
- **No shared cache between components** — component A's fetched data is trapped inside component A's `useState`. Component B can't see it, so B fetches it all over again.

#### ⚙️ How does it work?
Here's the wasteful reality when two components each fetch the same thing by hand:

```
  <UserBadge/>                  <UserProfile/>
  own isLoading                 own isLoading
  own error                     own error
  own useEffect ─┐              ┌─ own useEffect
                 │              │
                 ▼              ▼
            GET /api/user   GET /api/user
                 │              │
                 └──── TWO identical requests ────┘
                  no shared cache, no dedup,
                  loading flags written twice
```

Two components, two fetches, two copies of the data, two sets of loading flags — for one piece of information that should have been fetched once and shared.

#### 🌍 Real-life analogy
Imagine two roommates who both want milk. Neither checks the fridge or tells the other, so **both drive to the store and each buys a carton**. Now you have two cartons, double the trip, and no system to remember "we already have milk." Hand-rolled fetching is two roommates with no shared fridge — every component shops alone.

#### 💻 Code example
```javascript
// A reusable hand-rolled fetch hook — looks fine, hides the problems.
function useUser() {
  const [user, setUser] = useState(null);
  const [isLoading, setIsLoading] = useState(true); // duplicated in every hook
  const [error, setError] = useState(null);         // duplicated too

  useEffect(() => {
    let cancelled = false;
    setIsLoading(true);
    fetch('/api/user')
      .then((r) => r.json())
      .then((data) => { if (!cancelled) setUser(data); })
      .catch((e) => { if (!cancelled) setError(e); })
      .finally(() => { if (!cancelled) setIsLoading(false); });
    return () => { cancelled = true; };
  }, []);

  return { user, isLoading, error };
}

// Now used in TWO components on the same screen:
function UserBadge() {
  const { user, isLoading } = useUser();   // fires GET /api/user  (request #1)
  if (isLoading) return <span>Loading…</span>;
  return <span>{user.name}</span>;
}

function UserProfile() {
  const { user, isLoading } = useUser();   // fires GET /api/user  (request #2!)
  if (isLoading) return <p>Loading…</p>;
  return <h1>{user.email}</h1>;
}

// Result: the SAME user is fetched TWICE — two network round-trips,
// two independent copies, two separate loading states. No cache,
// no dedup, no sharing. And neither copy ever refreshes on its own.
```

#### 🎤 Interview question
**Q: What problems does a data-fetching library solve that `useEffect` doesn't?**
A: Hand-rolled `useEffect` fetching makes every component re-implement loading/error flags, and it has **no shared cache** — so the same data is re-fetched on every mount and **duplicated** across components that need it. It has **no deduplication** (two components wanting the same data fire two requests) and **no background refresh** (data goes stale and nothing re-checks). A library gives you one shared cache, request deduplication, automatic background refetching, and standardized loading/error states — the things `useEffect` leaves you to build (and get wrong) by hand.

---

### 🪞 The Reframe — your fetched data is a cache, not a source of truth

#### 🧩 What is it?
Here is the single idea that dissolves the whole problem: **the data you fetched is not your data.** It is a **cache** — a local copy — of the truth that lives on the server. You are not *storing state*; you are *holding a snapshot* of someone else's state.

A **cache** is just a nearby copy of data that really lives somewhere slower or farther away, kept so you don't have to go fetch it every single time.

#### 🤔 Why do we need this reframe? (the problem)
When you think "this is my state," you reach for the tools of state storage — put it in `useState`, or a Redux store — and you treat it as authoritative. But it *isn't* authoritative. The server can change it from under you. Treating a stale copy as the source of truth is exactly how you show users the wrong price, the old comment, the deleted item.

The moment you instead think **"this is a cache of the server's truth,"** your job description changes completely. You stop asking *"how do I store this?"* and start asking the questions a cache forces you to answer:

- **Freshness** — is my copy still trustworthy, or has it gone stale?
- **Invalidation** — when do I throw my copy away and get a new one?
- **Syncing** — how do I keep my copy reasonably close to the server's truth?

#### ⚙️ How does it work?
The reframe turns "store state" into "manage a cache":

```
  OLD MENTAL MODEL              NEW MENTAL MODEL
  "fetched data = my state"     "fetched data = a CACHE
                                  of the server's truth"

  questions you ask:            questions you ask:
   • where do I store it?        • is it still FRESH?
   • how do I set it?            • when do I INVALIDATE it?
                                 • how do I SYNC it back
   (wrong job)                     to the server's truth?
                                   (the right job)
```

Note this is a *simplification* of a deep field — caching has whole books written about it (eviction, TTLs, consistency). But for app developers the reframe is enough: freshness, invalidation, sync.

#### 🌍 Real-life analogy
Think of a **library book** versus your **own notebook**. Your notebook is yours — its contents are the truth because you wrote them (client state). A library book is **borrowed**: you can keep it on your desk (a cache), but the library owns it, the library's catalog is the truth, and your copy is due back and may be revised in the next edition. You'd never scribble in a library book and call it the master copy. Fetched data is the borrowed book, not your notebook.

#### 💻 Code example
```javascript
// WRONG FRAMING — "this is my state, I store and own it"
const [products, setProducts] = useState([]);
// Treating `products` as the truth. But the server can change
// prices any second — and this copy will keep showing the old ones.

// RIGHT FRAMING — "this is a cache of the server's truth"
// (conceptual — a server-state library does this for you)
const cache = {
  data: products,        // a COPY of the server's data
  fetchedAt: Date.now(), // WHEN we took the snapshot...
  staleTime: 30_000,     // ...so we can ask: is it still fresh?
};
const isStale = Date.now() - cache.fetchedAt > cache.staleTime;
// If stale, the right move is to RE-SYNC (re-fetch), not to keep
// trusting the snapshot. The job is cache management, not storage.
```

#### 🎤 Interview question
**Q: Is your fetched data a source of truth?**
A: No. The source of truth lives on the server (or its database); your fetched data is only a **cache** — a local snapshot of that truth at one moment. That reframe matters because it changes the job: instead of "storing state," you're managing a cache, which means worrying about **freshness** (has it gone stale?), **invalidation** (when to discard it), and **syncing** (keeping it close to the server). Treating a cached copy as authoritative is what leads to showing users out-of-date data.

---

### 🧰 Why a Server-State Library Beats a Store — right tool for a cache

#### 🧩 What is it?
A **server-state library** — TanStack Query (formerly React Query), RTK Query, or SWR — is a tool built specifically to manage the cache of server data. You tell it *how* to fetch something and give that data a **key** (a name like `['user']`), and the library handles the caching, deduplication, background refreshing, and loading/error states for you.

#### 🤔 Why do we need it? (the problem)
The popular instinct is to put fetched data into a general client-state store like **Redux**. But Redux was built to manage **client state** — synchronous data you own. It knows nothing about networks, staleness, or refetching. So if you push server data into it, *you* end up hand-writing all the cache logic — loading flags, dedup, invalidation, background refresh — inside Redux. You've just rebuilt a worse data-fetching library by hand, the exact trap from the second topic. A dedicated library ships all of that already, correct and battle-tested.

#### ⚙️ How does it work?
The library sits between your components and the network as **one shared cache keyed by request**:

```
   <UserBadge/>      <UserProfile/>
        │                  │
        └──── useQuery(['user']) ───┘   same KEY → same cache entry
                     │
                     ▼
            ┌─────────────────┐
            │  QUERY CACHE     │  one shared copy, keyed by ['user']
            │  • dedups calls  │  two components → ONE request
            │  • tracks fresh  │  knows when to refetch
            │  • refetches bg  │  refresh on focus/reconnect
            └────────┬────────┘
                     │ fetch only when needed
                     ▼
                  SERVER
```

Because both components ask for the *same key*, they share **one** cache entry and **one** request — the duplication and double-fetch from the hand-rolled version simply vanish.

#### 🌍 Real-life analogy
Redux is a brilliant **filing cabinet** for papers *you* wrote — but it has no idea your papers are photocopies of documents at city hall that keep getting amended. A server-state library is a **subscription service**: you ask once for "the user," and it keeps a shared copy for everyone, remembers when it last checked, fetches a fresh one when yours gets old, and never sends two people to city hall for the same document. Using Redux for server data is using a filing cabinet to do a subscription service's job.

#### 💻 Code example
```javascript
// The SAME two components from before — now with TanStack Query.
// One shared cache, keyed by ['user']. No duplicated flags,
// no double fetch.

function UserBadge() {
  const { data: user, isPending } = useQuery({
    queryKey: ['user'],            // the KEY into the shared cache
    queryFn: () => fetch('/api/user').then((r) => r.json()),
  });
  if (isPending) return <span>Loading…</span>;
  return <span>{user.name}</span>;
}

function UserProfile() {
  const { data: user, isPending } = useQuery({
    queryKey: ['user'],            // SAME key → SAME cache entry
    queryFn: () => fetch('/api/user').then((r) => r.json()),
  });
  if (isPending) return <p>Loading…</p>;
  return <h1>{user.email}</h1>;
}

// Result: ONE request for /api/user (deduped), ONE shared copy,
// loading/error handled by the library, and it refetches in the
// background when the data goes stale — none of which you wrote.
```

#### 🎤 Interview question
**Q: Why use a dedicated server-state library instead of putting fetched data in Redux?**
A: Redux is built for **client state** — synchronous data the app owns — so it has no concept of networks, staleness, or refetching. If you store server data there, you have to hand-build caching, deduplication, invalidation, background refresh, and loading/error flags yourself, which just re-creates the `useEffect` mess inside Redux. A server-state library (TanStack Query, RTK Query, SWR) is purpose-built for caching remote data: one shared cache keyed by request, automatic dedup and background refetch, and built-in loading/error states. It's the right tool because the job is **cache management**, not state storage.

<h2 id="module-8">Module 8 — Data Fetching Patterns & Pitfalls</h2>

You finally got data onto the screen with `fetch` inside a `useEffect`. It works on your machine — so why does the search box sometimes show results for a word you already deleted? This module is about the quiet bugs that hide in "just fetch the data": out-of-order responses, a tangle of loading flags, requests that wait in line when they could run side by side, and the bigger question of *where* fetching should even happen.

---

### 🪝 Fetch-in-`useEffect` — the pattern everyone starts with

#### 🧩 What is it?
The most common way beginners load data in React: run a `fetch` (a built-in browser function that asks a server for data) inside a `useEffect` (a hook that runs code *after* the component renders), then save the result with `useState` so the component re-renders with it.

#### 🤔 Why do we need it? (the problem)
A component renders **before** any network data exists. You can't fetch *during* render — rendering must be synchronous and side-effect-free, and the data isn't there yet. So you render once with "nothing", kick off the request as a side effect, and re-render when it arrives. `useEffect` is the official place for that side effect.

#### ⚙️ How does it work?
The lifecycle runs in this order:

```
  1. component renders  (data = null, show spinner)
  2. effect runs        (fetch starts in background)
  3. response arrives    -> setState(data)
  4. component re-renders (now shows the data)
```

The catch: steps 2 and 3 are **asynchronous**, and the component can render, re-run effects, or unmount many times while a request is still in flight. The naive version ignores all of that.

#### 🌍 Real-life analogy
You order takeout the moment you sit down at an empty table (the first render). The food shows up later, and only then do you start eating (the re-render). The trouble starts when you change your order halfway through — which is exactly the next topic.

#### 💻 Code example
```javascript
import { useState, useEffect } from "react";

function UserCard({ userId }) {
  const [user, setUser] = useState(null);

  useEffect(() => {
    // runs AFTER render, every time userId changes
    fetch(`/api/users/${userId}`)
      .then((res) => res.json())
      .then((data) => setUser(data)); // re-renders with the user
  }, [userId]); // dependency: re-run when userId changes

  if (!user) return <p>Loading...</p>;
  return <h1>{user.name}</h1>;
}
// Works for a single, stable request.
// Breaks the moment userId changes quickly — see the next topic.
```

#### 🎤 Interview question
**Q: Why can't you call `fetch` directly in a component's render body?**
A: Render must be synchronous and free of side effects — React may run it multiple times and the data isn't available yet anyway. Side effects like fetching belong in `useEffect`, which runs *after* the render is committed, so the network request happens off the render path.

---

### 🏁 The race condition — when old responses overwrite new ones

#### 🧩 What is it?
A **race condition** is a bug where the result depends on which async operation *finishes* first — and you have no control over that order. In fetch-on-effect, it shows up as a **stale response overwriting a fresh one**.

#### 🤔 Why do we need to know it? (the problem)
Imagine a search box. The user types `"ab"`, then quickly `"abc"`. Your effect fires **two** requests. The network doesn't promise to answer in order — the slower `"ab"` request can land *after* `"abc"`. Whichever `setState` runs last wins, so the screen ends up showing results for `"ab"` while the input says `"abc"`. The UI silently lies.

#### ⚙️ How does it work?
The two requests overlap in time, and responses can return out of order:

```
  type "ab"  --> request A sent ----------\
                                           \ (slow)
  type "abc" --> request B sent --\         \
                                   \ (fast)   \
                          B arrives -> setState(B)  "abc" shown
                          A arrives -> setState(A)  "ab"  shown  X
                          ^ the OLD response landed last and won
```

The fix is to make every effect run **ignore any response that isn't the latest one**. Two standard ways:

```
  1. CLEANUP FLAG: mark this run "stale" in the cleanup,
     then skip setState when the flag says stale.

  2. AbortController: actively CANCEL the in-flight
     request in the cleanup so it never resolves.
```

React runs the effect's **cleanup function** before re-running the effect (and on unmount), so the previous request always gets flagged or aborted right before the new one starts.

#### 🌍 Real-life analogy
You text a friend "pick up milk", then change your mind and text "pick up eggs". If the first text is delayed and arrives second, they buy milk — the *old* instruction wins. The fix is to add "ignore my previous text": that's the cleanup flag. Calling them to cancel the first errand entirely is the `AbortController`.

#### 💻 Code example
```javascript
import { useState, useEffect } from "react";

// ❌ BEFORE — race condition: the last response to arrive wins,
// even if it belongs to an old query.
function SearchBuggy({ query }) {
  const [results, setResults] = useState([]);

  useEffect(() => {
    fetch(`/api/search?q=${query}`)
      .then((res) => res.json())
      .then((data) => setResults(data)); // stale response can overwrite fresh
  }, [query]);

  return <ul>{results.map((r) => <li key={r.id}>{r.name}</li>)}</ul>;
}

// ✅ AFTER (fix 1) — cleanup flag: ignore a response from a stale run.
function SearchFlag({ query }) {
  const [results, setResults] = useState([]);

  useEffect(() => {
    let active = true; // true while THIS effect run is the latest

    fetch(`/api/search?q=${query}`)
      .then((res) => res.json())
      .then((data) => {
        if (active) setResults(data); // skip if a newer run replaced us
      });

    return () => {
      active = false; // cleanup: mark this run stale before the next runs
    };
  }, [query]);

  return <ul>{results.map((r) => <li key={r.id}>{r.name}</li>)}</ul>;
}

// ✅ AFTER (fix 2) — AbortController: actually CANCEL the old request.
function SearchAbort({ query }) {
  const [results, setResults] = useState([]);

  useEffect(() => {
    const controller = new AbortController();

    fetch(`/api/search?q=${query}`, { signal: controller.signal })
      .then((res) => res.json())
      .then((data) => setResults(data))
      .catch((err) => {
        if (err.name !== "AbortError") throw err; // ignore the cancel
      });

    return () => {
      controller.abort(); // cleanup: cancel the in-flight request
    };
  }, [query]);

  return <ul>{results.map((r) => <li key={r.id}>{r.name}</li>)}</ul>;
}
```
> **Which to use?** The cleanup flag is simpler and always safe — it just *ignores* the late response. `AbortController` is better when you also want to **stop the network work** (save bandwidth, cancel an expensive query). They're often combined; the flag alone is enough to kill the race.

#### 🎤 Interview question
**Q: Show the race condition in a fetch-on-effect and fix it.**
A: Two overlapping requests (e.g. fast-changing search input) can resolve out of order, so an *older* response's `setState` runs last and overwrites the newer data. Fix it in the effect's cleanup: set a `let active = true` flag and guard `setState` with `if (active)`, returning `() => { active = false }` so a superseded run is ignored — or pass an `AbortController`'s `signal` to `fetch` and call `controller.abort()` in cleanup to cancel the stale request outright.

### 🚦 Loading, error & empty states — taming the flag sprawl

#### 🧩 What is it?
Real fetching has more than "data / no data". You usually track **loading** (request in flight), **error** (request failed), the **data** itself, and the **empty** case (request succeeded but returned nothing). Done naively, each becomes its own boolean.

#### 🤔 Why do we need it? (the problem)
A spinner that never resolves on error, or a blank screen that can't tell "still loading" from "loaded but empty", makes a UI feel broken. So people add `isLoading`, `isError`, `data`, maybe `isEmpty`… and now several booleans can contradict each other. `isLoading: true` together with `error: "..."` is a nonsense state that your code can accidentally produce — this is the `isLoading`-flag sprawl.

#### ⚙️ How does it work?
The honest shape of a request is **one** of a few states, never several at once:

```
        +-----------+
        |   idle    |
        +-----------+
              | fetch starts
              v
        +-----------+   ok    +-----------+
        | loading   |-------->|  success  |
        +-----------+         +-----------+
              | fail               | data is []?
              v                    v
        +-----------+         +-----------+
        |   error   |         |   empty   |
        +-----------+         +-----------+
```

Modeling it as a single `status` value (`"loading" | "error" | "success"`) instead of independent booleans makes the impossible combinations *unrepresentable* — you literally can't be loading and errored at the same time.

#### 🌍 Real-life analogy
A package tracker doesn't show three lights — "shipped", "delivered", and "lost" — glowing at once. It shows **one** status at a time. Booleans let all the lights flicker on together; a single status field is the one honest tracker.

#### 💻 Code example
```javascript
import { useState, useEffect } from "react";

function Todos({ userId }) {
  // ONE status value instead of three tangled booleans
  const [status, setStatus] = useState("loading"); // loading|error|success
  const [todos, setTodos] = useState([]);

  useEffect(() => {
    let active = true;
    setStatus("loading");

    fetch(`/api/todos?user=${userId}`)
      .then((res) => res.json())
      .then((data) => {
        if (!active) return;
        setTodos(data);
        setStatus("success");
      })
      .catch(() => {
        if (active) setStatus("error");
      });

    return () => { active = false; };
  }, [userId]);

  if (status === "loading") return <p>Loading...</p>;
  if (status === "error") return <p>Something went wrong.</p>;
  if (todos.length === 0) return <p>No todos yet.</p>; // the EMPTY state
  return <ul>{todos.map((t) => <li key={t.id}>{t.title}</li>)}</ul>;
}
```
> **Simplification flagged:** a hand-rolled `status` string covers the basics. State machines (Module 6) and data libraries (Modules 9–10) formalize this further with derived flags like `isPending` / `isFetching` so you never reconstruct it by hand.

#### 🎤 Interview question
**Q: Why are separate `isLoading` and `isError` booleans an anti-pattern?**
A: They allow contradictory combinations (loading *and* errored, success with stale data) that your render logic must defend against, and they're easy to leave out of sync. Modeling the request as a single `status` enum makes impossible states unrepresentable and the rendering a clean switch. You also need a distinct **empty** branch — "succeeded with no rows" is not the same as "still loading".

### 🌊 Waterfalls vs parallel — and over-/under-fetching

#### 🧩 What is it?
A **request waterfall** is when fetches run **one after another** because each waits for the one before — even when they don't truly depend on each other. **Parallel fetching** fires independent requests at the same time and waits for all of them together with `Promise.all`.

#### 🤔 Why do we need it? (the problem)
Network requests are slow (latency dominates). If you fetch the user, *then* their posts, *then* their notifications in sequence, the total time is the **sum** of all three. If those three don't depend on each other, you've made the page three times slower for no reason. Waterfalls are the most common hidden performance bug in data fetching.

#### ⚙️ How does it work?
Sequential (waterfall) — each bar waits for the previous to finish:

```
  user    |====|
  posts        |====|
  notes              |====|
  total: user + posts + notes   (added up)
```

Parallel with `Promise.all` — all start at once, total is the slowest one:

```
  user    |====|
  posts   |======|
  notes   |===|
  total:   the SLOWEST single request (max, not sum)
```

A real waterfall is only justified when a request **genuinely depends** on a previous result (you need the user's id before you can fetch *that user's* posts). Independent requests should always run in parallel.

Two related sins:
- **Over-fetching:** asking for more than you show (the whole user record to display one name). Wasted bytes.
- **Under-fetching:** asking for too little, so you must make *more* round-trips to fill the gaps — which often creates a waterfall.

#### 🌍 Real-life analogy
Making coffee: you can boil the kettle, grind the beans, and warm the mug **at the same time** (parallel) and finish in the time of the slowest step. A waterfall is boiling the kettle, then *only after* grinding, then *only after* warming the mug — three times the wait for no reason. You truly must wait only when one step needs the last (you can't pour before the kettle boils).

#### 💻 Code example
```javascript
// ❌ WATERFALL — three independent requests run in sequence.
// Total time = user + posts + notes (added together).
async function loadSlow(userId) {
  const user = await fetch(`/api/users/${userId}`).then((r) => r.json());
  const posts = await fetch(`/api/posts?user=${userId}`).then((r) => r.json());
  const notes = await fetch(`/api/notes?user=${userId}`).then((r) => r.json());
  return { user, posts, notes };
}

// ✅ PARALLEL — start all three at once, await them together.
// Total time = the SLOWEST single request.
async function loadFast(userId) {
  const [user, posts, notes] = await Promise.all([
    fetch(`/api/users/${userId}`).then((r) => r.json()),
    fetch(`/api/posts?user=${userId}`).then((r) => r.json()),
    fetch(`/api/notes?user=${userId}`).then((r) => r.json()),
  ]);
  return { user, posts, notes };
}

// ✅ JUSTIFIED waterfall — posts genuinely DEPEND on the user's id,
// so this one ordering is unavoidable. But fetch siblings in parallel.
async function loadDependent(userId) {
  const user = await fetch(`/api/users/${userId}`).then((r) => r.json());
  const posts = await fetch(`/api/posts?author=${user.id}`)
    .then((r) => r.json());
  return { user, posts };
}
```
> **Note:** `Promise.all` rejects as soon as *any* request fails. If you want partial results even when one errors, use `Promise.allSettled`, which waits for all and reports each outcome separately.

#### 🎤 Interview question
**Q: How do you avoid request waterfalls?**
A: Identify which requests actually depend on each other. Independent fetches should be started together and awaited with `Promise.all` so the total cost is the slowest request, not the sum. Only keep a sequential (waterfall) shape where a later request genuinely needs an earlier result. Watch for *under-fetching* too — asking for too little forces extra round-trips that reintroduce a waterfall.

---

### 📍 Where should fetching live? — component, loader, or server

#### 🧩 What is it?
The architectural question: which layer kicks off the request? The three main homes are **inside the component** (fetch-on-effect), a **route loader** (the router fetches before rendering the screen), and **the server** (a server component or backend renders with data already in hand).

#### 🤔 Why do we need it? (the problem)
Fetching in the component is where waterfalls breed: a parent fetches, renders a child, the child *then* fetches — each level adds a round-trip, and nothing starts until its parent has rendered. Moving the fetch outward (to a loader or the server) lets requests start **earlier** and in **parallel**, and can ship HTML with the data already baked in.

#### ⚙️ How does it work?
Same data, three places it can be fetched:

```
  COMPONENT  render -> effect -> fetch -> re-render
             (latest start; risks nested waterfalls)

  ROUTE      navigate -> loader fetches -> THEN render
  LOADER     (data ready before the screen paints)

  SERVER     server fetches -> sends HTML with data
             (no client round-trip; closest to the DB)
```

Pushing fetching *outward* — component → loader → server — generally means it starts sooner, parallelizes better, and removes the loading flicker. The trade-off: server fetching needs a server (Next.js server components, a backend), and highly interactive, user-driven data (typeahead, infinite scroll) still belongs near the component, usually via a data library.

#### 🌍 Real-life analogy
A restaurant can take your order *after* you sit down (component fetch), or have your usual ready because you ordered ahead on the app (route loader), or be a buffet where the food is already out before you arrive (server). The earlier the kitchen starts, the less you wait at the table.

#### 💻 Code example
```javascript
// SERVER (Next.js App Router): a Server Component fetches before
// any HTML is sent — no client effect, no loading flicker, no race.
async function ProfilePage({ params }) {
  const { id } = await params;            // Next 15: params is a Promise
  // Independent data fetched in PARALLEL on the server:
  const [user, posts] = await Promise.all([
    fetch(`https://api.example.com/users/${id}`).then((r) => r.json()),
    fetch(`https://api.example.com/posts?user=${id}`).then((r) => r.json()),
  ]);
  return (
    <section>
      <h1>{user.name}</h1>
      <ul>{posts.map((p) => <li key={p.id}>{p.title}</li>)}</ul>
    </section>
  );
}
// Data arrives WITH the page. The race condition simply can't happen here —
// there's no overlapping client re-render to lose to.
```

#### 🎤 Interview question
**Q: Where should you fetch data — in the component, a route loader, or on the server?**
A: Push it as far *outward* as the situation allows. Server-side (server components or a backend) is ideal for initial page data: it parallelizes, ships HTML with data, and avoids client round-trips and the effect race entirely. Route loaders fetch before the screen renders, killing nested waterfalls. Keep in-component fetching (via a data library) for highly interactive, user-triggered data like search-as-you-type or infinite scroll, where the request depends on live client state.

<h2 id="module-9">Module 9 — TanStack Query: Queries</h2>

You finally accept that server data is a *cache*, not state you own — so what manages that cache for you? **TanStack Query** (the library formerly called React Query, now on **v5**) is the answer most teams reach for. This module is about the *read* side: `useQuery`, and the four ideas that make it feel like magic — query keys, freshness vs retention, background refetching, and request deduplication.

---

### 📥 useQuery — A Key + A Promise

#### 🧩 What is it?
`useQuery` is a React hook you call inside a component to **read** server data. You hand it two things: a **query key** (a serializable array that uniquely names this data, like `['todos', userId]`) and a **query function** (a function that returns a promise resolving to the data). It returns the data, plus status flags, and stashes everything in a shared **query cache** keyed by that key.

#### 🤔 Why do we need it? (the problem)
Done by hand, every screen that fetches re-writes the same chore: a `useState` for data, one for loading, one for error, a `useEffect` to fire the request, cleanup to dodge race conditions. Two components that need the same data each fetch it separately. Nothing is cached, so navigating back re-fetches from scratch. `useQuery` collapses all of that into one line that *also* caches and shares the result.

#### ⚙️ How does it work?
- The **query key** is the cache address. Same key in two components equals the same cache entry. The key is compared by **value** (deep, order-insensitive for object fields), so `['todos', 1]` and `['todos', 1]` are the same query.
- The **query function** runs when needed and must return a promise. Whatever it resolves to becomes `data`.
- On first use of a key, the data is fetched and stored. Next time that key is requested, the cached value is served instantly.

```
  Component calls useQuery({ queryKey: ['todos', 1] })
        │
        ▼
  ┌───────────────────────────┐
  │       QUERY CACHE         │
  │  key ['todos',1] → data   │  ← stored here, keyed by key
  │  key ['user', 1] → data   │
  └───────────────────────────┘
        │ already present? serve it. else run fn()
        ▼
  returns { data, isPending, isError, ... }
```

#### 🌍 Real-life analogy
Think of a **coat-check counter**. You hand over a numbered ticket (the query key); the attendant either gives you the coat already on that hook (cached data) or, if the hook is empty, goes and fetches it (runs the query function) and hangs it there for next time. Everyone holding ticket "42" gets the *same* coat — nobody fetches their own copy.

#### 💻 Code example
```javascript
import { useQuery } from '@tanstack/react-query';

function fetchTodos(userId) {
  return fetch(`/api/todos?user=${userId}`).then((r) => r.json());
}

function TodoList({ userId }) {
  const { data, isPending, isError, error } = useQuery({
    queryKey: ['todos', userId],   // the cache address
    queryFn: () => fetchTodos(userId), // returns a promise
    staleTime: 30_000,             // data is FRESH for 30s (see next topic)
  });

  if (isPending) return <p>Loading…</p>;     // initial load, no cached data yet
  if (isError) return <p>{error.message}</p>; // queryFn rejected
  return <ul>{data.map((t) => <li key={t.id}>{t.title}</li>)}</ul>;
}
// Mount with userId=1 → fetches once, caches under ['todos', 1].
// A second <TodoList userId={1}/> reuses that cache — no new request.
```

#### 🎤 Interview question
**Q: What are the two things `useQuery` needs, and what does the query key do?**
A: A **query key** and a **query function**. The query function returns a promise that resolves to the data. The query key — a serializable array — uniquely identifies that data in the **query cache**; it's how the library decides whether two components share a cached result, when to refetch, and what to invalidate. Same key equals same cache entry.

---

### ⏳ staleTime vs gcTime — Fresh, Stale, and Collected

#### 🧩 What is it?
Two different timers control a query's life. **`staleTime`** is how long fetched data is considered **FRESH** — during this window TanStack Query trusts the cache and will *not* refetch. **`gcTime`** (garbage-collection time) is how long an **UNUSED** query is kept in the cache before it's deleted entirely. They answer two different questions: "is this data still good?" vs "should we even keep it around?".

#### 🤔 Why do we need it? (the problem)
A single knob can't express "show this instantly but quietly check for updates." You want some data (a user's profile) treated as fresh for minutes, and other data (a live price) treated as stale immediately. And separately, you don't want the cache to grow forever — once nothing on screen uses a query, it should eventually be cleaned up. Two timers, two jobs.

#### ⚙️ How does it work?
- **`staleTime`** — default **`0`**, meaning data is stale the instant it arrives. While **fresh**, no automatic refetch happens. Once the `staleTime` elapses, the data is **stale** and becomes eligible for background refetch (on mount, window focus, reconnect).
- **`gcTime`** — default **5 minutes** (this is the v5 name; it was called **`cacheTime`** before v5). The clock starts only when the query becomes **inactive** — no mounted component is using that key. If it stays unused for `gcTime`, the entry is garbage-collected and removed from the cache.

```
  fetch done          staleTime ends         last observer unmounts
      │                    │                          │
      ▼                    ▼                          ▼
  [── FRESH ──────][──── STALE (still cached) ────][ INACTIVE ]
   no refetch       served instantly +              gcTime clock
                    background refetch when          starts → after
                    triggered                        gcTime: REMOVED
```
Key point: **stale ≠ deleted.** Stale data is still in the cache and still shown instantly — it's just allowed to be refreshed. `gcTime` only deletes data that no component is using.

#### 🌍 Real-life analogy
Milk in your fridge has two dates. The **"best before"** date is `staleTime` — past it the milk is still drinkable (still served), you just give it a sniff before relying on it (background refetch). The decision to actually **throw it out** only happens once nobody's reaching for it anymore, and only after it's sat unused for a while — that's `gcTime`.

#### 💻 Code example
```javascript
useQuery({
  queryKey: ['profile', userId],
  queryFn: () => fetchProfile(userId),
  staleTime: 5 * 60_000, // FRESH for 5 min: no refetch on focus/mount in window
  gcTime: 10 * 60_000,   // if unused, kept 10 min then garbage-collected
});

// staleTime 0  (default): every mount/focus while stale → background refetch
// staleTime Infinity     : never auto-stale; only manual invalidation refetches
```

#### 🎤 Interview question
**Q: What's the difference between `staleTime` and `gcTime`?**
A: `staleTime` (default `0`) is how long data is considered **fresh** — within it, no refetch happens; after it, data is **stale** and eligible for background refetch. `gcTime` (default **5 minutes**, renamed from `cacheTime` in v5) is how long an **inactive** query — one no component is using — stays in the cache before being garbage-collected. One governs *freshness*, the other governs *retention*; stale data is still cached and shown, gc'd data is gone.

---

### 🔄 Background Refetching — Stale-While-Revalidate

#### 🧩 What is it?
When data is **stale**, TanStack Query does two things at once: it shows you the **cached value immediately**, and it **refetches in the background** to get a fresh copy. This pattern is called **stale-while-revalidate** — never make the user stare at a spinner for data you already have, but quietly keep it up to date.

#### 🤔 Why do we need it? (the problem)
A pure cache risks showing outdated data forever. A pure refetch-every-time shows a spinner on every visit. Stale-while-revalidate gives you the best of both: instant UI from cache, *plus* a silent refresh so the data self-corrects. The user sees something immediately and it quietly becomes accurate.

#### ⚙️ How does it work?
A stale query refetches automatically on these triggers (all on by default):
- **on mount** — a component using a stale key mounts.
- **on window focus** — you tab back to the browser (`refetchOnWindowFocus`).
- **on reconnect** — the network comes back (`refetchOnReconnect`).

While that background refetch runs, your cached `data` stays visible and `isFetching` flips to `true`.

```
  Visit screen (data is STALE)
        │
        ▼
  show cached data NOW ──────────► UI not blocked
        │
        └─ in background: refetch ─► resolves
                                      │
                                      ▼
                            cache updated, UI re-renders
                            with fresh data (no spinner)
```
This is why two flags exist: **`isPending`** is the *initial* load when there's no cached data to show; **`isFetching`** is *any* fetch in flight, including a silent background one over existing data.

#### 🌍 Real-life analogy
It's a **newspaper on your doorstep**. You pick up this morning's paper and start reading right away (cached data shown instantly) while the delivery person is already out printing and dropping tomorrow's edition (background refetch). You never wait at an empty doorstep — yesterday's paper is there until the new one quietly replaces it.

#### 💻 Code example
```javascript
const { data, isPending, isFetching } = useQuery({
  queryKey: ['prices'],
  queryFn: fetchPrices,
  staleTime: 0, // stale immediately → refetches on focus/mount/reconnect
});

// isPending  → true ONLY on the very first load (no cached data yet)
// isFetching → true whenever a request is in flight, including background ones
return (
  <div>
    {isFetching && <Spinner small />}  {/* subtle "refreshing" hint */}
    <PriceTable rows={data} />          {/* old data stays visible meanwhile */}
  </div>
);
```

#### 🎤 Interview question
**Q: What is stale-while-revalidate in TanStack Query, and how is `isFetching` different from `isPending`?**
A: When data is stale, the library serves the **cached value instantly** and **refetches in the background** (on mount, window focus, or reconnect), then updates the UI — so the user never waits for data you already have. `isPending` is true only on the **initial** load when there's no cached data; `isFetching` is true during **any** request, including a silent background refetch over data that's already on screen.

---

### 🧬 Deduplication, Flags & Dependent Queries

#### 🧩 What is it?
**Deduplication** means that if several components request the **same query key while a fetch is already in flight**, they all share that **one** request instead of each firing their own. Alongside it: the status flags (`isPending` / `isFetching` / `isError`), `enabled` for **dependent/conditional** queries, and `select` to transform or narrow the data.

#### 🤔 Why do we need it? (the problem)
Render a page where a header, a sidebar, and a list all call `useQuery(['user', 1])` on mount and you'd naively fire three identical network requests. Dedup makes it **one**. And sometimes a query *can't* run yet — it needs an id from a *previous* query. Without a guard you'd fetch with `undefined`. `enabled` lets a query wait until its inputs exist.

#### ⚙️ How does it work?
- **Deduplication** — identical in-flight keys are coalesced into a single request; all callers receive the same resolved data. Combined with **structural sharing** (TanStack Query reuses unchanged parts of the previous result object), components avoid needless re-renders.
- **Flags** — `isPending` (initial load, no data yet), `isFetching` (any request in flight), `isError` (the query function rejected; `error` holds why). v5 renamed the old `isLoading` flag to **`isPending`**. *(`isLoading` still exists in v5, but is now defined as `isPending && isFetching` — i.e. true only on the very first fetch.)*
- **`enabled`** — set it to a boolean; while `false`, the query is **disabled** (never runs). Perfect for dependent queries: enable it only once the dependency is ready.
- **`select`** — a function that transforms `data` before you receive it (e.g. pick one field). It runs without changing what's stored in the cache.

```
  Header  ─┐
  Sidebar ─┼─ all call useQuery(['user', 1]) ──► ONE request
  List    ─┘                                       │
                                                   ▼
                                       resolves once, shared by all

  Dependent:  ['user', id] ──resolves──► user.teamId
                                            │ enabled: !!user.teamId
                                            ▼
                              ['team', teamId]  (waits until ready)
```

#### 🌍 Real-life analogy
Dedup is a **group coffee order**. Three coworkers want the same latte while the barista is already making it — the barista doesn't start three machines; one drink is split, or rather one order covers them all. The dependent query is **booking a connecting flight**: you can't pick seat on the second leg until the first leg's confirmation number exists — `enabled` is "don't even try until you have it."

#### 💻 Code example
```javascript
// 1) First query: get the user
const userQuery = useQuery({
  queryKey: ['user', userId],
  queryFn: () => fetchUser(userId),
});

// 2) Dependent query: needs userQuery's result → gate it with `enabled`
const teamId = userQuery.data?.teamId;
const teamQuery = useQuery({
  queryKey: ['team', teamId],
  queryFn: () => fetchTeam(teamId),
  enabled: !!teamId, // disabled until teamId exists → never fetches `undefined`
  select: (team) => team.name, // receive just the name, not the whole object
});

// While disabled, teamQuery.isPending stays true and queryFn never runs.
// Three components calling useQuery(['user', userId]) at once → ONE request.
```

#### 🎤 Interview question
**Q: How does TanStack Query dedupe requests, and how do you run a query that depends on another?**
A: If multiple components request the **same query key while a fetch is in flight**, the library coalesces them into a **single** request and shares the result — no duplicate network calls. For a dependent query, you gate it with **`enabled`**: keep it `false` (so it never runs) until the value it needs from the first query exists, e.g. `enabled: !!teamId`. You can also pass `select` to transform the data each component receives without touching the cached value.

<h2 id="module-10">Module 10 — TanStack Query: Mutations & Cache Updates</h2>

Reading data (queries) is only half the story. Real apps also **write** — adding a todo, liking a post, deleting a comment. And the instant a write succeeds, every screen showing that data is suddenly **wrong** until it catches up. This module is about the write side of TanStack Query (React Query v5): how `useMutation` runs a write, how **invalidation** tells stale queries to refetch, how **optimistic updates** make the UI feel instant, and when to write the cache directly versus letting the server stay the source of truth.

---

### ✍️ useMutation — The Hook for Writes

#### 🧩 What is it?
`useMutation` is the React Query hook for **changing** server data — the `POST`, `PUT`, `PATCH`, and `DELETE` side of things. Where `useQuery` *reads* and caches, `useMutation` *writes* and gives you back functions and callbacks to run the write on demand.

#### 🤔 Why do we need it? (the problem)
A query runs automatically when a component mounts — that is exactly what you want for *reading*. But a write should happen when the **user does something** (clicks "Save"), not on mount. You also need to track that one specific action: is it pending, did it fail, did it succeed? Hand-rolling that means juggling your own `isSaving` and `error` flags on every form. `useMutation` packages all of it.

#### ⚙️ How does it work?
You give `useMutation` a **mutation function** (an `async` function that does the write and returns the server's response). It hands back an object with:

- `mutate(variables)` — fire-and-forget; call it to start the write.
- `mutateAsync(variables)` — same, but returns a **Promise** you can `await`.
- `isPending`, `isError`, `isSuccess`, `data`, `error` — the live status.
- Lifecycle **callbacks** you pass in: `onSuccess`, `onError`, `onSettled`, `onMutate`.

```
   user clicks "Add"
        │
        ▼
   mutate(newTodo) ───▶ mutationFn runs (POST /todos)
        │                      │
        │            ┌─────────┴──────────┐
        │            ▼                    ▼
        │        succeeds             throws
        │            │                    │
        │       onSuccess            onError
        │            └────────┬───────────┘
        │                     ▼
        │                 onSettled   (runs either way)
```

`onSettled` always runs last, whether the write succeeded or failed — it is the "finally" of mutations.

#### 🌍 Real-life analogy
A query is like **subscribing to a magazine** — it just shows up regularly. A mutation is like **mailing a letter**: nothing happens until *you* drop it in the box (`mutate`). Then you can get a "delivered" notice (`onSuccess`), a "return to sender" (`onError`), or — either way — a note that the trip is over (`onSettled`).

#### 💻 Code example
```javascript
import { useMutation } from '@tanstack/react-query';

function AddTodo() {
  // The mutation function does the actual write and returns the result.
  const addTodo = useMutation({
    mutationFn: async (text) => {
      const res = await fetch('/api/todos', {
        method: 'POST',
        body: JSON.stringify({ text }),
      });
      if (!res.ok) throw new Error('Failed to add'); // throwing => onError
      return res.json();                              // returning => onSuccess
    },
    onSuccess: (data) => console.log('Saved todo', data.id),
    onError: (err) => console.log('Write failed:', err.message),
    onSettled: () => console.log('Done (success OR failure)'),
  });

  return (
    <button
      disabled={addTodo.isPending}            // true while the POST is in flight
      onClick={() => addTodo.mutate('Buy milk')}
    >
      {addTodo.isPending ? 'Adding…' : 'Add todo'}
    </button>
  );
}
```

#### 🎤 Interview question
**Q: How is `useMutation` different from `useQuery`, and what do `mutate` vs `mutateAsync` give you?**
A: `useQuery` reads and **auto-runs** on mount to populate a cache; `useMutation` writes and runs **only when you call it**. `mutate(vars)` is fire-and-forget — you handle results in the `onSuccess`/`onError` callbacks. `mutateAsync(vars)` returns a **Promise**, so you can `await` it and use `try/catch` — handy when one click chains several writes. With `mutateAsync` you must catch the rejection yourself or it becomes an unhandled promise rejection.

---

### 🔄 Invalidation — Telling Stale Queries to Refetch

#### 🧩 What is it?
**Invalidation** is how you tell React Query: *"the data behind these query keys just changed — treat it as stale and refetch it."* You do it with `queryClient.invalidateQueries({ queryKey: [...] })`, usually right after a successful write.

#### 🤔 Why do we need it? (the problem)
You just added a todo with a `POST`. But your todo **list** was loaded by a separate `useQuery(['todos'])` and is sitting in the cache, blissfully unaware that a new row exists on the server. Without a nudge, the list keeps showing the old data until something else triggers a refetch. Invalidation is that nudge — it keeps the read side honest after a write.

#### ⚙️ How does it work?
`invalidateQueries` takes a **filters object** — `{ queryKey }` is the common one. Any cached query whose key **matches** (by prefix) is marked **stale**, and if it is currently rendered on screen, it **refetches immediately**.

```
   POST /todos succeeds
        │
        ▼
   queryClient.invalidateQueries({ queryKey: ['todos'] })
        │
        ▼
   every query starting with ['todos'] → marked STALE
        │
        ├── ['todos']            → on screen → refetch now
        ├── ['todos', 'active']  → on screen → refetch now
        └── ['todos', { id: 7 }] → not rendered → refetch when used
```

Key detail: matching is by **prefix**, so invalidating `['todos']` also hits `['todos', 'active']` and `['todos', { id: 7 }]`. One call resyncs a whole family of related queries.

#### 🌍 Real-life analogy
Think of a **library noticeboard**. You don't walk to every reader and update them — you just stamp the relevant flyers "OUT OF DATE." Anyone standing at the board (a query on screen) immediately fetches a fresh flyer; anyone who walks up later gets the fresh one too. The stamp is `invalidateQueries`; the prefix match is "stamp every flyer in the *Todos* section."

#### 💻 Code example
```javascript
import { useMutation, useQueryClient } from '@tanstack/react-query';

function AddTodo() {
  const queryClient = useQueryClient();

  const addTodo = useMutation({
    mutationFn: (text) =>
      fetch('/api/todos', { method: 'POST', body: JSON.stringify({ text }) })
        .then((r) => r.json()),
    onSuccess: () => {
      // Mark the todos family stale -> visible lists refetch automatically.
      queryClient.invalidateQueries({ queryKey: ['todos'] });
    },
  });

  return <button onClick={() => addTodo.mutate('Walk dog')}>Add</button>;
}
```

#### 🎤 Interview question
**Q: After a mutation succeeds, how do you make sure every view shows the fresh data?**
A: Call `queryClient.invalidateQueries({ queryKey: [...] })` in `onSuccess` (or `onSettled`). It marks all queries whose key **prefix-matches** as stale; any that are mounted refetch right away, and the rest refetch the next time they're used. Because one cache backs every component, invalidating once keeps **all** views in sync — you don't update components manually. The trade-off is an extra network round-trip, which optimistic updates can hide.

---

### ⚡ Optimistic Updates — Instant UI, Roll Back on Failure

#### 🧩 What is it?
An **optimistic update** updates the cache **immediately** — *before* the server replies — so the UI reacts instantly. You're betting ("optimistically") that the write will succeed. If it doesn't, you **roll back** to exactly how things looked before.

#### 🤔 Why do we need it? (the problem)
Even a fast server takes 100–300ms. If you wait for the response before touching the UI, every "like" and "add" feels laggy. Optimistic updates remove that wait — the checkbox ticks the instant you click. But naively faking success is dangerous: if the write fails, the screen now shows a lie. The classic pattern fixes this with a **snapshot and rollback**.

#### ⚙️ How does it work?
This is the canonical v5 `onMutate` / `onError` / `onSettled` pattern. Four steps:

1. **`onMutate`** runs *before* the mutation function. Inside it you:
   - **cancel** any in-flight refetches for that key (`cancelQueries`) so a slow response can't overwrite your optimistic value;
   - **snapshot** the current cache (`getQueryData`) — your rollback point;
   - **optimistically set** the new value (`setQueryData`);
   - **return** the snapshot as a **context** object.
2. **`onError`** receives that context and **rolls back** with `setQueryData(key, context.previous)`.
3. **`onSettled`** **invalidates** the key so the cache resyncs with the server's real truth.

```
   onMutate (BEFORE the request)
     ├─ cancelQueries  → stop in-flight refetch racing us
     ├─ getQueryData   → SNAPSHOT  (previous)
     ├─ setQueryData   → write optimistic value (UI updates NOW)
     └─ return { previous }   ──┐  (context)
                                │
   request runs ───────┬────────┘
                       │
          ┌────────────┴─────────────┐
          ▼                          ▼
       success                    error
          │                          │
          │                   onError(err, vars, ctx)
          │                   setQueryData(key, ctx.previous)
          │                          │   ← ROLL BACK
          └────────────┬─────────────┘
                       ▼
                  onSettled → invalidateQueries (resync w/ server)
```

#### 🌍 Real-life analogy
It's like **writing a check at the store**. You walk out with the goods *immediately* — you don't wait for the bank to clear it (instant UI). You keep your receipt stub as proof of what your balance *was* (the snapshot). If the check bounces (the write fails), you undo the purchase — return the goods, restore your balance — using that stub (rollback). Either way you reconcile with the bank statement at month's end (`onSettled` invalidation).

#### 💻 Code example
```javascript
import { useMutation, useQueryClient } from '@tanstack/react-query';

function ToggleTodo({ id }) {
  const queryClient = useQueryClient();
  const key = ['todos'];

  const toggle = useMutation({
    mutationFn: (todo) =>
      fetch(`/api/todos/${todo.id}`, {
        method: 'PUT',
        body: JSON.stringify({ done: !todo.done }),
      }).then((r) => {
        if (!r.ok) throw new Error('Toggle failed');
        return r.json();
      }),

    // 1) BEFORE the request — update the cache optimistically.
    onMutate: async (todo) => {
      // Stop in-flight refetches so they can't clobber our optimistic write.
      await queryClient.cancelQueries({ queryKey: key });

      // Snapshot the current value — this is our rollback point.
      const previous = queryClient.getQueryData(key);

      // Optimistically flip `done` for this todo in the cache.
      queryClient.setQueryData(key, (old = []) =>
        old.map((t) => (t.id === todo.id ? { ...t, done: !t.done } : t))
      );

      // Whatever we return becomes `context` in onError / onSettled.
      return { previous };
    },

    // 2) On failure — restore the snapshot we took above.
    onError: (_err, _todo, context) => {
      if (context?.previous !== undefined) {
        queryClient.setQueryData(key, context.previous); // ROLL BACK
      }
    },

    // 3) Either way — resync with the server's real truth.
    onSettled: () => {
      queryClient.invalidateQueries({ queryKey: key });
    },
  });

  return <input type="checkbox" onChange={() => toggle.mutate({ id, done: false })} />;
}
```
> **Note (simplification):** the example uses a flat `['todos']` list for clarity. Real apps often have per-item keys like `['todos', id]` too — you'd cancel, snapshot, and roll back each affected key. The four-step shape (`cancelQueries` → `getQueryData` → `setQueryData` → return context) is identical regardless of how many keys you touch.

#### 🎤 Interview question
**Q: Walk me through an optimistic update with rollback in React Query v5.**
A: In `onMutate` (which runs *before* the request): `await cancelQueries` for the key so an in-flight refetch can't overwrite you, take a snapshot with `getQueryData`, write the optimistic value with `setQueryData`, and `return` the snapshot as context. In `onError`, roll back by calling `setQueryData(key, context.previous)`. In `onSettled`, call `invalidateQueries` to reconcile with the server's actual state. Cancelling matters because without it a slow background refetch could land *after* your optimistic write and undo it.

### 🎯 setQueryData vs Invalidate — Two Ways to Refresh

#### 🧩 What is it?
After a write you have two ways to update what the user sees: **`queryClient.setQueryData(key, updater)`** writes the new data straight into the cache (no network), or **`invalidateQueries`** marks the cache stale and lets it **refetch** from the server. They answer the same question — "show fresh data" — in opposite ways.

#### 🤔 Why do we need both? (the problem)
Often your `POST`/`PUT` response **already contains** the created or updated record. Invalidating then would fire a *second* request to fetch data you already hold — wasteful. Other times you only changed one field but a dozen derived values depend on it, and you'd rather trust the **server** to recompute the whole truth than patch the cache by hand. Two situations, two right answers.

#### ⚙️ How does it work?
- **`setQueryData(key, updater)`** — synchronously replaces the cached value. The `updater` receives the old data and returns the new data. No round-trip; the UI updates instantly. Use it when the **server response already gives you the new data**.
- **`invalidateQueries({ queryKey })`** — marks stale and refetches. Use it when you want the **server to be the source of truth**, or when one change ripples into many queries you can't easily patch.

```
   setQueryData                      invalidateQueries
   ─────────────                     ─────────────────
   write new data INTO cache         mark cache STALE
   no network call                   triggers a refetch
   instant                           one round-trip
   "I already HAVE the new data"     "let the SERVER decide"
```

A common belt-and-suspenders combo: `setQueryData` for instant feedback, **then** `invalidateQueries` in `onSettled` to confirm against the server.

#### 🌍 Real-life analogy
`setQueryData` is **updating your address book yourself** because your friend just told you their new number to your face — you have the answer, so write it down. `invalidateQueries` is **calling the front desk to re-confirm** — you trust them as the official record, so you ask them rather than guess. You write it yourself when you already know; you re-confirm when the official source should decide.

#### 💻 Code example
```javascript
// CASE A — server returns the new todo: write it straight in, no refetch.
const addTodo = useMutation({
  mutationFn: (text) =>
    fetch('/api/todos', { method: 'POST', body: JSON.stringify({ text }) })
      .then((r) => r.json()), // -> the full new todo, e.g. { id: 9, text, done: false }
  onSuccess: (newTodo) => {
    queryClient.setQueryData(['todos'], (old = []) => [...old, newTodo]);
    // No invalidate needed — the cache already holds the server's exact data.
  },
});

// CASE B — change ripples into many derived queries: let the server decide.
const archiveAll = useMutation({
  mutationFn: () => fetch('/api/todos/archive', { method: 'POST' }),
  onSuccess: () => {
    // counts, filters, summaries all depend on this — refetch the family.
    queryClient.invalidateQueries({ queryKey: ['todos'] });
  },
});
```

#### 🎤 Interview question
**Q: When do you use `setQueryData` versus invalidate-and-refetch, and how does one cache keep multiple views in sync?**
A: Use **`setQueryData`** when the mutation response already contains the new data — you write it into the cache directly and skip a redundant round-trip. Use **`invalidateQueries`** when the server should be the source of truth, or when one change affects many derived queries that are awkward to patch by hand. They stay in sync because **every component reads from one shared cache** keyed by query key: update or invalidate that key once, and every `useQuery` subscribed to it re-renders with the new data — no manual prop-passing between views.

<h2 id="module-11">Module 11 — Normalized Caching & RTK Query</h2>

You fetched a list of posts, each with its author baked in. Then the author renames themselves — and suddenly the same person shows two different names across your app, because one screen has the old copy and another has the new one. This module is about the two ways a cache can store data (as whole **documents** or as **normalized entities**), and about **RTK Query**, Redux Toolkit's data-fetching layer that caches by endpoint and refreshes data using **tags**.

---

### 📦 Document Cache vs Normalized Cache — Two Ways to Store the Same Data

#### 🧩 What is it?
A **document cache** stores data the way it arrived: each query key (like `["posts"]`) keeps its own blob — its own *document* — of JSON. TanStack Query (from Module 9) works this way. A **normalized cache** instead breaks that JSON apart and stores each entity (each user, each post) **once, by its id**, like rows in a tiny database, with other places holding only a *reference* to it. RTK Query with `createEntityAdapter`, and Apollo for GraphQL, work this way.

#### 🤔 Why do we need it? (the problem)
The trouble is **shared, relational data**. The same `user` object can appear inside many different queries — the post list, the comments, the profile sidebar. In a document cache, each of those queries holds its *own copy* of that user. So when the user updates their name, you have not one place to fix but *many* — and any copy you miss is now silently stale and wrong. A normalized cache stores that user once, so one update is seen everywhere.

#### ⚙️ How does it work?
A document cache keeps a separate, self-contained blob per key:

```
 DOCUMENT CACHE (one blob per query key)

 key ["posts"]      -> [ {id:10, author:{id:1,name:"Ada"}} ,
                         {id:11, author:{id:1,name:"Ada"}} ]
 key ["user", 1]    -> { id:1, name:"Ada" }

 "Ada" is copied 3 times. Rename = fix 3 spots.
```

A normalized cache splits entities out and links them by id:

```
 NORMALIZED CACHE (each entity stored ONCE)

 users:  { 1: {id:1, name:"Ada"} }
 posts:  { 10:{id:10, author:1},
           11:{id:11, author:1} }

 "Ada" lives in ONE spot. Rename once -> everywhere.
```

> **Simplification:** TanStack Query *can* be nudged toward sharing data (e.g. one query reading from another), but its native model is document-per-key. RTK Query caches per endpoint by default; you reach for `createEntityAdapter` when you want true id-keyed normalization.

#### 🌍 Real-life analogy
A document cache is like keeping a **photocopy of a customer's address stapled to every one of their invoices**. They move house, and now you must hunt down and re-staple every invoice — miss one and you ship to the wrong place. A normalized cache is a **spreadsheet with a Customers sheet and an Invoices sheet**, where each invoice just writes the customer's id. Change the address in the Customers sheet once, and every invoice that points to that id is instantly correct.

#### 💻 Code example
```javascript
// SAME data, two shapes.

// Document shape (TanStack Query style): author copied into each post.
const postsDoc = [
  { id: 10, title: "Hi",  author: { id: 1, name: "Ada" } },
  { id: 11, title: "Bye", author: { id: 1, name: "Ada" } },
];
// To rename Ada -> Grace, you must edit BOTH copies. Miss one = stale.

// Normalized shape: author stored once, posts hold only the id.
const normalized = {
  users: { 1: { id: 1, name: "Ada" } },
  posts: {
    10: { id: 10, title: "Hi",  author: 1 },
    11: { id: 11, title: "Bye", author: 1 },
  },
};
// Rename in ONE place:
normalized.users[1].name = "Grace";
// Every post that references author 1 now reads "Grace". No hunting.
```

#### 🎤 Interview question
**Q: What's the difference between a document cache and a normalized cache?**
A: A document cache (TanStack Query) stores a separate blob of data per query key, so a shared entity gets duplicated across keys and must be updated in each. A normalized cache (RTK Query with `createEntityAdapter`, Apollo) stores each entity once by its id and lets other entries reference it, so one update propagates everywhere — at the cost of more setup.

### 🗂️ Normalization — Flattening Nested Data into Tables by Id

#### 🧩 What is it?
**Normalization** is the act of turning nested, tree-shaped JSON into flat **tables keyed by id** — one table per entity type. Instead of a post *containing* its author, you keep a `users` table and a `posts` table, and the post just stores `author: 1`. Each entity is stored exactly **once**.

#### 🤔 Why do we need it? (the problem)
APIs return data nested for convenience — a post with its author and comments embedded. But nesting *duplicates* anything shared: the same author appears inside every one of their posts. Duplication means updates don't propagate (you fix one copy, others stay stale) and memory bloats. Flattening removes the duplication so there is a single source of truth per entity.

#### ⚙️ How does it work?
You walk the nested data, pull each entity into its type's table under its id, and replace the inline object with just its id:

```
 NESTED (from the API)
 post
  ├─ id: 10
  ├─ title: "Hi"
  └─ author
       ├─ id: 1
       └─ name: "Ada"

         normalize ⬇  (split by type, key by id)

 users: { 1: { id:1, name:"Ada" } }
 posts: { 10:{ id:10, title:"Hi", author:1 } }
          (author object  ->  author id)
```

To read a post back, you "denormalize": look up `post.author` (1) in the `users` table. The id is a **reference**, exactly like a foreign key in a relational database.

#### 🌍 Real-life analogy
It's the difference between a **paper recipe that re-prints the full butter supplier's details on every recipe card**, and a proper **pantry inventory database**: one Suppliers table, one Ingredients table, and recipes that just reference "supplier #1". Update the supplier once in the inventory, and every recipe pointing at #1 is current. The database avoids writing the same fact twice — that's normalization.

#### 💻 Code example
```javascript
// A tiny normalizer: nested posts -> tables keyed by id.
function normalizePosts(posts) {
  const result = { users: {}, posts: {} };
  for (const post of posts) {
    const author = post.author;
    result.users[author.id] = author;          // store user ONCE
    result.posts[post.id] = {
      id: post.id,
      title: post.title,
      author: author.id,                        // keep only the reference
    };
  }
  return result;
}

const api = [
  { id: 10, title: "Hi",  author: { id: 1, name: "Ada" } },
  { id: 11, title: "Bye", author: { id: 1, name: "Ada" } },
];

console.log(normalizePosts(api));
// {
//   users: { '1': { id: 1, name: 'Ada' } },          <- one entry
//   posts: {
//     '10': { id: 10, title: 'Hi',  author: 1 },
//     '11': { id: 11, title: 'Bye', author: 1 }
//   }
// }
```

#### 🎤 Interview question
**Q: What does it mean to normalize cached data, and why do it?**
A: To flatten nested JSON into tables keyed by entity id — one table per type — so each entity is stored exactly once and other records reference it by id. You do it to kill duplication: a shared entity has a single source of truth, so updating it propagates to every reference automatically instead of leaving stale copies behind.

### 🔌 RTK Query — Endpoints, Auto-Generated Hooks, and Caching by Args

#### 🧩 What is it?
**RTK Query** is the data-fetching and caching layer built into Redux Toolkit. You define an **API slice** with a set of **endpoints** (each describing one request), and RTK Query **auto-generates React hooks** for them — define a `getTodos` query endpoint and you get a `useGetTodosQuery()` hook for free. It caches each result by **endpoint name + arguments** and shares it across every component that calls the hook.

#### 🤔 Why do we need it? (the problem)
Doing server data by hand in Redux means writing thunks, actions, reducers, and loading/error flags for *every* endpoint — huge boilerplate, and you still hand-roll caching and dedup. RTK Query collapses all of that: you describe *what* to fetch, and it generates the hooks, manages the cache, dedupes identical in-flight requests, and tracks loading state for you. If your app already uses Redux, it keeps server data in the same store.

#### ⚙️ How does it work?
You declare endpoints; RTK Query builds hooks and a per-args cache:

```
 createApi
   endpoints:
     getTodos  (query)     -> useGetTodosQuery()
     addTodo   (mutation)  -> useAddTodoMutation()

 CACHE keyed by endpoint + args:
   getTodos()          -> [ ...todos ]
   getTodo({ id: 5 })  -> { id:5, ... }

 Two components calling useGetTodosQuery()
 share ONE cache entry (deduped, one request).
```

Each cached query entry has a lifecycle: it's kept while components subscribe to it, and garbage-collected a short time after the last component unmounts (default ~60s). Arguments are part of the cache key, so `getTodo({id:5})` and `getTodo({id:6})` are separate entries.

#### 🌍 Real-life analogy
RTK Query is like a **restaurant's order desk**. You hand it a written ticket (the endpoint + its args — "table 5, todo #5"); it knows how to fetch that, and if three waiters hand in the *same* ticket at once, the kitchen cooks it **once** and serves all three (deduplication). The desk keeps recent orders on the pass for a bit in case someone asks again, then clears them.

#### 💻 Code example
```javascript
import { createApi, fetchBaseQuery } from "@reduxjs/toolkit/query/react";

export const todosApi = createApi({
  reducerPath: "todosApi",
  baseQuery: fetchBaseQuery({ baseUrl: "/api/" }),
  tagTypes: ["Todo"],                         // entity types we tag (next topic)
  endpoints: (builder) => ({
    // QUERY endpoint -> generates useGetTodosQuery()
    getTodos: builder.query({
      query: () => "todos",                   // GET /api/todos
    }),
    // MUTATION endpoint -> generates useAddTodoMutation()
    addTodo: builder.mutation({
      query: (body) => ({ url: "todos", method: "POST", body }),
    }),
  }),
});

// Hooks are AUTO-GENERATED from the endpoint names:
export const { useGetTodosQuery, useAddTodoMutation } = todosApi;

// In a component:
// const { data, isLoading, isError } = useGetTodosQuery();
// const [addTodo] = useAddTodoMutation();
```

#### 🎤 Interview question
**Q: What are RTK Query endpoints and where do the hooks come from?**
A: An endpoint is a declaration of one request — a `query` (read) or `mutation` (write) — inside an `createApi` API slice. RTK Query auto-generates a React hook per endpoint from its name (`getTodos` becomes `useGetTodosQuery`), and caches each query result by endpoint name plus its arguments, deduping and sharing that entry across all subscribers.

### 🏷️ Tag-Based Invalidation — How a Write Refreshes Exactly the Right Reads

#### 🧩 What is it?
**Tag-based invalidation** is how RTK Query keeps cached data fresh after a change. Query endpoints declare which cache tags they **provide** (`providesTags`), and mutation endpoints declare which tags they **invalidate** (`invalidatesTags`). When a mutation runs, RTK Query finds every cached query carrying a matching tag and automatically refetches it.

#### 🤔 Why do we need it? (the problem)
After you add a todo, your cached todo *list* is now out of date. Something has to refresh it. Without a system you'd manually figure out which queries to refetch after each write — fragile and easy to forget. Tags make the dependency **declarative**: the list says "I provide `Todo` data", the add-mutation says "I invalidate `Todo`", and RTK Query connects them so the right — and *only* the right — queries refresh.

#### ⚙️ How does it work?
Think of tags as labels on cache entries; a mutation throws away the labels it names:

```
 getTodos  providesTags: ['Todo']   (list tagged Todo)
 addTodo   invalidatesTags: ['Todo']

   addTodo runs
        │ invalidates tag 'Todo'
        ▼
 every cached query providing 'Todo'  -> marked stale
        ▼
 RTK Query auto-refetches getTodos -> fresh list
```

For precision, tags can carry an id: a query can provide `{ type:'Todo', id: 5 }`, and a mutation that edits todo 5 invalidates exactly that one — so editing one todo doesn't needlessly refetch unrelated ones. This is RTK Query's parallel to TanStack Query's `invalidateQueries` from Module 10, but driven by entity tags instead of query keys.

#### 🌍 Real-life analogy
Tags are like **color-coded sticky flags on filing cabinet drawers**. Every drawer holding "Todo" paperwork gets a red flag. When a new todo arrives in the mail (a mutation), the clerk doesn't re-check every drawer in the building — they just pull and refresh **every red-flagged drawer**. Add an id to the flag ("red #5") and they refresh only that one specific drawer.

#### 💻 Code example
```javascript
import { createApi, fetchBaseQuery } from "@reduxjs/toolkit/query/react";

export const todosApi = createApi({
  reducerPath: "todosApi",
  baseQuery: fetchBaseQuery({ baseUrl: "/api/" }),
  tagTypes: ["Todo"],
  endpoints: (builder) => ({
    getTodos: builder.query({
      query: () => "todos",
      // This query's data is tagged Todo: a list tag + one tag per row.
      providesTags: (result = []) => [
        { type: "Todo", id: "LIST" },
        ...result.map((t) => ({ type: "Todo", id: t.id })),
      ],
    }),
    addTodo: builder.mutation({
      query: (body) => ({ url: "todos", method: "POST", body }),
      // Adding a todo changes the LIST -> invalidate the list tag.
      invalidatesTags: [{ type: "Todo", id: "LIST" }],
      // RTK Query now auto-refetches getTodos. No manual refetch call.
    }),
    updateTodo: builder.mutation({
      query: ({ id, ...patch }) => ({
        url: `todos/${id}`, method: "PATCH", body: patch,
      }),
      // Editing todo #id invalidates ONLY that todo's tag.
      invalidatesTags: (result, error, { id }) => [{ type: "Todo", id }],
    }),
  }),
});

export const {
  useGetTodosQuery,
  useAddTodoMutation,
  useUpdateTodoMutation,
} = todosApi;
```

#### 🎤 Interview question
**Q: How does RTK Query's tag-based invalidation work?**
A: Query endpoints list tags they `provide` (e.g. `{ type:'Todo', id:5 }`), and mutations list tags they `invalidate`. When a mutation completes, RTK Query marks every cached query that provides a matching tag as stale and refetches the ones currently in use — so a write refreshes exactly the queries tied to that entity, no more and no less. Using an `id` in the tag scopes invalidation to a single entity instead of the whole type.

### ⚖️ The Normalization Debate — Worth the Complexity, or Overkill?

#### 🧩 What is it?
The **normalization debate** is the architectural choice between a normalized cache and a document cache. Normalized caches (RTK Query with `createEntityAdapter`, Apollo Client) store entities once by id and update everywhere automatically. Document caches (TanStack Query) keep simpler per-key blobs and refresh by refetching. Neither is "correct" — it's a trade-off.

#### 🤔 Why do we need it? (the problem)
Beginners assume normalization is always "more correct" because it mirrors a database. But it isn't free: you write entity adapters, define tags or cache ids, and reason about references — real complexity for a real team. The honest question is *does your data actually need it?* Highly relational, heavily shared data (a chat app, a project tracker where one user shows up everywhere) benefits enormously. A dashboard of mostly independent lists does not, and a document cache plus targeted invalidation is simpler and entirely sufficient.

#### ⚙️ How does it work? (the trade-off)
```
 NORMALIZED (RTK Query+adapter, Apollo)
   + one update propagates everywhere
   + great for shared / relational data
   - more setup: adapters, tags, ids
   - must reason about references

 DOCUMENT (TanStack Query)
   + simple: a blob per key
   + enough for most apps
   - shared entity can duplicate
   - refresh by refetching the key
```

A note on Apollo: it normalizes automatically using each object's `__typename` plus its id (forming a cache id like `User:1`), which is why GraphQL caches can feel "magic" — the schema gives them stable identities to normalize by. RTK Query does *not* auto-normalize across endpoints; you opt in with `createEntityAdapter` and tags.

#### 🌍 Real-life analogy
It's choosing between a **single shared master spreadsheet with linked sheets** (normalized — change a customer once, every linked invoice updates, but someone must design and maintain those links) and **handing each team their own printed report** (document — dead simple, but when the numbers change you just reprint the whole report). A small team with a few reports is fine reprinting. A bank running on shared customer records needs the linked master sheet.

#### 💻 Code example
```javascript
// Normalized: RTK Query's createEntityAdapter gives you a
// ready-made { ids: [...], entities: { id: {...} } } shape.
import { createEntityAdapter } from "@reduxjs/toolkit";

const todosAdapter = createEntityAdapter();
const initial = todosAdapter.getInitialState();
// initial === { ids: [], entities: {} }   <- normalized by design

const next = todosAdapter.setAll(initial, [
  { id: 10, title: "Hi" },
  { id: 11, title: "Bye" },
]);
// next === {
//   ids: [10, 11],
//   entities: { 10: { id:10, title:'Hi' }, 11: { id:11, title:'Bye' } }
// }
// Each todo stored ONCE, keyed by id. Updating entities[10] is seen everywhere.

// Document (TanStack Query) by contrast just stores the blob you fetched
// under its key and refetches that key when it goes stale — no entity table.
```

#### 🎤 Interview question
**Q: When is normalization worth it, and when is a document cache enough?**
A: Normalization (RTK Query with `createEntityAdapter`, or Apollo, which normalizes by `__typename` + id) pays off when data is highly relational and shared — the same entity appears across many views and must stay consistent on update. It costs extra setup and the mental overhead of references. For most apps, where data is largely independent per view, a document cache like TanStack Query plus targeted invalidation is simpler and entirely sufficient — so default to the simpler model and reach for normalization only when shared-entity consistency actually hurts.

<h2 id="module-12">Module 12 — Real-time & Synchronization</h2>

Most of this path treats fetched data as a snapshot: you ask once, you cache it, you refetch when it goes stale. But some screens must stay *live* — a chat thread, a stock ticker, a collaborative document, a "3 people are typing" indicator. The question this module answers is: how do you keep the screen in sync with a server that's changing *right now*, who pushes the update, and how does that update flow through the same query cache you already built — without two sources of truth fighting each other?

---

### 🔄 Polling — Ask Again, And Again, And Again

#### 🧩 What is it?
**Polling** means re-running a fetch on a fixed timer. Instead of waiting for the server to tell you something changed, you just keep asking: "anything new? anything new? anything new?" every few seconds. In TanStack Query this is one option: `refetchInterval`.

#### 🤔 Why do we need it? (the problem)
A normal query fetches once and then sits still until something invalidates it. For data that changes on the server *without any action from this user* — a live scoreboard, a list of incoming orders — the screen would silently go stale. Polling is the simplest possible fix: refetch on a schedule so the cache never drifts too far behind reality.

#### ⚙️ How does it work?
You set an interval; the client fires a fresh request every tick and updates the cache with whatever comes back. The trade-off is built into the mechanism: between ticks the data is stale (**lag**), and most requests come back identical to the last one (**wasted** bandwidth and server work).

```
   POLLING  (client keeps asking on a timer)
   CLIENT                         SERVER
     │  ──── any new? ──────────▶  │   t=0s
     │  ◀──── no change ─────────  │
     │  ──── any new? ──────────▶  │   t=5s
     │  ◀──── no change ─────────  │
     │  ──── any new? ──────────▶  │   t=10s
     │  ◀──── here is 1 update ──  │   (changed at 7s,
     │                             │    seen 3s late!)
```

#### 🌍 Real-life analogy
Polling is **refreshing your email inbox by hand every minute** to see if a reply arrived. Most refreshes show nothing new (wasted effort), and a reply that landed 50 seconds ago waits until your next manual refresh (lag). It works, it's dead simple, but it's clearly not how a phone *should* tell you about new mail.

#### 💻 Code example
```javascript
import { useQuery } from '@tanstack/react-query';

function LiveScore({ matchId }) {
  const { data } = useQuery({
    queryKey: ['score', matchId],
    queryFn: () => fetch(`/api/score/${matchId}`).then(r => r.json()),
    refetchInterval: 5000,        // re-ask every 5 seconds
    refetchIntervalInBackground: false, // pause when tab is hidden (saves work)
  });
  // data updates ~every 5s; worst-case staleness ≈ 5s
  return <span>{data?.home} - {data?.away}</span>;
}
```

#### 🎤 Interview question
**Q: When is polling the right choice, and what are its downsides?**
A: Polling is right when updates are infrequent or mild staleness is acceptable, and you want the simplest implementation with zero server-side infrastructure — it's just a timer around a normal request. Downsides: **lag** (you only learn of a change at the next tick) and **waste** (most polls return unchanged data, costing bandwidth and server load). For high-frequency or instant updates, a push mechanism like SSE or WebSockets is better.

### 📡 Server-Sent Events (SSE) — A One-Way Stream From the Server

#### 🧩 What is it?
**Server-Sent Events (SSE)** is a way for the **server to push** messages to the browser over a single long-lived HTTP connection. The browser opens it with the built-in `EventSource` object; the server keeps the connection open and writes messages whenever it has news. It is **one-way**: server to client only.

#### 🤔 Why do we need it? (the problem)
Polling wastes requests and lags. What you usually want is the *opposite* arrangement: stay quiet until the server actually has something, then have the server tell you immediately. SSE gives you exactly that for the common case where the client only needs to *receive* a stream — notifications, a live activity feed, log output, progress updates. And because it rides on plain HTTP, `EventSource` **auto-reconnects** if the connection drops, and can resume from the last event id.

#### ⚙️ How does it work?
The client opens one connection and then just listens. The server holds it open and emits messages over time. There is no channel back up this connection — to *send* something the client makes a normal separate HTTP request.

```
   SSE  (one connection, server pushes; client only listens)
   CLIENT                         SERVER
     │  ── open EventSource ────▶  │   (stays open)
     │  ◀──── event: update ─────  │   pushed when ready
     │  ◀──── event: update ─────  │   pushed when ready
     │        (silence — no waste while idle)
     │  ✗ connection dropped       │
     │  ── auto-reconnect ──────▶  │   EventSource retries itself
```

#### 🌍 Real-life analogy
SSE is a **live radio broadcast**. You tune in once and the station streams to you whenever it has something to say — you never call the station to ask "anything new?". You only listen; you can't talk back over the radio (that's the one-way part). And if your signal cuts out, the radio quietly re-tunes to the same station on its own.

#### 💻 Code example
```javascript
import { useEffect } from 'react';
import { useQueryClient } from '@tanstack/react-query';

// Push live server events straight into the query cache.
function useNotificationStream(userId) {
  const queryClient = useQueryClient();

  useEffect(() => {
    const source = new EventSource(`/api/notifications/${userId}`);

    source.addEventListener('new-notification', (event) => {
      const incoming = JSON.parse(event.data); // server sends JSON in event.data

      // Write the pushed item into the SAME cache the UI already reads.
      queryClient.setQueryData(['notifications', userId], (old) => {
        const list = old ?? [];
        return [incoming, ...list]; // prepend the new notification
      });
    });

    // EventSource auto-reconnects on error; just log it.
    source.onerror = () => console.warn('SSE dropped — will retry');

    return () => source.close(); // clean up the stream on unmount
  }, [userId, queryClient]);
}
```

#### 🎤 Interview question
**Q: How is SSE different from WebSockets, and when would you pick it?**
A: SSE is **one-way** (server to client) over ordinary HTTP, with the browser's `EventSource` handling reconnection automatically. WebSockets are **two-way**. Pick SSE when the client only needs to *receive* a stream — notifications, feeds, live progress, dashboards — because it's simpler, works over standard HTTP, and reconnects for free. If the client must also send messages continuously (chat, collaboration), reach for WebSockets instead.

### 🔌 WebSockets — A Two-Way Live Channel

#### 🧩 What is it?
A **WebSocket** is a persistent, **full-duplex** connection between browser and server — both sides can send messages at any time over the *same* connection. It starts as an HTTP request that "upgrades" the connection to the WebSocket protocol, after which it stays open for real-time, two-way traffic.

#### 🤔 Why do we need it? (the problem)
SSE only flows downward. But chat, multiplayer games, collaborative editors, and live cursors need messages flying *both* ways constantly and instantly — you type, others see it; they move their cursor, you see it. Opening a fresh HTTP request for every keystroke would be far too slow and heavy. A WebSocket keeps one channel open so either side can fire a message with almost no overhead.

#### ⚙️ How does it work?
After the initial upgrade handshake, the connection is symmetric: the client can `send()` and the server can push, independently, whenever they like — no request needed to receive, no waiting for a turn.

```
   COMPARISON  (who can talk, on what)
   POLLING   : client asks repeatedly  →  HTTP, 1-way pull, laggy + wasteful
   SSE       : server pushes, 1 stream →  HTTP, 1-way (server→client)
   WEBSOCKET : both push anytime       →  WS,   2-way (full-duplex)

   WEBSOCKET in motion:
   CLIENT  ◀──── message ────  SERVER   (server pushes)
   CLIENT  ──── message ────▶  SERVER   (client sends)
            both directions, same open socket
```

#### 🌍 Real-life analogy
If SSE is a one-way radio broadcast, a WebSocket is a **phone call**: the line stays open and *both* people can speak the instant they want, talking over each other if they like. You don't redial to say each sentence — the connection is live for the whole conversation.

#### 💻 Code example
```javascript
import { useEffect } from 'react';
import { useQueryClient } from '@tanstack/react-query';

function useChatSocket(roomId) {
  const queryClient = useQueryClient();

  useEffect(() => {
    const socket = new WebSocket(`wss://example.com/rooms/${roomId}`);

    socket.onmessage = (event) => {
      const msg = JSON.parse(event.data);

      if (msg.type === 'chat') {
        // A small, known change → write it straight into the cache.
        queryClient.setQueryData(['messages', roomId], (old) =>
          [...(old ?? []), msg.payload]
        );
      } else if (msg.type === 'roster-changed') {
        // A broad change → just mark stale and let Query refetch the truth.
        queryClient.invalidateQueries({ queryKey: ['members', roomId] });
      }
    };

    // To SEND, the client uses the SAME open socket (full-duplex):
    // socket.send(JSON.stringify({ type: 'chat', text: 'hi' }));

    return () => socket.close(); // tear down on unmount
  }, [roomId, queryClient]);
}
```

#### 🎤 Interview question
**Q: Polling vs SSE vs WebSockets — when each?**
A: **Polling** when updates are rare or slight staleness is fine and you want zero infrastructure — it's just a timer around a fetch, but it lags and wastes requests. **SSE** when the client only needs to *receive* a live stream (notifications, feeds, progress): one-way server-to-client over HTTP, with free auto-reconnect via `EventSource`. **WebSockets** when both sides must send continuously and instantly (chat, collaboration, live cursors, games): a full-duplex, two-way channel. Rule of thumb: receive-only ⇒ SSE; true two-way ⇒ WebSockets; neither needed ⇒ polling.

### 🗃️ Pushing Live Updates Into the Query Cache

#### 🧩 What is it?
This is the pattern that ties real-time to everything you've learned: when a push message arrives (from SSE or a WebSocket), you don't render it directly — you feed it into the **same TanStack Query cache** your components already read. The incoming message either writes the cache with `queryClient.setQueryData` or marks data stale with `queryClient.invalidateQueries`.

#### 🤔 Why do we need it? (the problem)
Without this, real-time data lives in its own pile of `useState`, separate from your cached queries. Now you have **two sources of truth** for the same data that can disagree, and none of Query's machinery (background refetch, dedup, devtools, garbage collection) applies to the live half. Routing pushes *through* the cache means live updates and fetched data are the same data — every component reading that query key updates at once, automatically.

#### ⚙️ How does it work?
A subscription's message handler picks one of two moves:
- **`setQueryData`** — you already have the exact new value in the message, so write it directly. Instant, no network round-trip.
- **`invalidateQueries`** — the message only says "something over here changed"; mark that key stale and let Query refetch the authoritative version.

```
   WebSocket / SSE message
            │
            ▼
   ┌──────────────────────────────────────────┐
   │ message handler decides:                  │
   │   know exact new value? → setQueryData    │
   │   just "it changed"?    → invalidateQueries│
   └──────────────────────────────────────────┘
            │ writes / marks-stale
            ▼
      ONE Query Cache  (key: ['messages', roomId])
            │ Query notifies every subscriber
            ▼
   Component A   Component B   ...all re-render in sync
```

#### 🌍 Real-life analogy
Think of the query cache as the **single whiteboard** everyone in the office reads. A live message is a runner bursting in with news. If the runner knows the exact figure, they walk up and write it on the board themselves (`setQueryData`). If they only know "the sales numbers changed, go check," they cross out the old figure as outdated and someone fetches the real one (`invalidateQueries`). Either way there's *one* board — nobody keeps a private copy that drifts out of date.

#### 💻 Code example
```javascript
import { useEffect } from 'react';
import { useQueryClient, useQuery } from '@tanstack/react-query';

function useLiveOrders() {
  const queryClient = useQueryClient();

  // Components everywhere read THIS query as normal:
  const ordersQuery = useQuery({
    queryKey: ['orders'],
    queryFn: () => fetch('/api/orders').then(r => r.json()),
  });

  useEffect(() => {
    const socket = new WebSocket('wss://example.com/orders');

    socket.onmessage = (event) => {
      const msg = JSON.parse(event.data);

      if (msg.type === 'order-created') {
        // We have the full new order → write it straight into the cache.
        queryClient.setQueryData(['orders'], (old) =>
          [msg.order, ...(old ?? [])]
        );
      } else {
        // Unsure what exactly changed → refetch the source of truth.
        queryClient.invalidateQueries({ queryKey: ['orders'] });
      }
    };

    return () => socket.close();
  }, [queryClient]);

  return ordersQuery; // live + cached, one source of truth
}
```

#### 🎤 Interview question
**Q: How do you push real-time updates into a query cache, and when do you use `setQueryData` vs `invalidateQueries`?**
A: In the subscription's message handler, call into the `queryClient` so live data flows through the same cache as your queries. Use **`setQueryData`** when the message already carries the exact new value — you write it directly with no network round-trip. Use **`invalidateQueries`** when the message only signals that *something* changed without the new value — it marks the key stale so Query refetches the authoritative data. Routing pushes through the cache keeps a single source of truth, so every component on that key updates together.

### ⚡ Optimistic UI — Show It Now, Reconcile With the Truth

#### 🧩 What is it?
**Optimistic UI** means updating the screen *immediately* when the user acts — before the server confirms — by writing the expected result into the cache right away. If the server agrees, great; if it rejects the change, you **roll back** to the previous value.

#### 🤔 Why do we need it? (the problem)
Network round-trips take time. If every "like," "send," or "toggle" freezes until the server replies, the app feels sluggish. Real-time apps especially must feel instant. Optimism trades a small risk (the rare failure you must undo) for a UI that responds the moment the user clicks — assuming success because success is the common case.

#### ⚙️ How does it work?
TanStack Query's `useMutation` gives you the exact hooks: snapshot the current cache, write the optimistic value, and keep the snapshot so `onError` can restore it. `onSettled` then re-syncs with server truth.

```
   user clicks "like"
        │
        ▼  onMutate: snapshot old, write optimistic
   cache shows liked  ──────────────▶  UI feels instant
        │
        │   server responds...
        ├── success → keep it (optionally refetch to confirm)
        └── error   → onError: restore the snapshot (ROLL BACK)
```

#### 🌍 Real-life analogy
It's like **writing a cheque and updating your own budget app immediately** — you don't wait days for the bank to clear it before acting as if the money moved. Almost always it clears and your figure was right. On the rare bounce, you correct the entry back. You optimized for the common case and fixed the exception.

#### 💻 Code example
```javascript
import { useMutation, useQueryClient } from '@tanstack/react-query';

function useToggleLike(postId) {
  const queryClient = useQueryClient();

  return useMutation({
    mutationFn: async (liked) => {
      const res = await fetch(`/api/posts/${postId}/like`, { method: 'POST' });
      if (!res.ok) throw new Error('Like failed'); // so onError (rollback) fires
      return res.json();
    },

    onMutate: async (liked) => {
      // 1. Stop in-flight refetches from clobbering our optimistic write.
      await queryClient.cancelQueries({ queryKey: ['post', postId] });
      // 2. Snapshot the current value so we can roll back.
      const previous = queryClient.getQueryData(['post', postId]);
      // 3. Optimistically update the cache.
      queryClient.setQueryData(['post', postId], (old) =>
        ({ ...old, liked }));
      return { previous }; // passed to onError as context
    },

    onError: (_err, _liked, context) => {
      // Server said no → restore the snapshot (roll back).
      queryClient.setQueryData(['post', postId], context?.previous);
    },

    onSettled: () => {
      // Re-sync with the server's truth either way.
      queryClient.invalidateQueries({ queryKey: ['post', postId] });
    },
  });
}
```

#### 🎤 Interview question
**Q: How do you do an optimistic update with rollback?**
A: In `useMutation`'s `onMutate`, cancel in-flight queries for that key, snapshot the current cache value, then write the expected result so the UI updates instantly; return the snapshot as context. In `onError`, restore that snapshot to roll back. In `onSettled`, invalidate the key so the cache re-syncs with the server's authoritative value. The point is: apply locally now, then confirm or undo against server truth.

### 📴 Offline & Persistence — Surviving a Lost Connection

#### 🧩 What is it?
**Offline support** means the app keeps working without a network: it serves data from a **persisted** cache (saved to storage like `localStorage` or IndexedDB so it survives reloads) and **queues** any writes the user makes, then **retries** them automatically when the connection returns.

#### 🤔 Why do we need it? (the problem)
Networks drop — subways, planes, spotty wifi. A purely in-memory cache vanishes on reload, and a mutation fired while offline would normally just fail and be lost. Users expect to keep reading and even keep acting (sending a message, checking a box) offline, and to have those actions "go through" once they're back online — without re-doing anything.

#### ⚙️ How does it work?
Two pieces: **persistence** writes the cache to durable storage so a reload restores it instantly; a **mutation queue** holds writes made while offline and replays them in order on reconnect. TanStack Query supports both via its persistence plugins and a paused-mutation queue.

```
   OFFLINE                          BACK ONLINE
   ┌───────────────────┐            ┌───────────────────┐
   │ reads ← persisted │            │ replay queued      │
   │       cache       │            │ mutations in order │
   │ writes → QUEUE    │ ──reconnect▶│  retry each one    │
   │   (paused)        │            │  then refetch       │
   └───────────────────┘            └───────────────────┘
```

#### 🌍 Real-life analogy
It's an **outbox in a mail app**. Offline, you still read saved messages, and anything you "send" sits in the outbox marked pending. The moment signal returns, the app quietly flushes the outbox in order — you never re-typed or re-sent a thing.

#### 💻 Code example
```javascript
import { QueryClient } from '@tanstack/react-query';
import { persistQueryClient } from '@tanstack/react-query-persist-client';
import {
  createSyncStoragePersister,
} from '@tanstack/query-sync-storage-persister';

const queryClient = new QueryClient({
  defaultOptions: { queries: { gcTime: 1000 * 60 * 60 * 24 } }, // keep 24h
});

// Save the cache to localStorage so it survives reloads (offline reads).
persistQueryClient({
  queryClient,
  persister: createSyncStoragePersister({ storage: window.localStorage }),
});

// Mutations fired while offline are PAUSED, then replayed on reconnect.
// Query resumes them automatically when the network event fires:
//   queryClient.resumePausedMutations();
```

#### 🎤 Interview question
**Q: How do you handle offline mutations?**
A: Persist the query cache to durable storage (e.g. `localStorage` or IndexedDB) so reads survive reloads, and let the library **pause** mutations made while offline into a queue instead of failing them. On reconnect, the queued mutations are **replayed in order** and the affected queries refetch to confirm against server truth. In TanStack Query this is the persist plugins plus paused-mutation replay, so the user's offline actions "go through" once connectivity returns without manual retries.

### 🤝 Conflict Resolution — Last-Write-Wins vs CRDTs

#### 🧩 What is it?
When two users (or your offline edit and the live server) change the *same* data at once, you have a **conflict** — two truths, one slot. **Conflict resolution** is the strategy for merging them. Two common approaches: **last-write-wins (LWW)** — the latest timestamp simply overwrites the rest — and **CRDTs** (Conflict-free Replicated Data Types) — special data structures designed so concurrent edits **merge automatically** without losing work.

#### 🤔 Why do we need it? (the problem)
Optimistic and offline edits make conflicts inevitable: you edited a doc on the train while a teammate edited it at their desk. Naively, one overwrites the other and somebody's work vanishes. The strategy you choose decides whether that's acceptable (often fine for a single "status" field) or a disaster (a shared document where lost keystrokes are unacceptable).

#### ⚙️ How does it work?
- **Last-write-wins:** attach a timestamp/version to each write; on conflict, the newest wins and the older edit is discarded. Simple, but it can **silently drop** a real change.
- **CRDTs:** structure the data so any two concurrent edits have a single well-defined merged result — no central referee needed. Every replica converges to the same state. The cost is added complexity and library weight.

```
   Two edits to the same field, at once:
   A: "blue"  ──▶ ┐
                  ├─ LWW  → newer timestamp wins, other DROPPED
   B: "green" ──▶ ┘
   A: type "X" ─▶ ┐
                  ├─ CRDT → MERGE both edits, nobody's work lost
   B: type "Y" ─▶ ┘
```
> **Note (simplification):** real CRDTs (and the related Operational Transformation behind some editors) are a deep field — this is the conceptual gist, not the full algorithm. The key idea to remember: LWW is simple but lossy; CRDTs merge concurrent edits without loss.

#### 🌍 Real-life analogy
**Last-write-wins** is two people editing a shared shopping list on paper by *crossing out and rewriting the whole thing* — whoever wrote last erased the other's additions. **CRDTs** are like Google Docs: both type at the same moment and the document weaves both sets of edits together, so nobody's sentence disappears.

#### 🎤 Interview question
**Q: Last-write-wins vs CRDTs — what's the trade-off?**
A: **Last-write-wins** resolves a conflict by letting the newest timestamped write overwrite the others — trivial to implement but it can silently lose a concurrent edit, which is fine for low-stakes fields (a "last seen" status) and bad for shared documents. **CRDTs** are data structures engineered so concurrent edits merge deterministically with no lost work and all replicas converge — ideal for collaborative editing, at the cost of more complexity. Choose LWW when occasional loss is acceptable and simplicity matters; choose CRDTs when concurrent edits must all survive.

<h2 id="module-13">Module 13 — State Architecture: Choosing & Composing</h2>

You've now met every tool — local state, Context, Redux, Zustand, TanStack Query. The architect's real skill isn't knowing *how* each one works; it's knowing *which one to reach for* and resisting the urge to reach too far. The single biggest source of state-management pain is using a heavy tool for a job a lighter one would have done better. This module gives you a decision ladder you can defend in an interview, plus the two state categories people forget exist — **URL state** and **form state** — and the anti-patterns that quietly rot a codebase.

---

### 🪜 The State Ladder — Start Small, Climb Only When Forced

#### 🧩 What is it?
A **decision ladder**: a fixed order of tools you consider for any piece of state, cheapest first. You start at the bottom rung (local `useState`) and only climb to the next rung when the current one genuinely can't do the job. Each rung up adds power but also adds cost — more code, more coupling, more re-render surface.

#### 🤔 Why do we need it? (the problem)
Without a rule, every developer defaults to whatever feels powerful — "let's just put it in Redux" — and you end up with a global store full of things only one component ever reads. That's slower to write, harder to test, and causes re-renders all over the app. The ladder replaces gut feeling with a repeatable question: *"What is the lowest rung that works?"*

#### ⚙️ How does it work?
You ask one question at each rung and stop the moment the answer is "yes, this rung is enough":

```
  THE STATE LADDER  (climb only when forced)

  5. SERVER DATA?  -> query library
     (TanStack Query / RTK Query)  NEVER a store
        ^  data owned by the server, async, can go stale
        |
  4. shared + HIGH-FREQUENCY client state?
     -> client store (Redux / Zustand / Jotai)
        ^  many components, changes often (cart, editor)
        |
  3. app-wide + LOW-FREQUENCY config?
     -> Context  (theme / auth / locale)
        ^  rarely changes, read in many places
        |
  2. do SIBLINGS need to share it?
     -> lift state to nearest common parent
        ^  two components must agree on one value
        |
  1. used by ONE component? -> local useState
     <-- START HERE. most state stops on rung 1.
```

The key discipline: a "no" sends you up exactly one rung — not straight to the top. And rung 5 is special. **Server data is not on the same ladder as client state at all** — it has its own home (a query library) because it's a *cache* of data owned elsewhere, not a value you own.

#### 🌍 Real-life analogy
Think of storing your belongings. A pen lives **in your pocket** (local state) — instant, private. Something your roommate also uses goes on the **shared shelf** (lifted state). The house thermostat setting everyone reads but rarely changes is posted **on the fridge** (Context). The contents of a busy shared **warehouse** with constant traffic needs a real inventory system (a store). And anything owned by the **shop down the road** you don't store at home at all — you keep a receipt and re-check stock when it might have changed (a query library). You wouldn't rent a warehouse to hold one pen.

#### 💻 Code example
```javascript
// RUNG 1 — local: a dropdown's open/closed flag. Nobody else cares.
function Menu() {
  const [open, setOpen] = useState(false);
  return <button onClick={() => setOpen(o => !o)}>Toggle</button>;
}

// RUNG 2 — lifted: parent owns it so two children agree.
function Parent() {
  const [selectedId, setSelectedId] = useState(null);
  return (
    <>
      <List onSelect={setSelectedId} />
      <Detail id={selectedId} />   {/* sibling reads the same value */}
    </>
  );
}

// RUNG 3 — Context: theme, read everywhere, changes almost never.
const ThemeContext = createContext('light');

// RUNG 5 — server data: a query library, NOT useState, NOT a store.
function Profile() {
  const { data, isPending } = useQuery({
    queryKey: ['user', 7],
    queryFn: () => fetch('/api/user/7').then(r => r.json()),
  });
  // isPending true -> false; `data` is a cached copy of the server's truth
}
```

#### 🎤 Interview question
**Q: Walk me through choosing where a piece of state should live.**
A: I start at the bottom of the ladder. Is it used by one component? Keep it local with `useState`. Do sibling components need to share it? Lift it to their nearest common parent. Is it low-frequency app-wide config like theme, auth, or locale? Context. Is it genuinely shared client state that changes often, like a cart or an editor document? A client store such as Zustand or Redux. And if it's data owned by the server, it doesn't go on this ladder at all — it goes in a query library like TanStack Query, because that's a cache, not state I own. The rule is: climb only when the current rung genuinely can't do the job.

---

### 🔗 URL as State — Put It in the Address Bar

#### 🧩 What is it?
Some state belongs in the **URL** itself — specifically in the **search params** (the part after the `?`, like `?sort=price&page=2`). Filters, sort order, pagination, the active tab, and the search query are all state, but their natural home is the address bar, not `useState`.

#### 🤔 Why do we need it? (the problem)
If a product list's filters live in `useState`, then a user who filters to "red shoes under $50, sorted by price, page 2" and sends the link to a friend sends them a blank, unfiltered page. Refresh the tab and the view resets. Hit the back button and nothing happens. State in `useState` is **invisible and private** — it can't be shared, bookmarked, or survive a refresh. The URL fixes all three at once because the browser already persists, shares, and history-tracks it for free.

#### ⚙️ How does it work?
The view is **derived from the URL**, not from local state. Reading and writing the URL replaces reading and writing `useState`:

```
  URL is the source of truth for "view state"

  /products?category=shoes&sort=price&page=2
                 |            |          |
        +--------+      +-----+     +----+
        v               v           v
   filter UI        sort UI     pagination
        |               |           |
        +-------> read params <------+
                       |
            user clicks "page 3"
                       |
            write ?page=3 to URL  (router.push)
                       |
            component re-renders from new params
                       |
   FREE WINS: shareable . bookmarkable . survives refresh
              . back/forward button just works
```

In Next.js, `useSearchParams()` reads the params on the client, and `searchParams` (an awaited prop) reads them in a Server Component. You update them by pushing a new URL.

#### 🌍 Real-life analogy
The URL is like the **page number and chapter you tell a friend** so they open the book to the exact same spot. "Look at page 204" is shareable and reproducible. Holding the open book privately in your hands (`useState`) means the only way to show someone the spot is to physically hand them your copy — and if you close it, you lose your place.

#### 💻 Code example
```javascript
'use client';
import { useSearchParams, useRouter, usePathname } from 'next/navigation';

function ProductFilters() {
  const params = useSearchParams();          // reads ?sort=...&page=...
  const router = useRouter();
  const pathname = usePathname();

  // Derive UI from the URL — no useState for these values.
  const sort = params.get('sort') ?? 'newest';
  const page = Number(params.get('page') ?? '1');

  function setParam(key, value) {
    const next = new URLSearchParams(params); // copy current params
    next.set(key, value);                     // change one
    router.push(`${pathname}?${next.toString()}`); // write back to URL
  }

  return (
    <select value={sort} onChange={(e) => setParam('sort', e.target.value)}>
      <option value="newest">Newest</option>
      <option value="price">Price</option>
    </select>
  );
  // Sharing this URL reproduces the exact filtered/sorted view.
}
```

A quick **"where does this go?"** mapping:

```
  filters, sort, pagination, active tab, search query  -> URL
  dropdown open/closed, hover, focus, input draft      -> local state
  theme, auth user, locale                             -> Context
  cart, multi-step editor doc (shared + frequent)      -> client store
  fetched lists / records (owned by server)            -> query library
```

#### 🎤 Interview question
**Q: When should state go in the URL instead of React state?**
A: When the state describes *what the user is looking at* and would be useful to share, bookmark, or restore after a refresh — filters, sort order, pagination, the active tab, and the search query are the classic cases. Putting them in the URL means a link reproduces the exact view, the back/forward buttons work, and a refresh doesn't reset anything — all for free, because the browser already persists and history-tracks the URL. Transient, private UI like whether a dropdown is open stays in local state.

### 📝 Form State — Its Own Category

#### 🧩 What is it?
**Form state** is the live data inside inputs while a user is typing — field values, which fields have been touched, validation errors, whether the form is submitting. It's neither pure UI state nor server state; it's a category of its own, which is why dedicated **form libraries** like React Hook Form exist.

#### 🤔 Why do we need it? (the problem)
The obvious approach is a `useState` per field, updated on every keystroke — a **controlled input**. That works for a two-field form, but on a large form it means the whole form re-renders on *every single keystroke in any field*, which gets janky. There's also a pile of repetitive logic: tracking touched fields, running validation, wiring `value` and `onChange` to every input. Form state has enough special needs that hand-rolling it stops paying off.

#### ⚙️ How does it work?
The core distinction is **controlled vs uncontrolled inputs**:

```
  CONTROLLED                      UNCONTROLLED
  React owns the value            the DOM owns the value

  value={state}                   <input ref={ref} />
  onChange -> setState            React reads ref.value
       |                          only when needed (submit)
       v
  every keystroke =               typing does NOT
  a re-render                     re-render React
       |                                |
  fine for small forms            scales to huge forms
```

A controlled input re-renders React on every keystroke because React holds the value. An **uncontrolled input** lets the browser's DOM hold the value (the natural way HTML inputs already work), and React only reads it when it needs to — usually on submit. **React Hook Form is built on uncontrolled inputs precisely to minimize re-renders**: it registers inputs via refs, so typing in one field doesn't re-render the rest of the form. (Simplification: it can do controlled fields too when you need them, e.g. for custom components — uncontrolled is its default, not its only mode.)

#### 🌍 Real-life analogy
A controlled input is a **manager who copies down every word an employee says, in real time** — accurate but exhausting, and they interrupt constantly. An uncontrolled input is a manager who lets the employee **fill out the form themselves** and only reads it when they hand it in at the end. Far less overhead, same result — you collect the answers when it actually matters: at submission.

#### 💻 Code example
```javascript
import { useForm } from 'react-hook-form';

function SignupForm() {
  // register() wires inputs via refs (uncontrolled) -> minimal re-renders.
  const { register, handleSubmit, formState: { errors } } = useForm();

  // onValid only fires after validation passes.
  const onValid = (data) => console.log(data); // { email, password }

  return (
    <form onSubmit={handleSubmit(onValid)}>
      <input {...register('email', { required: 'Email is required' })} />
      {errors.email && <span>{errors.email.message}</span>}

      <input type="password" {...register('password', { minLength: 8 })} />
      <button type="submit">Sign up</button>
    </form>
  );
  // Typing in `email` does NOT re-render the password field. That's the win.
}
```

#### 🎤 Interview question
**Q: Why do form libraries like React Hook Form exist, and what's controlled vs uncontrolled?**
A: A controlled input stores its value in React state and updates it on every keystroke, so React re-renders each time — fine for small forms, but on large forms every keystroke re-renders the whole form. An uncontrolled input leaves the value in the DOM and React only reads it when needed, usually at submit. React Hook Form leans on uncontrolled inputs — registering fields via refs — specifically to minimize re-renders, and bundles the repetitive parts (validation, touched/dirty tracking, submission) that you'd otherwise hand-roll. That combination of performance plus less boilerplate is why form state is its own category.

### 🧬 Composing Client + Server State — No Overlap

#### 🧩 What is it?
Most real screens mix both kinds of state: **server data** (the list of todos from the API) and **client state** (which todo is selected, whether a modal is open). Composing them well means each piece has exactly **one home** — server data lives in the query cache, client state lives in local state or a store — and you never copy one into the other.

#### 🤔 Why do we need it? (the problem)
The classic mistake is fetching server data and then copying it into a client store (Redux/Zustand/`useState`) "so it's easy to read." Now you have **two copies** of the same data, and the moment the server changes, your copy is stale — you've hand-rolled a cache with no invalidation, no background refresh, no dedup. Bugs follow: the UI shows an old value because the store wasn't updated after the mutation. Keeping the two categories separate avoids the entire problem.

#### ⚙️ How does it work?
Draw a clean line. The query library owns server data; the client store/local state owns UI choices. They **reference** each other by id, they don't **duplicate**:

```
  SERVER STATE                 CLIENT STATE
  (query library)              (local / store)

  useQuery(['todos'])          selectedTodoId  (an id, not the todo)
   -> [ {id:1,...},            isModalOpen
        {id:2,...} ]           filterTabValue
        |                            |
        |   never copy the todo      |
        |   into the store ----------+
        v                            v
       look up by id when rendering:
       todos.find(t => t.id === selectedTodoId)
        |
   ONE source per fact:
   server data fresh from cache, UI choice from client
```

The store holds the *selected id* — a tiny client-owned fact — not the selected todo object. You join them at render time by looking the id up in the server data. Server data stays the cache's job; the client store stays small.

#### 🌍 Real-life analogy
A library catalog (the client store) doesn't keep a **photocopy of every book** — it keeps **call numbers** (ids) that point to where the real books live on the shelves (the server cache). If it photocopied every book, every reprint would make the catalog wrong. Storing the pointer, not the copy, keeps it correct and tiny.

#### 💻 Code example
```javascript
function TodoScreen() {
  // SERVER STATE — owned by the query cache.
  const { data: todos = [] } = useQuery({
    queryKey: ['todos'],
    queryFn: () => fetch('/api/todos').then(r => r.json()),
  });

  // CLIENT STATE — owned locally. Store the ID, not the todo object.
  const [selectedId, setSelectedId] = useState(null);

  // JOIN at render time. No duplicated data, so it can't go stale.
  const selected = todos.find(t => t.id === selectedId) ?? null;

  return (
    <>
      <ul>
        {todos.map(t => (
          <li key={t.id} onClick={() => setSelectedId(t.id)}>{t.title}</li>
        ))}
      </ul>
      {selected && <Detail todo={selected} />}
    </>
  );
  // When a mutation invalidates ['todos'], `todos` refreshes and `selected`
  // is recomputed from the fresh data automatically — nothing to sync.
}
```

#### 🎤 Interview question
**Q: How do you combine client and server state cleanly?**
A: Give each fact exactly one home. Server data lives in the query library's cache; client state — selections, toggles, filters — lives in local state or a small store. Crucially, I never copy server data into the client store. I store an identifier, like the selected id, and look the full record up in the cached server data at render time. That way there's a single source for each piece, so when the server data refetches there's nothing to manually keep in sync, and the UI can't show a stale copy.

### 🚫 State Anti-Patterns — The Four Classic Traps

#### 🧩 What is it?
A set of recurring mistakes that make state architecture worse: making everything global by default, parking server data in Redux, funneling the whole app through one giant Context, and storing values you could just compute. Recognizing them is half of avoiding them.

#### 🤔 Why do we need it? (the problem)
Each anti-pattern feels convenient in the moment and costs you later. They're the natural result of *not* using the ladder — of reaching for the most powerful tool first. Naming them gives you and your team a shared vocabulary to catch them in code review before they spread.

#### ⚙️ How does it work? — the four traps

```
  ANTI-PATTERN              WHY IT HURTS            FIX
  ---------------------------------------------------------------
  everything global         re-renders + coupling  start local;
  by default                for state only one      climb the
                            component uses          ladder

  server data in Redux      hand-rolled cache:      use a query
                            stale data, no dedup,   library; it
                            no background refresh    IS the cache

  one mega-Context          any change re-renders   split into
  (all app state in it)     EVERY consumer          small focused
                                                    contexts

  storing derivable data    two sources of truth    compute it:
  (e.g. fullName saved      that drift out of sync   derive from
   beside first + last)                              first+last
```

- **Everything-global-by-default** breaks the ladder's first rung. State only one component uses should be local; making it global adds coupling and widens re-render scope for nothing.
- **Server data in Redux** re-creates a cache by hand and loses staleness handling, deduplication, and background refresh — exactly what a query library gives you for free.
- **One mega-context** means a change to any field re-renders every consumer, because Context re-renders all consumers when its value's identity changes. Split it by concern.
- **Storing derivable data** creates two facts that can disagree. If you can compute it from existing state (`fullName` from `first` + `last`, a filtered list from the full list), compute it on render instead of storing it.

#### 🌍 Real-life analogy
These are the **hoarder's habits** of state. Everything-global is keeping every receipt on the kitchen table where the whole family has to step around it. Server-data-in-Redux is photocopying the public library's whole catalog into your house and never updating it. The mega-context is one light switch wired to every bulb in the building, so flicking it disturbs everyone. Storing derivable data is writing your age on a sticky note instead of just counting from your birthday — guaranteed to be wrong next year.

#### 🎤 Interview question
**Q: Name some state-management anti-patterns and how you'd fix each.**
A: Four common ones. Making everything global by default — fix by starting local and climbing the ladder only when forced. Putting server data in Redux — that's a hand-rolled cache with no staleness or refetch handling; use a query library instead, since it *is* the cache. One mega-context holding all app state — any change re-renders every consumer, so split it into small, focused contexts. And storing derivable data, like saving `fullName` next to `first` and `last` — that's two sources of truth that drift apart; compute the derived value on render instead. The thread through all of them is single source of truth and using the lightest tool that works.

## Conclusion

You now have the one distinction that untangles most state-management debates — **client state vs server state** — and a decision framework that flows from it: keep state local, lift it only as far as needed, reach for Context only for low-frequency app-wide config, use a store (Redux/atomic) for genuine shared client state, and treat server data as a **cache** managed by a query library, never a hand-rolled store. You can explain why Context re-renders all its consumers, why a state machine kills impossible states, and how TanStack Query's caching, invalidation, and optimistic updates keep every view in sync.

The architect's instinct isn't knowing every library — it's asking *"who owns this data, and is it a value or a cache?"* and letting the answer pick the tool.
