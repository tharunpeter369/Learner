# Performance & Core Web Vitals

A fast page is engineered, not lucky. Module 3 showed you *how* the browser renders; this module is the **discipline** of making a real application fast and keeping it fast — measure first, fix the right thing, and prove it with numbers. You'll learn to diagnose any "it's slow" report from first principles — the loading waterfall, the network, the JavaScript tax, images and fonts, your rendering strategy — and to lock the wins in with budgets and field monitoring so performance doesn't quietly rot.

<h2 id="module-0">Module 0 — The Performance Mindset & Methodology</h2>

Before you touch a single line of code to make an app faster, you need a way of *thinking*. Performance is an engineering discipline, not a bag of tricks — and the engineers who win at it all share the same habit: **they measure before they touch anything, and they prove the fix with numbers.**

---

### 📏 Measure First, Optimize Second — never guess

#### 🧩 What is it?
A working rule: **never change code to make it faster until you've measured *what* is slow.** First profile (let a tool tell you where the time goes), then change exactly **one** thing, then re-measure to confirm it actually helped. Profile → change one thing → re-measure. Repeat.

#### 🤔 Why do we need it? (the problem)
Human intuition about performance is famously wrong. You'll *swear* the slow part is your fancy animation, spend two days optimizing it, and discover the real cost was a 4 MB image loading before anything else. Worse: if you change five things at once and it gets faster, you have **no idea which change worked** — so you can't repeat it, and you might be carrying four useless (or harmful) changes. Measuring first turns guessing into knowing.

> **Note (simplification):** "profile" here means any reliable measurement — a browser tool like the Chrome DevTools Performance panel, a Lighthouse run, or a tiny timer in your code. The principle is the same at every scale.

#### ⚙️ How does it work?
The loop is deliberately boring and repeatable:

```
        ┌────────────────────────────────────┐
        │ 1. MEASURE (profile the baseline)  │
        └──────────────┬─────────────────────┘
                       ▼
        ┌────────────────────────────────────┐
        │ 2. Find the BIGGEST cost (not the  │
        │    most interesting one)           │
        └──────────────┬─────────────────────┘
                       ▼
        ┌────────────────────────────────────┐
        │ 3. Change ONE thing                │
        └──────────────┬─────────────────────┘
                       ▼
        ┌────────────────────────────────────┐
        │ 4. RE-MEASURE vs the baseline      │
        └──────────────┬─────────────────────┘
                       ▼
             better? keep it. worse/same? revert.
                       │
                       └──── back to step 1 ────►
```

Two reasons for "one thing at a time": you get a clean **cause-and-effect** signal, and you can confidently **revert** changes that didn't help instead of letting dead weight accumulate.

#### 🌍 Real-life analogy
It's like a doctor. A good doctor doesn't start surgery because you *feel* unwell — they run tests first (measure), treat the one thing the tests point to, then re-test to confirm you're better. A doctor who prescribed five medicines at once and you recovered would never know which one cured you — or which one is quietly harming you.

#### 💻 Code example
The smallest possible profiler — `performance.now()` returns a high-precision timestamp in milliseconds:

```javascript
// Measure how long a piece of work actually takes.
const start = performance.now();   // baseline clock reading
renderDashboard();                 // the work we suspect is slow
const end = performance.now();

console.log(`renderDashboard took ${(end - start).toFixed(1)} ms`);
// e.g. logs: "renderDashboard took 312.4 ms"

// Now change ONE thing (say, memoize the rows), run again,
// and compare the new number to 312.4 ms — did it actually move?
```

#### 🎤 Interview question
**Q: You get a ticket that just says "the site is slow." What's the first thing you do?**
A: Reproduce it and **measure** — I don't start optimizing from a hunch. I capture a baseline (a Lighthouse run plus a Performance-panel profile, ideally on a throttled mid-range device) to see *where* the time actually goes, find the single biggest cost, change one thing, and re-measure against the baseline to prove the change helped. Guessing wastes days optimizing the wrong thing.

### 🔬 Lab vs Field (RUM) Data — two different truths

#### 🧩 What is it?
There are two ways to get performance numbers. **Lab data** comes from a controlled test you run yourself — one device, one fixed network speed, in a quiet environment (e.g. **Lighthouse** in Chrome DevTools). **Field data**, also called **RUM** (*Real User Monitoring* — measuring actual visitors as they use the site), comes from your real users on their real phones and real networks (e.g. **CrUX**, the *Chrome User Experience Report*, which is Google's public database of real-Chrome-user measurements).

#### 🤔 Why do we need it? (the problem)
Lab and field data will often **disagree**, and beginners panic when they do. Your laptop on office wifi shows a beautiful 1-second load (lab); meanwhile a real user on a 4-year-old Android phone on a train sees 6 seconds (field). Both numbers are correct — they're just measuring different things. You need lab data because it's **repeatable** (great for debugging and CI), and you need field data because it's the **truth about real users** (great for knowing if you actually have a problem).

#### ⚙️ How does it work?

```
   LAB (you run it)              FIELD / RUM (real users send it)
   ┌───────────────────┐        ┌────────────────────────────┐
   │ 1 device you pick │        │ thousands of real devices  │
   │ 1 network you set │        │ every real network         │
   │ no real user      │        │ real users, real behavior  │
   │ REPEATABLE        │        │ MESSY but TRUE             │
   │ tool: Lighthouse  │        │ source: CrUX, web-vitals   │
   └───────────────────┘        └────────────────────────────┘
        good for:                     good for:
   debugging + CI gates          "do we actually have a problem?"
```

Lab is a **flight simulator**: controlled, repeatable, safe to crash in. Field is the **black box recorder** from thousands of real flights: it tells you what really happened to real people.

> **Note:** Some metrics simply **cannot** be reproduced well in the lab. **INP** (*Interaction to Next Paint* — how quickly the page responds to clicks and taps) depends on a real human clicking real things, so a lab tool that never clicks anything can't measure it realistically. For interaction responsiveness, field data is the source of truth.

#### 🌍 Real-life analogy
Lab data is a **car tested on a manufacturer's track** — perfect conditions, same driver every time. Field data is **fuel-economy reports from thousands of actual owners** stuck in traffic with the AC on and a full trunk. The track number helps you compare two car designs fairly; the owner reports tell you what you'll *really* get on your commute. You want both, and you trust the owner reports for "is this car actually good for me?"

#### 💻 Code example
A glimpse of how field data is collected — the `web-vitals` library reports real metrics from real sessions (we cover this in depth in Module 10):

```javascript
import { onLCP, onINP, onCLS } from 'web-vitals';

// These callbacks fire in REAL users' browsers, with REAL values,
// then you'd send each to your analytics endpoint.
onLCP((metric) => sendToAnalytics(metric)); // Largest Contentful Paint
onINP((metric) => sendToAnalytics(metric)); // Interaction to Next Paint
onCLS((metric) => sendToAnalytics(metric)); // Cumulative Layout Shift
// This is FIELD data — it captures the slow phone on the train
// that your fast laptop in the office never would.
```

#### 🎤 Interview question
**Q: Lab data and field data disagree for the same page. Which do you trust?**
A: Both — for different jobs. Field data (RUM/CrUX) is the **source of truth** for whether real users actually have a problem, because it's their real devices and networks. Lab data (Lighthouse) is **repeatable**, so it's what I use to debug a specific issue and to gate regressions in CI. They disagree because the lab uses one controlled device/network while the field spans every device and connection — and some metrics like INP can't be reproduced in the lab at all, since they need a real user interacting.

### 📊 Percentiles — why p75, not the average

#### 🧩 What is it?
A **percentile** describes how a value ranks within a whole group. The **p75** ("75th percentile") of load time is the time **75% of your users had at or below** — equivalently, the experience of your **slowest 1 in 4** users at the cutoff. The **average** (mean) just sums everyone's times and divides by the count.

#### 🤔 Why do we need it? (the problem)
The **average lies** when data has a long tail — and performance data always has a long tail, because a handful of users on terrible devices/networks are *far* slower than everyone else. A few huge numbers drag the average up (or get hidden in it), so the average describes **nobody's actual experience**. Reporting p75 instead keeps you honest about the people who are struggling, while not letting one freak 30-second outlier define your whole report. This is also why **Core Web Vitals are officially assessed at the p75 of real users** — Google grades your site by the experience of its slower quarter, not its luckiest visitor.

#### ⚙️ How does it work?
Sort everyone's measurements from fastest to slowest; p75 is the value 75% of the way along that line.

```
   8 users' load times (seconds), sorted slow→fast view:
   1.0  1.1  1.2  1.3  1.4  1.5  3.0  9.0
                              ▲              ▲
                          p75 ≈ 1.5s     one slow outlier

   average = (1.0+1.1+1.2+1.3+1.4+1.5+3.0+9.0)/8 = 2.4s
   p75     ≈ 1.5s

   The 9.0s outlier yanks the AVERAGE up to 2.4s — a number
   NObody actually experienced. p75 (1.5s) is far more honest.
```

To find p75 of a sorted list of N values, take the value at position `0.75 × N` (rounded up). The **median** is just p50 — the middle value — and is already more honest than the mean for the same reason.

#### 🌍 Real-life analogy
Imagine reporting the "average net worth" of ten people in a room. Nine earn a normal salary; one is a billionaire. The *average* makes everyone look like a millionaire — a useless, misleading number. The **median** (the middle person) tells you what a typical person in the room is actually like. Performance percentiles do the same: they stop one extreme value from painting a false picture of everyone.

#### 💻 Code example
A worked p75, computed by hand in code:

```javascript
// Real user load times in milliseconds, with one slow outlier.
const times = [900, 1000, 1100, 1200, 1300, 1500, 3000, 9000];

const mean = times.reduce((a, b) => a + b, 0) / times.length;
// mean = 18000 / 8 = 2375 ms  ← inflated by the 9000 outlier

const sorted = [...times].sort((a, b) => a - b); // ascending
const index  = Math.ceil(0.75 * sorted.length) - 1; // 0.75*8=6 → idx 5
const p75    = sorted[index];
// index = 5 → p75 = 1500 ms

console.log(mean, p75); // 2375 1500
// Report 1500 ms (p75): honest about the slower quarter,
// not distorted by the single 9000 ms user.
```

#### 🎤 Interview question
**Q: Why report p75 instead of the mean (average) for a metric like LCP?**
A: Because performance data has a long tail — a few users on slow devices/networks are far slower than the rest, and the mean gets dragged toward those outliers, describing nobody's real experience. p75 reports the experience of the slower quarter at the cutoff, which is honest about struggling users without letting one extreme outlier define the number. It's also exactly how Core Web Vitals are graded: at the p75 of real users.

### 🎭 Perceived vs Actual Performance — feeling fast beats being fast

#### 🧩 What is it?
**Actual performance** is the real, stopwatch-measured time something takes. **Perceived performance** is how fast it *feels* to the user. They're different — and the user only ever experiences the second one. Techniques like **skeleton screens** (gray placeholder shapes where content will appear), **optimistic UI** (showing the result immediately, before the server confirms), and **progress indicators** make an app *feel* faster without necessarily being faster.

#### 🤔 Why do we need it? (the problem)
A blank white screen for 2 seconds feels broken and endless; the *same* 2 seconds filled with a moving skeleton or a progress bar feels responsive and short. Waiting with **no feedback** is agonizing — users assume it froze and leave. So beyond cutting real milliseconds, you also manage **the experience of waiting**: give immediate feedback, show structure early, and let users keep moving. Crucially, perceived-performance tricks are a **complement**, not a substitute — they don't fix a genuinely slow backend, and they won't fix a bad Core Web Vital, which is measured on the real timeline.

#### ⚙️ How does it work?

```
   ACTUAL time to load: 2.0s in BOTH cases below.

   Without feedback:        With a skeleton screen:
   ┌────────────────┐       ┌────────────────┐
   │                │       │ ▭▭▭▭   ▭▭▭     │
   │  (blank white) │       │ ▭▭▭▭▭▭▭▭▭▭     │
   │                │  vs   │ ▭▭▭   ▭▭▭▭▭    │
   │   feels FROZEN │       │ feels ALIVE +  │
   │   "is it dead?"│       │ almost ready   │
   └────────────────┘       └────────────────┘
   Same 2 seconds. Wildly different FELT experience.
```

- **Skeleton screen:** show the page's *shape* instantly so the wait feels productive.
- **Optimistic UI:** assume the action will succeed and update the screen now (e.g. show the "liked" heart instantly), then quietly reconcile if the server disagrees.
- **Progress indicator:** for longer waits, a determinate bar (it's 60% done) reassures far more than an endless spinner.

#### 🌍 Real-life analogy
Some airports deliberately route arriving passengers on a **long walk** to baggage claim. The bags don't arrive any sooner — but by the time you walk there, they're already on the carousel, so the *wait feels gone*. Complaints dropped dramatically. Nothing got faster; the **experience of waiting** changed. Skeleton screens are that long walk.

#### 💻 Code example
Optimistic UI — update the screen instantly, reconcile with the server after:

```javascript
async function likePost(post) {
  post.liked = true;          // ① update UI NOW — feels instant
  renderHeart(post);

  try {
    await api.like(post.id);   // ② real request happens in the background
  } catch (err) {
    post.liked = false;        // ③ server said no — quietly roll back
    renderHeart(post);
    showToast('Could not like — try again');
  }
}
// The user sees the heart fill immediately (perceived: instant),
// even though the actual round-trip took 300 ms.
```

#### 🎤 Interview question
**Q: A screen takes 2 seconds to load and you can't make it any faster. What can you still do?**
A: Improve **perceived** performance. Replace the blank wait with a skeleton screen so the page's structure appears instantly and the wait feels productive; add a progress indicator for the longer parts; and use optimistic UI for user actions so they get immediate feedback. The actual time is unchanged, but the experience feels far faster — though I'd note these don't fix a real Core Web Vital, which is measured on the real timeline, so they complement real optimization rather than replace it.

### 💰 The Business Cost of Slowness — how to justify the work

#### 🧩 What is it?
Performance is not a vanity metric — slowness costs **real money**. Slow pages drive up **bounce rate** (visitors who leave immediately without interacting) and drive down **conversion rate** (the share of visitors who do the thing you want — buy, sign up, subscribe). Knowing how to frame performance in business terms is how you get time and budget to actually fix it.

#### 🤔 Why do we need it? (the problem)
Engineers often *feel* a page is too slow but can't get it prioritized, because "it feels slow" doesn't compete with shipping features. The fix is to translate milliseconds into the language leadership cares about: lost users and lost revenue. Study after study has found that as load time grows, more users abandon the page, and conversions drop. That reframes performance from a nice-to-have into a **revenue lever** — which is exactly how you win the argument to invest in it.

> **Note (simplification):** specific figures vary widely by industry, study, and traffic mix, so I'm describing the well-established **direction** (slower → more bounce, fewer conversions), not quoting any single number as universal law. For a real pitch, measure *your own* funnel.

#### ⚙️ How does it work?
The mechanism is human impatience compounding across a funnel:

```
   1,000 visitors arrive
        │
   slow load → some give up before it renders
        ▼
   say 200 bounce (left immediately)        ← higher when slow
        │
   800 remain → slowness causes more drop-off
        ▼
   conversions (signups/purchases) shrink   ← fewer when slow

   Faster load → fewer bounce → more reach checkout
              → more conversions → more revenue.
```

Because the loss happens at **every** step of the funnel, even a small speed improvement can compound into a meaningful revenue change. That compounding is the heart of the business case.

#### 🌍 Real-life analogy
Think of a **checkout line at a shop**. If the line is long and slow, some shoppers put their basket down and walk out (they bounce); of those who stay, some abandon halfway. Open a second register and the line moves faster — fewer people leave, more complete their purchase. A slow website is a slow checkout line: every second of friction quietly pushes paying customers out the door.

#### 💻 Code example
This topic is a business argument rather than a coding one, so here's a concrete back-of-envelope illustration instead:

```text
Worked example (illustrative numbers, not a universal law):

  Monthly visitors ............ 1,000,000
  Current conversion rate ..... 2.0%   → 20,000 conversions
  Average value per conversion  $50     → $1,000,000 / month

  Suppose speeding up the page lifts conversion to 2.2%:
  New conversions ............. 22,000  (+2,000)
  Extra monthly revenue ....... 2,000 × $50 = $100,000

  A 0.2-point conversion lift = $100k/month here.
  THAT is the sentence that gets a perf project approved.
```

#### 🎤 Interview question
**Q: Leadership won't prioritize performance work. How do you make the case?**
A: I translate speed into business outcomes instead of arguing about milliseconds. Slower load times measurably increase bounce and reduce conversion across the funnel, so I'd pull our own field data, tie our current p75 to our bounce/conversion numbers, and estimate the revenue impact of an improvement — e.g. a fraction-of-a-point conversion lift on high traffic is often six figures. Framing performance as a revenue lever, backed by our real funnel data, is what gets it prioritized.

### 🧭 The Shape of an Investigation — a repeatable methodology

#### 🧩 What is it?
A reusable **playbook** that turns a vague "it's slow" report into a shipped, proven fix. It strings together everything in this module into one ordered routine you can run on *any* performance problem, every time.

#### 🤔 Why do we need it? (the problem)
Under pressure, people skip straight to "I bet it's the images" and start hacking — and waste hours. A fixed sequence removes panic and bias: you always start from real data, always isolate one cause, and always prove the result. The same shape works whether the complaint is a slow load, a janky scroll, or a laggy button. Having a named methodology is also exactly what senior interviews probe for.

#### ⚙️ How does it work?

```
   ┌─────────────────────────────────────────────┐
   │ 1. REPRODUCE — confirm it's real;           │
   │    check FIELD data (do real users hurt?)   │
   ├─────────────────────────────────────────────┤
   │ 2. MEASURE  — capture a lab baseline        │
   │    (Lighthouse + Performance profile),      │
   │    throttled to a mid-range device          │
   ├─────────────────────────────────────────────┤
   │ 3. DIAGNOSE — find the BIGGEST cost at p75, │
   │    not the most interesting one             │
   ├─────────────────────────────────────────────┤
   │ 4. FIX      — change ONE thing              │
   ├─────────────────────────────────────────────┤
   │ 5. VERIFY   — re-measure vs baseline;       │
   │    revert if it didn't help                 │
   ├─────────────────────────────────────────────┤
   │ 6. SHIP + MONITOR — confirm the win shows   │
   │    up in FIELD data; add a budget so it     │
   │    can't silently regress                   │
   └─────────────────────────────────────────────┘
                  loop back to step 2 for the next cost
```

Notice it's the "measure first" loop wrapped in two outer steps — **start** by confirming real users actually hurt (field data, at p75), and **end** by confirming the field improved and guarding it with a budget so it stays fixed.

#### 🌍 Real-life analogy
It's a **detective's procedure**. A good detective doesn't arrest the first suspect they find interesting — they secure the scene, gather evidence, follow it to the most likely culprit, test that theory, and only close the case when the evidence confirms it. Then they file the report so the same crime is easier to catch next time. Step 6's "add a budget" is filing that report.

#### 💻 Code example
The methodology as a checklist you could literally keep in your repo:

```text
PERF INVESTIGATION CHECKLIST
[ ] 1. Reproduce — and check field data: do real users hurt? (p75)
[ ] 2. Measure   — Lighthouse + Performance profile (throttled)
[ ] 3. Diagnose  — identify the single biggest cost
[ ] 4. Fix       — change exactly ONE thing
[ ] 5. Verify    — re-measure vs baseline; revert if no gain
[ ] 6. Ship+watch— confirm field improved; add a budget in CI

Golden rules:
  • Never guess — measure.
  • One change at a time.
  • Judge by p75 of real users, not your laptop's average.
```

#### 🎤 Interview question
**Q: Walk me through your end-to-end approach to a performance investigation.**
A: I reproduce the issue and confirm with field data that real users (at p75) are actually affected. Then I capture a lab baseline with Lighthouse and a Performance profile, throttled to a mid-range device. I diagnose the single biggest cost, fix exactly one thing, and re-measure against the baseline — reverting if it didn't help. Finally I ship, confirm the win shows up in field data, and add a performance budget in CI so it can't silently regress. It's "measure first, one change at a time, judged by real users" turned into a repeatable loop.

<h2 id="module-1">Module 1 — Core Web Vitals: Diagnose & Fix</h2>

"The site feels slow" is a feeling. **Core Web Vitals** turn that feeling into three numbers Google measures on every page — how fast the main content appears, how much the layout jumps around, and how quickly the page reacts when you tap it. Module 3 explained *how* the browser paints pixels; this module is the **playbook**: given a bad score, how do you find the guilty resource and fix it? We'll take each vital, name its usual suspects, and hand you the exact fix.

---

### 🖼️ LCP — Largest Contentful Paint (is the main content there yet?)

#### 🧩 What is it?
**LCP (Largest Contentful Paint)** measures **loading speed**: the moment the *biggest* piece of content visible in the viewport — usually a hero image, a video poster, or a big block of text — finishes rendering. It answers the user's gut question: *"Has the page actually loaded?"*

- **Good: ≤ 2.5s** · Needs work: 2.5–4s · Poor: > 4s
- Measured at the **75th percentile (p75)** of real users — so it must be good for the slow-device, slow-network long tail, not just your fast laptop.

#### 🤔 Why do we need it? (the problem)
Older metrics like "page load" fired when *everything* finished — long after the user could already read the page, or while they were still staring at blank space. LCP pins down the single moment that matters most to a human: *when the main thing I came for showed up.* A slow LCP is the number one reason a page "feels" slow.

#### ⚙️ How do you diagnose & fix it?
LCP is really a **time budget** spent across a chain of steps. Find which step eats the budget, then attack that step:

```
 [ request HTML ]
        │  TTFB  (server slow? far away?)
        ▼
 [ HTML arrives ]
        │  render-blocking CSS/JS delays first paint
        ▼
 [ LCP resource discovered ]
        │  found late? lazy-loaded? low priority?
        ▼
 [ LCP resource downloads + paints ]  ← LCP timestamp
```

**Common causes → fixes:**

- **Slow TTFB** (server takes too long to send the first byte) → cache HTML at a CDN, speed up the server/database, render on the edge. (TTFB is its own metric — see below.)
- **Render-blocking CSS/JS** — the browser won't paint until blocking resources in the `<head>` load → inline critical CSS, defer non-critical JS, cut unused CSS.
- **The LCP image is lazy-loaded** → the single most common own-goal. **Never** put `loading="lazy"` on the LCP image — it tells the browser "this is below the fold, fetch it later," delaying the very thing LCP measures.
- **The LCP image is discovered late** (e.g. it's a CSS `background-image`, or injected by JS, so the browser doesn't see it while parsing HTML) → reference it in the HTML and **preload** it so the browser starts fetching immediately, at high priority.

> **Simplification flag:** LCP only considers content **in the viewport** at load. An image below the fold is never the LCP element — which is exactly why lazy-loading off-screen images is good and lazy-loading the hero is bad.

#### 🌍 Real-life analogy
Ordering at a restaurant: LCP is **when your main dish lands on the table** — not when the waiter first greets you, and not when dessert finally arrives. You judge the kitchen by how fast the main course shows up. Lazy-loading the hero image is like the kitchen deciding to start cooking your main *after* it has plated everyone's dessert.

#### 💻 Code example
```html
<!-- ❌ BAD: hero image lazy-loaded → LCP fires late -->
<img src="/hero.jpg" loading="lazy" alt="Hero" />

<!-- ✅ GOOD: eager-load the hero AND preload it so it's
     discovered immediately at high priority.
     fetchpriority="high" hints "this matters most". -->
<link rel="preload" as="image" href="/hero.jpg" fetchpriority="high" />
<!-- ...later in <body>: -->
<img src="/hero.jpg" fetchpriority="high" alt="Hero" />

<!-- ✅ Lazy-load is correct for images BELOW the fold -->
<img src="/footer-photo.jpg" loading="lazy" alt="Footer photo" />
```

#### 🎤 Interview question
**Q: Your LCP is 5s. How do you find and fix the cause?**
A: First identify the **LCP element** (Chrome DevTools → Performance, or the `web-vitals` library's attribution tells you which node it is). Then break the 5s into stages: a high **TTFB** points at the server/CDN; a gap before the resource even starts downloading means it was **discovered late** or render-blocking CSS/JS held up paint; a long *download* means the asset is too big or low-priority. Fixes follow the stage: speed up TTFB (cache/edge), **preload** the LCP image and remove any `loading="lazy"` on it, give it `fetchpriority="high"`, and cut render-blocking resources. A classic instant win: someone lazy-loaded the hero image.

### 📐 CLS — Cumulative Layout Shift (does the page jump around?)

#### 🧩 What is it?
**CLS (Cumulative Layout Shift)** measures **visual stability**: how much visible content unexpectedly *jumps* while the page loads. It's the metric behind the rage of going to tap a button, an ad loads above it, and you tap the wrong thing.

- **Good: ≤ 0.1** · Needs work: 0.1–0.25 · Poor: > 0.25
- It's a **unitless** score (not seconds): roughly *how much of the screen moved* × *how far it moved*, summed over the worst burst of shifts.

#### 🤔 Why do we need it? (the problem)
Other vitals reward speed, but a *fast* page that yanks content around is infuriating and even dangerous (mis-clicks on "Buy" or "Delete"). CLS captures jank that timing metrics miss entirely: the page loaded quickly, but it wouldn't *hold still*.

#### ⚙️ How do you diagnose & fix it?
Every shift has the same root cause: **something took up space that wasn't reserved for it**, pushing existing content down. Reserve the space up front and the shift disappears.

```
  BEFORE image loads        AFTER image loads (no size set)
  ┌──────────────────┐      ┌──────────────────┐
  │  Heading         │      │  Heading         │
  │  Paragraph text  │      │ [   IMAGE   ]    │ ← image appears
  │                  │      │  Paragraph text  │ ← text SHOVED down!
  └──────────────────┘      └──────────────────┘
            CLS = visible content jumped ↓
```

**Common causes → fixes:**

- **Images / videos / ads without dimensions** → always set `width` and `height` attributes (the browser reserves the right box from the aspect ratio), or use the CSS `aspect-ratio` property.
- **Content injected above existing content** (banners, ads, "cookie" bars, lazy-loaded widgets) → reserve a fixed-height slot, or inject **below** the fold / on top as an overlay instead of pushing layout.
- **Web fonts** — text first renders in a fallback font, then re-flows when the web font swaps in → use `font-display: optional` (no swap, no shift) or tune fallback metrics (covered in the Fonts module).
- **Animating layout properties** like `top`/`left`/`height`/`width` → animate `transform` and `opacity` instead; those are composited and **don't trigger layout**, so they never cause CLS.

> **Simplification flag:** Shifts caused **within 500ms of a user interaction** (clicking a "Show more" button, say) are *excluded* — expected motion isn't penalized. CLS only counts the *unexpected* jumps.

#### 🌍 Real-life analogy
Reading a newspaper where, as you read, the editor keeps **inserting a new headline at the top**, sliding your paragraph down the page mid-sentence. Setting `width`/`height` is like the layout artist leaving a **correctly-sized blank box** for the photo before it's printed — when the photo arrives, it drops neatly into its reserved slot and nothing else moves.

#### 💻 Code example
```html
<!-- ❌ BAD: no dimensions → text reflows when the image arrives -->
<img src="/photo.jpg" alt="Photo" />

<!-- ✅ GOOD: width/height let the browser reserve the box up front.
     Modern browsers derive aspect-ratio from these two numbers,
     so the slot is correct even when the displayed size is fluid. -->
<img src="/photo.jpg" width="800" height="600" alt="Photo" />
```
```css
/* ✅ Reserve space with aspect-ratio (great for responsive media) */
.thumb { width: 100%; aspect-ratio: 16 / 9; }

/* ✅ Animate transform, NOT top/left/width — no layout = no CLS */
.slide-in { transition: transform 0.3s; } /* good */
/* .slide-in { transition: left 0.3s; }   ❌ shifts layout */
```

#### 🎤 Interview question
**Q: What causes CLS and how do you eliminate it?**
A: Unexpected layout shifts from content that took space without reserving it: un-sized images/ads, content injected above existing content, font swaps, and animating layout properties. Fixes: set `width`/`height` (or `aspect-ratio`) on all media and embeds so the browser reserves the box; pre-allocate a fixed slot for dynamically-injected content; use `font-display: optional` (and fallback metric overrides) for fonts; and animate only `transform`/`opacity`, never `top`/`left`/`height`/`width`. Good CLS is **≤ 0.1**, and it's a unitless score, not a time.

### 👆 INP — Interaction to Next Paint (does the page react when I tap?)

#### 🧩 What is it?
**INP (Interaction to Next Paint)** measures **responsiveness**: from the moment you interact (tap, click, key press) to the moment the screen visibly updates in response. It reports (close to) the **worst** interaction across the whole visit, so it reflects how the page feels at its laggiest.

- **Good: ≤ 200ms** · Needs work: 200–500ms · Poor: > 500ms
- **INP replaced FID (First Input Delay) as a Core Web Vital in March 2024.** FID only timed the delay before the *first* interaction *started* processing; INP is stricter — it measures the **full** interaction (delay + handler work + rendering the next frame), for interactions throughout the visit.

#### 🤔 Why do we need it? (the problem)
A page can hit great LCP and CLS yet still feel **frozen** — you click and nothing happens for half a second because JavaScript is hogging the main thread. The browser has **one main thread** for both running JS and updating the screen; while a long task runs, clicks queue up and the next paint can't happen. INP exposes exactly this stutter that loading metrics can't see.

#### ⚙️ How do you diagnose & fix it?
An interaction's time splits into three parts; long **tasks** on the main thread inflate all three:

```
  click ─┬─ INPUT DELAY ──┬─ PROCESSING ──┬─ PRESENTATION ─→ next paint
         │ main thread     │ your event    │ browser does
         │ busy with a     │ handler runs  │ style/layout/
         │ long task       │ (heavy work?) │ paint
         └───────────── total = INP (ms) ──────────────────┘
  Rule of thumb: a "long task" is one that blocks > 50ms.
```

**Common causes → fixes:**

- **Long tasks** (big chunks of JS blocking the main thread) → **break them up** and **yield** so the browser can paint between chunks (e.g. `await scheduler.yield()`, or split work across `setTimeout`/`requestIdleCallback`).
- **Heavy event handlers** (expensive work synchronously inside `onClick`) → do only the **urgent visual update** now, then **defer** the rest (analytics, recomputation) to after the next paint.
- **A large/complex DOM** → every interaction recalculates style and layout over the whole tree, so a huge DOM makes each frame slow → reduce node count, **virtualize** long lists (render only what's on screen).

> **Simplification flag:** INP reports near the worst interaction, not literally the maximum — for pages with many interactions it ignores a few extreme outliers (roughly the worst-per-50). The mental model "INP ≈ your slowest interaction" is close enough for diagnosis.

#### 🌍 Real-life analogy
A **cashier with one pair of hands**. If they start a huge 5-minute price-check (a long task), every customer in line just *waits* — even someone who only wants to ask a quick question. INP is the wait the most-stuck customer felt. The fix is to **pause the big task between steps** to serve quick requests (yield), and to **hand the slow paperwork to a back office** (defer / move work off the main thread).

#### 💻 Code example
```javascript
// ❌ BAD: one long handler blocks the thread → the UI freezes,
//         and the click's "next paint" is delayed → high INP.
button.addEventListener('click', () => {
  updateUI();                 // urgent: cheap visual change
  processHugeDataset();       // 300ms of blocking work — janks INP
});

// ✅ GOOD: paint the urgent bit first, then yield before heavy work
button.addEventListener('click', async () => {
  updateUI();                 // user sees an instant response
  await scheduler.yield();    // let the browser paint the frame
  processHugeDataset();       // heavy work runs AFTER the paint
});
// scheduler.yield() is newer; setTimeout(fn, 0) is the classic fallback.
```

#### 🎤 Interview question
**Q: How do you improve INP?**
A: INP is the time from an interaction to the next paint; good is **≤ 200ms**, and it replaced FID in March 2024 because FID only measured input *delay*, not the full interaction. The enemy is **long tasks** blocking the single main thread. Fixes: break long tasks up and **yield** so the browser can paint between chunks; inside handlers do only the urgent UI update and **defer** non-urgent work (analytics, heavy recompute) past the next paint; and **shrink the DOM** / virtualize big lists so each frame's style+layout is cheap. Diagnose with DevTools Performance (look for long tasks on the main thread) or `web-vitals` attribution, which names the slow interaction.

### ⏱️ TTFB & FCP — The Supporting Metrics That Feed the Vitals

#### 🧩 What is it?
Two diagnostic metrics that aren't Core Web Vitals themselves but are the **early checkpoints** on the way to LCP:

- **TTFB (Time To First Byte)** — from the moment the browser *requests* the page to the moment the **first byte** of the response arrives. It's the "how long until the server even started answering?" number.
- **FCP (First Contentful Paint)** — when the browser paints the **first** piece of content (any text, image, or non-blank pixel). It's "the page stopped being blank."

A common rough guidance: **TTFB ≤ 0.8s** and **FCP ≤ 1.8s** are "good" targets.

#### 🤔 Why do we need them? (the problem)
LCP is a *result*; TTFB and FCP tell you *where in the timeline* it went wrong. If LCP is bad but TTFB is already huge, the problem is the **server/network**, not your images — no amount of image tuning will help. They split one scary number into a story you can debug.

#### ⚙️ How does it work? — the timeline
TTFB and FCP are milestones inside the same loading sequence that ends at LCP:

```
 request ──TTFB──▶ first byte ──parse + CSS──▶ FCP ──────▶ LCP
   │                  │                          │           │
 navigation       server done            first pixel    biggest
 starts           thinking               on screen      content done
```

So the relationships are: **TTFB feeds FCP feeds LCP.** Shave TTFB and you typically pull FCP *and* LCP earlier with it; that's why "fix the server first" is so often the highest-leverage move.

- Cut **TTFB**: cache HTML at a CDN, render closer to users (edge), speed up server/DB work, reuse connections (`preconnect`).
- Cut **FCP**: remove render-blocking CSS/JS, inline critical CSS, load fonts without blocking text.

#### 🌍 Real-life analogy
Think of a relay race. **TTFB** is how long the first runner takes to even *grab the baton* and start. **FCP** is the first runner crossing into view. **LCP** is the *anchor* runner crossing the finish line. If the first runner is slow off the blocks (high TTFB), the whole team finishes late no matter how fast the anchor is — so you fix the start first.

#### 💻 Code example
```html
<!-- Measure these in the browser with the Performance API -->
<script>
  // FCP: the first contentful paint entry
  new PerformanceObserver((list) => {
    for (const e of list.getEntries()) {
      if (e.name === 'first-contentful-paint') {
        console.log('FCP:', Math.round(e.startTime), 'ms');
      }
    }
  }).observe({ type: 'paint', buffered: true });

  // TTFB: responseStart from the navigation timing entry
  const nav = performance.getEntriesByType('navigation')[0];
  console.log('TTFB:', Math.round(nav.responseStart), 'ms');
</script>
```
```html
<!-- Reuse the connection to a critical third-party origin early,
     shaving DNS/TLS time off TTFB for that resource -->
<link rel="preconnect" href="https://cdn.example.com" crossorigin />
```

#### 🎤 Interview question
**Q: How do TTFB and FCP relate to LCP, and why measure them?**
A: They're sequential milestones in the same load: TTFB (first byte from the server) → FCP (first pixel painted) → LCP (largest content painted). They're diagnostic, not Core Web Vitals themselves, but they **localize the problem**. A bad LCP with an already-bad TTFB means fix the **server/CDN** (cache HTML, edge-render, faster backend); a fine TTFB but late FCP points at **render-blocking CSS/JS**; a fine FCP but late LCP points at the **LCP resource** (too big, late-discovered, or lazy-loaded). Because TTFB feeds FCP feeds LCP, fixing the earliest weak link usually moves everything downstream.

<h2 id="module-2">Module 2 — The Loading Waterfall & Critical Path</h2>

When a page is slow, the truth is hidden in the **Network panel** — a staircase of bars showing every file the browser fetched, in what order, and how long each waited. Learn to read that staircase and you can point at the exact resource costing you seconds. This module is the **diagnosis-and-fix view**: how a waterfall reveals dependency chains, what really sits inside "TTFB", which resources block the first paint, and the levers (`preconnect`, `preload`, `fetchpriority`, Early Hints) that flatten the staircase.

---

### 🌊 Reading a Request Waterfall — the page's flight recorder

#### 🧩 What is it?
A **request waterfall** is the timeline view in your browser's Network panel (the **DevTools** — the built-in developer tools). Each resource the page loads (HTML, CSS, JavaScript, images, fonts) gets one horizontal bar. The bars stack top-to-bottom in the order requests started, and each bar is split into **phases**: queued → connection → waiting (**TTFB** — time to first byte) → downloading.

#### 🤔 Why do we need it? (the problem)
"The site feels slow" is a feeling, not a diagnosis. Without the waterfall you're guessing which file is to blame. With it, you can see *exactly* where the time went: was a file stuck **queued** (the browser hadn't started it yet)? Stuck **waiting** (the server was slow to respond)? Or just **huge** (a long download bar)? Each phase points to a different fix.

#### ⚙️ How does it work?
Read each bar left to right as a sequence of phases. The crucial insight: a bar that **starts** only after another bar **finishes** means the second resource was *discovered* inside the first — that's a dependency chain, and it shows up as a **staircase** shape.

```
 Time ───────────────────────────────────▶
 index.html  ▆▆TTFB▆▆░dl░
 app.css            ░q░▆TTFB▆░dl░
 app.js             ░q░▆▆TTFB▆▆░░dl░░
 hero.jpg                       ░q░▆T▆░dl░  ← starts LATE
   legend:  ░q░ queued   ▆ waiting(TTFB)   ░dl░ download
 hero.jpg only began after app.js was parsed
 → that downward staircase = a dependency chain
```

A flat "all bars start together" block is healthy parallelism. A long diagonal staircase is the warning sign: each resource is waiting on the one above it, so latency **adds up** instead of overlapping.

#### 🌍 Real-life analogy
It's like a **security camera log of a kitchen** during a dinner rush. Each dish (resource) has a timeline bar: time spent waiting for a free station (queued), time the chef stood thinking (TTFB), time actually cooking (download). If dish #4 only *starts* after dish #3 is plated — because the recipe was hidden inside dish #3 — you see a staircase, and you know the kitchen is serving one-at-a-time instead of in parallel.

#### 💻 Code example
```text
# What each waterfall phase is telling you, and the likely fix:

# Long QUEUED bar      → browser hit its parallel-connection limit,
#                        or the request is low priority. Fix: reduce
#                        request count / raise priority.
# Long WAITING (TTFB)  → server (or connection setup) was slow.
#                        Fix: cache, faster backend, CDN, preconnect.
# Long DOWNLOAD bar    → the file is simply big.
#                        Fix: compress, resize, split, lazy-load.
# Bar STARTS LATE      → resource was discovered late (staircase).
#                        Fix: preload it, or stop hiding it in JS/CSS.
```

#### 🎤 Interview question
**Q: Walk me through a slow waterfall — how do you decide what to fix?**
A: I read each bar's phases. A long **queued** segment means too many parallel requests or a low priority. A long **waiting/TTFB** segment points at the server or connection setup, not the file. A long **download** segment means the file is too big. And a bar that **starts late**, after another finishes, reveals a dependency chain (the staircase) — I'd fix that by preloading the late-discovered resource or removing the chain. I always fix the resource on the **critical path** first, since that's what delays the first paint.

---

### ⏱️ TTFB, Broken Down — the wait before the first byte

#### 🧩 What is it?
**TTFB** stands for **Time To First Byte**: the gap between the browser sending a request and the *first byte* of the response arriving. It is **not** just "server processing time" — it includes everything that has to happen to even reach the server: finding it, connecting to it, securing the connection, *and then* the server thinking.

#### 🤔 Why do we need it? (the problem)
TTFB is the floor under everything else. Nothing — no CSS, no image, no paint — can start arriving until the first byte does. People often blame "a slow backend" when the real cost was DNS or the TLS handshake. Breaking TTFB into its parts tells you whether to optimize the **server** or the **connection**.

#### ⚙️ How does it work?
For the very first request to a new origin, TTFB is the sum of several steps that happen in order:

```
 Browser                                   Server
   │  1. DNS lookup  (name → IP address)
   │  ───────────── resolver ──────────▶
   │  2. TCP connect (the "handshake")
   │  ──── SYN ▸ ◂ SYN-ACK ▸ ACK ────▶
   │  3. TLS handshake (set up HTTPS)
   │  ──── keys & certificate exchange ─▶
   │  4. request sent ─────────────────▶
   │                       5. server processing
   │                          (think-time: DB,
   │                           render, etc.)
   │  ◂───────── 6. FIRST BYTE arrives ──
   │     ↑ everything 1→6 counts as TTFB
```

Steps 1–3 are **connection setup** (each is roughly one network round-trip). Step 5 is the server's own **think-time**. TTFB = setup + think-time. Crucially, once a connection is **reused**, steps 1–3 are skipped — which is why later requests to the same origin have a much smaller TTFB.

> **Note (simplification):** the round-trip counts above assume HTTP over TCP+TLS 1.3. Newer transports (HTTP/3 over QUIC, TLS 0-RTT resumption) fold these steps together and cut round-trips — that's a Module 3 topic. Here, just remember TTFB = *connection setup + server think-time*.

#### 🌍 Real-life analogy
Ordering pizza by phone. **DNS** = looking up the pizzeria's number. **TCP connect** = dialing and them picking up ("Hello?"). **TLS** = confirming it's really them and switching to a private line. **Server think-time** = them actually making your pizza. **First byte** = the very first slice arriving. If the first slice is late, it might be a slow kitchen — or it might be that you spent ages just finding the number and getting through.

#### 💻 Code example
```text
# A TTFB of 800ms — where did it go? (read from a waterfall's
# "Connection" + "Waiting" timing breakdown)

DNS lookup .............  120 ms   ← warm with `preconnect`
TCP connect ............   90 ms   ← warm with `preconnect`
TLS handshake ..........  140 ms   ← warm with `preconnect`
Server think-time ......  450 ms   ← cache / faster backend / CDN
                         -------
TTFB ...................  800 ms

# Lesson: ~350ms here was pure CONNECTION SETUP, not the server.
# preconnect to the origin could erase most of it.
```

#### 🎤 Interview question
**Q: What is TTFB made of?**
A: TTFB is the time from sending the request to receiving the first byte, and it includes **both** connection setup and server processing. The setup part is DNS lookup, the TCP handshake, and (for HTTPS) the TLS handshake — each roughly a round-trip. Then the server does its think-time (database queries, rendering) before sending the first byte. So a high TTFB isn't automatically a "slow server" — it can be slow DNS or handshakes, which you warm up with `preconnect` and connection reuse.

### ⛓️ The Critical Request Chain — what must load before you see anything

#### 🧩 What is it?
The **critical request chain** is the sequence of resources that *must* be downloaded and processed before the browser can produce the first meaningful paint — and, in particular, before it can render the **LCP** element (**Largest Contentful Paint**, the biggest thing in view, usually the hero image or headline). It's the longest dependency path from the HTML to "the user sees the main content".

#### 🤔 Why do we need it? (the problem)
Not all requests are equal. A footer icon loading slowly doesn't matter; the stylesheet and hero image that gate the first paint matter enormously. If you optimize random files, you waste effort. The critical chain tells you the **one path** whose total length *is* your loading time — shorten that path and the page feels faster; shorten anything else and nothing visible changes.

#### ⚙️ How does it work?
The browser can only request what it has **discovered**. It discovers the hero image only after parsing the CSS that references it, which it got only after parsing the HTML. Each hop is a request that can't start until the previous one is parsed — so the chain's length is the **sum** of its links, not the max.

```
 index.html ─▶ app.css ─▶ font.woff2
      │             └────▶ hero.jpg  (the LCP image)
      └─▶ app.js  (not on the paint path)

 Critical chain to LCP:
   html → css → hero.jpg   (3 links, added end-to-end)

 Goal: make this chain SHORTER and SHALLOWER.
 - shorter = fewer hops (e.g. preload hero.jpg from the HTML)
 - shallower = each hop smaller/faster (compress, cache, CDN)
```

The fix is almost always to **flatten** the chain: let the browser start the deep resource *early* (via `preload`) instead of waiting to discover it three hops down.

#### 🌍 Real-life analogy
A relay race. The anchor runner (the hero image) can't start until the baton has passed through every earlier runner (HTML, then CSS). Your finishing time is the **sum** of all legs. You don't win by making the fastest runner faster — you win by shortening the *whole* relay: handing the anchor the baton sooner so they're already running while the others finish.

#### 💻 Code example
```html
<!-- BEFORE: hero is discovered late, deep in the chain -->
<!-- html → css → hero.jpg : the browser finds hero.jpg only -->
<!-- after parsing app.css, so its request starts late.       -->
<link rel="stylesheet" href="/app.css" />
<!-- ...hero.jpg is referenced inside app.css as a background -->

<!-- AFTER: preload pulls the LCP image to the front of the   -->
<!-- chain so it downloads in parallel with the CSS.          -->
<link rel="preload" as="image" href="/hero.jpg" fetchpriority="high" />
<link rel="stylesheet" href="/app.css" />
<!-- Now html → hero.jpg happens directly: one hop, not three. -->
```

#### 🎤 Interview question
**Q: How do you speed up the LCP resource?**
A: First I identify the critical chain that leads to it — usually html → css → image. Because the chain's links add up, the image often starts downloading far too late. I shorten the chain by **preloading** the LCP image from the HTML (`<link rel="preload" as="image">`) with `fetchpriority="high"`, so it starts immediately and in parallel rather than after the CSS is parsed. I also make sure it isn't lazy-loaded and that its origin is warmed with `preconnect`.

### 🚦 Prioritization & Eliminating Waterfalls — make the staircase flat

#### 🧩 What is it?
Browsers assign every resource a **priority** (Highest → Low) and fetch high-priority ones first. **Prioritization** is the set of tools to *correct* those guesses and to start the right things earlier: the `fetchpriority` attribute, the resource hints `preconnect` and `preload`, and the server feature **`103 Early Hints`**. Together they let you **eliminate waterfalls** — turn a deep staircase into a flat parallel block.

#### 🤔 Why do we need it? (the problem)
The browser's default priorities are good guesses, not perfect. It might rank your hero image as "Low" because images usually aren't urgent — but *this* one is your LCP. And even with perfect priorities, a resource discovered late simply can't start early. Prioritization fixes both: it re-ranks the important resource, and it lets the browser start critical work before it would naturally discover it.

#### ⚙️ How does it work?
Four levers, each attacking a different part of the staircase:

```
 Lever          What it does
 ─────────────  ────────────────────────────────────────
 fetchpriority  re-ranks a resource: "high" or "low".
                Mark the LCP image high; mark below-the-
                fold / analytics low.
 preconnect     warms DNS + TCP + TLS to an origin EARLY,
                so the first real request skips setup.
 preload        starts downloading a late-discovered but
                critical resource NOW (give it `as=...`).
 103 Early      server sends preload/preconnect hints
 Hints          BEFORE the final response, so the browser
                fetches assets DURING server think-time.
```

The combined effect on the waterfall:

```
 BEFORE (staircase)        AFTER (flat, parallel)
 html ▆▆░dl░               html ▆▆░dl░
 css     ░q░▆░dl░          css  ▆░dl░
 hero        ░q░▆░dl░      hero ▆░dl░   ← preloaded, high prio
        ↘ adds up               ↘ overlaps → total time shrinks
```

The big ideas, beyond the four levers: **inline critical CSS** (put the small amount of CSS needed for the first paint directly in the HTML so there's no separate CSS request blocking paint), and **avoid making your own chains** — chained `@import` in CSS and resources injected by JavaScript (`document.createElement('script')`) are discovered late and deepen the staircase.

> **Note:** `103 Early Hints` is an *informational* status the server can send before the real `200`. It does not replace the final response — it's an early heads-up: "while I'm thinking, start fetching these."

#### 🌍 Real-life analogy
A restaurant taking your **drink order before the food is ready** (`103 Early Hints`) so the drinks arrive while the kitchen cooks. **Preconnect** is the host warming up a table — clearing it, setting cutlery — before you even sit. **Preload** is telling the kitchen "start the slow-roast now, we'll definitely order it." **fetchpriority** is flagging the VIP's dish to jump the queue. None of it makes any single step faster — it just stops everyone from waiting in single file.

#### 💻 Code example
```html
<!-- 1. Warm the connection to a key third-party origin so the -->
<!-- first request there skips DNS + TCP + TLS setup.          -->
<link rel="preconnect" href="https://cdn.example.com" crossorigin />

<!-- 2. Preload the LCP image AND mark it high priority, so it  -->
<!-- starts immediately instead of being discovered late.      -->
<link rel="preload" as="image" href="/hero.jpg" fetchpriority="high" />

<!-- 3. De-prioritise something non-urgent (below the fold).   -->
<img src="/footer-art.jpg" fetchpriority="low" loading="lazy" alt="" />
```

```css
/* AVOID: chained @import builds its own hidden waterfall.       */
/* base.css must download & parse before theme.css is discovered. */
@import url("theme.css");   /* ❌ html → base.css → theme.css */

/* PREFER: separate <link> tags in the HTML so both are          */
/* discovered up-front and fetched in parallel.                  */
```

#### 🎤 Interview question
**Q: How do you eliminate a deep loading waterfall?**
A: I attack it from three angles. First, **start critical resources earlier**: `preconnect` to warm key origins (DNS+TCP+TLS), `preload` late-discovered critical assets like the LCP image, and `fetchpriority="high"` to re-rank them. Second, **remove the chain itself**: inline the critical CSS so the first paint doesn't wait on a separate request, and avoid chained `@import` and JS-injected scripts that are discovered late. Third, if I control the server, **`103 Early Hints`** lets it tell the browser what to preload *during* its own think-time, so assets download before the final response even arrives. The goal is to turn a diagonal staircase into a flat block of parallel requests.

<h2 id="module-3">Module 3 — Network: HTTP/2, HTTP/3, Compression & CDNs</h2>

Your code can be perfectly optimized and your server lightning-fast, yet the page still feels slow — because between the user and your server sits **the network**, and the network has rules. Most of those rules come down to one brutal fact: light is fast, but not infinitely fast, and every back-and-forth trip across the planet costs real time. This module is about beating the network: fewer round-trips, smarter connections, smaller bytes, and serving content from somewhere physically close to the user.

---

### 🐌 Latency vs Bandwidth — Why Round-Trips Rule

#### 🧩 What is it?
Two different things people lump together as "speed". **Bandwidth** is *how much* data fits through the pipe per second (your "100 Mbps"). **Latency** is *how long* one message takes to travel to the server and back — one **round-trip**, measured as **RTT** (round-trip time).

#### 🤔 Why do we need to know this? (the problem)
People assume "faster internet = faster page". But a page load is rarely one big download — it's *dozens of little conversations*: ask for the HTML, get told about a CSS file, ask for that, it mentions a font, ask for that... Each "ask and wait" is at least one RTT. So page load is dominated by the **number of round-trips**, not by how fat your pipe is. Upgrading bandwidth past a point does almost nothing; cutting round-trips does everything.

#### ⚙️ How does it work?
RTT is bounded by physics — data can't travel faster than light, and through fibre it's even slower. New York to London is roughly 28 ms one-way at best, so ~56 ms per round-trip *before* any server even thinks. Stack many sequential round-trips and the delays add up:

```
  Sequential requests (each waits a full RTT):

  Client          Server
    │ ── ask HTML ──▶ │   ┐
    │ ◀── HTML ─────  │   │ 1 RTT
    │ ── ask CSS ───▶ │   ┐
    │ ◀── CSS ──────  │   │ 1 RTT
    │ ── ask JS ────▶ │   ┐
    │ ◀── JS ───────  │   │ 1 RTT
    ▼                 ▼
  Total wait grows with NUMBER of round-trips,
  not with how big the pipe is.
```

#### 🌍 Real-life analogy
Bandwidth is the **width of a highway** — how many cars fit side by side. Latency is **how long the drive takes**. If you have to drive to the store and back five separate times to get five items, a 12-lane highway doesn't help — what hurts you is the *number of trips*. Make one trip with a big list, and you win.

#### 💻 Concrete illustration
```
  Page needs 30 resources fetched one-after-another.

  RTT = 50 ms  →  30 × 50 ms = 1500 ms just in round-trips
                  (before counting any download time!)

  Doubling bandwidth: ~no change to that 1500 ms.
  Cutting trips to 10: 10 × 50 ms = 500 ms. 1000 ms saved.
```
> **Simplification flag:** real loads overlap some requests, so it's not a clean multiply — but the lesson holds: round-trip *count* is the lever, not bandwidth.

#### 🎤 Interview question
**Q: A user on fast fibre still loads your page slowly. Bandwidth isn't the issue — what is?**
A: Almost always **latency / too many round-trips**. Each resource discovered late adds an RTT, and RTT is bounded by distance (speed of light). The fix is to *reduce round-trips* — fewer requests, parallelism (HTTP/2), connection reuse, preconnect, and serving from a nearby CDN edge — not to buy more bandwidth.

### 🚦 HTTP/1.1 → HTTP/2 → HTTP/3 — The Connection Evolution

#### 🧩 What is it?
The version of HTTP — the rules browsers and servers use to talk — decides *how many things can be in flight at once* over a connection. Three generations matter: **HTTP/1.1** (one request at a time per connection), **HTTP/2** (many parallel **streams** over one connection), and **HTTP/3** (the same parallelism, but over a different transport that survives packet loss better).

#### 🤔 Why do we need it? (the problem)
In **HTTP/1.1**, a single connection handles **one request at a time** — the next request can't start until the current response finishes. This is **head-of-line (HOL) blocking**: one slow response stalls everything behind it. Browsers worked around it by opening ~6 connections per origin, but that's a small, expensive band-aid — each connection costs its own setup round-trips, and 6 is still tiny when a page needs 50 files.

#### ⚙️ How does it work?
- **HTTP/2 multiplexing:** one connection carries many independent **streams** at once. Requests and responses are chopped into small **frames** that interleave on the wire, so a slow response no longer blocks others *at the HTTP layer*. **But** HTTP/2 still runs over **TCP**, and TCP delivers bytes strictly in order — so if one packet is lost, TCP holds back *all* streams until it's resent. That's **TCP-level HOL blocking**, which HTTP/2 cannot fix.
- **HTTP/3 over QUIC:** moves to **QUIC**, a transport built on **UDP**. QUIC tracks each stream's bytes separately, so a lost packet only stalls *its own* stream — the others keep flowing. This removes the TCP-level HOL blocking that HTTP/2 was stuck with.

```
  HTTP/1.1  — one at a time per connection (×6 connections)
    [req A][resp A][req B][resp B]...     ← serial; slow A blocks B

  HTTP/2    — many streams, ONE TCP connection
    A1 B1 C1 A2 B2 C2 ...  (interleaved frames)
    ⚠ a lost TCP packet stalls ALL streams (TCP HOL)

  HTTP/3    — many streams over QUIC (UDP)
    A1 B1 C1 A2 ✗ C2 ...   (B's packet lost)
    ✓ only stream B waits; A and C keep flowing
```

#### 🌍 Real-life analogy
HTTP/1.1 is a **single-file checkout lane** — one shopper finishes before the next starts. HTTP/2 is **one cashier ringing several shoppers' items in a clever interleave** — much faster, but if the *conveyor belt* jams (TCP packet loss), *everyone* waits. HTTP/3 gives each shopper their **own little belt**, so one jam only delays that one person.

#### 💻 Concrete illustration
```
  Inspect a response header to see the version:

  HTTP/1.1 200 OK
  HTTP/2 200          ← multiplexed over one TCP connection
  HTTP/3 200          ← over QUIC/UDP

  In DevTools → Network → "Protocol" column shows
  h2 (HTTP/2) or h3 (HTTP/3) per request.
```

#### 🎤 Interview question
**Q: HTTP/1.1 vs HTTP/2 vs HTTP/3 — explain the head-of-line blocking story.**
A: HTTP/1.1 sends one request per connection at a time, so a slow response blocks the rest (application-level HOL); browsers hack around it with ~6 connections. HTTP/2 multiplexes many streams over **one TCP connection**, fixing HTTP-layer HOL — **but** because TCP delivers in order, a single lost packet still stalls *all* streams (TCP-level HOL). HTTP/3 runs over **QUIC (on UDP)**, which keeps per-stream ordering, so packet loss only blocks the affected stream. Net: HTTP/3 is the real fix for HOL on lossy networks.

### 🔐 TLS, Connection Reuse & Preconnect — The Setup Tax

#### 🧩 What is it?
**TLS** is the encryption layer that makes a URL `https`. Before any data flows, the client and server must do a **handshake** to agree on keys — and that handshake costs round-trips. **Connection reuse** and **`preconnect`** are about paying that setup cost as rarely, and as early, as possible.

#### 🤔 Why do we need it? (the problem)
A brand-new HTTPS connection isn't free: you pay a **DNS lookup** (find the server's address), a **TCP handshake** (1 RTT), and a **TLS handshake** (1 RTT with TLS 1.3) — *before* the first byte of your actual content. If every resource opened a fresh connection, you'd pay this tax over and over. And if you discover a third-party origin *late* (a font host, an analytics domain), you pay the whole setup right when you can least afford it.

#### ⚙️ How does it work?
- **Connection reuse:** keep the connection open and send many requests over it, so you pay setup **once**. HTTP/2's single multiplexed connection makes this natural.
- **0-RTT resumption:** TLS 1.3 lets a *returning* client resume a prior session and send data in the **first** message — zero handshake round-trips. (Caveat: 0-RTT data can be **replayed** by an attacker, so it's only safe for idempotent requests like GETs.)
- **`preconnect`:** a hint that tells the browser "you'll need this origin soon — do the DNS + TCP + TLS *now*", so the connection is warm before the request fires.

```
  Cold connection (first visit):
    DNS ─▶ TCP(1 RTT) ─▶ TLS(1 RTT) ─▶ request ─▶ data
    └────── setup tax paid BEFORE any content ──────┘

  preconnect warms it early, in parallel with parsing:
    <link rel="preconnect"> ─▶ setup happening...
    ...by the time you need the font, connection is READY
```

#### 🌍 Real-life analogy
Opening a connection is like **getting through airport security** — slow, and you only want to do it once. Connection reuse is **staying airside** instead of re-clearing security for every shop. `preconnect` is **sending someone ahead to clear security for you** so you breeze through when you arrive. 0-RTT is the **TSA PreCheck fast-lane** for travellers already known to the system.

#### 💻 Concrete illustration
```html
<!-- Warm up a third-party origin before you need it -->
<!-- crossorigin is required for fonts (CORS-fetched) -->
<link rel="preconnect" href="https://fonts.gstatic.com" crossorigin>

<!-- Lighter hint: just resolve DNS early -->
<link rel="dns-prefetch" href="https://analytics.example.com">
```

#### 🎤 Interview question
**Q: Why does `preconnect` speed up loading a web font from a third-party host?**
A: The font lives on a *different origin*, so fetching it normally triggers a fresh DNS + TCP + TLS handshake — several round-trips paid only *after* the browser discovers the font, on the critical path. `preconnect` tells the browser to do that handshake **early, in parallel** with parsing, so the connection is already warm when the font request fires, removing those round-trips from the critical path. (Use it sparingly — each preconnect ties up resources.)

### 🗜️ Compression — gzip vs Brotli

#### 🧩 What is it?
**Compression** shrinks a response before sending it, and the browser expands it on arrival. The two common algorithms are **gzip** (old, universal) and **Brotli** (newer, made by Google), advertised via the `Content-Encoding` header.

#### 🤔 Why do we need it? (the problem)
Text-based assets — HTML, CSS, JavaScript, SVG, JSON — are *hugely* repetitive (think how often `function` or `</div>` appears). Sending them raw wastes bandwidth and, more importantly, adds download time on slow connections. Compression often cuts text by 70–90%. The catch: it only helps data that has *redundancy to squeeze*.

#### ⚙️ How does it work?
- The browser sends `Accept-Encoding: gzip, br` (`br` = Brotli). The server picks one it supports and replies with `Content-Encoding`.
- **Brotli generally beats gzip on text** (better ratios, especially at higher compression levels), thanks to a built-in dictionary of common web strings. Trade-off: Brotli's highest levels are slow to compress, so they suit *static, pre-compressed* assets; for dynamic responses a mid level or gzip may be chosen.
- **Do NOT compress already-compressed formats** — JPEG, PNG, WebP, AVIF, MP4, and `.woff2` fonts are *already* compressed. Re-compressing them wastes CPU and can even make them slightly *larger*. Compress text; leave media alone.

```
  Browser ── Accept-Encoding: gzip, br ──▶ Server
  Server  ── Content-Encoding: br ────────▶ Browser
            (text shrunk ~70–90%; browser inflates it)

  app.js   220 KB  ──gzip──▶  ~68 KB
                   ──brotli─▶  ~58 KB   ← usually smaller
  photo.jpg        ──▶ leave as-is (already compressed)
```

#### 🌍 Real-life analogy
Compression is **vacuum-packing for shipping**. A fluffy duvet (text, full of air/repetition) squashes down tiny — huge win. But a brick (a JPEG, already dense) won't compress; vacuum-sealing it just wastes effort and the same space. Brotli is a *better vacuum machine* than gzip for the squashable stuff.

#### 💻 Concrete illustration
```
  Request:
    GET /app.js
    Accept-Encoding: gzip, deflate, br

  Response:
    HTTP/2 200
    Content-Type: application/javascript
    Content-Encoding: br          ← Brotli was chosen
    Vary: Accept-Encoding         ← caches must key on encoding
```

#### 🎤 Interview question
**Q: gzip vs Brotli — when would you use each, and what must you NOT compress?**
A: Prefer **Brotli for text** (HTML/CSS/JS/SVG/JSON) — it generally compresses smaller than gzip. Use Brotli's highest levels for **static assets** you compress once ahead of time; for **dynamic responses**, a mid-level Brotli or gzip avoids the CPU cost. Keep **gzip as a fallback** for older clients. Never (re-)compress **already-compressed binaries** — images (JPEG/PNG/WebP/AVIF), video (MP4), or `.woff2` fonts — there's no redundancy to remove, so you only burn CPU.

### 🌍 CDNs & The Edge — Serving Close to the User

#### 🧩 What is it?
A **CDN** (Content Delivery Network) is a global fleet of servers ("edge" locations) that cache copies of your content near users, so requests are answered from a city close by instead of from your single origin server far away.

#### 🤔 Why do we need it? (the problem)
Latency is bounded by distance. If your one server is in Virginia, a user in Sydney pays a huge RTT on *every* round-trip — and that tax repeats for the whole loading waterfall. A CDN cuts the distance: the user talks to an edge node maybe 20 ms away instead of 200 ms away, slashing every round-trip and offloading work from your origin.

#### ⚙️ How does it work?
- **Edge caching:** the first request in a region fetches from origin and caches it at the nearby edge; later users in that region are served instantly from the edge.
- **Edge compute:** small functions can run *at the edge* (redirects, auth, personalization, A/B logic) without a trip to the origin.
- **Origin shielding:** a designated mid-tier cache sits in front of the origin so that on a cache miss, many edges don't all stampede the origin at once — they go through the shield, which fetches origin **once**.

```
            ┌────────── Origin (Virginia) ──────────┐
            │            ▲  (cache miss only)        │
            │      Origin Shield (one fetch)         │
            └────────────▲───────────────────────────┘
        ┌────────────────┼─────────────────┐
   ┌────┴────┐      ┌────┴────┐       ┌─────┴───┐
   │ Edge:   │      │ Edge:   │       │ Edge:   │
   │ Sydney  │      │ London  │       │ Tokyo   │
   └────▲────┘      └────▲────┘       └────▲────┘
        │ ~20ms         │ ~10ms           │ ~15ms
      User             User              User
   (close = low RTT; origin distance hidden)
```

#### 🌍 Real-life analogy
A CDN is a chain of **local grocery stores** instead of one giant central warehouse. You drive five minutes to the nearby branch (the edge) rather than across the country to the warehouse (the origin). Popular items are stocked locally (cached); the rare special-order goes back to the warehouse — but routed through one regional depot (origin shield) so the warehouse isn't mobbed by every store at once.

#### 💻 Concrete illustration
```
  Response served from a CDN edge usually shows headers like:

  HTTP/3 200
  cache-control: public, max-age=31536000, immutable
  age: 842                ← seconds it's lived in the edge cache
  x-cache: HIT            ← served from edge, never touched origin
  server: cloudflare      ← (or fastly, akamai, cloudfront...)
```

#### 🎤 Interview question
**Q: What does a CDN actually do for performance, beyond "caching"?**
A: Three things. (1) **Proximity** — it serves from an edge near the user, cutting the RTT on every round-trip, which matters because latency is distance-bound. (2) **Origin offload** — cached hits never reach your server, and **origin shielding** prevents many edges from stampeding the origin on a miss. (3) **Edge compute** — running logic (auth, redirects, personalization) at the edge avoids a full trip back to origin. Together they cut latency *and* protect the origin.

### 📦 Why "Bundle Everything Into One File" Faded

#### 🧩 What is it?
An old performance rule under HTTP/1.1: **concatenate** all your JS into one big bundle (and all CSS into one), because each request was so expensive. Under HTTP/2's multiplexing, that advice flipped from "always" to "it depends".

#### 🤔 Why do we need to revisit it? (the problem)
Under **HTTP/1.1**, with only ~6 connections and one request at a time each, every separate file was a costly round-trip — so smashing 50 files into 1 was a clear win. People still cite this rule out of habit. But **HTTP/2 multiplexes many requests cheaply over one connection**, so the per-request penalty that justified mega-bundling largely went away — and mega-bundles have real downsides.

#### ⚙️ How does it work?
With HTTP/2, splitting into several smaller files becomes viable and often *better*:
- **Caching granularity:** change one line and a single mega-bundle's hash changes → users re-download *everything*. With smaller chunks, only the changed chunk is re-fetched; the rest stays cached.
- **Parallel + prioritized loading:** many chunks stream together over the one connection, and the browser can fetch only what a route needs (code-splitting).
- **The nuance (flagged):** it's not "more files is always better" — too many tiny files add overhead (per-request bookkeeping, worse compression, request scheduling cost). The modern answer is *moderate* splitting, not one giant blob **or** a thousand fragments.

```
  HTTP/1.1 thinking:   many files = many costly trips
     → CONCATENATE into 1 huge bundle

  HTTP/2 reality:      many files share 1 multiplexed conn
     → SPLIT into sensible chunks
        ✓ change 1 chunk → re-download only that chunk
        ✓ load only the route's chunks
        ⚠ but don't over-split into 1000 tiny files
```

#### 🌍 Real-life analogy
HTTP/1.1 was like a **toll booth that charged a flat fee per car** — so you crammed everyone into one bus. HTTP/2 removed most of the toll, so now several smaller cars travel together fine — and if one passenger changes their mind, only *that* car turns around, not the whole bus. But sending a thousand one-person cars still clogs the road, so you balance it.

#### 💻 Concrete illustration
```
  One mega-bundle, then a 1-line edit:
    bundle.[hash].js   400 KB  →  hash changes  →  re-download all 400 KB

  Split bundles, same 1-line edit:
    vendor.[hash].js   300 KB  →  unchanged  →  served from cache
    app.[hash].js      100 KB  →  hash changes  →  re-download 100 KB only

  Result: 300 KB saved on every deploy that didn't touch vendor code.
```

#### 🎤 Interview question
**Q: Why is "bundle everything into one file" no longer the default advice under HTTP/2?**
A: That rule existed because HTTP/1.1 made each request expensive (≤6 connections, one-at-a-time), so fewer files meant fewer round-trips. **HTTP/2 multiplexes many requests cheaply over a single connection**, erasing most of that penalty. Splitting into sensible chunks then wins on **caching granularity** (a small change re-downloads only the changed chunk, not the whole app) and lets you **load only what a route needs**. The caveat: don't over-split into thousands of tiny files — that reintroduces overhead and hurts compression. Aim for moderate, logical splitting.

<h2 id="module-4">Module 4 — Strategic Caching</h2>

The fastest request is the one you never make. Caching is the art of keeping a copy of something close by so you can reuse it instead of fetching it again — but done wrong, your users get stuck on a stale version of your app for days. This module is about caching *strategically*: aggressively caching the stuff that never changes, never caching the stuff that does, and shipping updates instantly anyway.

---

### 🗂️ The Layered Cache — A Copy at Every Step

#### 🧩 What is it?
Between your browser and the server that owns a file, there isn't *one* cache — there's a **stack of caches**, each one closer to the user than the last. A request only travels as far as the first layer that already has a fresh copy.

#### 🤔 Why do we need it? (the problem)
A round-trip to the origin server (the machine that actually generated the file) can take hundreds of milliseconds, especially for a user on another continent. If every image, script, and stylesheet had to come all the way from the origin every single time, even a well-built site would feel sluggish. Each cache layer lets a request **stop early** and reuse a copy that's physically nearer.

#### ⚙️ How does it work?
A request checks each layer top to bottom and returns from the first one that has a fresh copy:

```
   Browser memory cache   (RAM, this tab only, instant)
        │ miss
        ▼
   Browser disk cache     (on-disk, survives reloads)
        │ miss
        ▼
   Service Worker cache   (your JS decides — see Mod 3)
        │ miss
        ▼
   CDN / edge cache       (shared, near the user)
        │ miss
        ▼
   Origin server          (the source of truth, far away)
```

The higher the layer that answers, the faster and cheaper the response. The browser's two caches are **private** to one user; the CDN (Content Delivery Network — a fleet of servers spread worldwide) is **shared** by everyone in that region. The **Service Worker** — a script the browser runs in the background — sits in between and can serve from its own cache under rules *you* write (its mechanics are covered in Module 3; here it's just one layer in the stack).

#### 🌍 Real-life analogy
Looking for a stapler. First you check your own desk drawer (browser memory) — instant. Not there? The shelf behind you (disk). Still nothing? Ask your team's supply cabinet (CDN, shared by the floor). Empty? Someone drives to the central warehouse (origin). You only make the long trip if every closer spot came up empty.

#### 💻 Code example
```text
# A response tells caches HOW it may be stored, via headers.
# The same file gets very different rules depending on what it is:

# index.html — the entry point. Must always reflect the latest deploy:
Cache-Control: no-cache

# app.9f2a1c.js — a content-hashed bundle. Safe to keep forever:
Cache-Control: public, max-age=31536000, immutable
#                                ^31536000 seconds = 1 year
```

#### 🎤 Interview question
**Q: A user in Tokyo loads your site hosted in Virginia and it's fast on the second visit. Where did the speed come from?**
A: The layered cache. The first visit populated nearer layers — the CDN edge node in Tokyo holds shared copies, and the user's own browser disk cache holds private copies. On the second visit most requests are answered by those near layers instead of crossing the Pacific to the origin, cutting latency dramatically.

### 🎛️ `Cache-Control` — The Caching Rulebook

#### 🧩 What is it?
`Cache-Control` is an HTTP response header where the server states the **rules** for caching a file: who may store it, for how long, and whether to double-check before reusing it. Every cache layer obeys these directives.

#### 🤔 Why do we need it? (the problem)
Caches don't know your intent. Without explicit rules, a cache might keep your HTML for hours (users miss your deploy) or refuse to cache your logo (wasted bandwidth on every page). `Cache-Control` lets *you* — who knows which files change and which never do — set the policy precisely instead of leaving it to guesswork.

#### ⚙️ How does it work?
The header is a comma-separated list of directives. The key ones:

```text
max-age=N    Reuse without asking for N seconds. After that,
             the copy is "stale" and must be revalidated.

no-cache     MAY store the copy, but MUST revalidate with the
             server before every reuse. (NOT "don't cache"!)

no-store     MUST NOT store this at all, anywhere. For secrets
             / per-request private data.

public       Shared caches (the CDN) may store it too.

private      Only the user's browser may store it, never a
             shared CDN. (e.g. a personalized page.)

immutable    Within max-age, do NOT even bother revalidating —
             the file will never change. Skips the check.

stale-while-revalidate=N
             After going stale, serve the OLD copy instantly
             AND refresh it in the background for next time.
```

Two pairs cause the most confusion, so be precise:

- **`no-cache` vs `no-store`.** `no-cache` *does* store the file — it just won't reuse it without a quick "is this still current?" check first (see validation, next topic). `no-store` is the strict one: nothing is written to any cache, ever.
- **`private` vs `public`.** `private` means only the end user's browser may keep it; shared caches like the CDN must not. `public` explicitly allows shared caches to store it.

`immutable` is the speed trick: normally even a fresh-but-old copy might get a revalidation check; `immutable` tells the browser "don't waste a round-trip, this exact URL's bytes never change."

#### 🌍 Real-life analogy
Think of a carton of milk. `max-age` is the **best-before date** — fine to drink until then. `no-cache` is milk you keep in the fridge but **always sniff before pouring**. `no-store` is sushi you must **eat now or bin** — never save it. `private` is *your* lunch in the shared fridge with your name on it; `public` is the office snack basket anyone may take from. `immutable` is a sealed can with a 1-year date — no need to inspect it before the date, it cannot have spoiled.

#### 💻 Code example
```text
# HTML shell — always check for a new deploy before reusing:
Cache-Control: no-cache

# A hashed JS bundle — keep a full year, never re-check:
Cache-Control: public, max-age=31536000, immutable

# A personalized dashboard fragment — user's browser only:
Cache-Control: private, max-age=0, must-revalidate

# An API response with a card number — never write to disk:
Cache-Control: no-store

# A news feed — serve instantly, refresh quietly in the bg:
Cache-Control: max-age=60, stale-while-revalidate=300
# For 60s it's fresh; for the next 300s it serves the stale
# copy at once while fetching a fresh one for next time.
```

#### 🎤 Interview question
**Q: What's the difference between `no-cache` and `no-store`?**
A: `no-cache` still **stores** the response, but the cache must **revalidate** it with the server before each reuse — if the server says it's unchanged, the cached copy is served (fast, tiny round-trip). `no-store` forbids writing the response to **any** cache at all, so it's re-downloaded in full every time — used for sensitive or always-unique data. The common mistake is reading `no-cache` as "don't cache"; it actually means "cache, but verify first."

### 🔁 Validation — `ETag`, `Last-Modified` & the `304`

#### 🧩 What is it?
**Validation** is the quick "has this changed?" check a cache does when its copy is stale (or marked `no-cache`). Instead of re-downloading the whole file, it asks the server using a **validator** — an `ETag` or a `Last-Modified` date — and the server can reply "nope, reuse what you have."

#### 🤔 Why do we need it? (the problem)
A stale copy is often *still correct* — the file may not have changed at all. Re-downloading it in full would waste bandwidth and time for nothing. Validation lets the cache confirm freshness with a tiny request and, when nothing changed, skip the download entirely.

#### ⚙️ How does it work?
When the server first sends a file, it attaches a validator. The browser stores it and sends it back on the next request to ask "still good?":

```
   First response from server:
     ETag: "v23-9f2a1c"          (a fingerprint of the bytes)
     Last-Modified: Tue, 10 Jun 2026 ...

   Later, browser revalidates:
     If-None-Match: "v23-9f2a1c"        ──▶  server
     If-Modified-Since: Tue, 10 Jun ... ──▶

   Server compares:
     unchanged ─▶ 304 Not Modified   (EMPTY body — reuse copy)
     changed   ─▶ 200 OK             (full new body + new ETag)
```

The `ETag` is a fingerprint of the content (often a hash); `If-None-Match` sends it back. `Last-Modified` is a timestamp; `If-Modified-Since` sends it back. If the file is unchanged, the server returns **`304 Not Modified`** with an **empty body** — the browser then serves its cached copy. The win: a `304` carries almost no data, so you pay one small round-trip instead of a full re-download.

#### 🌍 Real-life analogy
You photocopied a long report yesterday. Today, before copying it again, you call the author: "Is version 9f2a1c still current?" If they say "yes, unchanged" (a `304`), you just reuse your existing copy — no need to re-print 200 pages. Only if they say "I revised it" do you make a fresh copy.

#### 💻 Code example
```text
# Round 1 — first download
GET /style.css
< 200 OK
< ETag: "abc123"
< Cache-Control: no-cache
< (full CSS body sent)

# Round 2 — copy is present but no-cache forces a check
GET /style.css
> If-None-Match: "abc123"
< 304 Not Modified
< (NO body — browser reuses its cached style.css)

# Round 3 — the file was edited and redeployed
GET /style.css
> If-None-Match: "abc123"
< 200 OK
< ETag: "def456"
< (full new CSS body sent)
```

#### 🎤 Interview question
**Q: What is a `304 Not Modified` and why is it useful?**
A: It's the server's reply to a conditional (revalidation) request saying the cached copy is still current. It has an **empty body**, so instead of re-downloading the whole resource the browser pays only a tiny round-trip and then serves its existing cached copy. It's what makes `no-cache` cheap — you verify freshness without re-transferring unchanged bytes.

### 🏷️ Content Hashing — Cache Forever, Update Instantly

#### 🧩 What is it?
The killer caching pattern for a modern web app: give every built asset a filename containing a **hash of its contents** (like `app.9f2a1c.js`), cache those hashed files for a **year** as `immutable`, and serve the **HTML shell** that links them with `no-cache`. Updates ship the instant you deploy.

#### 🤔 Why do we need it? (the problem)
You want two things that seem to fight each other: (1) cache scripts and styles **aggressively** so repeat visits are instant, and (2) push a new version **immediately** when you deploy. Cache a file for a year and users are stuck on old code; cache nothing and you throw away all the speed. Content hashing dissolves the conflict.

#### ⚙️ How does it work?
The trick: a file's URL changes **only when its contents change**, because the hash is derived from the bytes. So you never "update" a cached file — you ship a **new filename**, which is a guaranteed cache miss. The always-fresh HTML points at whichever filenames exist now:

```
   index.html        ── no-cache (always revalidated)
     │   references
     ▼
   app.9f2a1c.js     ── immutable, max-age=1yr
   style.4b8e02.css  ── immutable, max-age=1yr

   ── you deploy a code change ──

   index.html        ── revalidated, gets the NEW links
     │
     ▼
   app.7d3f55.js     ← NEW name = forced fetch (cache miss)
   style.4b8e02.css  ← unchanged name = still served from cache
```

On every visit the browser revalidates only the tiny HTML (cheap, via a `304` when nothing changed). When you deploy, the changed bundle gets a new hash → new filename → the HTML now references it → the browser must fetch it because it has never seen that URL. Unchanged files keep their old hash and are still served instantly from cache. Best of both: year-long caching *and* instant updates.

#### 🌍 Real-life analogy
Imagine a library where you never edit a book in place. Each edition gets a **new catalogue number** printed from its contents. The reading list (the HTML) is reprinted often and cheaply, and it points at the current catalogue numbers. Readers keep editions on their shelf forever — when a book is revised, it simply gets a new number, so the new list sends them to fetch the new copy while every unchanged book stays on the shelf.

#### 💻 Code example
```text
# The HTML shell — small, always checked for a new deploy:
GET /index.html
< Cache-Control: no-cache
< <script src="/app.9f2a1c.js"></script>

# Hashed assets — locked down for a year, never revalidated:
GET /app.9f2a1c.js
< Cache-Control: public, max-age=31536000, immutable

# After a deploy that changed app.js, the shell now serves:
< <script src="/app.7d3f55.js"></script>
#                   ^ new hash → new URL → guaranteed fresh fetch
```
Your bundler (Webpack, Vite, etc.) generates the hashed filenames automatically — you just configure the two `Cache-Control` policies on the server: `no-cache` for HTML, `immutable` for hashed assets.

#### 🎤 Interview question
**Q: How do you cache a JS bundle for a year but still ship updates instantly?**
A: Put a content hash in the filename (`app.<hash>.js`) and serve hashed assets with `Cache-Control: public, max-age=31536000, immutable`, while serving the HTML that links them with `no-cache`. Because the hash changes only when the contents change, a code update produces a **new filename** — a guaranteed cache miss — and the always-revalidated HTML points at it. Unchanged files keep their name and stay cached. You get a full year of caching plus instant rollout.

### 💥 Cache Invalidation — The Hard Problem

#### 🧩 What is it?
**Cache invalidation** is making caches drop or refresh a copy that's no longer correct. There's a famous joke in computing: "There are only two hard things — naming things, and cache invalidation." It's hard because a cache is, by design, a copy you *don't* want to re-check, so telling every copy everywhere to let go is genuinely tricky.

#### 🤔 Why do we need it? (the problem)
The moment you cache something, you risk serving a **stale** version after the real one changes. If you cached `style.css` for a year and then fixed a bug in it, every returning user keeps the broken copy until the year is up. You need a reliable way to ensure users get the new version — without giving up the speed caching bought you.

#### ⚙️ How does it work?
The robust answer is to **avoid invalidation entirely** with the content-hashing pattern from the last topic — called **cache busting**. Rather than fight to evict an old `style.css`, you change the URL so the old copy is simply never requested again:

```
   Hard way: try to evict the cached file everywhere
     ┌─ browser disk?  CDN edges?  Service Worker? ─┐
     │  must reach EVERY layer and force a refresh  │  ✗ fragile
     └──────────────────────────────────────────────┘

   Easy way: change the URL (cache busting)
     style.css  →  style.4b8e02.css   (new name, new bytes)
     old URL is never requested again; it just expires quietly  ✓
```

Other invalidation tools exist — `no-cache` forces revalidation on each use, CDNs offer a manual **purge** to evict a path on demand, and a Service Worker can delete entries from its own cache in code — but these are about *checking* or *evicting*. Cache busting **sidesteps** the problem: a new filename is automatically a cache miss, so there's nothing to invalidate.

> **Simplification flag:** "immutable forever" is the ideal, but real systems still need a CDN purge for things you *can't* hash — a fixed `/index.html` path, an edge-cached API route, or a third-party file. The hashing pattern shrinks the invalidation problem to those few cases; it doesn't make it vanish completely.

#### 🌍 Real-life analogy
You printed a phone number on 10,000 business cards already in people's wallets, and the number changed. Chasing down every wallet to correct it (true invalidation) is hopeless. Instead you **print new cards with a new design** and hand those out — old cards naturally fall out of use. Changing the artifact beats trying to recall every copy.

#### 🎤 Interview question
**Q: Why is cache invalidation considered hard, and how do you avoid it for static assets?**
A: It's hard because a cached copy can live in many independent layers — browser memory, browser disk, the Service Worker, CDN edges — and reliably forcing all of them to drop a stale copy is fragile and slow. For static assets you **avoid** invalidation with cache busting: put a content hash in the filename so any change yields a new URL, which is automatically a cache miss. The old copy is never requested again and quietly expires, so there's nothing to invalidate — leaving manual CDN purges only for the handful of unhashable paths.

<h2 id="module-5">Module 5 — The JavaScript Cost</h2>

A 200 KB image and a 200 KB JavaScript file weigh the same on the network — but they are *not* equally expensive. The image gets shown and forgotten. The JavaScript has to be read, understood, and *run* by the device, on the same thread that handles taps and scrolls. This module is about that hidden CPU bill: why it hurts most on cheap phones, and the tools (budgets, code splitting, tree shaking, modern output, analyzers) you use to keep it small.

---

### 💸 The Most Expensive Byte — why JS costs more than its size

#### 🧩 What is it?
"The most expensive byte" is the idea that a byte of JavaScript costs your users far more than a byte of almost any other resource. An image is just *decoded and drawn*. A byte of JS must be **parsed, compiled, and executed** — real CPU work — before it does anything.

#### 🤔 Why do we need it? (the problem)
Teams obsess over file *size* (the network) and forget the *CPU*. On a fast laptop the difference hides. On a $100 Android phone, that same script can take **many times longer** to run, because the phone's processor is slow even when the download was quick. So a page that feels instant for the developer feels frozen for a real user — frozen because the **main thread** (the single thread that runs your JS *and* paints the page *and* handles taps) is busy chewing through JavaScript.

#### ⚙️ How does it work?
A script goes through more stages than an image. The image's heavy step (decoding) can happen on a **background thread**; the browser's main thread stays free. JavaScript's parse / compile / execute happen **on the main thread** — so while they run, the page cannot respond to the user.

```
 JavaScript (.js)        on the MAIN THREAD (blocks the UI)
 ┌──────────┐   ┌───────┐   ┌─────────┐   ┌─────────┐
 │ download │──▶│ parse │──▶│ compile │──▶│ execute │
 └──────────┘   └───────┘   └─────────┘   └─────────┘
   network        CPU         CPU            CPU

 Image (.jpg)
 ┌──────────┐   ┌──────────────────────┐
 │ download │──▶│ decode (off-thread)  │──▶ paint
 └──────────┘   └──────────────────────┘
   network        usually NOT main thread
```

The CPU stages scale with how much code there is and how slow the device is. Note the parse/execute time is also affected by *what* the code does, not just byte count — but as a rule of thumb, fewer JS bytes means less main-thread work.

> **Note (simplification):** modern engines like V8 are cleverer than a straight line — they do *lazy* parsing (skim a function now, fully parse it only when first called) and compile hot code further in the background. The takeaway stands: parse/compile/execute is **main-thread CPU work** that an image largely avoids.

#### 🌍 Real-life analogy
Shipping someone a **printed photo** vs. shipping them **flat-pack furniture** of the same weight. The photo: glance at it, done. The furniture: they must unpack it, read the instructions, and *assemble it themselves* before it's usable — and someone with fewer tools (a low-end phone) takes far longer to build it. Same parcel weight, wildly different effort on arrival.

#### 💻 Code example
```javascript
// Two 200 KB downloads — same network cost, very different CPU cost.

// (a) An image: the browser decodes it (often off the main thread)
//     and paints it. Your JS does ~nothing.
const img = new Image();
img.src = '/hero.jpg';   // 200 KB → decode → paint. Main thread mostly free.

// (b) 200 KB of JavaScript: the engine must parse + compile + run it,
//     all on the main thread. While this runs, taps/scrolls wait.
import('./heavy-200kb-module.js').then((mod) => {
  mod.init();            // parse + compile happened first, THEN this runs
});
// On a slow phone, (b) can block the UI for hundreds of ms;
// (a) typically does not.
```

#### 🎤 Interview question
**Q: Why is JavaScript more expensive than an equivalent-sized image?**
A: Because cost is not just bytes. An image is downloaded and decoded — and decoding often happens off the main thread — then painted. A JavaScript file of the same size must be **parsed, compiled, and executed on the main thread**, which is real CPU work that blocks the UI. That CPU cost is disproportionately worse on low-end mobile, where the processor is slow even when the network is fine. So shipping less JS matters more than shipping fewer image bytes.

---

### 📏 Bundle-Size Budgets — drawing a line you refuse to cross

#### 🧩 What is it?
A **bundle-size budget** is a hard limit you set on how many kilobytes of JavaScript (and other assets) a page is allowed to ship — for example, "the initial JS bundle must stay under 170 KB compressed." Cross it, and the build warns or fails.

#### 🤔 Why do we need it? (the problem)
JavaScript grows silently. Every new feature, every added library, every "just one more dependency" adds bytes, and no single change feels like the problem. Six months later the page is twice as heavy and nobody decided that on purpose. A budget turns "be careful" into a *number a machine can check*, so a regression gets caught in review instead of in production.

#### ⚙️ How does it work?
You pick a target, often tied to a real-world goal (e.g. "interactive within ~5s on a mid-range phone on slow 4G" implies roughly a 130–170 KB *compressed* JS budget). The build tooling measures the output and compares it to the budget.

```
   build output     budget        result
   ┌──────────┐   ┌────────┐
   │ 152 KB   │ ≤ │ 170 KB │  →  ✅ pass
   └──────────┘   └────────┘
   ┌──────────┐   ┌────────┐
   │ 188 KB   │ > │ 170 KB │  →  ❌ fail the build / warn in PR
   └──────────┘   └────────┘
```

Budgets are usually expressed in **compressed** (gzip/Brotli) size, because that's what travels over the wire — but remember the *CPU* cost from the last topic scales with the **uncompressed** size, since the engine parses the decompressed code. Track both.

#### 🌍 Real-life analogy
A **carry-on luggage sizer** at the airport gate. It doesn't care how nicely you packed — if the bag doesn't fit the frame, it doesn't fly. The budget is the frame: an objective, unarguable limit that stops slow creep before it boards.

#### 💻 Code example
```javascript
// A size budget expressed in build config (webpack-style).
// The build emits a warning (or error) when an asset crosses the line.
module.exports = {
  performance: {
    hints: 'error',              // 'warning' | 'error' | false
    maxAssetSize: 170_000,       // bytes, per asset
    maxEntrypointSize: 170_000,  // bytes, for the initial entry bundle
  },
};
// Build a feature that pushes main.js to 188 KB →
//   ERROR: asset size limit: main.js (188 KiB) exceeds 170 KiB
```

#### 🎤 Interview question
**Q: What goes in a JavaScript size budget, and why?**
A: A cap on shipped JS — usually the *initial* (above-the-fold / critical-path) bundle, measured in **compressed** kilobytes because that's the network cost, while also watching uncompressed size because that drives parse/compile CPU. You tie the number to a real target (time-to-interactive on a mid-range phone) and enforce it in CI so regressions fail the build instead of silently shipping. The point is to make "the bundle got heavier" a decision someone has to make on purpose, not an accident.

---

### ✂️ Code Splitting & Dynamic import() — load only what this screen needs

#### 🧩 What is it?
**Code splitting** is breaking one giant JavaScript bundle into several smaller pieces (**chunks**) that load *when needed* instead of all up front. **Dynamic `import()`** is the JavaScript feature that triggers it: an `import()` *call* (not the static `import` statement) that returns a **Promise** and tells the bundler "make this its own chunk and fetch it on demand."

#### 🤔 Why do we need it? (the problem)
Without splitting, a user who opens your homepage downloads, parses, and compiles the code for the *entire* app — the settings page, the admin dashboard, the chart library — even though they may never visit those. That's a huge upfront tax for code that isn't used yet. Splitting defers that cost until (and unless) the user actually needs it.

#### ⚙️ How does it work?
There are two common places to split:
- **Route-level:** each page/route becomes its own chunk; navigating to `/settings` fetches the settings chunk.
- **Component-level:** a heavy widget (a rich text editor, a charting library) loads only when it's about to be shown (e.g. when a modal opens).

A static `import` is pulled into the current bundle at build time. A dynamic `import()` becomes a **split point** — its own file — fetched at runtime, returning a Promise that resolves to the module:

```
 Without splitting        With code splitting
 ┌────────────────┐       ┌──────────┐  loaded now
 │  main.js       │       │ main.js  │
 │  (everything)  │       └──────────┘
 │  ~600 KB       │       ┌──────────┐  fetched when
 └────────────────┘       │ chart.js │  the chart is
   all up front           └──────────┘  actually shown
```

Trade-off to flag: each chunk is an extra request, and a chunk fetched *at the moment* it's needed adds a small delay (often hidden behind a loading spinner, or avoided by **prefetching** the chunk during idle time).

#### 🌍 Real-life analogy
A restaurant doesn't cook **every dish on the menu** the second you sit down. They cook a dish **when you order it**. Code splitting is ordering à la carte: the kitchen (the browser) only does the work for what this customer actually asked for, instead of plating the entire menu just in case.

#### 💻 Code example
```javascript
// RUNNABLE: load a heavy module only when the user clicks — on demand.
// Static imports load up front; dynamic import() defers until the click.

const button = document.getElementById('open-editor');

button.addEventListener('click', async () => {
  button.textContent = 'Loading…';

  // import() returns a Promise and creates a SEPARATE chunk.
  // The editor's bytes are NOT in the initial bundle.
  const { createEditor } = await import('./rich-text-editor.js');

  createEditor(document.getElementById('editor-slot'));
  button.textContent = 'Editor ready';
});

// Result: users who never click never download/parse/run the editor.
// The /* webpackChunkName */ comment can name the chunk if you like:
//   await import(/* webpackChunkName: "editor" */ './rich-text-editor.js');
```

#### 🎤 Interview question
**Q: How does code splitting help, and where do you split?**
A: It shrinks the *initial* download/parse/execute cost by deferring code the user doesn't need yet into separate chunks loaded on demand via dynamic `import()` (which returns a Promise and creates its own file). The natural split points are **route-level** — each page loads its own chunk — and **component-level** — heavy widgets (editors, charts) load when they're about to render. The trade-off is extra requests and a possible just-in-time delay, which you soften by prefetching likely-next chunks during idle time.

### 🌳 Tree Shaking & Modern Output — ship only the code you actually use

#### 🧩 What is it?
**Tree shaking** is automatically removing code you import but never use — "dead-code elimination" for your dependencies. Import one helper from a library and tree shaking aims to leave the *other 200 helpers* out of your bundle. It pairs with shipping **modern** (smaller) JavaScript and **minification** to squeeze the bundle further.

#### 🤔 Why do we need it? (the problem)
Libraries are big, but you usually use a sliver of them. Without tree shaking you'd ship the whole library to use one function — pure waste that costs download *and* parse/compile time. Separately, transpiling code down to ancient syntax (for browsers you may not even support) makes the output **larger and slower**; shipping modern syntax keeps it lean.

#### ⚙️ How does it work?
Tree shaking depends on **static ES modules** (`import` / `export`). Because ESM imports are statically analyzable — the bundler can see exactly what's used *without running the code* — it can prove a function is never referenced and drop it. Then **minification** removes whitespace, comments, and shortens names.

```
   import { sum } from 'mathlib';   // you use ONE export
   ┌──────────── mathlib ───────────┐
   │ sum    ← used    → KEPT        │
   │ mean   ← unused  → SHAKEN OUT  │
   │ stdDev ← unused  → SHAKEN OUT  │
   └────────────────────────────────┘
```

**When tree shaking fails** (flag these honestly):
- **CommonJS** (`require()` / `module.exports`) — it's dynamic, resolved at runtime, so the bundler *can't* statically prove what's unused. Tree shaking needs ESM.
- **Side effects** — code that *does something* just by being imported (modifies a global, registers a polyfill, injects CSS). The bundler can't safely remove a module if dropping it might skip a needed side effect. You promise a package is safe to prune with **`"sideEffects": false`** in its `package.json` (or list the files that *do* have side effects).
- **Namespace / dynamic access** (`import * as x` then `x[name]()`) can defeat it, since the bundler can't tell which members you'll touch.

The **duplicate-dependency trap:** two libraries each depend on, say, two *different* versions of `lodash`, so the bundle ships both copies — paying for the same code twice. A bundle analyzer (next topic) is how you catch it.

#### 🌍 Real-life analogy
Packing for a trip with a **shopping list vs. a junk drawer**. A static `import` is a precise list — "I need the sum function" — so the packer knows exactly what to bring and leaves the rest. A side-effecting CommonJS module is a junk drawer wired to the house alarm: the packer dares not remove anything, in case unplugging it sets something off — so it all comes along.

#### 💻 Code example
```javascript
// TREE-SHAKEABLE: a named import from an ES module.
// The bundler sees you use only `clamp`, so `debounce`/`throttle`
// (if unused) are eliminated from the final bundle.
import { clamp } from './utils.js';   // ES module, named export

console.log(clamp(120, 0, 100));      // → 100

// ❌ HARDER TO SHAKE: importing the whole namespace can pull
//    in everything, because access is dynamic.
//    import * as utils from './utils.js';  // avoid if you only need clamp

// In the LIBRARY's package.json — promise it's safe to prune:
//   { "sideEffects": false }
// or, if some files DO have side effects (e.g. CSS imports):
//   { "sideEffects": ["*.css", "./src/polyfills.js"] }
```

#### 🎤 Interview question
**Q: What is tree shaking and when does it fail?**
A: It's dead-code elimination — dropping imported-but-unused code from the bundle. It works because **ES modules** are statically analyzable, so the bundler can prove what's never referenced. It fails when the code isn't statically analyzable or isn't safe to remove: **CommonJS** (`require`) is resolved at runtime so it can't be shaken; **side-effectful modules** can't be dropped unless the package declares **`"sideEffects": false"`** (or lists its side-effecting files); and dynamic/namespace access (`import * as x; x[key]`) can defeat it. Pairing it with shipping modern syntax and minification gives the smallest, fastest output — and a bundle analyzer catches the duplicate-dependency trap where the same library ships twice.

<h2 id="module-6">Module 6 — Images & Media</h2>

On most pages, the pictures and videos weigh more than everything else combined — and the big banner photo at the top is usually the very thing Google's stopwatch is timing. So if you want a fast page, images are where the easy wins (and the embarrassing mistakes) live. This module shows you how to ship the *right* image, at the *right* size, in the *right* format, without making the page jump around while it loads.

---

### 🐘 Images Are the Heaviest Bytes & the Usual LCP — start where the weight is

#### 🧩 What is it?
On a typical web page, images are the **largest chunk of downloaded data** — often more than the HTML, CSS, and JavaScript put together. And the single biggest image visible when the page first loads (a hero banner, a product photo) is frequently the **LCP element** — **LCP** is *Largest Contentful Paint*, Google's measure of "how long until the main thing shows up."

#### 🤔 Why do we need to know this? (the problem)
When a page feels slow, people guess it's "the code." Usually it's a 2 MB photo someone dropped in at full camera resolution. Because images are both the **biggest bytes** *and* the **thing being timed for LCP**, optimizing one image often does more for your score than hours of JavaScript tuning. You optimize where the weight is.

#### ⚙️ How does it work?
Three levers shrink image cost, and we'll pull each in this module:

```
   1. FORMAT      pick AVIF/WebP over JPEG/PNG  → fewer bytes
   2. RESOLUTION  serve a size that fits the    → fewer bytes
                  device (srcset / sizes)
   3. LOADING     load the LCP image EARLY,     → faster LCP,
                  lazy-load the rest, reserve     no layout jump
                  space to stop CLS
```

The LCP image specifically must arrive **early and at the right size** — anything that delays it (lazy-loading it, serving a huge file, discovering it late) pushes LCP up.

#### 🌍 Real-life analogy
Imagine packing a suitcase. The socks (your JavaScript) are annoying but small. It's the **winter coat** (the hero image) that eats all the space and decides whether the bag closes. You don't reorganize socks to make room — you deal with the coat first.

#### 💻 Code example
```html
<!-- The hero image: it is the LCP element here. -->
<!-- Goal for THIS image: small file, right size, loads EARLY. -->
<img
  src="hero-1200.jpg"
  width="1200"
  height="600"
  alt="Mountain sunrise"
/>
<!-- We will improve this exact tag in the topics below:
     better format, multiple resolutions, and correct loading. -->
```

#### 🎤 Interview question
**Q: A page's LCP is 4 seconds and the LCP element is a hero image. Where do you look first?**
A: The image itself, before touching code. Is it in a modern format (AVIF/WebP), is it sized to what's actually displayed (not the full-res original), is it discovered and downloaded early (not lazy-loaded, ideally preloaded with high priority), and does the layout reserve space for it? Images are usually both the heaviest bytes and the LCP element, so that's the highest-leverage place to start.

---

### 🗜️ Modern Formats: AVIF & WebP vs JPEG/PNG — same picture, fewer bytes

#### 🧩 What is it?
A **format** is *how* the picture is encoded into bytes. The old defaults are **JPEG** (photos) and **PNG** (graphics/transparency). The modern ones are **WebP** and **AVIF**, which use smarter compression to make a visually similar image in far fewer bytes.

#### 🤔 Why do we need them? (the problem)
JPEG was designed in 1992. Compression has improved a lot since. For roughly the same visual quality, the modern formats are smaller — **AVIF is usually the smallest, then WebP, then JPEG** — so you ship less data for the same-looking image. Smaller bytes means faster LCP, less mobile data burned, lower bandwidth bills.

> **Simplification flag:** "AVIF smaller than WebP smaller than JPEG" is the *usual* ranking and a safe default, but it is not a law. The exact ordering depends on the specific image, the quality setting, and the encoder. For some images WebP or even JPEG can tie or win. Always test on *your* assets if bytes are critical — but reach for AVIF/WebP first.

#### ⚙️ How does it work?
Two ideas decide which format fits:

- **Lossy vs lossless.** *Lossy* throws away detail the eye barely notices to save bytes (great for photos). *Lossless* keeps every pixel exactly (needed for sharp logos, screenshots, line art). JPEG is lossy-only; PNG is lossless-only; **WebP and AVIF can do both.**
- **Transparency.** PNG supports transparent areas (an alpha channel); JPEG does not. **WebP and AVIF support transparency too** — so they can replace *both* JPEG and PNG.

```
   NEED                        REACH FOR
   ─────────────────────────   ───────────────────────────
   Photo, smallest file    →   AVIF (then WebP, then JPEG)
   Transparency (logo)     →   AVIF / WebP / PNG  (not JPEG)
   Sharp graphic, exact    →   lossless WebP/AVIF or PNG
   Maximum compatibility   →   JPEG/PNG as the fallback
```

The catch: not every browser decodes AVIF (and very old ones miss WebP). So you don't *replace* JPEG/PNG — you **offer the modern format first and fall back** to the old one. The `<picture>` topic below shows exactly how.

#### 🌍 Real-life analogy
It's like shipping the same gift in different packaging. JPEG is a roomy old cardboard box. WebP is vacuum-sealed. AVIF is vacuum-sealed *and* folded by an expert — same gift inside, a fraction of the size. You still keep a normal box around for the one relative whose mailbox can't accept vacuum packs.

#### 💻 Code example
```text
Rough bytes for the SAME 1200px photo at similar quality
(illustrative — real numbers depend on the image & encoder):

   JPEG  ████████████████████  ~220 KB
   WebP  ███████████           ~130 KB   (~40% smaller)
   AVIF  ███████               ~ 85 KB   (~60% smaller)

Same picture on screen. Less than half the download with AVIF.
```

#### 🎤 Interview question
**Q: When would you choose WebP/AVIF over JPEG or PNG, and what's the catch?**
A: Almost always for photos and graphics — they give similar quality in fewer bytes (AVIF usually smallest, then WebP, then JPEG/PNG), and unlike JPEG they support both lossy *and* lossless and transparency, so they can replace PNG too. The catch is browser support: older browsers may not decode AVIF (or WebP), so you serve the modern format with a JPEG/PNG fallback via `<picture>` rather than dropping the old format entirely.

---

### 📐 Responsive Images: `srcset` + `sizes` and `<picture>` — the right file for the screen

#### 🧩 What is it?
**Responsive images** mean serving a *different image file depending on the device*. Two tools do two different jobs:
- **`srcset` + `sizes`** let the browser pick the right **resolution** (a small file for a phone, a big file for a 4K monitor) — same picture, different sizes.
- **`<picture>`** lets *you* choose a **different image** entirely — a different **format** (AVIF with a JPEG fallback) or a different **crop** for different screens (**art direction**).

#### 🤔 Why do we need them? (the problem)
Sending one giant 2000px image to everyone wastes bytes on a 360px phone and looks blurry if you instead send a tiny one to a big screen. And a wide landscape hero that looks great on desktop becomes a thin, unreadable strip on a phone where you'd rather show a tight crop. One file can't be optimal for every device.

#### ⚙️ How does it work?
**`srcset` lists candidate files with their widths; `sizes` tells the browser how wide the image will be drawn.** The browser does the math and picks — *before* layout, so it can choose early.

```
   You provide:  small-400.jpg  400w
                 mid-800.jpg    800w
                 big-1600.jpg  1600w
   You declare:  sizes = "(max-width: 600px) 100vw, 50vw"
                 ("full width on phones, half width otherwise")

   Browser knows screen width + device pixel ratio (DPR)
         │
         ▼
   picks the smallest file that still looks crisp
   (e.g. 800w on a phone, 1600w on a retina desktop)
```

Key distinction to nail in interviews:
- **`srcset`/`sizes` = same image, browser picks the RESOLUTION.**
- **`<picture>`/`<source>` = YOU pick a different file** — used for **format** fallback (AVIF → WebP → JPEG) and **art direction** (different crop per breakpoint). The browser uses the **first** `<source>` whose conditions match.

#### 🌍 Real-life analogy
`srcset`/`sizes` is a coffee shop offering small, medium, and large of the *same* drink — you take the size that fits your cup. `<picture>` is the barista swapping to a *different* recipe: decaf for the kid, oat milk for the lactose-intolerant — not a size choice, a *different drink* for a different need.

#### 💻 Code example
```html
<!-- 1) srcset + sizes: SAME photo, browser picks the resolution. -->
<img
  src="photo-800.jpg"                              
  srcset="photo-400.jpg 400w,
          photo-800.jpg 800w,
          photo-1600.jpg 1600w"
  sizes="(max-width: 600px) 100vw, 50vw"
  width="1600"
  height="900"
  alt="Coastline at dusk"
/>
<!-- src="photo-800.jpg" is the fallback for very old browsers
     that ignore srcset. width/height reserve space (see CLS topic). -->


<!-- 2) <picture>: format fallback. Browser uses the FIRST source it
     can decode. Modern browsers get AVIF, then WebP; the rest get
     the <img> JPEG. The <img> is REQUIRED — it is the real image
     and carries alt, width, height. -->
<picture>
  <source srcset="photo.avif" type="image/avif" />
  <source srcset="photo.webp" type="image/webp" />
  <img
    src="photo.jpg"
    width="1600"
    height="900"
    alt="Coastline at dusk"
  />
</picture>


<!-- 3) <picture> for ART DIRECTION: a DIFFERENT crop per screen.
     Phones get a tight square; wider screens get the landscape. -->
<picture>
  <source media="(max-width: 600px)" srcset="hero-square.jpg" />
  <source media="(min-width: 601px)" srcset="hero-wide.jpg" />
  <img src="hero-wide.jpg" width="1600" height="600" alt="City skyline" />
</picture>
```

#### 🎤 Interview question
**Q: `srcset` vs `<picture>` — when do you reach for each?**
A: Use **`srcset` + `sizes`** when it's the *same image* and you just want the browser to pick the best **resolution** for the device's width and pixel density — the browser decides. Use **`<picture>`** when *you* need to pick a **different file**: for **format** fallback (offer AVIF/WebP with a JPEG `<img>` fallback) or for **art direction** (a different crop/aspect per breakpoint, like a tight portrait on mobile vs a wide landscape on desktop). Rule of thumb: resolution → `srcset`; format or crop → `<picture>`.

### 📏 Sizing to Prevent CLS — reserve the space before the pixels arrive

#### 🧩 What is it?
**CLS** is *Cumulative Layout Shift* — Google's measure of how much your content **jumps around** while loading. An image with no declared size is a classic cause: it takes up zero height until it downloads, then suddenly pops in and shoves everything below it down the page.

#### 🤔 Why do we need to fix it? (the problem)
You've seen it: you go to tap a link, an image loads above it, the whole page lurches, and you tap an ad instead. That lurch is layout shift — annoying for users and a direct hit to your CLS score. It happens because the browser didn't know how tall the image would be, so it reserved **no space** for it.

#### ⚙️ How does it work?
Give the browser the image's intrinsic **`width` and `height`** (as attributes). Modern browsers turn those into an **aspect ratio** and reserve a correctly-shaped box *before* the image arrives — so when it loads, it slots into space already held for it. Nothing jumps. (CSS like `max-width: 100%; height: auto;` still scales it responsively; the attributes just supply the ratio.)

```
   WITHOUT width/height          WITH width/height
   ┌───────────────┐             ┌───────────────┐
   │  Title        │             │  Title        │
   │  Text…        │             │  Text…        │
   │  [link]  ◀ tap │            │ ┌───────────┐ │  ← space
   └───────────────┘             │ │  (image)  │ │    reserved
       ↓ image loads             │ └───────────┘ │    up front
   ┌───────────────┐             │  [link]       │
   │  Title        │             └───────────────┘
   │  Text…        │                 image loads INTO
   │ ┌───────────┐ │                 the held box →
   │ │  (image)  │ │                 NOTHING shifts
   │ └───────────┘ │
   │  [link] ◀ MOVED!│
   └───────────────┘
```

If you can't set fixed attributes (e.g. fluid layouts), set the CSS **`aspect-ratio`** property instead — it reserves the same correctly-shaped box.

#### 🌍 Real-life analogy
It's like reserving seats at a theatre. If you tell the usher "four people are coming," they rope off four seats and latecomers fit right in — no shuffling. If you say nothing, others fill the row, and when your group arrives everyone has to shift down. `width`/`height` is telling the usher up front.

#### 💻 Code example
```html
<!-- width + height attributes give the browser the aspect ratio.
     It reserves a 16:9 box before the image downloads → no shift. -->
<img
  src="banner-1600.jpg"
  width="1600"
  height="900"
  alt="Product banner"
  style="max-width: 100%; height: auto;"
/>

<!-- No fixed dimensions? Reserve the shape with CSS aspect-ratio. -->
<style>
  .thumb { width: 100%; aspect-ratio: 16 / 9; }
</style>
<img class="thumb" src="thumb.jpg" alt="Video thumbnail" />
```

#### 🎤 Interview question
**Q: How do images cause CLS, and how do you eliminate it?**
A: An image with no declared dimensions occupies no space until it loads, then pushes surrounding content down when it arrives — that's the layout shift. Fix it by always giving the browser the image's proportions up front: set the `width` and `height` attributes (modern browsers derive an `aspect-ratio` from them and reserve a correctly-shaped box), or set the CSS `aspect-ratio` property when fixed attributes don't fit a fluid layout. The image then loads into space already reserved, so nothing moves.

### 🦥 Lazy Loading & Async Decoding — but never the LCP image

#### 🧩 What is it?
- **`loading="lazy"`** tells the browser: *don't download this image until it's about to scroll into view.* Great for images far down a long page.
- **`decoding="async"`** tells the browser it may decode (turn the downloaded bytes into pixels) **off the main thread**, so decoding a big image doesn't freeze the page.

#### 🤔 Why do we need them? (the problem)
A long article might have 40 images, but the visitor sees only the top 2 before maybe leaving. Downloading all 40 up front wastes bandwidth and competes with the images that *are* on screen. Lazy loading defers the off-screen ones until they're needed. Async decoding stops a large image's decode step from blocking interaction.

#### ⚙️ How does it work?
The browser tracks each lazy image's position. When it nears the viewport (the browser keeps a margin so it loads *just before* you reach it), the download starts.

```
   VIEWPORT (what you see now)
   ┌─────────────────────────┐
   │  img A   loading="eager" │  ← above the fold: load NOW
   │  img B   loading="eager" │
   └─────────────────────────┘
   ─ ─ ─ scroll line ─ ─ ─ ─ ─
     img C  loading="lazy"      ← below: wait until near viewport
     img D  loading="lazy"
     img E  loading="lazy"
```

**The critical rule: never lazy-load the LCP / above-the-fold hero image.** Lazy-loading delays its *discovery and download*, which directly **delays LCP** — the exact opposite of what you want for the most important image. Lazy loading is for the images you *can't see yet*. For the hero, do the reverse: load it eagerly (the default), and ideally hint `fetchpriority="high"` so it's fetched ahead of less important resources.

> **Simplification flag:** browsers ship a default "load margin" for lazy images (it can vary by browser and connection speed), and they generally won't lazy-load images already in the initial viewport even if you ask. Still, **explicitly mark the hero as not-lazy** rather than relying on that — don't gamble your LCP on a heuristic.

#### 🌍 Real-life analogy
A good waiter brings your **first course immediately** and holds dessert until you're ready — that's lazy loading the later dishes. But imagine a waiter who "lazily" delays your *appetizer* (the thing you're waiting for) to pre-plate desserts nobody's touching yet. That's lazy-loading the LCP image: you've delayed the one dish that's actually being timed.

#### 💻 Code example
```html
<!-- HERO / LCP image: load it EARLY. Do NOT add loading="lazy".
     fetchpriority="high" asks the browser to fetch it ahead of
     lower-priority resources. -->
<img
  src="hero-1200.avif"
  width="1200"
  height="600"
  alt="Homepage hero"
  fetchpriority="high"
  decoding="async"
/>

<!-- OFF-SCREEN images further down the page: lazy is perfect here. -->
<img
  src="figure-7.avif"
  width="800"
  height="450"
  alt="Diagram seven"
  loading="lazy"
  decoding="async"
/>
```

#### 🎤 Interview question
**Q: You added `loading="lazy"` to every image and LCP got *worse*. Why?**
A: Because the hero (the LCP element) got lazy-loaded too. `loading="lazy"` delays an image's discovery and download until it nears the viewport — fine for off-screen images, but the LCP image is on-screen immediately, so deferring it directly pushes LCP up. The fix: lazy-load only off-screen images; load the hero eagerly and, if anything, hint `fetchpriority="high"` so it's prioritized. Pair both with `decoding="async"` so decoding doesn't block the main thread.

### 🎬 Video & Media — poster frames, `preload`, streaming, and killing the GIF

#### 🧩 What is it?
Video is the *other* heavy media type, and it has its own loading controls: a **poster** (a still image shown before play), the **`preload`** hint (how much to fetch up front), and **streaming** (sending video in small pieces so it can start before the whole file arrives). A key modern move is **replacing animated GIFs with a real `<video>`**.

#### 🤔 Why do we need to manage it? (the problem)
Video files are enormous. Auto-downloading a full video on page load can dwarf every other resource and stall the page. And the animated **GIF** — beloved but terrible — is an ancient format that produces *huge* files for short clips; the same animation as an MP4/WebM `<video>` is often **a fraction of the size**.

#### ⚙️ How does it work?
- **`poster`** shows a lightweight still image immediately, so the slot isn't blank while video data loads (and gives you a quick "LCP-able" visual).
- **`preload`** controls how eager the fetch is:

```
   preload="none"      fetch nothing until the user hits play
   preload="metadata"  fetch just dimensions/duration (cheap)   ← good default
   preload="auto"      browser may fetch the whole thing (heavy)
```

- **Streaming** (via adaptive formats like HLS/DASH) ships the video in chunks and adapts quality to the network, so playback starts fast and doesn't stall — far better than one giant file.
- **GIF → `<video>`:** put a short, muted, looping clip in a `<video>` with `autoplay muted loop playsinline`. It looks like a GIF but downloads a fraction of the bytes. (`muted` is required for autoplay to be allowed.)

#### 🌍 Real-life analogy
Streaming video is like a **water tap**, not a **water-truck delivery**: you don't wait for the whole tank to arrive before drinking — water flows as you need it, and you can turn it down if pressure drops. A GIF, by contrast, is hauling a giant ice block to get a single glass of water: wildly inefficient for what you actually wanted.

#### 💻 Code example
```html
<!-- Replace an animated GIF with a real <video>: tiny by comparison.
     autoplay needs muted; playsinline keeps it inline on iOS. -->
<video
  width="640"
  height="360"
  autoplay
  muted
  loop
  playsinline
  poster="clip-poster.jpg"
>
  <source src="clip.webm" type="video/webm" />
  <source src="clip.mp4"  type="video/mp4" />
  Your browser does not support HTML5 video.
</video>

<!-- A normal (not-autoplay) video: show a poster, fetch only metadata
     until the user decides to play. Saves a huge download up front. -->
<video
  width="1280"
  height="720"
  controls
  preload="metadata"
  poster="lesson-poster.jpg"
>
  <source src="lesson.mp4" type="video/mp4" />
</video>
```

#### 🎤 Interview question
**Q: A marketing page autoplays a decorative animation as a GIF and it's killing load time. What do you do?**
A: Replace the GIF with a `<video>` (WebM/MP4) set to `autoplay muted loop playsinline` — the same animation in a fraction of the bytes because modern video codecs compress far better than GIF. For longer or user-initiated video, add a `poster` still so the slot isn't blank, set `preload="metadata"` (or `none`) so you don't download the whole file before anyone presses play, and use adaptive streaming (HLS/DASH) for long content so it starts fast and adjusts to the network instead of shipping one giant file.

<h2 id="module-7">Module 7 — Font Performance</h2>

Custom fonts make a site look polished — but they are a download, and text can't show its final form until that download finishes. Handle it wrong and visitors stare at invisible words, or watch the whole paragraph jump as the real font swaps in. This module is the small set of levers — `font-display`, preloading, subsetting, metric overrides — that let you ship beautiful type **without** blocked or jumping text.

---

### 🪟 The Web-Font Loading Problem — invisible or jumping text

#### 🧩 What is it?
A **web font** is a font file (the shapes of the letters) that the browser must download from the server before it can paint your text in that exact typeface. While that file is in flight, the browser has a choice to make: show nothing, or show a temporary fallback. Both choices have a downside.

There are three names for what you might see:
- **FOIT** — *Flash Of Invisible Text*: the browser hides the text until the font arrives.
- **FOUT** — *Flash Of Unstyled Text*: the browser shows the text in a backup font first, then re-paints in the real one.
- **CLS** — *Cumulative Layout Shift*, a Core Web Vital that measures how much content visibly **jumps**. If the backup font and the real font are different sizes, the swap pushes text around and counts against CLS.

#### 🤔 Why do we need it? (the problem)
Text is the most important thing on most pages. If a font download is slow (bad network, big file, far-away server), the reader either sees a **blank space where the headline should be** (FOIT) or sees the headline **redraw and shove the rest of the page down** (FOUT → CLS). Either way the experience feels broken, and the layout jump literally hurts your Core Web Vitals score, which affects search ranking.

#### ⚙️ How does it work?
The browser discovers a font is needed, requests the file, and during the wait it follows a **timeout policy** with two phases:

```
  font requested
        │
   ┌────▼─────────┐  block period  ┌──────────────┐
   │ BLOCK PERIOD │───times out───▶│  SWAP PERIOD │
   │ text hidden  │  (invisible)   │ fallback font│
   │  (FOIT)      │                │ shown (FOUT) │
   └──────────────┘                └──────┬───────┘
        │ font arrives                    │ font arrives
        ▼                                 ▼
   paint real font                  re-paint real font
                                    (may shift = CLS)
```

The lengths of the block and swap periods are exactly what `font-display` (next topic) lets you control.

#### 🌍 Real-life analogy
You ordered custom name cards for a party but they're still at the printer. **FOIT** is leaving every seat unlabeled — guests can't sit until the real cards arrive. **FOUT** is putting up cheap handwritten labels now and swapping them for the printed ones later. If the handwritten labels are a different size, swapping them nudges every plate on the table — that nudge is **CLS**.

#### 💻 Code example
```css
/* Declaring a web font. With NO font-display set, browsers default to
   'auto', which most treat like 'block' → FOIT (invisible text first). */
@font-face {
  font-family: "Inter";
  src: url("/fonts/inter.woff2") format("woff2");
  /* font-display omitted on purpose here to show the default problem */
}

body {
  /* The web font, then real fallbacks the user already has installed. */
  font-family: "Inter", system-ui, sans-serif;
}
```

#### 🎤 Interview question
**Q: What is the difference between FOIT and FOUT, and how do they relate to CLS?**
A: **FOIT** (Flash Of Invisible Text) hides text until the web font loads — readers see a blank gap. **FOUT** (Flash Of Unstyled Text) shows a fallback font immediately, then re-paints in the web font. FOUT avoids the blank gap but risks **CLS** (layout shift) if the fallback and web font take up different amounts of space, because the swap reflows the text. The goal is text that's always visible **and** doesn't jump.

---

### 🎛️ `font-display` — choosing block, swap, or optional

#### 🧩 What is it?
`font-display` is a `@font-face` descriptor (a setting inside a font declaration) that tells the browser **what to do while the font downloads and after it arrives**. It picks your trade-off between "never show wrong text" and "never show blank/jumping text."

#### 🤔 Why do we need it? (the problem)
Without it, browsers default to a block-like behavior (FOIT) — readers can stare at invisible text for up to about 3 seconds on a slow connection. `font-display` lets you override that and choose a behavior that matches your priority: readability now, brand font guaranteed, or zero layout shift.

#### ⚙️ How does it work?
The values map onto the block/swap timeline from the previous topic:

```
 value     block period   swap period    result
 ────────  ─────────────  ─────────────  ──────────────────────
 block     ~3s invisible  infinite       FOIT, then real font
 swap      ~0s (none)     infinite       FOUT now, swap when ready
 fallback  ~100ms invis   short (~3s)    brief FOIT, else stick
                                         with fallback
 optional  ~100ms invis   none           use font ONLY if ready
                                         fast; else fallback for
                                         good (best for CLS)
```

The three you'll actually reach for:
- **`block`** = **FOIT**: hide text up to ~3s, then show the web font. Pick only when the wrong font would look badly broken (e.g. an icon font).
- **`swap`** = **FOUT**: show the fallback immediately, swap to the web font whenever it lands — even seconds later. Text is always readable, but a late swap **can shift layout (CLS)**.
- **`optional`** = the font is used **only if it loads almost instantly** (within ~100ms, often from cache); otherwise the browser keeps the fallback **for this page load** and never swaps. No late swap means **no font-driven CLS** — the best choice when avoiding layout shift matters most. Trade-off: first-time visitors may not see your brand font at all on that visit.

> **Simplification flag:** the ~3s block and ~100ms numbers are the typical Chrome/Firefox behavior, not a hard cross-browser guarantee — the spec defines the *phases*, and browsers choose the exact durations.

#### 🌍 Real-life analogy
A waiter taking your order while the kitchen preps the printed menu. **`block`**: he refuses to speak until the fancy menu prints (silence = FOIT). **`swap`**: he tells you the specials from memory now, then hands you the printed menu when it's ready (helpful, but you re-read it). **`optional`**: if the printed menu is already at the stand he hands it over; if not, he just tells you from memory and never bothers swapping — smoothest experience, you might not see the fancy menu today.

#### 💻 Code example
```css
/* swap = FOUT: text is visible immediately in the fallback,
   then re-painted in Inter once it downloads. Most common choice. */
@font-face {
  font-family: "Inter";
  src: url("/fonts/inter.woff2") format("woff2");
  font-display: swap;   /* immediate fallback, may shift on swap */
}

/* optional = lowest CLS risk: use Inter only if it's ready fast,
   otherwise stay on the fallback for this page load (no late swap). */
@font-face {
  font-family: "InterFast";
  src: url("/fonts/inter.woff2") format("woff2");
  font-display: optional;  /* minimizes layout shift */
}
```

#### 🎤 Interview question
**Q: `font-display: swap` vs `optional` — when do you use each?**
A: Use **`swap`** when it's important that visitors actually see your brand font, accepting a possible layout shift when it swaps in late. Use **`optional`** when avoiding **CLS** is the priority: the browser uses the web font only if it's ready almost instantly (usually from cache), and otherwise keeps the fallback for that page load with **no swap**, so there's no font-driven layout shift. `swap` guarantees the font shows; `optional` guarantees no late jump.

### 🚀 Preloading & Self-Hosting — making the font arrive first

#### 🧩 What is it?
**Preloading** tells the browser, very early, "you're going to need this font — start downloading it now," using a `<link rel="preload" as="font" crossorigin>` tag in the page `<head>`. **Self-hosting** means serving the font file from your own domain instead of a third-party like Google Fonts. **`woff2`** is the modern, best-compressed font format.

#### 🤔 Why do we need it? (the problem)
Normally a font is discovered *late* — the browser has to download the HTML, then the CSS, then find the `@font-face`, *then* start the font download. That chain wastes precious round-trips, so even with `font-display: swap` the swap happens late and you get a visible flash or shift. Preloading skips the wait by starting the font download up front.

#### ⚙️ How does it work?
Without vs with preload, on the loading timeline:

```
 WITHOUT preload (font discovered late):
   HTML ──▶ CSS ──▶ parse @font-face ──▶ FONT downloads ──▶ paint
                                         (starts late)

 WITH preload (font fetched in parallel):
   HTML ──▶ CSS ──────────────────────▶ paint
        └──▶ FONT downloads ───────────┘
             (starts immediately)
```

Three rules that matter:
- **`crossorigin` is required** on a font preload — even for your own domain. Fonts are always fetched in *anonymous CORS mode*, so a preload without `crossorigin` fetches a **second** copy instead of matching the real request. Always include it.
- **Self-host when you can.** A third-party host (e.g. `fonts.googleapis.com`) means an extra DNS lookup + TLS handshake to a new domain, which adds latency. Serving from your own origin reuses the existing connection. If you must use a third party, add `<link rel="preconnect">` to warm the connection.
- **Prefer `woff2`.** It's the most compressed font format and is supported by all modern browsers — smaller download, faster paint. Only ship older formats if you must support very old browsers.

#### 🌍 Real-life analogy
Preloading is **calling the kitchen to start your dish the moment you book the table**, instead of ordering only after you've sat down, read the menu, and flagged a waiter. Self-hosting is **cooking in your own kitchen** rather than ordering from a restaurant across town — no travel time (DNS + TLS) to a new place. The `crossorigin` flag is writing the order on the *same form* the kitchen already uses, so they don't start a duplicate dish by mistake.

#### 💻 Code example
```html
<!-- In <head>, BEFORE the stylesheet. crossorigin is mandatory for fonts,
     even same-origin, or the browser downloads the file twice. -->
<link
  rel="preload"
  href="/fonts/inter.woff2"
  as="font"
  type="font/woff2"
  crossorigin
/>
```

```css
/* The matching @font-face. Preload + swap = font shows up early
   AND text is never invisible while waiting. */
@font-face {
  font-family: "Inter";
  src: url("/fonts/inter.woff2") format("woff2");
  font-display: swap;
}
```

#### 🎤 Interview question
**Q: Why must a font preload include `crossorigin`, and why preload fonts at all?**
A: Browsers always fetch fonts in anonymous CORS mode, so a `<link rel="preload" as="font">` **without** `crossorigin` won't match the actual font request — the browser ends up downloading the file twice and wastes the preload. You preload fonts to start the download immediately rather than after the HTML → CSS → `@font-face` discovery chain, so the font arrives early and the swap/flash happens sooner or not at all.

### ✂️ Subsetting & `unicode-range` — shipping only the glyphs you use

#### 🧩 What is it?
A font file contains a **glyph** (a drawn shape) for every character it supports — often thousands, covering many languages, symbols, and accents. **Subsetting** is trimming the file down to only the characters your site actually uses. **`unicode-range`** is a `@font-face` descriptor that tells the browser *which characters* a given font file covers, so it only downloads that file when those characters appear on the page.

#### 🤔 Why do we need it? (the problem)
A full font with every language can be hundreds of kilobytes. If your site is English-only, downloading Cyrillic, Greek, and thousands of CJK glyphs you'll never show is pure waste — slower download, slower paint. Subsetting can cut a font to a fraction of its size.

#### ⚙️ How does it work?
You split the font into per-language files and label each with the Unicode code-point ranges it covers. The browser downloads a file **only if** the page contains a character in that range:

```
  Page text: "Hello"  (all Latin)
        │
        ▼ browser checks each @font-face unicode-range
   ┌───────────────┬───────────────┬───────────────┐
   │ latin.woff2   │ greek.woff2   │ cyrillic.woff2│
   │ U+0000–00FF   │ U+0370–03FF   │ U+0400–04FF   │
   │ ✅ matches    │ ❌ no match   │ ❌ no match   │
   │ → downloaded  │ → skipped     │ → skipped     │
   └───────────────┴───────────────┴───────────────┘
```

This is exactly how Google Fonts ships its CSS — multiple `@font-face` blocks for the same family, each with a different `unicode-range`, so users only pay for the scripts they actually display.

#### 🌍 Real-life analogy
It's a **carry-on packed for one trip** instead of dragging your entire wardrobe everywhere. You're flying somewhere warm, so you pack shorts (Latin glyphs) and leave the snow gear (Cyrillic, CJK) at home. `unicode-range` is the packing list that says "only bring the bag if the trip actually needs it."

#### 💻 Code example
```css
/* Same family, split by script. The browser downloads latin.woff2
   only because the page uses Latin characters; greek.woff2 is fetched
   ONLY if a Greek character (U+0370–03FF) actually appears. */
@font-face {
  font-family: "Inter";
  src: url("/fonts/inter-latin.woff2") format("woff2");
  font-display: swap;
  unicode-range: U+0000-00FF;          /* Basic Latin + Latin-1 */
}

@font-face {
  font-family: "Inter";
  src: url("/fonts/inter-greek.woff2") format("woff2");
  font-display: swap;
  unicode-range: U+0370-03FF;          /* Greek — skipped unless needed */
}
```

#### 🎤 Interview question
**Q: How does subsetting with `unicode-range` reduce font payload?**
A: A full font carries glyphs for many scripts you may never display. Subsetting splits the font into smaller per-script files, and `unicode-range` labels which code points each file covers. The browser then downloads a given file **only when** the page actually contains a character in that range — so an English page never fetches the Cyrillic or CJK subsets, dramatically cutting the bytes shipped.

---

### 🧱 System Stacks, Metric Overrides & Variable Fonts — killing the swap shift

#### 🧩 What is it?
Three related techniques for reducing or removing font cost:
- A **system font stack** uses fonts already installed on the user's device — **zero download**.
- **Metric overrides** (`size-adjust`, `ascent-override`, `descent-override`, `line-gap-override`) are `@font-face` descriptors that **resize and re-space the fallback font** so it occupies the *same* room as the web font — making the swap invisible.
- A **variable font** is a single file that contains a whole range of weights/styles, instead of one file per weight.

#### 🤔 Why do we need it? (the problem)
Even with `swap`, the swap from a fallback to your web font causes **CLS** when the two fonts have different letter widths and line heights — the text reflows and jumps. System stacks dodge the problem entirely (no swap), metric overrides shrink the fallback to match so the swap doesn't move anything, and variable fonts replace 4–6 separate weight files with one, cutting download count and bytes.

#### ⚙️ How does it work?
The metric-override trick: you define a *second* `@font-face` that points at a **local** system font but tweaks its metrics to match your web font's footprint, then use it as the fallback. When the real font swaps in, the box was already the right size — no shift.

```
  Without size-adjust:        With size-adjust on fallback:
  ┌─────────────────┐         ┌─────────────────┐
  │ Fallback (wide) │         │ Fallback resized│
  │  takes 3 lines  │         │  takes 2 lines  │
  └─────────────────┘         └─────────────────┘
          │ swap                       │ swap
          ▼ JUMPS up a line            ▼ no movement
  ┌─────────────────┐         ┌─────────────────┐
  │ Web font:2 lines│         │ Web font:2 lines│
  └─────────────────┘         └─────────────────┘
       CLS! ❌                     no CLS ✅
```

- **`size-adjust`** scales the fallback glyphs up/down (a percentage) so their overall width/height matches the web font — the main lever for cutting swap shift.
- **`ascent-override` / `descent-override` / `line-gap-override`** fine-tune the vertical metrics (how tall above/below the baseline, and line spacing) so line heights line up too.
- A **variable font**: instead of `inter-400.woff2`, `inter-700.woff2`, etc., you ship one `inter.woff2` and pick any weight with `font-weight` in CSS — fewer requests, usually fewer total bytes when you use several weights.

> **Simplification flag:** the exact `size-adjust` percentage that makes a fallback match a given web font is computed per font-pair (tools like Next.js's font system or "Fontaine" generate it for you) — there's no single universal number.

#### 🌍 Real-life analogy
A system font stack is **using the furniture already in the room** — nothing to deliver. Metric overrides are like **putting a placeholder box of the exact same size** where the real appliance will go: when the real one arrives, it drops straight into the gap and nothing else has to move. A variable font is a **single dimmer switch** that covers every brightness, instead of carrying a separate bulb for each level.

#### 💻 Code example
```css
/* 1. A zero-download system stack — no web font at all. */
.native {
  font-family: system-ui, -apple-system, "Segoe UI", Roboto, sans-serif;
}

/* 2. A metric-tuned fallback so the swap to the web font won't shift. */
@font-face {
  font-family: "Inter Fallback";
  src: local("Arial");        /* reuse an installed font */
  size-adjust: 107%;          /* scale Arial to match Inter's width */
  ascent-override: 90%;       /* align vertical metrics */
  descent-override: 22%;
  line-gap-override: 0%;
}

/* 3. One variable font file covers every weight 100–900. */
@font-face {
  font-family: "Inter";
  src: url("/fonts/inter-variable.woff2") format("woff2");
  font-weight: 100 900;       /* the full range, one file */
  font-display: swap;
}

body {
  /* Web font first, metric-matched fallback second → minimal CLS. */
  font-family: "Inter", "Inter Fallback", sans-serif;
}
```

#### 🎤 Interview question
**Q: How do you eliminate font-driven CLS?**
A: Best case, avoid the swap entirely with a **system font stack** (no download, no swap) or `font-display: optional` (no late swap). If you do swap in a web font, **reserve the same space** by giving the fallback a metric-matched `@font-face`: use `size-adjust` to match the web font's width/height and `ascent-override`/`descent-override`/`line-gap-override` to match its vertical spacing, so when the web font replaces the fallback the layout box is already correct and nothing moves. Preloading the font also shrinks the window in which a shift could happen.

<h2 id="module-8">Module 8 — Rendering & Delivery Strategies</h2>

You have a page of HTML to show a user. *Where* and *when* you build that HTML — in the browser, on the server at request time, or ahead of time during a build — changes everything about how fast the page feels. This module is the decision: pick the wrong strategy and even perfectly optimized assets land late or sit there looking ready but frozen. Pick the right one and the page feels instant.

---

### 🎬 CSR vs SSR vs SSG vs ISR — Where the HTML Gets Built

#### 🧩 What is it?
Four ways to produce the HTML a user sees:
- **CSR (Client-Side Rendering):** the server sends a near-empty HTML shell plus JavaScript; the **browser** builds the page.
- **SSR (Server-Side Rendering):** the server builds the full HTML **on each request** and sends it ready-to-paint.
- **SSG (Static Site Generation):** the full HTML is built **once at build time** and served as a plain file.
- **ISR (Incremental Static Regeneration):** SSG that **rebuilds individual pages** in the background on a schedule or on demand, so static pages can stay fresh.

#### 🤔 Why do we need it? (the problem)
A single strategy can't win everywhere. A blog post is the same for everyone, so rebuilding it on every request is wasted work — but a logged-in dashboard is different for every user, so you *can't* prebuild it. The choice trades off three things you care about:
- **TTFB** (Time To First Byte) — how fast the server starts replying.
- **FCP** (First Contentful Paint) — when the user first sees real content.
- **TTI** (Time To Interactive) — when clicks and typing actually work.

#### ⚙️ How does it work?
Each strategy moves the "build the HTML" work to a different time and place. The timeline below shows when content becomes **visible** (V) and when it becomes **interactive** (I):

```
 Time ──────────────────────────────────▶

 CSR  [TTFB fast] blank... JS loads/runs  V&I
      shell arrives early, but nothing
      to SEE until JS builds the page

 SSR  [TTFB slower] ──── V (paint) ── I
      server builds HTML first, so you
      SEE it sooner; still wait to hydrate

 SSG  [TTFB fastest] V (paint) ──── I
      prebuilt file, instant byte+paint;
      still needs JS to become interactive

 ISR  = SSG speed, but page is rebuilt in
        the background to fight staleness

 V = visible   I = interactive
```

Key trade-offs, stated precisely:
- **CSR:** fast TTFB (tiny shell), but **slow first paint** and a heavy JS download/parse/execute before anything appears. Great for app-like screens behind a login.
- **SSR:** **faster FCP/LCP** because real content is in the HTML, but **slower TTFB** (the server does work per request) and it still needs **hydration** (next topic) before it's interactive.
- **SSG:** **fastest** TTFB and FCP — it's just a file, often served from a CDN — but the content is **frozen at build time** and goes stale until the next rebuild.
- **ISR:** keeps SSG's speed while **regenerating** stale pages periodically or on demand, so you don't rebuild the whole site for one changed page.

> **Note (simplification):** "fastest/slowest" is the typical case. A cached SSR response or a slow CDN can flip these — always measure your own app rather than trusting the ranking blindly.

#### 🌍 Real-life analogy
Think of a coffee shop:
- **CSR** = you get an empty cup and a kit, and **you** make the coffee at your table.
- **SSR** = the barista makes a **fresh** cup **when you order** — best taste, but you wait in line.
- **SSG** = a wall of **pre-made** cups — grab one instantly, but it was brewed this morning.
- **ISR** = those pre-made cups, but staff quietly **swap in fresh ones** every hour.

#### 💻 Code example
A tiny pseudo-flow contrasting what arrives over the wire:

```html
<!-- CSR: server sends an empty shell; browser fills it in -->
<div id="root"></div>
<script src="/app.js"></script>
<!-- User sees a blank page until app.js downloads, parses, runs. -->

<!-- SSR / SSG: real content is already in the HTML -->
<div id="root">
  <h1>Today's Top Story</h1>
  <p>Full article text, painted immediately...</p>
</div>
<script src="/app.js"></script>
<!-- User SEES content right away; app.js then makes it interactive. -->
```

#### 🎤 Interview question
**Q: CSR vs SSR vs SSG vs ISR — pick one for a product and justify it.**
A: Match the strategy to the content. A **marketing/blog page** that's identical for everyone → **SSG** (or **ISR** if it updates regularly) for the fastest TTFB/FCP from a CDN. A **personalized, frequently-changing dashboard** → **SSR** (real content fast, fresh per request) or **CSR** (if it's app-like and SEO doesn't matter). The trade-off is freshness and per-request cost (SSR) versus staleness (SSG) versus a slow first paint and heavy JS (CSR).

---

### 💧 Hydration — Why a "Fast" Page Can Still Be Frozen

#### 🧩 What is it?
**Hydration** is the step where the JavaScript runs on the client and "wakes up" server-rendered HTML — attaching event handlers and rebuilding the framework's in-memory view so buttons, forms, and menus actually respond. The HTML arrives looking finished; hydration is what makes it *work*.

#### 🤔 Why do we need it? (the problem)
SSR and SSG send you HTML that **looks** ready, but it's a photograph — clicking does nothing yet. To become interactive, the same component tree has to be re-rendered in the browser so the framework can match its handlers to the existing DOM. Until that finishes, the page is in the **"uncanny valley": visibly complete but unresponsive.** Worse, hydration runs JS on the main thread, and if it's a long task, an early click can be **delayed or ignored — directly hurting INP** (Interaction to Next Paint, the responsiveness metric).

#### ⚙️ How does it work?
```
 SSR/SSG page lifecycle on the client:

   HTML arrives ──▶ user SEES content  (looks ready!)
        │
        ▼
   JS downloads ──▶ parse ──▶ HYDRATE
        │                       │ re-run components,
        │                       │ attach listeners
        ▼                       ▼
   ❄ FROZEN window ........ ✅ INTERACTIVE
   (clicks queue or drop → bad INP)
```
The "uncanny valley" is that frozen window between visible and interactive. Bigger pages and more components = more hydration work = a longer freeze.

#### 🌍 Real-life analogy
It's a **movie set storefront**. From the street it looks like a real shop — shelves, signage, a door. But walk up and the door won't open: it's a façade until the crew "wires it up." The HTML is the façade; hydration is the crew connecting the door, lights, and till so customers can actually buy something.

#### 💻 Code example
Same component, two phases. The server output is static text; only after hydration does the handler fire:

```jsx
function LikeButton({ count }) {
  // On the SERVER this renders to plain HTML:
  //   <button>♥ 12</button>   ← visible, but onClick does NOTHING yet
  const [likes, setLikes] = React.useState(count);

  // After HYDRATION runs on the client, this handler is attached
  // and clicks finally work:
  return <button onClick={() => setLikes(likes + 1)}>♥ {likes}</button>;
}
// Gap between "button is visible" and "button is clickable"
// = the hydration cost. Big trees widen that gap and hurt INP.
```

#### 🎤 Interview question
**Q: What is hydration and why can it hurt INP?**
A: Hydration is the client-side JS pass that attaches event handlers to server-rendered HTML and rebuilds the framework's view, turning a static page into an interactive one. It can hurt **INP** because it runs as work on the main thread: while hydration is executing, the page looks ready but can't respond, so an early interaction is queued or dropped and its "next paint" arrives late. The fix is to **ship less hydration work** — stream it, split it, or hydrate only the interactive parts (streaming SSR, islands, and RSC, below).

---

### 🌊 Streaming SSR — Send the Page in Pieces

#### 🧩 What is it?
**Streaming SSR** sends the HTML to the browser **in chunks as it's ready**, instead of waiting for the entire page to finish building on the server. Fast parts (the header, the article) flush early; slow parts (a personalized sidebar that needs a database call) arrive a moment later. Frameworks mark the slow parts with **Suspense boundaries** — a fenced-off region that can show a placeholder while its data loads.

#### 🤔 Why do we need it? (the problem)
Plain SSR is **all-or-nothing**: if one slow query holds up the page, the user stares at a blank screen until *everything* is ready, inflating TTFB and FCP. That's unfair — most of the page was ready instantly. Streaming lets the browser **paint the fast content first** and fill in the slow regions as they arrive.

#### ⚙️ How does it work?
```
 Without streaming (blocking SSR):

   request ──[wait for the SLOWEST part]── whole page ▶ paint
             (one slow query stalls everything)

 With streaming SSR:

   request ─▶ header + article  ▶ paint NOW
              │
              │  slow sidebar still loading...
              ▼
            shows a placeholder (Suspense fallback)
              │
              ▼
            sidebar HTML streams in ▶ swaps into place
```
A **Suspense boundary** wraps a slow region: the server streams a fallback (e.g. a skeleton) immediately, then streams the real HTML for that region when its data resolves, and the browser slots it in. This improves FCP/LCP because the user sees meaningful content without waiting on the slowest dependency.

#### 🌍 Real-life analogy
A **restaurant that serves courses as they're ready** instead of holding your whole table's food until the slowest dish is done. Bread and salad come out immediately; the steak that takes longer arrives when it's ready — you're never left staring at an empty table.

#### 💻 Code example
Conceptually, wrap the slow region so the rest can paint first:

```jsx
function Page() {
  return (
    <main>
      <Header />          {/* fast — streams + paints immediately */}
      <Article />         {/* fast — streams immediately */}

      {/* Slow region: a fallback streams now, real content later */}
      <Suspense fallback={<SidebarSkeleton />}>
        <PersonalizedSidebar />   {/* waits on a DB call */}
      </Suspense>
    </main>
  );
}
// Result: user sees Header + Article right away (good FCP),
// while the sidebar shows a skeleton until its HTML streams in.
```

#### 🎤 Interview question
**Q: How does streaming SSR improve perceived performance over blocking SSR?**
A: Blocking SSR waits for the entire page before sending any bytes, so one slow data dependency delays the whole first paint. Streaming SSR flushes ready HTML in chunks and uses **Suspense boundaries** to show a placeholder for slow regions, so the fast content paints immediately (better FCP/LCP) and slow regions fill in as their data resolves — the page feels faster even though total work is the same.

---

### 🏝️ Islands & React Server Components — Ship Less JavaScript

#### 🧩 What is it?
Two related ideas for cutting the JavaScript a page ships:
- **Islands architecture:** treat the page as mostly **static HTML** with small, independent **"islands"** of interactivity (a search box, a carousel). Only the islands get hydrated; the static sea between them ships **no JS at all**. **Partial hydration** = hydrate only some components; **progressive hydration** = hydrate them gradually (e.g. as they scroll into view), not all at once up front.
- **React Server Components (RSC):** components that render **only on the server** and never ship their JavaScript to the browser. They produce a description of UI that the client renders; only the genuinely interactive client components ship JS and hydrate.

#### 🤔 Why do we need it? (the problem)
With traditional SSR, even a page that's 95% static text hydrates the **whole tree** — you pay to download and run JS for components that never do anything interactive. That's wasted bytes, wasted parse/compile, and a longer hydration freeze (bad INP). Islands and RSC attack the root cause: **don't ship JS for the non-interactive parts.**

#### ⚙️ How does it work?
```
 Traditional SSR — hydrate EVERYTHING:

   ┌───────────────────────────────┐
   │ header  article  footer  nav  │  all hydrated
   │ ▓▓▓▓▓▓  ▓▓▓▓▓▓▓  ▓▓▓▓▓▓  ▓▓▓  │  = lots of JS
   └───────────────────────────────┘

 Islands / RSC — hydrate only what's interactive:

   ┌───────────────────────────────┐
   │ header  article  footer [Srch]│
   │ static  static   static  ▓▓▓▓ │  only the search
   └───────────────────────────────┘  box ships + hydrates
   ▓ = ships JS + hydrates   plain = no JS
```
Islands hydrate each interactive piece independently (and can defer it). RSC goes further: server-only components emit no client JS at all, so the bundle shrinks to just the interactive **client components**.

> **Note (simplification):** islands and RSC are different mechanisms (one is a hydration strategy, the other moves rendering to the server), but they share the same goal — **less client JS, less hydration, better INP.**

#### 🌍 Real-life analogy
A **printed newspaper with a few interactive ad inserts**. The articles are just paper — nothing to power. Only the handful of pop-up or scratch-off inserts need any "wiring." You'd never run electricity to the whole paper just because three ads light up.

#### 💻 Code example
An island is loaded lazily so its JS doesn't block the static page — a concrete dynamic import:

```jsx
// The static page ships almost no JS. The interactive search
// "island" is code-split and hydrated on its own.
import dynamic from 'next/dynamic';

// Only this component's JS downloads — and only when needed:
const SearchBox = dynamic(() => import('./SearchBox'), {
  loading: () => <div className="h-10" />, // reserve space, avoid CLS
});

export default function Page() {
  return (
    <article>
      <h1>Static headline (no JS)</h1>
      <p>Static body text (no JS)...</p>
      <SearchBox />   {/* the only hydrated island */}
    </article>
  );
}
```
> **Note (simplification):** `next/dynamic` here is *code-splitting* — `SearchBox`'s JS loads on demand. True "**zero** JS for the static parts" comes from an islands framework (Astro) or **React Server Components**, where the static markup is server-only and never hydrates. `next/dynamic` defers a chunk; RSC/islands remove the chunk entirely.

#### 🎤 Interview question
**Q: What problem do islands / React Server Components solve?**
A: They cut the amount of JavaScript shipped and hydrated. Traditional SSR hydrates the entire component tree even though most of a typical page is static, wasting download, parse/compile, and main-thread time (hurting INP). **Islands** hydrate only the small interactive regions (and can do so progressively); **RSC** render some components only on the server so their JS never reaches the client. Both ship less client JS, shrinking the hydration cost and improving responsiveness.

<h2 id="module-9">Module 9 — Runtime & Interaction Performance</h2>

A page can finish loading with a perfect LCP and still feel *broken* — you tap a button and nothing happens for half a second. That lag has one root cause: the browser's main thread was too busy to react. This module is about keeping that thread free so every tap, type, and click feels instant.

---

### 🐢 Long Tasks — The Half-Second Freeze

#### 🧩 What is it?
A **long task** is any single piece of work on the **main thread** — the one thread that runs your JavaScript *and* paints the page — that takes longer than **50 milliseconds** to finish. Below 50ms is fine; cross that line and it officially counts as "long".

#### 🤔 Why do we need it? (the problem)
The main thread can only do **one thing at a time**. While it's chewing through a long task, it *cannot* respond to a click, run an animation frame, or process a keystroke — they all wait in line until the task ends. So a 300ms task means up to 300ms of frozen, unresponsive UI. Long tasks are the number-one cause of bad **INP** (Interaction to Next Paint).

#### ⚙️ How does it work?
The browser processes work as a queue of tasks. Input events (a click) get queued too — but they can only run **between** tasks, never in the middle of one.

```
 main thread timeline (one lane only)
 ──[ long task: 300ms ]──────► [click handler]──►
        ▲                            ▲
   user clicks HERE          but it runs HERE
   (input is queued)         300ms later = lag
```

Why 50ms? The browser tries to paint every ~16ms (60 frames/sec). A budget of 50ms leaves a little room before users *perceive* a stall. You find long tasks in **Chrome DevTools → Performance**: record an interaction and look for tasks marked with a red triangle, or the gray "long task" bars.

#### 🌍 Real-life analogy
The main thread is a **single cashier** at a shop. If one customer's order takes five minutes (a long task), *every* person behind them waits — even the one who just wants to ask a quick question (a click). The line is frozen until the big order is done.

#### 💻 Code example
```javascript
// A single long task — this loop blocks everything for its whole duration.
function blockingWork() {
  const start = performance.now();
  let total = 0;
  for (let i = 0; i < 50_000_000; i++) {
    total += i;
  }
  // On a typical laptop this loop takes ~100–300ms of UNINTERRUPTED
  // main-thread time. During it, clicks and animations are FROZEN.
  console.log('done in', performance.now() - start, 'ms');
}
// You can also observe them at runtime:
new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    console.log('Long task:', entry.duration, 'ms'); // duration is always > 50
  }
}).observe({ type: 'longtask', buffered: true });
```

#### 🎤 Interview question
**Q: What is a "long task" and why does it hurt responsiveness?**
A: It's any main-thread task longer than **50ms**. Because the main thread runs JavaScript and handles input on the same single lane, a long task blocks the browser from responding to clicks, typing, and rendering until it finishes — directly worsening **INP**. The fix is to break the work into smaller chunks and yield control back between them.

---

### ⚡ INP Optimization In Depth — Make the Click Feel Instant

#### 🧩 What is it?
**INP (Interaction to Next Paint)** measures how long it takes, in the worst interactions of a visit, from a user action (click, tap, key press) until the browser **paints the next frame** showing a response. A good INP is **200ms or less**; over 500ms is poor.

#### 🤔 Why do we need it? (the problem)
LCP and CLS describe *loading*. INP describes whether the page actually **responds** once loaded. A site can load fast yet feel sluggish on every interaction — INP is the Core Web Vital that catches exactly that.

#### ⚙️ How does it work?
Every interaction's latency is the sum of **three phases**:

```
 user clicks ──────────────────────────────► next paint
   │                │                   │           │
   │  INPUT DELAY   │   PROCESSING      │ PRESENTATION
   │ (main thread   │ (your event       │ (style, layout,
   │  was busy)     │  handlers run)    │  paint the frame)
   └────────────────┴───────────────────┴───────────┘
        INP = input delay + processing + presentation
```

Three levers, one per phase:
- **Input delay** — caused by the main thread being busy with a long task when the click arrives. Fix: break up long tasks (previous topic) so the thread is free.
- **Processing** — your event handler doing too much synchronous work. Fix: do *only* the urgent visual update now (e.g. show a spinner), and **defer non-urgent work** (analytics, heavy computation) to *after* the paint.
- **Presentation** — a costly style/layout/paint. The big trap here is **forced reflow** (covered in Module 3): if your handler *writes* to the DOM and then *reads* a layout value like `offsetHeight`, the browser must recompute layout synchronously, mid-handler. Batch reads before writes to avoid it.

#### 🌍 Real-life analogy
Imagine a waiter taking your order. **Input delay** is how long before they even reach your table (they were stuck elsewhere). **Processing** is them writing the whole order, the wine pairing notes, and tomorrow's specials before walking away. **Presentation** is the kitchen plating it. To feel fast, a good waiter acknowledges you *immediately*, jots the essentials, and saves the paperwork for later.

#### 💻 Code example
```javascript
button.addEventListener('click', () => {
  // ✅ URGENT: the visible response — do it now, before paint.
  spinner.hidden = false;

  // ❌ Avoid forced reflow: don't write then immediately read layout.
  //    box.style.width = '200px';
  //    const h = box.offsetHeight; // forces synchronous layout mid-handler!

  // ✅ NON-URGENT: defer heavy work until AFTER the browser paints,
  //    so the spinner appears immediately instead of after the work.
  setTimeout(() => {
    sendAnalytics();
    recomputeExpensiveStuff();
  }, 0);
});
```

#### 🎤 Interview question
**Q: A button feels laggy on click — how do you fix it?**
A: Profile the interaction in DevTools and find which of INP's three phases is slow: **input delay**, **processing**, or **presentation**. Common fixes: break up long tasks so the thread is free when the click lands (input delay); inside the handler do only the urgent visual update and **defer** non-urgent work to after paint (processing); and avoid **forced reflow** by not reading layout right after writing to the DOM (presentation).

---

### 🧵 Scheduling — Yielding the Main Thread on Purpose

#### 🧩 What is it?
**Scheduling primitives** are browser APIs that let you voluntarily *give up* the main thread so the browser can handle pending input, then continue your work. The newest is **`scheduler.yield()`**; alongside it sit `scheduler.postTask()`, `isInputPending()`, and `requestIdleCallback()`.

#### 🤔 Why do we need it? (the problem)
Breaking a long task into chunks only helps if you actually **hand the thread back between chunks** — otherwise the browser never gets a turn to process that queued click. Scheduling APIs are how you yield cleanly and control *which* work runs first.

#### ⚙️ How does it work?
- **`scheduler.yield()`** — returns a **Promise**; you `await` it. This pauses your function, lets the browser process pending input and rendering, then **resumes** your function where it left off. Crucially, your continuation is prioritized to come back *soon* after the yield.
- **`scheduler.postTask(fn, { priority })`** — queues a task with an explicit priority: `'user-blocking'` (highest), `'user-visible'` (default), or `'background'` (lowest). The browser runs higher-priority tasks first.
- **`navigator.scheduling.isInputPending()`** — returns `true` if a user input is waiting. You can poll it inside a loop to decide *when* it's worth yielding.
- **`requestIdleCallback(fn)`** — runs `fn` only during **idle** moments when the main thread has spare time. Great for truly low-priority work (e.g. prefetching), but it may be delayed a long time on a busy page.

```
 without yielding:  [████ one 300ms task ████]  click waits ✗
 with yielding:     [██]→click→[██]→click→[██]   input handled ✓
                      ▲ await scheduler.yield() between chunks
```

> **Simplification flag:** `scheduler.yield()` and `scheduler.postTask()` are newer APIs with growing but not universal browser support. In production, feature-detect them and fall back to a `setTimeout(…, 0)`-based yield where they're missing.

#### 🌍 Real-life analogy
You're washing a huge stack of dishes (a long task). `scheduler.yield()` is **pausing to answer the doorbell** the moment it rings, then going straight back to the sink. `isInputPending()` is **glancing at the door to check if anyone's there** before you bother pausing. `requestIdleCallback()` is "I'll polish the silverware *only* once everything else is done."

#### 💻 Code example
```javascript
// Chunk a long task and YIELD to the main thread between chunks,
// so queued clicks/keystrokes get handled instead of being frozen.
async function processAll(items) {
  const CHUNK = 100;
  for (let i = 0; i < items.length; i++) {
    doExpensiveWork(items[i]);          // one unit of heavy work

    if ((i + 1) % CHUNK === 0) {  // after EACH group of 100 (not on i=0)
      // Hand the thread back: browser processes input + paints,
      // THEN our function resumes right here. Feature-detect first.
      if ('scheduler' in window && 'yield' in scheduler) {
        await scheduler.yield();
      } else {
        // Fallback yield: a 0ms timeout also lets the browser run
        // pending tasks before our continuation is queued.
        await new Promise((resolve) => setTimeout(resolve, 0));
      }
    }
  }
  // Result: same total work, but split into many SHORT tasks (< 50ms each),
  // so the UI stays responsive the whole time.
}
```

#### 🎤 Interview question
**Q: How do you keep a long task from blocking input?**
A: Split the work into small chunks and **yield** between them with `await scheduler.yield()` (or a `setTimeout(…, 0)` fallback). Yielding returns a Promise that, when awaited, lets the browser process any pending input and render a frame before resuming your work — so each chunk stays under 50ms and clicks are handled promptly. Use `scheduler.postTask()` priorities to order work, and `isInputPending()` to yield only when input is actually waiting.

### 🪟 List Virtualization & DOM Size — Render Only What's Visible

#### 🧩 What is it?
**Virtualization** (also called **windowing**) means rendering only the rows of a long list that are *currently on screen*, instead of all of them. As the user scrolls, you swap the rendered rows for the new visible ones. **Pagination** is the simpler cousin: show one page of N items at a time.

#### 🤔 Why do we need it? (the problem)
Rendering 10,000 list items creates 10,000+ DOM nodes. A **large DOM** is expensive: every style recalculation and layout pass must walk the whole tree, memory balloons, and the initial render is slow. The browser does all that work even though the user can only *see* a dozen rows.

#### ⚙️ How does it work?
You measure the scroll container, calculate which rows fall inside the visible "window", and render only those — plus a small buffer above and below. The rows above and below are replaced by **spacer** elements (or padding) so the scrollbar still reflects the full list height.

```
 full list = 10,000 rows        virtualized
 ┌───────────┐                  ┌───────────┐
 │ row 1     │                  │  (spacer) │ ← empty, sized
 │ row 2     │   only ~12       ├───────────┤
 │   ...     │   rows exist  →  │ row 41    │ ← visible window
 │ row 10000 │   in the DOM     │ row 42 …  │   (real nodes)
 └───────────┘                  ├───────────┤
   slow, huge DOM               │  (spacer) │ ← empty, sized
                                └───────────┘
```

The win: the DOM holds ~12 nodes instead of 10,000, so style and layout are cheap and scrolling stays smooth. Libraries like `react-window` or `@tanstack/react-virtual` do this for you.

#### 🌍 Real-life analogy
A virtual list is a **train window**. The whole landscape (all 10,000 rows) exists, but you only ever *see* the slice framed by the window. As the train moves, new scenery slides into view and old scenery slides out — you never need the entire country painted onto the glass at once.

#### 💻 Code example
```javascript
// Minimal windowing: render only rows inside the visible area.
const ROW_H = 40;             // each row is 40px tall
const allRows = data;         // e.g. 10,000 items
const viewport = document.getElementById('viewport'); // a scrollable box

function render() {
  const scrollTop = viewport.scrollTop;
  const visibleCount = Math.ceil(viewport.clientHeight / ROW_H);
  const start = Math.floor(scrollTop / ROW_H);
  const end = start + visibleCount + 5;   // +5 buffer rows

  // Spacer pushes visible rows to the right offset; full height preserved.
  const top = start * ROW_H;
  const bottomPad = (allRows.length - end) * ROW_H;

  list.style.paddingTop = top + 'px';
  list.style.paddingBottom = Math.max(bottomPad, 0) + 'px';
  list.replaceChildren(
    ...allRows.slice(start, end).map(makeRowElement)
  );
  // Only ~visibleCount+5 real nodes exist, no matter how big allRows is.
}
viewport.addEventListener('scroll', render);
```

#### 🎤 Interview question
**Q: Why virtualize a long list?**
A: Because rendering every item builds a huge DOM, and a large DOM makes every style recalc and layout pass slow, inflates memory, and drags out the initial render. Virtualization renders **only the visible rows** (plus a small buffer) and uses spacers to preserve scroll height, so the node count stays tiny and constant regardless of list size — keeping interaction and scrolling smooth. Pagination achieves a similar effect by only loading one page at a time.

<h2 id="module-10">Module 10 — Field Measurement (RUM)</h2>

Your lab tests say the site is fast. Then a real user on a three-year-old phone, on a train, with a flaky connection, has a miserable time — and you never saw it, because your test machine was a fast laptop on office Wi-Fi. **Field measurement** (also called **RUM** — Real User Monitoring) closes that gap: it records how the site actually performed for *real people, on their real devices and networks*, and ships those numbers back to you. This module shows how to collect Core Web Vitals from real sessions, learn *which* element caused a bad score, read the raw browser performance timeline, and send it all home reliably.

---

### 📡 Field Data vs Lab Data — Why Your Test Lies to You

#### 🧩 What is it?
**Lab data** is a performance measurement you take in a controlled environment — your machine, or a tool like Lighthouse — under fixed, simulated conditions. **Field data** (RUM — Real User Monitoring) is performance measured *on the devices of the people actually using your site*, then reported back to you. RUM is the source of truth because it reflects reality, not a simulation.

#### 🤔 Why do we need it? (the problem)
Lab numbers are repeatable, but they describe *one* fake user. Real users are wildly varied: old phones, cheap CPUs, slow networks, browser extensions, far-away locations, different ways of interacting with the page. A metric like **INP** (Interaction to Next Paint — how fast the page responds to taps and clicks) literally *cannot* be measured in a quick lab run, because it depends on a human actually interacting. If you only trust the lab, you optimize for a user who does not exist.

#### ⚙️ How does it work?
Two complementary tools, two different jobs:

```
   LAB (synthetic)              FIELD / RUM (real users)
   ┌──────────────────┐         ┌──────────────────────┐
   │ 1 fake user      │         │ thousands of real    │
   │ fixed device     │         │ users, all devices   │
   │ fixed network    │         │ all networks         │
   │ repeatable       │         │ messy but TRUE       │
   │ great for DEBUG  │         │ great for TRUTH      │
   └──────────────────┘         └──────────────────────┘
        diagnose                      decide / monitor
```

Use the lab to *debug and reproduce* (change one thing, re-measure). Use the field to *decide what to fix* and to *know if real users improved*. They often disagree — and when they do, the field wins, because it is what your users felt.

#### 🌍 Real-life analogy
A car maker's wind tunnel is the lab: clean, controlled, perfect for tweaking one part. But the real road test — actual drivers, potholes, rain, traffic — is the field. A car that's flawless in the wind tunnel can still rattle on a real highway. You ship based on the road test, not the tunnel.

#### 💻 Code example
```javascript
// Conceptual: the same metric, two sources.
// LAB → you run a tool against the page (no user needed).
//   lighthouse https://example.com  → simulated LCP, etc.

// FIELD → code that ships WITH your page and runs in
//   every real user's browser, then reports home:
import { onLCP } from 'web-vitals';
onLCP((metric) => {
  // `metric.value` is THIS real user's LCP, in milliseconds.
  // We collect many of these and look at the p75 (see below).
  console.log('Real-user LCP:', metric.value);
});
```

#### 🎤 Interview question
**Q: Field vs lab data — why do they differ, and which do you trust?**
A: Lab is one simulated user under fixed conditions — great for debugging and reproducing a fix. Field (RUM) is many real users on real devices and networks — messy but true. They differ because real users have slower CPUs, worse networks, and actually *interact* (so INP only exists in the field). For deciding what to fix and confirming real impact, trust the field; use the lab to diagnose.

### 📈 The `web-vitals` Library — CWV From Real Sessions

#### 🧩 What is it?
**`web-vitals`** is a tiny official JavaScript library from the Google Chrome team. You add it to your page, and it gives you simple callbacks — `onLCP`, `onCLS`, `onINP` — that fire with the *correct, final* Core Web Vital values for the current real-user session.

#### 🤔 Why do we need it? (the problem)
Measuring the vitals *correctly* by hand is surprisingly hard. **LCP** (Largest Contentful Paint) can change as bigger elements paint, so the "real" LCP is only known later. **CLS** (Cumulative Layout Shift — how much content visibly jumps) accumulates over the *whole* visit. **INP** is the worst interaction across the *whole* visit. Each has tricky edge cases (when to stop measuring, what counts, how to handle back-forward cache). `web-vitals` encodes all of that the same way Chrome and Google Search do, so your numbers match theirs.

#### ⚙️ How does it work?
The key idea: each callback fires **once, when that metric is final** — not continuously. The library watches the page and waits for the right moment to report.

```
   page loads ──► interactions happen ──► page hidden / unload
       │                  │                       │
   onLCP fires       (CLS & INP keep            onCLS fires
   when largest       accumulating as           onINP fires
   paint is known     things shift / are        (final values,
                      tapped)                    reported here)
```

- `onLCP` reports the largest paint once it's settled (e.g. when you first interact or the page is hidden).
- `onCLS` and `onINP` report their *final* totals when the page is being hidden or unloaded — because only then do we know the full story of shifts and the slowest interaction.

> **Flagging a simplification:** "fires once when final" is the mental model. Precisely, you can pass `{ reportAllChanges: true }` to get interim updates, but the default — and what you want for real reporting — is the single final value, emitted on `visibilitychange`/unload.

#### 🌍 Real-life analogy
It's like a referee scoring a whole gymnastics routine. They don't shout a score after each flip — they watch the *entire* routine and announce one final score at the end, because an early stumble or a late one both change the total. `onCLS`/`onINP` are that final, end-of-routine score.

#### 💻 Code example
```javascript
import { onLCP, onCLS, onINP } from 'web-vitals';

// Each callback runs ONCE with the final value for this visit.
function logMetric(metric) {
  // metric = { name, value, rating, id, ... }
  // name:   'LCP' | 'CLS' | 'INP'
  // value:  the number (LCP/INP in ms; CLS is a unitless score)
  // rating: 'good' | 'needs-improvement' | 'poor'
  console.log(metric.name, metric.value, metric.rating);
}

onLCP(logMetric);   // e.g. LCP 2310  'good'   (when paint settles)
onCLS(logMetric);   // e.g. CLS 0.04  'good'   (on page hide)
onINP(logMetric);   // e.g. INP 180   'good'   (on page hide)
```

#### 🎤 Interview question
**Q: How do you measure Core Web Vitals for real users?**
A: Add the official `web-vitals` library and subscribe to `onLCP`, `onCLS`, and `onINP`. Each callback fires once with the *final* value for that session — LCP once the largest paint settles, and CLS/INP when the page is hidden or unloaded (because they accumulate over the whole visit). You then send those values to your analytics endpoint and look at the p75 across users.

### 🔍 Attribution — *Which* Element or Script Is to Blame

#### 🧩 What is it?
A plain vital tells you the *score* ("LCP was 4.2s") but not *why*. **Attribution** adds the diagnostic detail: which DOM element was the LCP element, which layout shift was largest and what moved, which interaction was slowest and what it was waiting on. You get it by importing from the library's **attribution build**: `web-vitals/attribution`.

#### 🤔 Why do we need it? (the problem)
A bare number is not actionable. If real users have a poor LCP, you still have to find the culprit — and you can't open DevTools on someone else's phone. Attribution ships the "blame" alongside the score, so your dashboard can say "LCP element was the hero `<img src="/banner.jpg">`, and most of the time went to TTFB" instead of just "LCP is bad."

#### ⚙️ How does it work?
You import the metric functions from `web-vitals/attribution`. The `metric` object now carries an extra `attribution` field with details specific to each vital:

```
   metric.value      ──►  the SCORE (e.g. LCP = 4200ms)
   metric.attribution──►  the BLAME:
        LCP  → which element, + time breakdown
               (TTFB, load delay, load time, render delay)
        CLS  → the largest shift's source element(s)
        INP  → which interaction (interactionType: 'pointer' or 'keyboard'),
               + which phase was slow (input / processing /
               presentation)
```

This is what turns "we have a problem" into "fix *this* image / *this* handler."

#### 🌍 Real-life analogy
A fire alarm that only beeps tells you there's a fire *somewhere* — useless when you're trying to put it out. Attribution is the modern panel that says "smoke detected in **Kitchen, Zone 3**." Same alert, but now you know exactly where to run.

#### 💻 Code example
```javascript
import { onLCP, onINP } from 'web-vitals/attribution';

onLCP((metric) => {
  const a = metric.attribution;
  console.log('LCP element:', a.target);    // a selector string, e.g. 'img.hero'
  console.log('LCP url:', a.url);           // the resource URL
  console.log('TTFB part:', a.timeToFirstByte);
  console.log('Render delay:', a.elementRenderDelay);
});

onINP((metric) => {
  const a = metric.attribution;
  console.log('Slowest interaction:', a.interactionType); // 'pointer'
  console.log('On element:', a.interactionTarget);        // selector
  // a.inputDelay / a.processingDuration / a.presentationDelay
  // tell you WHICH phase of the interaction was slow.
});
```

#### 🎤 Interview question
**Q: What does `web-vitals` attribution give you that the plain metric doesn't?**
A: The *cause*, not just the score. By importing from `web-vitals/attribution`, each metric gains an `attribution` object: for LCP, the LCP element and a time breakdown (TTFB, load delay, load time, render delay); for CLS, the elements responsible for the largest shift; for INP, the interaction type, target element, and which phase (input delay, processing, or presentation) was slowest. That turns a vague "it's slow" into a precise, fixable target.

### 🛰️ The Performance APIs via `PerformanceObserver`

#### 🧩 What is it?
The browser keeps a detailed, low-level log of timing events — when the navigation started, when each resource downloaded, when paints happened, when interactions occurred, and when the main thread was blocked. You read this log with **`PerformanceObserver`**, an API that calls you back whenever new timing entries are recorded. The `web-vitals` library is built *on top of* these APIs — knowing them lets you measure custom things too.

#### 🤔 Why do we need it? (the problem)
`web-vitals` gives you the three headline scores, but sometimes you need the raw detail: how long DNS took, whether a specific script was render-blocking, how long the main thread was frozen by a long task. The Performance APIs expose all of it, and `PerformanceObserver` is the modern, non-polling way to subscribe to it as it happens.

#### ⚙️ How does it work?
You create a `PerformanceObserver`, give it a callback, and tell it which **entry types** you care about. Each type is a different lens on performance:

```
   PerformanceObserver  ──observes──►  entryType:
   ───────────────────────────────────────────────
   'navigation'   →  the page load itself (DNS, TLS,
                     TTFB, DOM, full load)         (Navigation Timing)
   'resource'     →  every img/script/css/fetch    (Resource Timing)
   'paint'        →  first-paint, first-contentful  (Paint Timing)
   'largest-contentful-paint' → the LCP candidate
   'event' / 'first-input' → interaction latency    (Event Timing)
   'longtask'     →  any main-thread block >50ms    (Long Tasks)
```

The callback receives a list of entries; you read `entry.startTime`, `entry.duration`, etc. Pass `{ buffered: true }` to also receive entries that occurred *before* the observer was created — important for early events like the first paint.

#### 🌍 Real-life analogy
Think of an airport's flight log: every takeoff, landing, and delay is recorded with a timestamp. `PerformanceObserver` is signing up for alerts on specific event types — "ping me on every landing" (`resource`) or "ping me whenever a runway is blocked over 50 seconds" (`longtask`) — instead of standing there reading the whole board.

#### 💻 Code example
```javascript
// Measure LCP by hand, straight from the Performance API.
const po = new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    // The LAST largest-contentful-paint entry is the real LCP.
    console.log('LCP candidate at', entry.startTime, 'ms');
    console.log('LCP element:', entry.element);
  }
});

// buffered: true → also get entries from before this ran.
po.observe({ type: 'largest-contentful-paint', buffered: true });

// Catch every main-thread freeze that hurts responsiveness:
new PerformanceObserver((list) => {
  for (const task of list.getEntries()) {
    console.warn('Long task blocked UI for', task.duration, 'ms');
  }
}).observe({ type: 'longtask', buffered: true });
```

#### 🎤 Interview question
**Q: How do you read raw performance timing in the browser?**
A: With `PerformanceObserver`. You create one, give it a callback, and call `.observe({ type, buffered: true })` for the entry types you want — `navigation` (page load phases), `resource` (every asset), `paint` (FP/FCP), `largest-contentful-paint`, `event`/`first-input` (interaction latency), and `longtask` (main-thread blocks over 50ms). The callback fires with new entries as they're recorded; `buffered: true` also delivers entries from before the observer existed.

### 🌐 CrUX — The Field Data Google Search Uses

#### 🧩 What is it?
**CrUX** (the **Chrome User Experience Report**) is Google's own giant dataset of *real-user* Core Web Vitals, collected automatically from millions of opted-in Chrome users browsing real websites. It's field/RUM data that Google publishes — and that **Google Search uses as a ranking signal**.

#### 🤔 Why do we need it? (the problem)
Your own RUM tells you about *your* users. CrUX gives you Google's authoritative view of your site (and even competitors' sites) without writing any code — and crucially, it's the *exact* data that affects your search ranking. If you want to know whether Google thinks your site passes Core Web Vitals, CrUX is the answer, not your lab score.

#### ⚙️ How does it work?
CrUX aggregates real visits over a **rolling 28-day window** and reports each metric at the **75th percentile (p75)** — meaning 75% of visits were at least that fast (so it's tilted toward the *worse* experiences, on purpose).

```
   Millions of real Chrome users
            │  (opted-in, anonymous)
            ▼
   Aggregate over a rolling 28-DAY window
            │
            ▼
   Report each vital at the p75 (75th percentile)
            │
            ▼
   ┌───────────────┬───────────────┬───────────────┐
   │ PageSpeed     │ Search Console│ BigQuery /     │
   │ Insights      │ (CWV report)  │ CrUX API/Dash  │
   └───────────────┴───────────────┴───────────────┘
```

Why p75 and not the average? An average hides the long tail — a few terrible sessions get washed out by many fast ones. p75 guarantees that *three out of four* visits met the bar, so it reflects what most users actually get.

> **Flagging a nuance:** CrUX only covers traffic that meets a minimum sample size, and only Chrome users who opted in to telemetry — so a brand-new or low-traffic page may have *no* CrUX data, which is exactly why you still need your own RUM.

#### 🌍 Real-life analogy
CrUX is like a city-wide health survey run by the government: it samples huge numbers of real people over a month and publishes the results, and that report decides things like public funding (your search ranking). Your own RUM is your personal doctor checking *you* specifically. You want both — the official survey for the big picture, your own checkup for the details.

#### 🎤 Interview question
**Q: What is CrUX and how does Search use field vitals?**
A: CrUX (Chrome User Experience Report) is Google's dataset of real-user Core Web Vitals, gathered from opted-in Chrome users. It aggregates over a rolling 28-day window and reports each metric at the p75. Google Search uses this field data as a ranking signal — so passing CWV "in the field" per CrUX is what matters for SEO, not your lab Lighthouse score. Low-traffic pages may lack CrUX data, which is why first-party RUM still matters.

### 🚀 `navigator.sendBeacon` — Reporting Without Hurting Performance

#### 🧩 What is it?
**`navigator.sendBeacon(url, data)`** is a browser method built for one job: send a small chunk of data to your server *reliably*, *without blocking* the page, *even as the page is closing*. It's the right way to ship your collected vitals home.

#### 🤔 Why do we need it? (the problem)
Your final CLS and INP values are only known when the page is being *hidden or unloaded* — exactly when the user is leaving. A normal `fetch` or XHR at that moment is unreliable: the browser is tearing the page down and may kill the request before it's sent. And you must never make the *previous* page slow just to log the *current* one. `sendBeacon` solves both: the browser takes the data and promises to send it in the background, on its own, after your page is gone.

#### ⚙️ How does it work?
`sendBeacon` queues the request with the browser and returns immediately (`true` if queued). It's **non-blocking** (doesn't hold up navigation or the main thread) and **survives unload** (the browser sends it even after the page closes).

```
   page is closing  ──► you call navigator.sendBeacon(url, body)
                              │
                    returns instantly (true = queued)
                              │
              browser sends it in the BACKGROUND
              ── survives even though the page is gone ──►  your server
```

Fire your beacon from the `visibilitychange` event (when the page becomes `hidden`) — this is the most reliable signal that the visit is ending, more so than the old `unload` event. The `web-vitals` docs recommend exactly this pattern.

#### 🌍 Real-life analogy
It's the difference between *waiting at the post office* for your letter to be processed (a blocking `fetch` that dies if you have to leave) versus *dropping it in the mailbox on your way out the door* (`sendBeacon`). You don't wait, you don't block your exit, and the postal service delivers it later — even though you've already left.

#### 💻 Code example
```javascript
import { onLCP, onCLS, onINP } from 'web-vitals';

// Collect every final metric into one queue.
const queue = new Set();
function addToQueue(metric) {
  queue.add(metric);
}

function flushQueue() {
  if (queue.size === 0) return;
  const body = JSON.stringify([...queue]);

  // sendBeacon: non-blocking + survives page unload.
  // Falls back to fetch(keepalive) where unsupported.
  if (navigator.sendBeacon) {
    navigator.sendBeacon('/analytics', body); // returns true if queued
  } else {
    fetch('/analytics', { body, method: 'POST', keepalive: true });
  }
  queue.clear();
}

onLCP(addToQueue);
onCLS(addToQueue);
onINP(addToQueue);

// 'visibilitychange' → hidden is the most reliable "leaving" signal.
addEventListener('visibilitychange', () => {
  if (document.visibilityState === 'hidden') flushQueue();
});
```

#### 🎤 Interview question
**Q: How do you send RUM metrics without hurting the page you're measuring?**
A: Use `navigator.sendBeacon(url, data)`. It queues a small request with the browser and returns immediately, so it never blocks the main thread or the navigation, and the browser delivers it in the background — even after the page has unloaded. That last part is essential because CLS and INP are only finalized as the user leaves. Trigger the beacon on `visibilitychange` (state `hidden`), which is more reliable than the legacy `unload` event, with `fetch(..., { keepalive: true })` as a fallback.

<h2 id="module-11">Module 11 — Performance Budgets & CI</h2>

You spent weeks making the site fast. Six months and forty pull requests later, it's slow again — no single change broke it; it died by a thousand cuts. This module is the discipline that stops that: turning "fast" from a heroic cleanup into a **rule the build enforces**, so a regression is caught in a pull request instead of by an angry user.

---

### 📏 Performance Budgets — A Speed Limit You Agree On

#### 🧩 What is it?
A **performance budget** is a set of **numbers you promise not to exceed**. There are two flavours: a **size budget** (e.g. "the JavaScript we ship must stay under 170KB **gzipped**" — gzip is a compression step that shrinks text before sending it) and a **metric budget** (e.g. "**LCP** ≤ 2.5s, **INP** ≤ 200ms" — LCP is how fast the biggest thing paints; INP is how fast the page responds to a tap). Cross a budget and the change is treated as a bug, not a "nice to fix later".

#### 🤔 Why do we need it? (the problem)
"Make it fast" is not a target — it's a vibe. Two engineers will disagree on whether 3 seconds is "fine". Without a number, every code review becomes an argument, and performance quietly erodes because no single pull request looks bad enough to block. A budget replaces opinion with a **pass/fail line everyone agreed to in advance**.

#### ⚙️ How does it work?
You pick budgets from two angles and they reinforce each other:

```
   CAUSE (what you ship)        EFFECT (what users feel)
   ┌───────────────────┐        ┌────────────────────┐
   │  SIZE budget      │        │  METRIC budget     │
   │  JS  <= 170KB gz  │ ─────▶ │  LCP <= 2.5s       │
   │  CSS <= 50KB  gz  │        │  INP <= 200ms      │
   │  img <= 200KB     │        │  CLS <= 0.1        │
   └───────────────────┘        └────────────────────┘
   Size is easy to measure       Metrics are what
   in CI and predicts the        actually matter to
   metric you care about         the user
```

Size budgets are cheap to check (just weigh the files) and give a fast, early warning. Metric budgets are the real goal but are slower and noisier to measure, so teams often gate on **both**: size as the quick guard, metrics as the truth.

> **Note (the 170KB number):** "≤ 170KB of gzipped JS" is a well-known rule of thumb, not a law of physics — it roughly maps to a few seconds of parse-plus-execute on a mid-tier phone over slow mobile data. Pick budgets that match **your** users' real devices, not a number from a blog.

#### 🌍 Real-life analogy
A budget is a **carry-on bag sizer at the airport gate**. The airline doesn't argue about whether your bag "feels heavy" — there's a metal frame, and if the bag doesn't fit, it doesn't board. The frame is objective, decided ahead of time, and applies to everyone equally. A performance budget is that frame for your code.

#### 💻 Code example
A `size-limit` config (`size-limit` is a tool that weighs your built bundles and **fails the build** if they exceed the limit you set):

```json
// .size-limit.json
[
  {
    "name": "Main app bundle (JS)",
    "path": "dist/assets/index-*.js",
    "limit": "170 KB",        // measured GZIPPED by default
    "gzip": true
  },
  {
    "name": "App styles (CSS)",
    "path": "dist/assets/index-*.css",
    "limit": "50 KB",
    "gzip": true
  }
]
```

```bash
# Running it in CI prints a table and exits NON-ZERO if over budget:
$ npx size-limit
#   Main app bundle (JS)
#   Size limit: 170 KB
#   Size:       182 KB  with all dependencies, minified and gzipped
#   ❌ exceeded by 12 KB   ->  exit code 1  ->  the build FAILS
```

#### 🎤 Interview question
**Q: What goes in a performance budget?**
A: Two kinds of limits. **Size budgets** — caps on bytes shipped (e.g. JS ≤ 170KB gzipped, CSS, images), which are cheap to measure and predict cost. **Metric budgets** — caps on the user-facing numbers (LCP ≤ 2.5s, INP ≤ 200ms, CLS ≤ 0.1). You set them from real user devices and gate on both: size as the fast early signal, metrics as the thing that actually matters.

### 🚦 Lighthouse CI — Failing the Pull Request on a Regression

#### 🧩 What is it?
**Lighthouse** is Google's automated auditing tool that loads a page and scores it on performance, accessibility, and more. **Lighthouse CI (LHCI)** is the version built to run **inside your CI** — the automated pipeline that runs on every pull request — where it can **assert** that scores and metrics stay within your budget and **fail the pull request** if they don't.

#### 🤔 Why do we need it? (the problem)
A size budget weighs files, but it can't tell you the page *felt* slow. Maybe the bytes are fine but a render-blocking script pushed LCP to 4 seconds. You need something that actually **loads the page in a real browser, measures the metrics, and blocks the merge** when they regress — automatically, on every change, with no human remembering to check.

#### ⚙️ How does it work?
LHCI runs as a step in your pipeline:

```
   Pull request opened
        │
        ▼
   CI builds the app  ──▶  starts a local server
        │
        ▼
   Lighthouse loads the page (real headless browser)
        │  measures LCP, INP-proxy, CLS, scores
        ▼
   Compare each result to the ASSERTIONS
        │
        ├─ all within budget  ──▶  ✅ check passes, merge allowed
        └─ LCP over 2.5s      ──▶  ❌ check fails, merge BLOCKED
```

You declare the rules in a config file. An assertion can be an **error** (fails the build) or a **warning** (shows up but doesn't block). Because lab numbers vary run-to-run, LHCI can run the page several times and use the **median**, and you set thresholds with a little headroom so normal noise doesn't cause false failures.

> **Note (lab, not field):** Lighthouse measures in a **lab** — one simulated device and network in CI, not your real users. It's perfect for catching a regression *before* merge, but it is not the same as field data (covered next). INP especially needs real interaction, so in the lab Lighthouse uses a related proxy metric, **Total Blocking Time**, rather than a true INP.

#### 🌍 Real-life analogy
Lighthouse CI is the **health inspector who visits before the restaurant is allowed to open each day**. Same checklist every time, objective pass/fail, and if the kitchen fails, the doors stay locked until it's fixed. Nobody opens "just this once" — the gate is the point.

#### 💻 Code example
A Lighthouse CI assertion config that fails a pull request when LCP or the performance score regresses:

```json
// lighthouserc.json
{
  "ci": {
    "collect": {
      "url": ["http://localhost:3000/"],
      "numberOfRuns": 3
    },
    "assert": {
      "assertions": {
        "categories:performance": ["error", { "minScore": 0.9 }],
        "largest-contentful-paint": ["error", { "maxNumericValue": 2500 }],
        "cumulative-layout-shift": ["error", { "maxNumericValue": 0.1 }],
        "total-blocking-time": ["warn", { "maxNumericValue": 200 }]
      }
    }
  }
}
```

```bash
# In the CI pipeline:
$ npx lhci autorun
#   Running Lighthouse 3 times, taking the median...
#   ✅ categories:performance     0.94  (>= 0.90)
#   ❌ largest-contentful-paint   2780ms (max 2500ms)
#   Assertion failed -> exit code 1 -> pull request check is RED
```

#### 🎤 Interview question
**Q: How would you set up performance checks in CI?**
A: Run **Lighthouse CI** as a pipeline step on every pull request: build the app, start a local server, load the page in a headless browser a few times for the median, and **assert** against budgets (e.g. performance score ≥ 0.9, LCP ≤ 2500ms, CLS ≤ 0.1). Failing assertions exit non-zero so the check goes red and the merge is blocked. I'd pair it with a size-limit/bundle check for a fast early signal, and treat lab results as regression detection — not a substitute for field monitoring.

### 📦 Bundle Analysis in CI — Catching the Heavy Dependency Before Merge

#### 🧩 What is it?
**Bundle analysis** breaks your built JavaScript down into **which modules and dependencies take up the space**, so a "the bundle grew by 90KB" turns into "because someone imported all of `moment` for one date format". Running it **in CI** means the report appears on the pull request, before the heavy or duplicate dependency is ever merged.

#### 🤔 Why do we need it? (the problem)
A size budget tells you the bundle got bigger; it doesn't tell you **why**. The two classic culprits are a **heavy dependency** (a library that drags in far more than you use) and a **duplicate dependency** (the same package bundled twice at two different versions because two libraries each pulled their own). Both are invisible in a normal diff — the pull request just adds one innocent-looking `import` line. Analysis surfaces the real cost while it's still cheap to reverse.

#### ⚙️ How does it work?
The build is asked to emit a map of every module and its size, which a comparison step diffs against the main branch:

```
   main branch bundle        this pull request's bundle
   ┌────────────────┐        ┌──────────────────────┐
   │ app      40KB  │        │ app      41KB        │
   │ react    45KB  │        │ react    45KB        │
   │                │        │ moment   72KB  ⚠ NEW │
   │                │        │ lodash   24KB  ⚠ DUP │  (v3 AND v4!)
   └────────────────┘        └──────────────────────┘
                  Δ +96KB  ── flagged on the PR
```

A CI bot can post this diff as a pull-request comment ("+96KB, mostly `moment`"), so the reviewer sees the cost next to the code that caused it and can ask for a lighter library or a deduped lockfile before approving.

#### 🌍 Real-life analogy
It's the **itemised receipt** instead of just the total at the bottom. "You spent $96 more this trip" starts an argument; "$72 of it was one fancy cheese, and you bought the same milk twice" ends it. Seeing the line items is what lets you actually decide what to cut.

#### 💻 Code example
A CI step that generates a bundle report and a duplicate check:

```yaml
# .github/workflows/perf.yml  (the bundle-analysis job)
- name: Build with bundle stats
  run: npm run build -- --stats   # emit a module-size map

- name: Check for duplicate packages
  run: npx npm-why lodash         # lists EVERY version in the tree
  # Output reveals the duplicate to fix:
  #   lodash@4.17.21  (your app)
  #   lodash@3.10.1   (via legacy-charts)  <-- two copies shipped!

- name: Comment bundle diff on the PR
  uses: some-bundle-diff-action@v1
  with:
    # fails the job if the bundle grows more than the allowed delta
    fail-on-increase-kb: 25
```

#### 🎤 Interview question
**Q: How do you catch a heavy or duplicate dependency before it ships?**
A: Run bundle analysis in CI. The build emits a per-module size map, and a step diffs it against the main branch, posting the delta on the pull request so the reviewer sees *which* dependency caused a jump. For duplicates I check the dependency tree (e.g. `npm-why`/`npm ls`) to spot the same package bundled at two versions — usually fixed by deduping the lockfile or aligning a peer version. Wired to fail the job past an allowed delta, it stops the regression at review time.

### 🔭 Monitoring, Alerting & the Ratchet — Keeping It Fast Forever

#### 🧩 What is it?
This is the **cultural and operational** half. **Monitoring** means continuously collecting performance from **real users in the field** (called **RUM** — Real User Monitoring) and watching it on **dashboards**. **Alerting** means getting paged when a metric crosses a line. The **ratchet** is the team rule: performance is only ever allowed to get **better or stay the same** — never worse. Together they make performance a **definition of done**, like tests or security, instead of a one-off cleanup.

#### 🤔 Why do we need it? (the problem)
CI's Lighthouse checks run in a **lab** — one machine, one fake network. Real users are on cracked Androids on a train in a tunnel. A change can pass every lab gate and still wreck the experience for the slow tail of real users. And even a great launch decays: with no owner and no ratchet, every team adds "just a little" until the budget is blown and nobody remembers when. You need eyes on the **field** and a culture that refuses to backslide.

#### ⚙️ How does it work?
Lab gates and field monitoring are two halves of one loop:

```
   BEFORE merge (lab)              AFTER deploy (field / RUM)
   ┌────────────────────┐         ┌──────────────────────────┐
   │ size-limit         │         │ real users' LCP/INP/CLS   │
   │ Lighthouse CI      │ ──ship─▶ │ streamed to a dashboard   │
   │ bundle diff        │         │ p75 watched over time     │
   └────────────────────┘         └─────────────┬────────────┘
        gate the PR                              │ p75 LCP jumps
                                                 ▼
                                          ALERT fires -> owner
                                          investigates -> fix
                                          -> budget RATCHETS down
```

Field metrics are read at the **p75** (the 75th percentile — three out of four users are at least this fast), because averages hide the suffering tail. When you ship an improvement, you **lower the budget to match** — that's the ratchet: today's best becomes tomorrow's ceiling, so the only allowed direction is better.

> **Note (lab vs field, why both):** the lab catches regressions *deterministically before merge*; the field catches what the lab can't simulate — real devices, networks, caches, and user behaviour. Neither replaces the other. A change that's green in CI but red in the field is a real and common outcome.

#### 🌍 Real-life analogy
A **socket-wrench ratchet** turns one way and locks — it physically can't slip back. Pair it with the **smoke detector** in the same room: monitoring is the detector that screams when something's burning in the field, and the ratchet is the wrench that makes sure every fix you make is permanent. Progress clicks forward and never unwinds.

#### 💻 Code example
Sending real-user vitals to a monitoring endpoint, which then feeds dashboards and alerts:

```javascript
import { onLCP, onINP, onCLS } from 'web-vitals';

function report(metric) {
  // metric.name = 'LCP' | 'INP' | 'CLS', metric.value = the number
  const body = JSON.stringify({
    name: metric.name,
    value: metric.value,
    path: location.pathname,
  });
  // sendBeacon survives page unload without delaying the user
  navigator.sendBeacon('/rum', body);
}

onLCP(report);   // ─┐
onINP(report);   //  ├─ streamed from REAL sessions to your backend,
onCLS(report);   // ─┘  which aggregates p75 on a dashboard + alerts
```

On the backend you aggregate these into p75 per route and set an alert rule, for example: *"page on-call if p75 LCP for `/` stays above 2.8s for 30 minutes."*

#### 🎤 Interview question
**Q: How do you stop performance from regressing over time?**
A: Make it a product requirement enforced by machines and culture, not willpower. **In CI:** budgets gated by size-limit, Lighthouse CI, and a bundle diff that block merges on regression. **In the field:** RUM (e.g. the `web-vitals` library beaconed to a dashboard) watched at p75, with alerts when a metric crosses a threshold. **Culturally:** a named owner, regression reviews, and the **ratchet** — every improvement lowers the budget so the agreed ceiling can only ever move down. Lab gates catch regressions before merge; field monitoring catches what the lab can't simulate.

Performance is now an engineering discipline for you, not a guessing game. You can measure before you touch anything, read a request waterfall, trace each Core Web Vital to its root cause, and reach for the right lever — network, caching, JavaScript, images, fonts, or rendering strategy.
